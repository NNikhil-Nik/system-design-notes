Chapter 9

Design a Web Crawler

A web crawler (also called a robot or spider) is a program that visits web pages, saves them, finds the links on them, and then visits those links too. Search engines like Google use crawlers to discover the web. Designing one at the scale of a billion pages a month teaches you queues, politeness, deduplication and how to survive a messy, hostile internet.

~35 min readBeginnerPrerequisites: Ch 1 (scaling), Ch 2 (estimation), Ch 5 (consistent hashing)

The big picture

A crawler starts with a few web pages, downloads them, collects the links they contain, and then downloads the pages those links point to. Repeat this forever and you slowly discover a huge part of the web. Crawlers are used for many purposes:

Search engine indexing

The most common use. A crawler collects pages to build a local index for a search engine. Googlebot is the crawler behind Google Search.

Web archiving

Collecting pages to preserve them for future use. National libraries run crawlers to archive websites; the US Library of Congress and the EU web archive are examples.

Web mining

Discovering useful knowledge from the web. For example, financial firms crawl shareholder meetings and annual reports to learn key company initiatives.

Web monitoring

Watching the web for copyright and trademark infringements. For example, Digimarc uses crawlers to discover pirated works and reports.

The basic algorithm

  1. Start with a set of URLs (the seed URLs) and download all the web pages they address.
  2. Extract URLs from these web pages.
  3. Add the new URLs to the list of URLs to be downloaded. Repeat these 3 steps.
The crawl loop
That is all a crawler is at heart. The difficulty is doing this loop for a billion pages a month without overloading websites, downloading duplicates or getting stuck.
Real-world analogy

Imagine a librarian told to collect every book in a vast city. She starts with a few bookshops she knows (seed URLs). In each shop she buys the books (downloads pages) and notes every other shop mentioned in them (extracts links). She adds those shops to her to-do list (the URL frontier). She must be polite - not barge into the same small shop a hundred times a minute - skip books she already owns (duplicates), obey "no entry" signs (robots.txt), and avoid shops that are an endless hall of mirrors (spider traps). That is a web crawler.

A short fingerprint computed from content. Same content gives the same fingerprint, so comparing fingerprints is fast.

A memory-efficient structure that tells you "definitely not seen" or "probably seen". Good for tracking billions of URLs.

Queries (here, pages downloaded) per second.

Breadth-first search explores all neighbours before going deeper; depth-first search goes as deep as possible first. The web is a graph of pages (nodes) and links (edges).

First-in, first-out: items leave in the same order they arrived, like a line at a ticket office.

Not sending too many requests to the same website in a short time.

A measure of how important a page is based on the links pointing to it.

How up to date the crawler's copy of a page is compared with the live page.

A web page or site that causes a crawler to loop forever, e.g. URLs that go infinitely deep.

Running a page's JavaScript on the crawler to produce the final HTML, since many links only appear after scripts run.

Characteristics of a good crawler

Scalability

The web is enormous - billions of pages. Crawling should be extremely efficient using parallelization.

Robustness

The web is full of traps: bad HTML, unresponsive servers, crashes, malicious links. The crawler must handle all these edge cases.

Politeness

The crawler should not make too many requests to a website within a short time interval.

Extensibility

The system should be flexible so that minimal changes are needed to support new content types (e.g. images).

Back-of-the-envelope estimation

These numbers are based on the book's assumptions. Let us go step by step.

  1. Pages per month. Assume 1 billion web pages are downloaded every month.
  2. Pages per second (QPS). 1,000,000,000 / 30 days / 24 hours / 3600 seconds. That is 1,000,000,000 / 2,592,000 = about 386, which we round to ~400 pages per second.
  3. Peak QPS. Traffic is not perfectly even, so assume peak = 2 x average = 800 pages per second.
  4. Storage per month. Assume the average page size is 500 KB. 1 billion x 500 KB = 500 billion KB = 500 TB per month.
  5. Storage for 5 years. 500 TB x 12 months x 5 years = 30,000 TB = 30 PB (petabytes).

Here is the overall design. Every box is explained below, and then we walk through the numbered workflow.

Each component, explained

Seed URLs
The starting point. A good seed set lets the crawler reach as many links as possible. For a university site, the domain name might be enough. For the whole web, be creative: divide the URL space into smaller parts, either by locality (different countries have different popular websites) or by topic (shopping, sports, healthcare and so on). The choice is open-ended - you are not expected to give the perfect answer.
URL Frontier
Most modern crawlers split crawl state into two: to be downloaded and already downloaded. The component storing URLs to be downloaded is the URL frontier. Think of it as a FIFO queue for now; the deep dive makes it smarter.
HTML Downloader
Downloads web pages from the internet. The URLs come from the URL frontier.
DNS Resolver
To download a page, a URL must be translated into an IP address. The downloader asks the DNS resolver for the IP. For example, www.wikipedia.org is converted to 198.35.26.96 (as of the book's writing).
Content Parser
After download, the page must be parsed and validated, because malformed pages can cause problems and waste storage. Running the parser inside the crawl servers would slow crawling, so it is a separate component.
Content Seen?
Research shows about 29% of web pages are duplicated content, which may cause the same content to be stored multiple times. This component removes redundancy. Comparing two pages character by character is slow and time-consuming, so instead we compare the hash values of the two pages.
Content Storage
Stores HTML content. Choice depends on data type, size, access frequency and life span. Both disk and memory are used: most content is stored on disk because the data set is too big for memory, and popular content is kept in memory to reduce latency.
URL Extractor
Parses and extracts links from HTML pages. Relative paths are converted to absolute URLs by adding the prefix (see the example below).
URL Filter
Excludes certain content types, file extensions, error links and URLs on "blacklisted" sites.
URL Seen?
Keeps track of URLs that have been visited before or are already in the frontier. This avoids adding the same URL multiple times, which would increase server load and cause potential infinite loops. Bloom filters and hash tables are common techniques to implement it.
URL Storage
Stores already-visited URLs.

The web crawler workflow, step by step

  1. Add seed URLs to the URL frontier.
  2. The HTML downloader fetches a list of URLs from the URL frontier.
  3. The HTML downloader gets the IP addresses of the URLs from the DNS resolver and starts downloading.
  4. The content parser parses the HTML pages and checks whether the pages are malformed.
  5. After parsing and validation, the content is passed to the "Content Seen?" component.
  6. "Content Seen?" checks whether the page is already in storage. If it is, the same content at a different URL has already been processed, so the page is discarded.
  7. If it is not in storage, the system has not processed it before, and the content is passed to the link extractor (and saved to content storage).
  8. The link extractor extracts links from the HTML pages.
  9. Extracted links are passed to the URL filter.
  10. After filtering, links go to the "URL Seen?" component.
  11. "URL Seen?" checks whether a URL is already in storage; if yes, it was processed before and nothing needs to be done. If not, it is added to the URL frontier (and recorded in URL storage).

Step 3 - Deep dive: DFS vs BFS

You can think of the web as a directed graph: web pages are nodes and hyperlinks (URLs) are edges. Crawling is traversing that graph. The two classic ways to traverse a graph are:

DFS (depth-first search)

Follow one link, then the first link on that page, then the first link on that one... going as deep as possible before backing up. Usually not a good choice, because the depth of the web can be very deep and the crawler can wander off forever.

BFS (breadth-first search)

Visit all links on the current page first, then all links on those pages, level by level. Commonly used by crawlers, implemented with a FIFO queue: URLs are dequeued in the order they were enqueued.

BFS order on a tiny web graph
BFS visits nodes in number order: the whole of one level before the next. A FIFO queue achieves this naturally - add children to the back, take the next URL from the front.

Two problems with plain BFS

  1. It is impolite. Most links on a page link back to the same host. For example, nearly all links on wikipedia.com are internal links to other Wikipedia pages. When the crawler processes them in parallel, Wikipedia servers get flooded with requests. This is considered "impolite".
  2. It has no priority. Standard BFS treats every page equally. But not every page has the same quality and importance. We may want to prioritise URLs by ranking, web traffic, update frequency and so on.

The queue fills with URLs from one host, so parallel workers all hammer that host at the same moment.

The URL frontier solves both problems.

URL frontier

The URL frontier is a data structure that stores URLs to be downloaded. It is the key component that ensures politeness, URL prioritization and freshness.

Politeness

A crawler should avoid sending too many requests to the same hosting server within a short period. Sending too many can be seen as "impolite" or even treated as a denial-of-service (DoS) attack.

The general idea: download one page at a time from the same host, and add a delay between two download tasks. We do this by keeping a mapping from website hostnames to download (worker) threads. Each downloader thread has its own FIFO queue and only downloads URLs from that queue.

Politeness design (back queues)
The router puts every URL from the same host into the same queue. Each worker handles one queue at a time, one URL after another, with a pause in between. So no host ever sees more than one request at a time from us.
  • Queue router: ensures that each queue (b1, b2, ... bn) only contains URLs from the same host.
  • Mapping table: maps each host to a queue (e.g. wikipedia.com → b1, apple.com → b2, nike.com → bn).
  • FIFO queues b1 to bn: each queue contains URLs from the same host.
  • Queue selector: each worker thread is mapped to a FIFO queue, and only downloads URLs from that queue. The queue selection logic is done by the queue selector.
  • Worker threads 1 to N: a worker thread downloads web pages one by one from the same host. A delay can be added between two download tasks.

Priority

A random post on a discussion forum about Apple products carries very different weight than a post on the Apple home page. Both contain the "Apple" keyword, but it is sensible for a crawler to crawl the Apple home page first. We prioritise URLs based on usefulness, which can be measured by PageRank, website traffic, update frequency and so on. A prioritizer is the component that handles this.

Priority design (front queues)
The prioritizer computes a priority for each URL and places it in the matching front queue. The queue selector picks queues randomly but with a bias toward high-priority ones.
  • Prioritizer: takes URLs as input and computes their priorities.
  • Queues f1 to fn: each queue has an assigned priority. Queues with high priority are selected with higher probability.
  • Queue selector: randomly chooses a queue with a bias toward queues with higher priority.
Why "random with a bias" instead of "always highest first"?

If the selector always drained f1 first, low-priority pages might never be crawled (starvation). A biased random choice crawls important pages much more often while still making progress on everything else.

Putting politeness and priority together

The full URL frontier combines both designs:

  • Front queues manage prioritization.
  • Back queues manage politeness.
URL frontier: front queues (priority) + back queues (politeness)
A URL first gets a priority (front queues), then is routed by host (back queues). Workers pull from back queues, so important pages come out first and no host is overloaded.

Freshness

Web pages are constantly being added, deleted and edited. A crawler must periodically recrawl downloaded pages to keep its data set fresh. Recrawling all URLs is time-consuming and resource intensive. Strategies to optimise freshness:

  • Recrawl based on web pages' update history. A news homepage that changes hourly is recrawled often; a page unchanged for years, rarely.
  • Prioritize URLs and recrawl important pages first and more frequently.

Storage for the URL frontier

In real-world search engine crawls, the number of URLs in the frontier can be hundreds of millions. Where do we keep them?

OptionProblem
Everything in memoryNeither durable (lost on crash) nor scalable (hundreds of millions of URLs).
Everything on diskDisk is slow and easily becomes a bottleneck for crawling.
Hybrid (chosen)The majority of URLs are stored on disk, so space is not a problem. To reduce the cost of reading and writing disk, we keep buffers in memory for enqueue/dequeue operations. Data in the buffer is periodically written to disk.

HTML downloader

The HTML downloader downloads web pages from the internet using the HTTP protocol. Before discussing it, we need to look at the Robots Exclusion Protocol.

robots.txt

robots.txt is a standard used by websites to communicate with crawlers. It specifies which pages crawlers are allowed to download. Before crawling a site, a crawler should check its robots.txt first and follow its rules.

To avoid repeat downloads of the robots.txt file, we cache the results. The file is downloaded and saved to cache periodically. Here is a piece of Amazon's robots.txt, as shown in the book. Some directories like creatorhub are disallowed for Google's bot:

User-agent: Googlebot
Disallow: /creatorhub/*
Disallow: /rss/people/*/reviews
Disallow: /gp/pdp/rss/*/reviews
Disallow: /gp/cdp/member-reviews/
Disallow: /gp/aw/cr/

User-agent says which crawler the rules apply to. Each Disallow line is a path pattern that crawler must not download.

Performance optimization

1. Distributed crawl

To achieve high performance, crawl jobs are distributed across multiple servers, and each server runs multiple threads. The URL space is partitioned into smaller pieces, so each downloader is responsible for a subset of URLs.

2. Cache DNS resolver

DNS resolution is a bottleneck because DNS requests may take time (10ms to 200ms) and many DNS interfaces are synchronous: one thread's DNS request blocks others until done. Keep our own DNS cache (domain name → IP) updated periodically by cron jobs.

3. Locality

Distribute crawl servers geographically. When crawl servers are closer to website hosts, download time is faster. Locality applies to most components: crawl servers, cache, queue, storage and so on.

4. Short timeout

Some web servers respond slowly or not at all. To avoid long waits, specify a maximal wait time. If a host does not respond within a predefined time, the crawler stops the job and crawls other pages.

Robustness

Besides performance, robustness is just as important. The book lists these approaches:

  • Consistent hashing: helps distribute load among downloaders. A new downloader server can be added or removed using consistent hashing (Chapter 5) with minimal reshuffling.
  • Save crawl states and data: to guard against failures, crawl states and data are written to a storage system. A disrupted crawl can be restarted easily by loading saved states and data.
  • Exception handling: errors are inevitable and common in a large-scale system. The crawler must handle exceptions gracefully without crashing the system.
  • Data validation: an important measure to prevent system errors.

Detect and avoid problematic content

This section covers redundant, meaningless or harmful content.

1. Redundant content

As discussed, nearly 30% of web pages are duplicates. Hashes or checksums help detect duplication. For example, compute a hash of each page's content; if the hash already exists in storage, the page is a duplicate and is dropped.

2. Spider traps

A spider trap is a web page that causes a crawler to be stuck in an infinite loop. For instance, an infinitely deep directory structure:

www.spidertrapexample.com/foo/bar/foo/bar/foo/bar/...
A spider trap
Each URL is technically unique, so deduplication alone does not catch it.

How to avoid them:

  • Set a maximal length for URLs. Simple and catches the infinitely deep case.
  • No one-size-fits-all solution. Websites containing spider traps are easy to identify because they have an unusually large number of web pages discovered. It is hard to build an automatic algorithm for all traps, but a user can manually verify and identify a spider trap, then either exclude those websites or apply customised URL filters.

3. Data noise

Some content has little or no value, such as advertisements, code snippets, spam URLs and so on. These are not useful for crawlers and should be excluded if possible.

Step 4 - Wrap up

We first discussed the characteristics of a good crawler (scalability, politeness, extensibility, robustness), proposed a design, and discussed key components. Building a scalable crawler is not trivial because the web is enormously large and full of traps. If there is time left, the book suggests these talking points:

Server-side rendering

Numerous websites use scripts like JavaScript and AJAX to generate links on the fly. If we download and parse pages directly, we will not retrieve those dynamic links. Server-side rendering (also called dynamic rendering) runs the scripts first, then parses the result.

Filter out unwanted pages

With finite storage capacity and crawl resources, an anti-spam component helps filter out low-quality and spam pages.

Database replication and sharding

Techniques like replication and sharding improve the data layer availability, scalability and reliability.

Horizontal scaling

For large-scale crawls, hundreds or even thousands of servers are needed. The key is to keep servers stateless.

Availability, consistency, reliability

Core concepts for the success of any large system (see Chapter 1).

Analytics

Collecting and analysing data is important for any system, because data is a key ingredient for fine-tuning.

Walkthrough: one URL's journey

  1. Seed: https://en.wikipedia.org/wiki/Web_crawler enters the frontier.
  2. Prioritize: the prioritizer scores it highly (popular site) and puts it in front queue f1.
  3. Route by host: the front queue selector picks it (biased toward f1); the back queue router looks up en.wikipedia.org in the mapping table and appends it to b1.
  4. Polite download: the worker for b1 waits for the delay since its last Wikipedia request, checks the cached robots.txt, gets the IP from the DNS cache and downloads with a short timeout.
  5. Parse and dedupe: the parser validates the HTML; the content hash is new, so the page is saved to content storage.
  6. Extract: links like /wiki/Kay_Hagan become https://en.wikipedia.org/wiki/Kay_Hagan.
  7. Filter and check: the URL filter drops unwanted types and over-long URLs; URL seen? drops ones already known.
  8. Loop: genuinely new URLs are recorded in URL storage and added to the frontier. Later, freshness logic schedules a recrawl of this page based on its update history.

Common mistakes

Forgetting politeness

A design where many threads pull from one big FIFO queue will flood popular hosts. Always explain per-host back queues and delays.

Choosing DFS

The web is extremely deep. DFS can wander down one site forever. Use BFS with a FIFO queue, improved by the URL frontier.

Only one deduplication check

There are two: Content Seen? (same content at different URLs, via hashes) and URL Seen? (same URL found again, via Bloom filter or hash table). Mention both.

Ignoring robots.txt

A real crawler must check and cache each site's robots.txt before crawling it.

Keeping the frontier entirely in memory

Hundreds of millions of URLs are neither durable nor scalable in memory. Store most on disk with in-memory buffers.

Treating DNS as free

DNS lookups take 10-200ms and are often synchronous. Without a DNS cache, they bottleneck the downloaders.

Test yourself

1. What are the three steps of the basic crawl algorithm?

Given seed URLs, download the pages; extract URLs from those pages; add the new URLs to the to-download list and repeat.

2. Compute the average and peak QPS for 1 billion pages a month.

1,000,000,000 / 30 / 24 / 3600 is about 386, rounded to ~400 pages per second. Peak is assumed to be 2x, so 800.

3. How much storage is needed over 5 years if a page averages 500 KB?

1 billion x 500 KB = 500 TB per month. 500 TB x 12 x 5 = 30 PB.

4. Why is BFS preferred over DFS, and what two problems does plain BFS have?

The web can be very deep, so DFS may go down one path forever. BFS (with a FIFO queue) explores level by level. Its problems: it is impolite, because most links on a page point to the same host so parallel workers flood it; and it has no priority, treating every page as equally important.

5. Your crawler is hammering a small blog with 50 requests a second. Which part of the design fixes this and how?

The back queues of the URL frontier. A queue router uses a mapping table to send all URLs from that blog's host to one FIFO queue. One worker thread handles that queue, downloading one page at a time with a delay in between.

6. How does the queue selector in the front queues choose a queue, and why?

Randomly, but with a bias toward higher-priority queues. Important pages get crawled more often, while lower-priority queues still get a turn instead of starving.

7. What is the difference between "Content Seen?" and "URL Seen?"

Content Seen? detects the same page content under different URLs by comparing hashes of the content (about 29-30% of pages are duplicates). URL Seen? detects a URL that has already been visited or is already in the frontier, using a Bloom filter or hash table, avoiding repeat work and infinite loops.

8. Name four performance optimizations for the HTML downloader.

Distributed crawl (many servers and threads, partitioned URL space), a cached DNS resolver, locality (crawl servers close to website hosts), and short timeouts for slow servers.

9. Your crawler keeps discovering URLs like site.com/foo/bar/foo/bar/foo/... What is happening and what do you do?

It is a spider trap: an infinitely deep directory structure. Set a maximum URL length; flag sites with an unusually large number of discovered pages, verify manually, then exclude them or apply custom URL filters.

10. The product team now wants to crawl PNG images too. How does the design handle that?

Through extensibility: plug in a new module, such as a PNG downloader, alongside the existing URL extractor. The rest of the pipeline is unchanged.

Cheat sheet

  • Uses: search engine indexing, web archiving, web mining, web monitoring.
  • Scope: indexing, 1B HTML pages/month, new + edited pages, store 5 years, ignore duplicates.
  • Goals: scalability, robustness, politeness, extensibility.
  • Math: ~400 QPS (800 peak); 500 KB/page → 500 TB/month → 30 PB over 5 years.
  • Loop: seeds → frontier → downloader (+DNS) → parser → content seen? → storage → URL extractor → filter → URL seen? → frontier.
  • BFS with a FIFO queue, not DFS. Plain BFS is impolite and has no priority.
  • Front queues (prioritizer, f1..fn, biased selector) = priority. Back queues (router, mapping table, b1..bn, one host each, worker + delay) = politeness.
  • Freshness: recrawl by update history; important pages first and more often.
  • Frontier storage: mostly disk, with in-memory buffers for enqueue/dequeue.
  • Downloader: obey and cache robots.txt; distributed crawl, DNS cache, locality, short timeout.
  • Robustness: consistent hashing, save crawl state, exception handling, data validation. Extensibility: plug-in modules.
  • Problematic content: duplicates (hashes), spider traps (max URL length, manual filters), data noise (ads, spam).
