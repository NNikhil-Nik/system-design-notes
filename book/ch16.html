The Learning Continues

The book ends by pointing outward. Real companies have published how their systems work, and reading those write-ups is the best way to keep learning. This page lists the architectures and engineering blogs the book recommends, then adds a beginner's roadmap: how all the chapters connect, a 30-day practice plan, and new problems to try.

~20 min readBeginnerPrerequisites: Chapters 1–15

The big picture

Designing good systems takes years of experience. The book's closing advice is simple: the fastest way to build that experience without living through every outage yourself is to study real-world system architectures. Companies like Facebook, Netflix and Twitter have written about the problems they hit and how they solved them.

You will notice that the same ideas from this book keep coming back: caches, sharding, replication, queues, unique IDs. Seeing them in real systems makes them stick, and it gives you concrete stories to mention in interviews.

Real-world analogy

Learning system design from one book is like learning to cook from one cookbook. You learn the core techniques: how to chop, braise, make a sauce. To get really good, you eat at other restaurants, read chefs' notes and see how professionals handle a busy Saturday night. Engineering blogs are those chefs' notes. Each one shows a familiar technique used under real pressure.

How to read an architecture write-up

The book suggests that while reading, you pay attention to the shared principles and underlying technologies. For each article ask: What problem were they facing? Which building blocks from this book did they use? What trade-off did they make? A short answer to each is enough.

Key terms

Architecture write-up
An article or paper in which a company explains how a system is built and why.
Engineering blog
A company's public blog where its engineers share lessons, designs and post-mortems.
Paper
A formal technical document, often presented at a conference. Google's Bigtable and Amazon's Dynamo are famous examples.
Denormalization
Storing copies of data in several places so reads are faster, at the cost of more storage and harder updates.
Social graph
The network of who is connected to whom (friends, followers).
Building block
A reusable component like a load balancer, cache or message queue that appears in many systems.
Post-mortem
A write-up after an outage explaining what went wrong and what was changed to prevent it.

Which building blocks each design uses
A dot means the block plays a visible role in that chapter's design. This is simplified: most real systems use almost every block somewhere. Notice that caches, load balancers and message queues are nearly everywhere, which is why Chapter 1 matters so much.
Key idea

Two blocks give the most value for your study time: caching and message queues. If you understand when to cache (read-heavy data) and when to queue (slow work that need not block the user), you can explain a large part of any design.

Practise the wrap-up too

Most people practise only the diagram. In every practice session, spend the last 3–5 minutes naming bottlenecks, failure cases and the next scale step. It is the part beginners most often skip.

Classic practice problems not in this volume

These are popular interview problems that this book does not cover. Try each with the 4-step framework. The hints point you to the right building blocks without giving the full answer.

Proximity service (find nearby restaurants)

  • Searching "everything within 1 km" on raw latitude and longitude is slow. Look up geohash or quadtree to group nearby places.
  • Business data changes rarely but is read constantly. Think read replicas and caching.
  • Separate the "search nearby" service from the "business details" service.

Ticketing system (concert tickets)

  • The hard part is preventing two people from buying the same seat. Think about locking or atomic updates on seat rows.
  • Popular events cause sudden spikes. Consider a virtual waiting room (a queue) and rate limiting.
  • Hold a seat for a few minutes during checkout, then release it if payment does not finish.

Payment system

  • Correctness beats speed. Use idempotency keys so retrying a request never charges twice.
  • Record every money movement in a ledger and reconcile with external payment providers.
  • Plan for failures from the external provider: retries with backoff, and a way to track payments stuck in a pending state.

Distributed message queue

  • Store messages in an append-only log split into partitions so many brokers share the load.
  • Replicate each partition to survive broker failures (Chapter 6 ideas apply).
  • Discuss delivery guarantees: at-most-once, at-least-once, exactly-once, and their trade-offs.

Metrics monitoring and alerting

  • Metrics are time-stamped numbers, so a time-series database fits well.
  • Huge write volume: put a message queue between collectors and storage.
  • Keep recent data at full detail and roll old data up into coarser summaries to save space.

Hotel reservation system

  • Like ticketing, avoid double booking. Track available room counts per room type per date.
  • Use idempotency so a double-clicked "Book" button creates only one reservation.
  • Booking data needs strong consistency, so a relational database with transactions is a natural fit.

Stock exchange

  • The core is a matching engine that pairs buy and sell orders in an order book. Latency is critical.
  • Orders must be processed in a strict, deterministic sequence so results can be replayed and audited.
  • Separate the fast trading path from slower paths like reporting and market data distribution.

Putting it all together

  1. Master the method. The 4-step framework (Chapter 3) and quick estimation (Chapter 2) work for any problem.
  2. Know the blocks. Load balancer, cache, CDN, queue, sharding, replication, consistent hashing, rate limiter, unique IDs, KV store.
  3. Study the combinations. Chapters 8–15 show how the blocks are assembled for real products.
  4. Learn from real companies. Read architecture write-ups and engineering blogs, especially for companies you are interviewing with.
  5. Practise out loud, timed. Use the 30-day plan and the new problems to build fluency.

How to answer this in an interview

Reading real architectures pays off when interviewers ask about your knowledge or push you on a design choice.

1
Using real-world examples
anytime
  • Mention a real system briefly to support a choice. Do not lecture.
  • Connect it straight back to your design.
For unique post IDs across many servers, I'd use a Snowflake-style approach, like the one Twitter published: a timestamp, a machine ID and a sequence number packed into 64 bits. That gives us IDs that are roughly sortable by time without a central bottleneck.
Why not just use the database's auto-increment?
With one database that works. Once we shard across many databases, auto-increment can't guarantee global uniqueness or time ordering without extra coordination. Snowflake IDs avoid that.
2
"How do you keep learning?"
behavioural
How do you stay current on system design?
I read engineering blogs regularly, including yours. For each post I note the problem, the building blocks they used and the trade-off they chose. For example, reading about how a key-value store like Dynamo uses quorum reads and writes helped me understand the consistency and availability trade-off much better than theory alone.

Common mistakes

Memorising designs instead of understanding them

Interviewers change requirements on purpose. If you only memorised the YouTube chapter's diagram, you will struggle when they say "now it's live streaming." Understand why each block is there.

Name-dropping without substance

Saying "Facebook uses TAO" without explaining what problem it solves impresses nobody. If you mention a real system, give one sentence on the problem and the trade-off.

Only reading, never practising

Reading feels productive but the interview is a speaking exercise under time pressure. Timed practice out loud is what builds the skill.

Test yourself: whole-book review

1. (Ch 1) Why should the web tier be stateless?

If servers keep no user session data locally (it lives in a shared store instead), any server can handle any request. That makes horizontal scaling and auto-scaling easy, and the load balancer can send traffic anywhere.

2. (Ch 2) Roughly how many seconds are in a day, and why does it matter?

About 86,400 (often rounded to ~100,000 for quick maths). Dividing daily request counts by it turns "requests per day" into QPS, the number you size servers with.

3. (Ch 3) What are the four steps of the framework?

Understand the problem and establish design scope; propose a high-level design and get buy-in; design deep dive; wrap up.

4. (Ch 4) Why does the token bucket algorithm allow short bursts?

Tokens build up to the bucket's capacity while traffic is quiet. A burst can spend all saved tokens at once, and after that requests are limited to the refill rate.

5. (Ch 5) What problem do virtual nodes solve in consistent hashing?

With few servers on the ring, partitions can be very uneven. Giving each server many virtual positions spreads keys more evenly and balances load.

6. (Ch 6) In a quorum system with N=3, what do W=1 and R=1 optimise for, and what do you lose?

Fast writes and fast reads, because only one replica has to respond. You lose strong consistency, since a read may hit a replica that has not received the latest write. W + R > N is needed for strong consistency.

7. (Ch 7) What are the parts of a Snowflake ID?

A sign bit, a timestamp (milliseconds since a custom epoch), a datacenter ID, a machine ID and a sequence number. The timestamp at the front makes IDs roughly sortable by time.

8. (Ch 8) 301 or 302 redirect for a URL shortener, and why?

A 301 (permanent) lets browsers cache the redirect, which reduces server load. A 302 (temporary) sends every click to your servers, which is better if you need click analytics. Pick based on the goal.

9. (Ch 11) Why use a hybrid fanout approach for a news feed?

Fanout on write makes reads fast but is very costly for celebrities with huge followings. The hybrid pushes posts for most users and lets followers pull celebrity posts at read time.

10. (Ch 12 and 15) Why does chat use WebSocket while Google Drive's notifications use long polling?

Chat needs fast, frequent, two-way messages, which WebSocket's persistent bidirectional connection provides. Drive's notifications are infrequent and only flow from server to client, so the book picks long polling as the simpler fit.
