Chapter 14

Design YouTube

In this chapter you design a video-sharing service like YouTube: people upload videos, and millions of others watch them smoothly on phones, laptops and TVs. The interesting parts are what happens to a video after it is uploaded (transcoding), how it reaches viewers fast (CDNs and streaming protocols), and how to keep the bill from exploding.

~40 min readAdvancedPrerequisites: Ch 1 (scaling), Ch 2 (estimation), Ch 3 (framework), CDN and message queue basics

The big picture

On the surface YouTube looks simple: a creator uploads a video, and viewers press play. Under the hood, it is one of the biggest systems on Earth. The book opens with these numbers to show the scale:

A video service has two very different jobs:

  • Upload path — accept a big raw file (up to 1 GB here), store it safely, and convert it into many formats and qualities so every device can play it. This is heavy, slow, CPU-hungry work that happens once per video.
  • Watch path — deliver those converted files to viewers all over the world, quickly and without buffering. This happens millions of times per video and is mostly about bandwidth and money.

Most of this chapter is about the upload path, especially transcoding, because that is where the clever engineering lives. For the watch path, we mostly lean on an existing CDN (Content Delivery Network).

Real-world analogy

Think of a film studio and a chain of cinemas. A director hands over one giant master reel (the raw upload). The studio's lab makes many copies: a 4K print for premium theatres, a smaller version for airplanes, a dubbed version, a trailer, a poster image (transcoding, thumbnails). Then trucks deliver those copies to local cinemas in every city (the CDN), so audiences never have to travel to the studio. The lab work is expensive but happens once; the delivery happens every night in every town, so you want the copies stored close to the audience.

What makes this problem special

Unlike a chat app or URL shortener, the data here is huge (hundreds of megabytes per item), processing is expensive (converting video takes lots of CPU), and the main cost is bandwidth. Good answers talk about money as much as about speed.

How many pixels are in each frame, written by height: 360p, 480p, 720p (HD), 1080p (Full HD), 4K.

How many bits are used to represent one second of video. Higher bitrate means better quality but bigger files and more bandwidth needed.
Adaptive bitrate streaming
The player automatically switches between lower and higher quality versions as the viewer's network gets slower or faster.
Container
The "box" file format that holds video, audio and metadata together. Recognised by the file extension: .avi, .mov, .mp4.
Codec
"Coder-decoder": the compression algorithm that shrinks the video while keeping quality. Common ones: H.264, VP9, HEVC.
Streaming
Playing a video while it is still arriving, piece by piece, instead of waiting for the whole file to download first.
Streaming protocol
A standard way of splitting video into pieces and sending it to players. Examples: MPEG-DASH, Apple HLS, Microsoft Smooth Streaming, Adobe HDS.
GOP (Group of Pictures)
A small group of video frames in a fixed order, usually a few seconds long. Each GOP can be played (and processed) on its own, which makes it a natural "chunk" for splitting video.
DAG (Directed Acyclic Graph)
A set of tasks connected by arrows that show "this must happen before that," with no loops. Used to describe a video processing pipeline.
Message queue
A buffer where one component drops messages (jobs) and another picks them up later. It decouples components so they don't wait on each other.
Pre-signed URL
A temporary URL with built-in permission that lets a client upload (or download) directly to a storage bucket. Amazon S3 term; Azure calls it a "Shared Access Signature."
DRM (Digital Rights Management)
Technology that stops people from copying or playing videos without permission. Examples: Apple FairPlay, Google Widevine, Microsoft PlayReady.
AES encryption
A standard, strong encryption algorithm. Encrypted video can only be decrypted by authorised players.
Watermark
A logo or text overlaid on the video to show ownership.
Thumbnail
The small preview image shown for a video in lists and search results.
Long-tail distribution
A pattern where a few items are hugely popular and a very long list of items get only a little attention each.
ISP (Internet Service Provider)
The company that gives users internet access (Comcast, AT&T, Verizon...).
Stateless server
A server that keeps no user-specific data between requests, so any copy of it can handle any request.
Replica / master-slave
Copies of a database or cache. The master takes writes; slaves (replicas) copy it and serve reads. If the master dies, a slave can be promoted.

Step 2: High-level design

First, a key decision: we do not build our own CDN or blob storage. The interviewer said we can use existing cloud services, and that is what real companies do. The book points out that even giants rely on others: Netflix uses Amazon's cloud (AWS), and Facebook uses Akamai's CDN. Building a global CDN takes years and enormous money; in an interview, choosing the right existing technology is the better use of your time.

At the highest level, the system has three components:

The three main components
The client talks to two places. Video bytes come from the CDN. Everything else (recommendations, upload URLs, metadata updates, sign-up) goes through API servers.
Client
The YouTube app on a phone, a web browser on a computer, or a smart TV app.
CDN
Videos are stored in the CDN. When you press play, the video streams from the CDN edge server nearest to you.
API servers
Everything except streaming: feed recommendation, generating video upload URLs, updating the metadata database and cache, user sign-up, and so on.

Why a queue for completion events?

Transcoding servers should just transcode. If they had to also update the database directly, a slow or broken database would block transcoding. Dropping a "done" message into a queue lets the transcoders move on immediately, and the completion handlers update the database at their own pace. This is decoupling, a theme you will see again in the optimizations.

Video streaming flow

When you watch a YouTube video, it starts playing almost immediately; you don't wait for the whole file to download. That is the difference between downloading and streaming:

Downloading

The whole file is copied to your device first. Only then can you watch. A 300 MB video on a slow connection could take minutes before anything plays.

Streaming

Your device continuously receives small pieces of the video from remote servers and plays them as they arrive. Playback starts in seconds; the rest keeps arriving in the background.

To stream, client and server must agree on how video is chopped up and sent. That agreement is a streaming protocol. Popular ones:

You don't need to know the details of each. What matters: different protocols support different video encodings and playback players, so when designing a video streaming service you must pick the right protocol(s) for your use cases. That is one more reason we transcode into multiple formats.

Videos stream from the nearest CDN edge server
Each viewer streams from the edge server closest to them, so the data travels a short distance and latency is very low. The origin copy is only fetched once per edge.

Step 3 deep dive: video transcoding

When you record a video, your phone or camera saves it in a particular format. If you want it to play smoothly on every other device, it must be converted (encoded) into compatible bitrates and formats.

What is bitrate?

Bitrate is the rate at which bits are processed over time, usually measured in kilobits or megabits per second. A higher bitrate generally means higher video quality. High-bitrate streams need more processing power and fast internet speed.

Concrete example

Imagine the same 10-minute clip encoded twice. At a low bitrate, it might be tens of megabytes and look a bit blurry on a big TV, but it plays fine on a weak mobile signal. At a high bitrate, it might be several hundred megabytes and look crisp, but it will buffer on a slow connection. Neither is "right" — we want both, and let the player choose.

Why transcoding is important

  1. Raw video is huge Raw video consumes large amounts of storage. An hour-long high-definition video recorded at 60 frames per second can take up hundreds of GB. Compressing it saves storage and bandwidth.
  2. Compatibility Many devices and browsers only support certain types of video formats. Encoding into several formats makes sure everyone can play it.
  3. Adapt to network conditions To give users high-quality video while keeping playback smooth, deliver higher resolution to users with high bandwidth and lower resolution to users with low bandwidth.
  4. Quality switching mid-video Network conditions can change, especially on mobile. Switching quality automatically or manually as bandwidth changes is essential for a smooth experience. Having multiple versions ready makes this possible.
Adaptive bitrate: the player switches quality as bandwidth changes
Because the video is stored at several bitrates, the player can fetch each next segment at whatever quality the network can currently handle. The viewer sees a quality dip instead of a frozen screen.

Encoding formats: container + codec

Many encoding formats exist, but most contain two parts:

Container

Like a basket that holds the video file, audio, and metadata. You can usually tell the container from the file extension: .avi, .mov, .mp4.

Codecs

Compression and decompression algorithms that reduce video size while preserving quality. The most used codecs are H.264, VP9, and HEVC.

Real-world analogy

The container is a shipping box with a label (".mp4"). The codec is the way you folded and vacuum-packed the clothes inside so they take less space. Two boxes can look the same from outside but use different packing methods; the receiver needs to know the packing method (codec) to unpack it.

The DAG model for transcoding

Transcoding is computationally expensive and slow. And different creators want different processing: some want a watermark on their video, some upload their own thumbnail, some upload HD video while others don't.

To support many different processing pipelines while keeping lots of work running in parallel, we need an abstraction: a way for client programmers to define what tasks to run. Facebook's streaming video engine uses a directed acyclic graph (DAG) programming model, which defines tasks in stages so they can be executed sequentially or in parallel. We use a similar model.

Break "DAG" down:

  • Graph: boxes (tasks) connected by lines.
  • Directed: the lines are arrows; "A → B" means A must finish before B starts.
  • Acyclic: there are no loops, so the pipeline always finishes.

The original video is split into video, audio, and metadata. Each part then goes through its own tasks:

DAG for video transcoding
The original is split into video, audio and metadata. The video branch runs inspection, encoding to several resolutions, thumbnail generation and watermarking. The audio branch is encoded separately. At the end, all outputs are combined into the final encoded result.

Tasks that can be applied on a video file:

Inspection
Make sure videos have good quality and are not malformed (corrupted or broken).
Video encodings
Videos are converted to support different resolutions, codecs, bitrates, etc. For example, 360p.mp4, 480p.mp4, 720p.mp4, 1080p.mp4, 4k.mp4.
Thumbnail
Thumbnails can be uploaded by a user or automatically generated by the system.
Watermark
An image overlay on top of the video containing identifying information about the video.
Audio encoding
Compressing and converting the audio track.
Why the DAG is powerful

The DAG makes the pipeline configurable (each creator's video can get a different graph, e.g. with or without watermark) and parallel (anything without an arrow between them, like "encode 720p" and "make thumbnail", can run at the same time on different machines).

Video transcoding architecture

Who actually runs the DAG? The book proposes this architecture, which uses cloud services as building blocks:

Video transcoding architecture
Six components: preprocessor, DAG scheduler, resource manager, task workers, temporary storage, and encoded video as the output. Each is explained below.

1. Preprocessor

The preprocessor has four responsibilities:

  1. Video splitting The video stream is split or further split into smaller Group of Pictures (GOP) alignment. A GOP is a group of frames arranged in a specific order. Each chunk is an independently playable unit, usually a few seconds long.
  2. Support for old clients Some old mobile devices or browsers might not support video splitting on the client. The preprocessor splits videos by GOP alignment for them.
  3. DAG generation The processor generates a DAG based on configuration files that client programmers write. For example, a simple config might say: download → transcode for the video, and download → transcode for the audio.
  4. Cache data The preprocessor is a cache for segmented videos. For better reliability, it stores GOPs and metadata in temporary storage. If video encoding fails, the system can use the persisted data for retry operations.
Preprocessor: split into GOP chunks, cache them, build the DAG
Left: the video is cut into GOP-aligned chunks, which are saved to temporary storage so a failed encode can be retried without starting over. Right: a configuration file written by programmers is turned into a DAG.

2. DAG scheduler

The DAG scheduler splits a DAG graph into stages of tasks and puts them in the task queue in the resource manager. Tasks in the same stage can run in parallel; a stage starts only after the stage before it finishes.

DAG scheduler: splitting into stages
In the book's example, stage 1 splits the original into video, audio and metadata. Stage 2 runs video encoding, thumbnail and audio encoding (and watermark if configured) in parallel.

3. Resource manager

The resource manager is responsible for managing the efficiency of resource allocation: matching the right task to the right machine. It contains three queues and a task scheduler:

Task queue
A priority queue containing tasks to be executed.
Worker queue
A priority queue containing worker utilization info (how busy each worker is).
Running queue
Info about the currently running tasks and the workers running them.
Task scheduler
Picks the optimal task/worker pair and instructs the chosen task worker to execute the job.

The resource manager works in a loop:

  1. Get a task The task scheduler gets the highest-priority task from the task queue.
  2. Get a worker The task scheduler gets the optimal task worker to run the task from the worker queue.
  3. Run it The task scheduler instructs the chosen task worker to run the task.
  4. Track it The task scheduler binds the task/worker info and puts it in the running queue. When the job is done, it removes the job from the running queue.
Resource manager internals
The four-step loop. Priority queues let urgent tasks (say, a popular creator's upload) jump ahead, and the worker queue lets the scheduler send work to the least-busy suitable machine.

4. Task workers

Task workers run the tasks defined in the DAG. Different task workers may run different tasks.

5. Temporary storage

Multiple storage systems are used here. The choice depends on factors like data type, data size, access frequency, and data life span.

Metadata → memory

Metadata is frequently accessed by workers and the data size is usually small. So caching metadata in memory is a good idea.

Video / audio → blob storage

Video and audio data are large, so they go in blob storage.

Encoded video is the final output of the encoding pipeline. An example output: funny_720p.mp4.

System optimizations: speed

At this point the design works. Now we refine it for speed, safety, and cost. We start with speed.

Speed optimization 1: parallelize video uploading

Uploading a whole video as one unit is inefficient: if the connection drops at 90%, you start over. Instead, the client splits the video into smaller chunks by GOP alignment and uploads them in parallel. This allows fast resumable uploads when a previous upload failed. The job of splitting a video file by GOP can be done by the client to improve upload speed.

Client-side splitting into GOP chunks
Chunks upload at the same time, which is faster. If chunk 2 fails, only chunk 2 is retried, not the whole 1 GB file.

Speed optimization 2: place upload centers close to users

Another way to improve upload speed is setting up multiple upload centers across the globe. People in the United States can upload videos to the North America upload center, and people in China can upload to the Asian upload center. To achieve this, we use the CDN as upload centers.

System optimizations: safety

Safety optimization 1: pre-signed upload URL

Safety is one of the most important aspects of any product. We want only authorized users to upload videos to the right location. Without protection, anyone who knew the storage bucket address could dump files into it. The fix is a pre-signed URL:

Pre-signed URL upload flow
The API server, which knows who the user is, hands out a URL that grants permission to upload one object to one location for a limited time. The big file then goes straight to storage.
  1. Request The client makes an HTTP request to API servers to fetch the pre-signed URL, which gives access permission to the object identified in the URL. The term "pre-signed URL" comes from uploading files to Amazon S3. Other cloud providers may use a different name; Microsoft Azure blob storage calls it "Shared Access Signature."
  2. Receive API servers respond with a pre-signed URL.
  3. Upload Once the client receives the response, it uploads the video using the pre-signed URL.

Safety optimization 2: protect your videos

Many content makers are reluctant to post videos online because they fear their original videos will be stolen. To protect copyrighted videos, we can adopt one of three options:

Digital rights management (DRM)

Three major DRM systems are Apple FairPlay, Google Widevine, and Microsoft PlayReady. The player must get a licence before it can play the video.

AES encryption

You can encrypt a video and configure an authorization policy. The encrypted video is decrypted upon playback, which ensures only authorized users can watch it.

Visual watermarking

An image overlay on top of the video containing identifying information, such as a company logo or name.

System optimizations: cost-saving

Remember the estimate: $150,000 per day on the CDN. The CDN is a crucial part of the system: it makes video fast globally. But it is expensive, especially when data is large. How do we cut the bill?

Previous research shows that YouTube video streams follow a long-tail distribution: a few popular videos are accessed very frequently, but many others have few or no viewers.

Long-tail distribution of video views
A small number of videos get most of the views. Paying CDN prices to cache the entire long tail is wasteful.

Based on this observation, the book suggests these optimizations:

  1. Serve only popular videos from the CDN Other videos are served from high-capacity storage video servers that we run ourselves, which is cheaper per GB.
  2. Fewer encoded versions for less popular content Short videos can be encoded on demand. Less popular videos may not need 5 versions; that saves storage and transcoding work.
  3. Regional popularity Some videos are popular only in certain regions. There is no need to distribute these videos to other regions.
  4. Build your own CDN, like Netflix, and partner with Internet Service Providers (ISPs) Building a CDN is a giant project, but it can make sense for large streaming companies. An ISP can be Comcast, AT&T, Verizon, or other internet providers. ISPs are located all around the world and are close to users. By partnering with ISPs, you can improve the viewing experience and reduce bandwidth charges.

Error handling

For a large-scale system, errors are unavoidable. To build a highly fault-tolerant system, we must handle errors gracefully and recover from them fast. Two types of errors exist:

Recoverable errors

For recoverable errors, such as a video segment failing to transcode, the general idea is to retry the operation a few times. If the task keeps failing and the system believes it is not recoverable, it returns a proper error code to the client.

Non-recoverable errors

For non-recoverable errors, such as a malformed video format, the system stops the running tasks associated with the video and returns the proper error code to the client.

Step 4: Wrap up

If there is extra time at the end, the book suggests these talking points:

Scale the API tier
Because API servers are stateless, it is easy to scale the API tier horizontally: just add more servers behind the load balancer.
Scale the database
Talk about database replication and sharding.
Live streaming
Recording and broadcasting video in real time. Our system is not designed for live streaming, but it has some similarities: both need uploading, encoding and streaming. Notable differences:
  • Live streaming has a higher latency requirement, so it might need a different streaming protocol.
  • Live streaming has a lower requirement for parallelism, because small chunks of data are already processed in real time.
  • Live streaming requires different sets of error handling. Any error handling that takes too much time is not acceptable.
Video takedowns
Videos that violate copyrights, pornography, or other illegal acts must be removed. Some can be discovered by the system during the upload process, while others are discovered through user flagging.

Walkthrough: one video's life

  1. Get permission Priya opens the app and picks a 600 MB video. The app asks the API servers (through the load balancer) for a pre-signed upload URL. The API server checks she is logged in and returns the URL.
  2. Upload fast The app splits the file into GOP chunks and uploads them in parallel to the nearest upload center. If one chunk fails, only that chunk is retried. Meanwhile, the app sends her title and description to the API servers, which store them in the metadata DB and cache.
  3. Preprocess The preprocessor reads the original, splits it into GOPs if needed, caches the segments in temporary storage, and builds a DAG from the configuration (her channel has a watermark, so the DAG includes a watermark task).
  4. Schedule and run The DAG scheduler splits the DAG into stages and pushes tasks into the resource manager's task queue. The task scheduler pairs each task with the best available worker: encoders make 360p, 480p, 720p and 1080p; another worker makes the thumbnail; another adds the watermark; a merger assembles the output.
  5. Finish Encoded files go to transcoded storage and (if expected to be popular) out to the CDN. A completion event goes into the completion queue; a completion handler marks the video "ready" in the metadata DB and cache. Priya is notified.
  6. Watch Rahul in another city taps the video. The API server returns metadata including the stream URL. His player streams segments from the nearest CDN edge using a protocol like HLS, starting at 480p and moving up to 1080p when his Wi-Fi proves fast. The stream is protected with DRM/AES so it can't simply be copied.

How to answer this in an interview

1
Understand the problem and scope
3–10 min
  • Narrow to upload + watch. Ask about clients, DAU, watch time, international users, formats, encryption, max file size, and whether cloud services are allowed.
  • Do the two key estimates: 150 TB/day storage and $150,000/day CDN.
"Let me confirm scope: we focus on uploading and watching videos, on mobile, web and smart TV, with 5 million DAU, mostly international, files up to 1 GB, and we can use existing cloud storage and CDN. With 10% of users uploading a 300 MB video daily, that's 150 TB of new storage per day. Viewing 5 videos each through CloudFront at 2 cents a GB costs about $150,000 per day, so CDN cost will be a major design driver."
2
High-level design
10–15 min
  • Three components: client, CDN, API servers. Justify using existing blob storage and CDN (Netflix on AWS, Facebook on Akamai).
  • Draw the upload architecture; explain flow a (video) and flow b (metadata) running in parallel.
  • Explain streaming vs downloading and name streaming protocols.
"Video bytes never pass through our API servers. The client uploads to blob storage; transcoding servers pick it up, write outputs to transcoded storage and the CDN, and drop a completion event on a queue. A completion handler updates the metadata DB and cache. In parallel, the client sends metadata through the API servers."
"Why not just store the uploaded file and serve it as is?"
"Raw files are large and in whatever format the phone produced. Many devices can't play every format, and viewers on slow networks would buffer constantly. Transcoding gives us compressed versions in several resolutions and formats, which also enables adaptive bitrate streaming."
3
Deep dive
10–25 min
  • Transcoding: bitrate, container vs codec, the DAG model, and the six-part transcoding architecture.
  • Optimizations: speed (GOP chunk uploads, upload centers, message queues), safety (pre-signed URLs, DRM/AES/watermark), cost (long tail).
  • Error handling: recoverable vs non-recoverable; retry, replicate, stateless.
"I'd model transcoding as a DAG, like Facebook's streaming video engine. The preprocessor splits the video into GOPs, caches them, and builds the DAG from config. The DAG scheduler splits it into stages, and the resource manager matches tasks to workers using a task queue, a worker queue and a running queue."
"The CDN bill is too high. What would you do?"
"Views follow a long tail. I'd serve only popular videos from the CDN and the rest from our own high-capacity video servers; keep fewer encoded versions for unpopular videos and encode short ones on demand; distribute regionally popular videos only to those regions; and at very large scale, build our own CDN and partner with ISPs like Netflix does. I'd analyze historical viewing patterns first."
"How do you stop random people from uploading to your bucket?"
"The client first asks our API servers for a pre-signed URL, after authentication. That URL grants time-limited permission to write one specific object. The client then uploads directly to storage with it. Azure calls this a Shared Access Signature."
"A task worker crashes in the middle of encoding 1080p. What happens?"
"It's a recoverable error. The GOP segments are cached in temporary storage by the preprocessor, so the resource manager retries the task on a new worker without re-uploading or re-splitting. If it keeps failing, we return an error code to the client."
4
Wrap up
3–5 min
  • Scale the stateless API tier horizontally; scale DB with replication and sharding.
  • Live streaming differences: latency, parallelism, error handling. Video takedowns.
"How would live streaming change this?"
"Live streaming needs much lower latency, so it may need a different protocol. It needs less parallelism, because small chunks are processed in real time. And error handling must be fast, because a slow retry is visible to live viewers."

Common mistakes

Sending video bytes through API servers

Pushing 1 GB uploads through your application servers wastes their capacity and bandwidth. Upload directly to blob storage (with a pre-signed URL) and keep API servers for small requests.

Forgetting transcoding

Storing and serving the original file ignores device compatibility, file size, and adaptive bitrate. Transcoding is the heart of this problem.

Ignoring cost

Saying "just put everything on the CDN" without noticing the $150,000/day bill misses what the interviewer is looking for. Bring up the long tail.

Proposing to build a CDN from scratch first

Unless the company is Netflix-sized, use an existing CDN and blob storage. Mention building your own CDN only as a later cost optimization.

Tightly coupled pipeline

A chain where each module calls the next directly can't parallelize and fails as a whole. Use message queues between modules.

Treating all errors the same

Retrying a malformed video forever wastes resources. Separate recoverable errors (retry) from non-recoverable ones (stop and return an error).

Test yourself

Using the book's assumptions, how much new storage is needed per day?

5 million DAU × 10% uploading × 300 MB = 150 TB per day. The 10% is the share of users who upload one video daily.

How is the daily CDN cost of $150,000 calculated?

5 million users × 5 videos × 0.3 GB × $0.02 per GB (CloudFront) = $150,000. It shows that serving video is very expensive, which motivates the cost optimizations.

What are the three main components at the highest level, and what does each do?

Client (phone, browser, TV), CDN (stores and streams videos), and API servers (everything else: feed, upload URLs, metadata updates, sign-up).

Why are container and codec different things?

The container (.mp4, .mov, .avi) is the box holding video, audio and metadata. The codec (H.264, VP9, HEVC) is the compression algorithm used for the content. The same container can hold content compressed with different codecs.

Why is the DAG model useful for transcoding?

Different creators need different pipelines (watermark or not, custom thumbnail, HD or not). The DAG lets programmers define tasks and their order in config files, and tasks without dependencies between them run in parallel.

Describe the resource manager's four-step loop.

1) The task scheduler gets the highest-priority task from the task queue. 2) It gets the optimal worker from the worker queue. 3) It tells that worker to run the task. 4) It records the task/worker pair in the running queue, removing it when the job is done.

Scenario: users in Asia complain uploads are slow and often fail halfway. What two changes help?

Split videos into GOP chunks on the client and upload them in parallel, so a failure only retries one chunk. And place upload centers close to users, using the CDN as upload centers, so Asian users upload to an Asian center.

Scenario: an old smart TV app can't split videos into GOPs. What happens?

The entire video is uploaded to the server, and the preprocessor splits it by GOP alignment on the server side. This is one of the preprocessor's responsibilities ("support for old clients").

What is a pre-signed URL and why use it?

A temporary URL from the API servers that grants permission to upload a specific object to storage. It ensures only authorized users upload, to the right location. S3 calls it a pre-signed URL; Azure calls it a Shared Access Signature.

Scenario: the metadata DB master crashes. What should happen? And if a slave crashes?

If the master is down, promote one of the slaves to be the new master. If a slave is down, use another slave for reads and bring up a new database server to replace the dead one.

Cheat sheet

  • Scope: upload + watch; 5M DAU; mobile/web/TV; max 1 GB; use existing cloud blob storage + CDN.
  • Estimates: 150 TB/day storage (5M × 10% × 300 MB); $150,000/day CDN (5M × 5 × 0.3 GB × $0.02).
  • Three components: client, CDN (streams video), API servers (everything else).
  • Upload = two parallel flows: (a) video to original storage, transcode, transcoded storage + CDN, completion queue + handler; (b) metadata via API servers.
  • Streaming plays pieces as they arrive; protocols: MPEG-DASH, Apple HLS, Microsoft Smooth Streaming, Adobe HDS. Stream from the nearest CDN edge.
  • Transcode because raw video is huge, devices differ, and adaptive bitrate needs multiple qualities. Format = container (.mp4) + codec (H.264, VP9, HEVC).
  • DAG model (from Facebook): split into video/audio/metadata; tasks include inspection, encodings, thumbnail, watermark, audio encoding.
  • Transcoding architecture: preprocessor (GOP split, cache, DAG generation), DAG scheduler (stages), resource manager (task/worker/running queues + scheduler), task workers, temp storage (memory + blob), encoded video.
  • Speed: client GOP-chunk parallel uploads; upload centers near users (CDN); message queues between modules.
  • Safety: pre-signed upload URLs; DRM (FairPlay, Widevine, PlayReady), AES encryption, visual watermark.
  • Cost: long tail; popular on CDN, rest on own video servers; fewer versions / on-demand encoding; regional distribution; own CDN + ISP partners.
  • Errors: recoverable = retry; non-recoverable = stop + error code; replicas for queues/cache/DB; stateless API servers; promote slave if master dies.
