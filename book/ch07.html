Chapter 7

Design a Unique ID Generator in Distributed Systems

Every tweet, order and message needs an ID that no other record will ever share. On one database that is trivial: just count 1, 2, 3. Across hundreds of servers in several data centers, generating thousands of IDs per second without ever colliding, and keeping them sorted by time, takes a clever trick. This chapter compares four approaches and then takes apart Twitter's snowflake bit by bit.

~35 min readIntermediatePrerequisites: Ch 1 (scaling basics), binary numbers (explained here)

The big picture

Databases identify each row with a primary key, a value that is unique to that row. In a traditional single database, you mark the ID column as auto_increment, and the database hands out 1, 2, 3, 4... automatically.

The book's opening point: auto_increment does not work in a distributed environment. A single database server is not large enough to handle all the traffic, and generating unique IDs across multiple databases with minimal delay is challenging. If two databases both count from 1, they will both hand out ID 1, 2, 3... and you get duplicates.

With one database, auto_increment is perfect but that database becomes a bottleneck and a single point of failure. With many, each counts independently and IDs collide.
Real-world analogy

Think of a deli counter where you pull a ticket number. One ticket machine works great for one shop. Now imagine a chain of 1,000 shops that must never print the same number twice, anywhere, ever, and the numbers should roughly show who came first across the whole chain. You could have all shops phone one central machine (slow, and if it breaks every shop stops). Or you could print tickets that combine the exact time, the shop number, and a small counter for that shop that moment. Two shops cannot collide because the shop number differs; one shop cannot collide with itself because the time or counter differs. That second idea is Twitter's snowflake.

Understand the problem and design scope

Asking clarification questions is the first step. The book's candidate-interviewer dialogue goes roughly like this:

From that, the requirements are:

Unique

IDs must be unique, across every server, forever.

Numerical

IDs are numerical values only.

64-bit

IDs fit into 64 bits.

Ordered by date

Later IDs are bigger than earlier ones (roughly).

10,000 / second

The ability to generate over 10,000 unique IDs per second.

Why "ordered by date" matters

If IDs grow with time, you can sort records by ID instead of keeping a separate timestamp index, and "give me the 20 newest tweets" becomes "the 20 largest IDs". Databases also insert time-ordered keys more efficiently than random ones.

Why 64 bits?

A 64-bit number fits in a standard integer type in almost every language and database, so it is compact, fast to compare and index. 64 bits can hold about 18 quintillion values (264), which is plenty if we use the bits wisely.

High-level design: four options

The book lists multiple options for generating unique IDs in distributed systems:

  1. Multi-master replication
  2. Universally unique identifier (UUID)
  3. Ticket server
  4. Twitter snowflake approach

For each, we look at how it works, then pros and cons against our five requirements.

Option 1: Multi-master replication

This approach still uses the databases' auto_increment feature, but with a twist: instead of increasing the next ID by 1, we increase it by k, where k is the number of database servers in use.

Multi-master replication with k = 2
With two servers (k = 2), server 1 hands out odd numbers and server 2 even numbers. They can never collide, and each can work independently.

How it works: the next ID on a server equals the previous ID on that same server plus k. With 3 servers, server 1 gives 1, 4, 7...; server 2 gives 2, 5, 8...; server 3 gives 3, 6, 9.... This solves some scalability issues because IDs can scale with the number of database servers.

Pros

  • Simple: reuses a built-in database feature.
  • Numeric IDs that fit in 64 bits.
  • Throughput scales with the number of database servers.

Cons (from the book)

  • Hard to scale with multiple data centers.
  • IDs do not go up with time across multiple servers. If server 2 is busier, it might be at ID 1,000 while server 1 is at 11, so a newer record can have a smaller ID.
  • It does not scale well when a server is added or removed: k changes, and every server's step must be reconfigured without creating overlaps.

Option 2: UUID

A UUID is another easy way to obtain unique IDs. A UUID is a 128-bit number used to identify information in computer systems. It is usually written as 32 hexadecimal characters in five groups, for example:

09c93e62-50b4-468d-bf8a-c07e1040bfb2

UUIDs have a very low probability of collision. Quoting the book's source (Wikipedia): after generating 1 billion UUIDs every second for approximately 100 years, the probability of creating a single duplicate would reach 50%. In other words, collisions are not a practical concern.

How it works: UUIDs can be generated independently without coordination between servers. Each web server contains its own ID generator, and each web server is responsible for generating IDs independently.

  • Generating UUIDs is simple. No coordination between servers is needed, so there are no synchronization issues.
  • The system is easy to scale because each web server is responsible for generating the IDs it consumes. The ID generator scales with web servers.

Cons (from the book)

  • IDs are 128 bits long, but our requirement is 64 bits.
  • IDs do not go up with time.
  • IDs could be non-numeric (they contain letters a-f in their usual form).
When UUID is the right answer

If the interviewer did not require 64-bit, numeric or time-sorted IDs, a UUID is often the simplest correct choice. Requirements drive the design.

Option 3: Ticket server

Ticket servers are another interesting way to generate unique IDs. Flickr developed ticket servers to generate distributed primary keys.

How it works: use a centralized auto_increment feature in a single database server, the Ticket Server. Every web server asks the ticket server for the next number whenever it needs an ID.

Pros (from the book)

  • Numeric IDs.
  • It is easy to implement, and it works for small to medium-scale applications.

Cons (from the book)

  • Single point of failure. A single ticket server means if it goes down, all systems that depend on it face issues.
  • To avoid a single point of failure, we can set up multiple ticket servers. However, this introduces new challenges such as data synchronization.
Real-world analogy

The ticket server is the one ticket machine at the entrance of a huge government office. Everyone gets a perfectly ordered number. But if it jams, nobody gets served, and with a long enough queue it becomes the slowest part of the visit.

Option 4: Twitter snowflake approach

None of the approaches above meets all our requirements. Twitter's unique ID generation system, called snowflake, is inspiring and can satisfy them.

The key idea is divide and conquer. Instead of generating an ID directly, we divide the 64 bits of an ID into different sections, each with its own job.

Why this satisfies every requirement

  • Unique: two different machines differ in datacenter ID or machine ID. The same machine never repeats because either the millisecond or the sequence number differs.
  • Numerical and 64-bit: the whole ID is one 64-bit integer.
  • Ordered by date: the timestamp occupies the highest bits, so larger timestamps mean larger IDs.
  • 10,000 per second: even one machine can theoretically produce 4096 per millisecond, which is about 4 million per second.
  • No coordination: each machine generates IDs on its own, like UUID, so there is no single point of failure like the ticket server.
Same millisecond, same sequence, different machines: still unique
Two generators fire in the same millisecond, each issuing its 6th ID (sequence 5). Because no two generators share the same datacenter + machine pair, their IDs can never be equal.

A 2-minute binary primer

To understand the deep dive, you only need three ideas about binary numbers.

  1. Each position is a power of 2. From the right: 1, 2, 4, 8, 16... Binary 1011 = 8 + 0 + 2 + 1 = 11.
  2. n bits can hold 2n different values, from 0 to 2n-1. 5 bits: 0 to 31 (32 values). 12 bits: 0 to 4095 (4096 values).
  3. Shifting left makes room. x << 12 slides x twelve places left and fills the right with twelve zeros, so another 12-bit value can be dropped into that space with OR (|). That is how we pack several small numbers into one big one.
Real-world analogy

A phone number like +1 415 555 0123 packs a country code, area code, exchange and line number into one long number. Each part has a fixed number of digits, so you can always split it back apart. A snowflake ID does exactly this, but in binary digits.

Deep dive: the timestamp

The most important 41 bits make up the timestamp section. As timestamps grow with time, IDs are sortable by time.

The value stored is milliseconds since a custom epoch. Why not since the standard Unix epoch (1 January 1970)? Because every millisecond between 1970 and when your system launched would be wasted space in those 41 bits. Starting the clock at your own launch date gives you the full lifetime going forward. Twitter's epoch is 1288834974657 ms after the Unix epoch, which is Nov 04, 2010, 01:42:54 UTC.

Worked example: binary timestamp back to UTC (from the book)

  1. Take the 41-bit timestamp section of an ID:
    00100010101001011010011011000101101011000
  2. Convert binary to decimal: 297616116568. This is how many milliseconds have passed since Twitter's epoch.
  3. Add Twitter's epoch to get milliseconds since the Unix epoch:
    297616116568 + 1288834974657 = 1586451091225
  4. Convert milliseconds since the Unix epoch to UTC: 1586451091225 ms = Apr 09 2020 16:51:31 UTC.
timestamp_bits = 0b00100010101001011010011011000101101011000
ms_since_twitter_epoch = 297616116568
unix_ms = ms_since_twitter_epoch + 1288834974657   # = 1586451091225
utc = from_unix_millis(unix_ms)                    # 2020-04-09 16:51:31.225 UTC

How long does 41 bits last?

The maximum timestamp that can be represented in 41 bits is:

2^41 - 1 = 2199023255551 milliseconds
         = 2199023255551 / 1000 / 365 / 24 / 3600
         ~ 69 years

Deep dive: datacenter ID, machine ID and sequence number

Datacenter ID and machine ID

Datacenter IDs and machine IDs are chosen at the startup time, and generally fixed once the system is up and running. Any changes in datacenter IDs and machine IDs require careful review, since an accidental change in those values can lead to ID conflicts. For example, if two machines are accidentally both configured as datacenter 3, machine 7, they could produce identical IDs in the same millisecond.

With 5 bits each, we can have 25 = 32 datacenters and 32 machines per datacenter.

Sequence number

The sequence number is 12 bits, which gives 212 = 4096 combinations. This field is 0 unless more than one ID is generated in a millisecond on the same server. In theory, a machine can support a maximum of 4096 new IDs per millisecond.

Sequence numbers on one machine
The sequence counter only ticks up when several IDs are requested in the same millisecond, and resets to 0 each new millisecond.
4,096IDs per ms per machine
~4.1 millionIDs per second per machine (theory)
10,000IDs per second required

So even a single machine has far more capacity than the 10,000 IDs per second requirement. More machines simply add more capacity, up to 1,024 of them.

Worked example: building an ID bit by bit

Let us build a real 64-bit ID on datacenter 3, machine 7, as the 6th ID in that millisecond (sequence 5, because counting starts at 0), at the same moment as the book's example (timestamp 297616116568).

  1. Sign bit: 0
  2. Timestamp (41 bits): 297616116568 = 00100010101001011010011011000101101011000
  3. Datacenter ID (5 bits): 3 = 00011
  4. Machine ID (5 bits): 7 = 00111
  5. Sequence (12 bits): 5 = 000000000101
  6. Concatenate them left to right to get 64 bits.

In code, "concatenate" is done with shifts and OR. Each value is shifted left by the number of bits to its right:

Decoding an ID back into its parts

timestamp  = id >> 22            // 297616116568 -> + epoch -> Apr 09 2020 16:51:31 UTC
datacenter = (id >> 17) & 0x1F   // 0x1F = 31 = binary 11111 -> 3
machine    = (id >> 12) & 0x1F   //                         -> 7
sequence   = id & 0xFFF          // 0xFFF = 4095            -> 5
Why this is useful

Any snowflake ID tells you when and where it was created, which helps with debugging ("which machine made this bad record?") and lets you fetch "everything after time T" with a simple WHERE id > ... query.

The generator, in pseudocode

The book describes the layout; here is how a generator on one machine typically puts it into practice. Two edge cases matter: the sequence running out within one millisecond, and the clock moving backwards.

class SnowflakeGenerator:
    EPOCH          = 1288834974657   # Twitter epoch, ms
    DATACENTER_BITS = 5
    MACHINE_BITS    = 5
    SEQUENCE_BITS   = 12
    MAX_SEQUENCE    = 4095           # 2^12 - 1

    constructor(datacenterId, machineId):
        require 0 <= datacenterId <= 31
        require 0 <= machineId <= 31     # chosen at startup, then fixed
        this.datacenterId  = datacenterId
        this.machineId     = machineId
        this.lastTimestamp = -1
        this.sequence      = 0

    synchronized nextId():                # one thread at a time on this machine
        now = currentTimeMillis()

        if now < lastTimestamp:
            # Clock moved backwards (e.g. NTP correction).
            # Issuing IDs now could repeat old ones, so wait or fail.
            if lastTimestamp - now is small: now = waitUntil(lastTimestamp)
            else: throw ClockMovedBackwardsError

        if now == lastTimestamp:
            sequence = (sequence + 1) & MAX_SEQUENCE
            if sequence == 0:
                # All 4096 values used in this ms: spin until the next ms.
                now = waitUntilNextMillis(lastTimestamp)
        else:
            sequence = 0                  # new millisecond, reset

        lastTimestamp = now
        return ((now - EPOCH) << 22)
             | (datacenterId << 17)
             | (machineId << 12)
             | sequence

The three branches are what keep IDs unique on a single machine; datacenter and machine IDs keep machines apart from each other.
Scenario: a burst of 5,000 requests in one millisecond

IDs 1 to 4096 use sequence 0 to 4095. Request 4097 wraps the sequence to 0 in the same millisecond, which would duplicate the first ID, so the generator waits (well under a millisecond) for the clock to tick and continues with sequence 0 of the next millisecond. Requests are slightly delayed, never duplicated.

Wrap up: additional talking points

The book closes by noting we settled on snowflake because it supports all our use cases and is scalable in a distributed environment. If there is extra time at the end of the interview, here are additional talking points:

Clock synchronization

In our design, we assume ID generation servers have the same clock. This assumption might not be true when a server is running on multiple cores. The same challenge exists in multi-machine scenarios. Solutions to clock synchronization are out of scope, but it is important to understand the problem exists. Network Time Protocol (NTP) is the most popular solution.

Section length tuning

For example, fewer sequence numbers but more timestamp bits are effective for low-concurrency and long-term applications. An app creating only a few IDs per millisecond does not need 4096 sequence values, and could spend those bits on extending the 69-year lifetime.

High availability

Since an ID generator is a mission-critical system, it must be highly available. Every write in the product depends on getting an ID.

Section length tuning, with numbers

LayoutTimestamp bitsLifetimeSequence bitsIDs per ms per machine
Standard snowflake41~69 years124096

Each bit moved from sequence to timestamp halves the burst capacity and doubles the lifetime. You can make similar trades between datacenter and machine bits (for example 3 bits for 8 datacenters and 7 bits for 128 machines each).

Why clock problems are dangerous

If NTP adjusts a server's clock backwards by 5 ms, the server will see timestamps it has already used. If it keeps issuing IDs, it can produce duplicates. That is why practical generators detect "clock moved backwards" and refuse or wait, as in the pseudocode above.

Generators never talk to each other while creating IDs. Uniqueness comes from the layout; sortability comes from the timestamp in the top bits.
  1. Startup: each generator machine reads its datacenter ID and machine ID from configuration. These are fixed while running and changed only with careful review.
  2. Clocks: all machines sync their clocks with NTP so timestamps are close across machines.
  3. Request: an application needs an ID (a new tweet, say) and calls the local or nearby generator.
  4. Generate: the generator takes milliseconds since the custom epoch, picks the next sequence number for that millisecond, and packs 0 | timestamp | datacenter | machine | sequence into 64 bits.
  5. Edge cases: if 4096 IDs are used in one millisecond, it waits for the next; if the clock jumps backwards, it waits or raises an error.
  6. Use: the ID becomes the record's primary key. Sorting by ID now sorts by creation time.
  7. Availability: because there are many independent generators, losing one machine only removes a little capacity; nothing else stops.

Common mistakes

Jumping straight to snowflake

The interviewer wants to see you reason about alternatives. Briefly cover multi-master, UUID and the ticket server and say which requirement each fails before choosing snowflake.

Forgetting the sequence overflow case

Saying "the sequence resets every millisecond" is half the story. Explain what happens when it hits 4095 within one millisecond: wait for the next millisecond.

Ignoring clocks

Snowflake relies on clocks. Mention NTP and what the generator does if the clock moves backwards.

Using the Unix epoch without thinking

Counting from 1970 wastes decades of the 41-bit range. Use a custom epoch close to launch to delay overflow.

Claiming IDs are strictly ordered across machines

Snowflake IDs are ordered by time, but two machines in the same millisecond, or with slightly different clocks, produce IDs whose order does not exactly match real time. They are roughly time-sorted, which is what the requirements ask for.

Getting the bit counts wrong

1 + 41 + 5 + 5 + 12 = 64. If your sections do not add up to 64, the interviewer will notice.

Test yourself

1. Why doesn't a database's auto_increment work for a distributed system?

A single database server is not large enough to handle all traffic and is a single point of failure. If you use many databases, each counts independently from 1 and IDs collide. Coordinating them with minimal delay is challenging.

2. In multi-master replication with 3 servers, what IDs does server 2 generate, and what is the main ordering problem?

Server 2 generates 2, 5, 8, 11... (step k = 3). IDs do not go up with time across servers: a busy server can be far ahead of a quiet one, so a newer record may have a smaller ID. It is also hard to add or remove servers and to scale across data centers.

3. Name three reasons UUID fails our requirements.

It is 128 bits (we need 64), it is not ordered by time, and it can be non-numeric. Collisions are not the problem.

4. What is the main weakness of the ticket server and why is adding a second one not trivial?

It is a single point of failure: if it goes down, every system that needs IDs is affected. Adding more ticket servers introduces data synchronization challenges, because they must avoid giving out the same numbers.

5. List the five sections of a snowflake ID and their sizes.

Sign bit (1, always 0), timestamp (41, ms since custom epoch), datacenter ID (5), machine ID (5), sequence number (12). Total 64.

6. An ID's timestamp section in decimal is 297616116568. When was it generated, using Twitter's epoch?

Add the epoch: 297616116568 + 1288834974657 = 1586451091225 ms since the Unix epoch, which is Apr 09 2020 16:51:31 UTC.

7. Why does 41 bits give about 69 years?

The maximum is 241-1 = 2,199,023,255,551 ms. Divided by 1000 (seconds), 3600 (hours), 24 (days) and 365 (years) that is about 69 years. A custom epoch near today's date delays overflow.

8. How many generator machines and how many IDs per millisecond per machine does the standard layout support?

32 datacenters x 32 machines = 1,024 machines. 212 = 4,096 IDs per millisecond per machine.

9. Your app creates about 10 IDs per second but must run for 150 years. How might you change the layout?

Use section length tuning: move bits from the sequence to the timestamp. With 42 timestamp bits (about 139 years) or 43 (about 278 years), and 10-11 sequence bits, which is still far more than 10 IDs per second needs. Alternatively choose a later epoch.

10. NTP moves a generator's clock back by 3 ms. What could go wrong, and what should the generator do?

It might reuse timestamps it already issued, and with the sequence reset it could produce duplicate IDs. It should compare the current time to the last timestamp it used and, if earlier, wait until time catches up (for small gaps) or refuse and alert (for large gaps).

Cheat sheet

  • auto_increment fails in distributed systems: one DB cannot handle the traffic; many DBs collide.
  • Requirements: unique, numerical, 64-bit, ordered by date, 10,000+ IDs per second.
  • Multi-master: step by k servers. Not time-ordered across servers; hard with multiple DCs and adding/removing servers.
  • UUID: 128 bits, no coordination, easy to scale. Too long, not time-ordered, non-numeric. 50% chance of one duplicate only after 1 billion per second for ~100 years.
  • Ticket server (Flickr): central auto_increment. Simple and numeric, but a single point of failure; multiple servers need synchronization.
  • Snowflake layout: 1 sign | 41 timestamp | 5 datacenter | 5 machine | 12 sequence = 64 bits.
  • Timestamp = ms since custom epoch; Twitter's is 1288834974657 (Nov 04 2010 01:42:54 UTC). Lasts 241-1 ms, about 69 years.
  • Decode: timestamp = id >> 22, add epoch, convert to UTC.
  • Datacenter and machine IDs chosen at startup and fixed; 32 x 32 = 1,024 machines.
  • Sequence: 4,096 per ms per machine; reset each ms; on overflow wait for next ms.
  • Build: (ts << 22) | (dc << 17) | (machine << 12) | seq.
  • Wrap-up: clock sync (NTP), section length tuning, high availability.
