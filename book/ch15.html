Chapter 15

Design Google Drive

In this chapter you design a cloud file storage and sync service like Google Drive or Dropbox. You put a file in a folder on your laptop, and a moment later it shows up on your phone, safely stored and shareable. The big ideas are splitting files into blocks, syncing only what changed, strong consistency for metadata, and notifying devices when something changes.

~40 min readAdvancedPrerequisites: Ch 1 (scaling), Ch 2 (estimation), Ch 3 (framework), Ch 12 (long polling / WebSocket)

The big picture

In recent years, cloud storage services such as Google Drive, Dropbox, Microsoft OneDrive, and Apple iCloud have become very popular. Google Drive is a file storage and synchronization service that helps you store documents, photos, videos, and other files in the cloud. You can access your files from any computer, smartphone, or tablet, and easily share them with friends, family, and coworkers.

What makes this hard?

  • Data loss is unacceptable. If a chat message is lost, it's annoying. If your tax documents or wedding photos vanish, it's a disaster.
  • Files are big and change often. Re-uploading a 2 GB file because you changed one paragraph would waste time and bandwidth.
  • Many devices, one truth. Your laptop, phone and work PC must all agree on what each file looks like, even when two of them edit at once.
Real-world analogy

Imagine a bank safe-deposit service with branches in every city. You hand a clerk a large binder. Instead of storing it as one heavy item, the clerk removes the pages, photocopies them into a secure vault in two cities, and writes a card in a catalogue saying "binder X = pages 1 to 40, version 3." When you replace page 7, they only swap page 7 and update the catalogue card. A messenger then calls your other branches: "binder X changed, come pick up the new page." The vault is cloud storage, the pages are blocks, the catalogue is the metadata database, and the messenger is the notification service.

Step 2: Start with a single server

Instead of showing the final design right away, the book starts simple: everything on one server, then grows it. This is a great interview technique, because each step is motivated by a problem with the previous one.

The single-server setup:

  • A web server to upload and download files (Apache).
  • A database to keep track of metadata like user data, login info, file info, etc. (MySQL).
  • A storage directory to store files. 1 TB of storage space is allocated.

Under the drive/ directory there is a list of directories called namespaces. Each namespace contains all the uploaded files for one user. The filename on the server is kept the same as the original. Each file can be uniquely identified by joining the namespace and the relative path.

Storage layout on the single server
Each user gets a namespace folder under drive/. A file's unique identity is namespace + relative path, for example user1/recipes.txt.

Security for every API

All the APIs require user authentication and use HTTPS. Secure Sockets Layer (SSL) protects data transfer between the client and backend servers.

Moving away from a single server

As more files are uploaded, eventually you get the space-full alert: only 10 MB of storage space is left! Users can't upload files anymore. What now?

Idea 1: shard the data

The first solution that comes to mind is to shard the data so it is stored on multiple storage servers, for example by user_id.

Sharding storage by user_id
Each user's files live on one storage server chosen from their user_id. This spreads storage but doesn't solve durability.

This works for now, but you are still worried about potential data loss if a storage server goes down or catches fire. You talk to colleagues, and they point out that Netflix and Airbnb use Amazon S3 for storage.

Idea 2: use Amazon S3

Amazon Simple Storage Service (S3) is an object storage service that offers industry-leading scalability, data availability, security, and performance. S3 supports same-region and cross-region replication. A region is a geographic area where Amazon Web Services (AWS) have data centers. Data can be replicated within one region or across regions. Redundant files stored in multiple regions guard against data loss and ensure availability.

S3 replication: same-region vs cross-region
Same-region replication copies data within one geographic region; cross-region replication copies it to another region, which survives even a regional disaster.

An S3 bucket is like a folder in a file system. After putting files in S3, you can sleep well without worrying about data loss.

Sync conflicts

For a large storage system like Google Drive, sync conflicts happen from time to time. When two users modify the same file or folder at the same time, a conflict happens. How do we resolve it?

The book's strategy: the first version that gets processed wins, and the version that gets processed later receives a conflict.

Sync conflict: user 1 wins, user 2 gets a conflict
Both users edit the same file at the same moment. User 1's change is processed first, so it syncs successfully. User 2's change arrives later and is flagged as a conflict.

How does user 2 resolve the conflict? The system presents both copies of the same file: user 2's local copy and the latest version from the server. User 2 has the option to merge both files or override one version with the other.

File on user 2's deviceMeaning
SystemDesignInterviewThe latest version from the server (user 1's edit).
SystemDesignInterview_user 2_conflicted_copy_2019-05-01User 2's local edit, kept so nothing is lost.
Why not just pick one silently?

Because "data loss is unacceptable." Silently overwriting would throw away someone's work. Keeping both copies and letting the human decide is safe and simple.

High-level design

Now we put the pieces together into the book's high-level design:

High-level design
File contents flow through block servers to cloud storage (and later to cold storage). Metadata and everything else flows through the load balancer to API servers, which use the metadata cache and DB. The notification service tells clients when files change, and an offline backup queue holds changes for clients that are offline.

Each component, explained

User
Uses the application through a browser or mobile app.
Block servers
Upload blocks to cloud storage. Block storage, also referred to as block-level storage, is a technology to store data files in cloud-based environments. A file can be split into several blocks, each with a unique hash value, stored in our metadata database. Each block is treated as an independent object and stored in our storage system (S3). To reconstruct a file, blocks are joined in a particular order. As for block size, the book uses Dropbox as a reference: it sets the maximal size of a block to 4 MB. Block servers also compress and encrypt each block.
Cloud storage
A file is split into smaller blocks, and the blocks are stored in cloud storage.
Cold storage
A computer system designed for storing inactive data, meaning files that are not accessed for a long time.
Load balancer
Evenly distributes requests among API servers.
API servers
Responsible for almost everything other than the uploading flow: user authentication, managing user profile, updating file metadata, etc.
Metadata database
Stores metadata of users, files, blocks, versions, etc. Note: files are stored in the cloud; the metadata database only contains metadata.
Metadata cache
Some of the metadata is cached for fast retrieval.
Notification service
A publisher/subscriber system that transfers data from the notification service to clients as certain events happen. Here, it notifies relevant clients when a file is added/edited/removed elsewhere so they can pull the latest changes.
Offline backup queue
If a client is offline and cannot pull the latest file changes, the offline backup queue stores the info so changes will be synced when the client is online.
The core split

Notice the two separate paths: file content (heavy bytes) goes through block servers to cloud storage; metadata (small facts) goes through API servers to the database. Keeping them apart lets each be scaled and optimized on its own.

Step 3 deep dive: block servers

For large files that are updated regularly, sending the whole file on each update consumes a lot of bandwidth. Two optimizations minimize the amount of network traffic:

Delta sync

When a file is modified, only modified blocks are synced instead of the whole file, using a sync algorithm.

Compression

Applying compression on blocks can significantly reduce the data size. Blocks are compressed using algorithms that depend on file type: for example, gzip and bzip2 are used to compress text files. Different compression algorithms are needed to compress images and videos.

Block servers do the heavy lifting for uploads. Here is how a new file is processed:

Block server upload flow
A file is split into smaller blocks; each block is compressed, then encrypted before being sent to cloud storage.
  1. Split A file is split into smaller blocks (max 4 MB each).
  2. Compress Each block is compressed using compression algorithms.
  3. Encrypt To ensure security, each block is encrypted before it is sent to cloud storage.
  4. Upload Blocks are uploaded to the cloud storage.

Delta sync in action: suppose a file has 10 blocks and you edit two paragraphs that land in block 2 and block 5. Only those two blocks are uploaded.

Delta sync: only changed blocks are uploaded
The highlighted blocks are the modified ones. Uploading 2 blocks instead of 10 cuts bandwidth by roughly 80% for this edit.
How does the system know which blocks changed?

Each block has a hash. The client (or block server) computes hashes for the new version and compares them with the hashes stored in the metadata DB for the old version. Blocks whose hashes differ are the modified ones.

Block servers allow us to save network traffic by providing delta sync and compression.

High consistency requirement

Our system requires strong consistency by default. It is unacceptable for a file to be shown differently by different clients at the same time. Imagine your phone shows version 3 of a contract and your laptop shows version 2: you might sign the wrong one.

The system needs to provide strong consistency for the metadata cache and database layers.

Memory caches adopt an eventual consistency model by default, meaning different replicas might have different data. To achieve strong consistency, we must ensure:

  • Data in cache replicas and the master is consistent.
  • Invalidate caches on database write, to ensure cache and database hold the same value.
Invalidate the cache on write
API serverfile v2 saved
→1. write
Metadata DBnow v2
→2. invalidate
Metadata cacheold v1 removed
After the database is updated, the old cache entry is removed. The next read misses the cache, loads v2 from the DB and caches it. Nobody keeps reading v1.

Achieving strong consistency in a relational database is easy because it maintains the ACID (Atomicity, Consistency, Isolation, Durability) properties. However, NoSQL databases do not support ACID properties by default; ACID must be programmatically incorporated in synchronization logic. In our design, we choose relational databases because ACID is natively supported.

Metadata database

The book shows a simplified database schema containing only the most important tables:

Metadata database schema
Simplified schema. Relationships: one user has many devices and namespaces; a namespace contains many files; a file has many file versions; a file version is made of many blocks in a specific order.
User
Contains basic information about the user such as username, email, profile photo, etc.
Device
Stores device info. push_id is used for sending and receiving mobile push notifications. Note a user can have multiple devices.
Namespace
A namespace is the root directory of a user.
File
Stores everything related to the latest file.
File_version
Stores version history of a file. Existing rows are read-only to keep the integrity of the file revision history.
Block
Stores everything related to a file block. A file of any version can be reconstructed by joining all the blocks in the correct order.
Why read-only versions?

If old file_version rows could be edited, the "see revisions" feature couldn't be trusted. A new edit always creates a new version row; the old ones stay exactly as they were.

Upload flow

Let's discuss what happens when a client uploads a file. Two requests are sent in parallel: add file metadata, and upload the file to cloud storage. Both requests originate from client 1. Client 2 is another device of the same user (or a collaborator) that needs to learn about the change.

Upload flow (sequence diagram)
Request A records the file's existence with status "pending" and tells other clients. Request B uploads the bytes through block servers; when cloud storage finishes, a callback flips the status to "uploaded" and other clients are notified again.

Request A: add file metadata

  1. Client 1 sends a request to add the metadata of the new file.
  2. Store Store the new file metadata in the metadata DB and change the file upload status to "pending."
  3. Notify Notify the notification service that a new file is being added.
  4. Fan out The notification service notifies relevant clients (client 2) that a file is being uploaded.

Request B: upload file content

  1. Upload Client 1 uploads the content of the file to block servers.
  2. Process Block servers chunk the files into blocks, compress, encrypt the blocks, and upload them to cloud storage.
  3. Callback Once the file is uploaded, cloud storage triggers an upload completion callback. The request is sent to API servers.
  4. Update status File status changes to "uploaded" in the metadata DB.
  5. Notify Notify the notification service that a file status is changed to "uploaded."
  6. Fan out The notification service notifies relevant clients (client 2) that a file is fully uploaded.

When a file is edited, the flow is similar, so the book doesn't repeat it.

Download flow

The download flow is triggered when a file is added or edited elsewhere. How does a client know a file was changed by another client? There are two ways:

  • If client A is online while a file is changed by another client, the notification service informs client A that changes are made somewhere so it needs to pull the latest data.
  • If client A is offline while a file is changed by another client, the data is saved to the cache (the offline backup queue). When the offline client is online again, it pulls the latest changes.

Once a client knows a file is changed, it first requests metadata via API servers, then downloads blocks to construct the file.

Download flow (sequence diagram)
The client learns of a change, asks API servers for the new metadata (which blocks, in which order), downloads those blocks via block servers from cloud storage, and reconstructs the file locally.
  1. Notified The notification service informs client 2 that a file is changed somewhere else.
  2. Ask for metadata Once client 2 knows that new updates are available, it sends a request to fetch metadata.
  3. Fetch API servers call the metadata DB to fetch metadata of the changes.
  4. Return to API Metadata is returned to the API servers.
  5. Return to client Client 2 gets the metadata.
  6. Request blocks Once the client receives the metadata, it sends requests to block servers to download blocks.
  7. Block servers fetch Block servers download blocks from cloud storage.
  8. Cloud returns Cloud storage returns blocks to the block servers.
  9. Client receives Client 2 downloads all the new blocks.
  10. Reconstruct Client 2 reconstructs the file from the blocks in the right order.

Notification service

To maintain file consistency, any mutation of a file performed locally needs to be told to other clients to reduce conflicts. The notification service serves this purpose. At the high level, it allows data to be transferred to clients as events happen. A few options:

Long polling

Dropbox uses long polling. The client asks "any changes?" and the server holds the request open until there is a change (or a timeout). Then the client asks again.

WebSocket

WebSocket provides a persistent connection between the client and the server. Communication is bi-directional.

Long polling vs WebSocket
Long polling is a series of held-open requests, good for occasional one-way news. WebSocket is a permanent two-way pipe, good for chatty real-time apps.

Even though both options work well, the book opts for long polling for two reasons:

  1. Not bi-directional Communication for the notification service is not bi-directional. The server sends information about file changes to the client, but not vice versa.
  2. Infrequent WebSocket is suited for real-time bi-directional communication such as a chat app. For Google Drive, notifications are sent infrequently with no burst of data.

With long polling, each client establishes a long poll connection to the notification service. If changes to a file are detected, the client closes the long poll connection. Closing the connection means the client must connect to the metadata server to download the latest changes. After a response is received or the connection timeout is reached, the client immediately sends a new request to keep the connection open.

Save storage space

To support file version history and ensure reliability, multiple versions of the same file are stored across multiple data centers. Storage space can fill up quickly with frequent backups of all file revisions. Three techniques reduce storage costs:

1. De-duplicate data blocks

Eliminating redundant blocks at the account level is an easy way to save space. Two blocks are identical if they have the same hash value.

De-duplication by hash
Before storing a block, check whether a block with the same hash already exists for this account. If it does, just point to it instead of storing a second copy.

2. Adopt an intelligent data backup strategy

  • Set a limit: We can set a limit for the number of versions to store. If the limit is reached, the oldest version is replaced with the new version.
  • Keep valuable versions only: Some files might be edited frequently. For example, saving every edited version of a heavily modified document could mean the file is saved over 1,000 times within a short period. To avoid unnecessary copies, we could limit the number of saved versions, giving more weight to recent versions. Experimentation helps to figure out the optimal number of versions to save.

3. Moving infrequently used data to cold storage

Cold data is data that has not been active for months or years. Cold storage like Amazon S3 Glacier is much cheaper than S3.

Hot vs cold storage tiers
Cloud storage (S3)active files, fast, pricier
→not accessed for months
Cold storage (S3 Glacier)inactive files, slow, much cheaper
Most stored files are rarely opened again. Moving them to cold storage cuts cost while keeping them safe.

Failure handling

Failures can occur in a large-scale system, and we must adopt design strategies to address them. The book goes through every component:

Component failsHow the system recovers
Load balancerIf a load balancer fails, the secondary becomes active and picks up the traffic. Load balancers usually monitor each other using a heartbeat, a periodic signal sent between load balancers. A load balancer is considered failed if it has not sent a heartbeat for some time.
Block serverIf a block server fails, other servers pick up unfinished or pending jobs.
Cloud storageS3 buckets are replicated multiple times in different regions. If files are not available in one region, they can be fetched from different regions.
API serverIt is a stateless service. If an API server fails, the traffic is redirected to other API servers by a load balancer.
Metadata cacheMetadata cache servers are replicated multiple times. If one node goes down, you can still access other nodes to fetch data. Bring up a new cache server to replace the failed one.
Metadata DBMaster down: promote one of the slaves to act as a new master and bring up a new slave node. Slave down: use another slave for read operations and bring another database server to replace the failed one.
Notification serviceEvery online user keeps a long poll connection with the notification server, so each notification server is connected with many users. According to the Dropbox talk cited in the book, over 1 million connections are open per machine. If a server goes down, all the long poll connections are lost, so clients must reconnect to a different server. Even though one server can keep many open connections, it cannot reconnect all the lost connections at once. Reconnecting with all the lost clients is a relatively slow process.
Offline backup queueQueues are replicated multiple times. If one queue fails, consumers of the queue may need to re-subscribe to the backup queue.
Load balancer failover via heartbeat
The two load balancers check on each other. When the primary goes silent, the secondary takes over.

Step 4: Wrap up

The design combines two flows: managing file metadata and file sync. The notification service is the third important component: it uses long polling to keep clients up to date with file changes. Like any system design question, there is no perfect solution. The book offers two alternatives to discuss:

Alternative 1: upload files directly to cloud storage from the client

Instead of going through block servers, the client could upload straight to cloud storage.

Pros

  • Faster file upload, because a file only needs to be transferred once to cloud storage (not client → block server → cloud).

Cons

  • The same chunking, compression, and encryption logic must be implemented on different platforms (iOS, Android, Web). It is error-prone and requires a lot of engineering effort. In our design, all that logic lives in a centralized place: block servers.
  • A client can easily be hacked or manipulated, so implementing encryption logic on the client side is not ideal.

Alternative 2: move online/offline logic into a separate service

Another interesting evolution is moving presence logic (whether a user is online or offline) out of the notification servers into a separate presence service. By doing so, presence service can be easily integrated by other services.

Walkthrough: editing a file on the laptop, seeing it on the phone

  1. Edit Maya edits a 40 MB presentation on her laptop (client 1). The file is 10 blocks of up to 4 MB; her change touches blocks 2 and 5.
  2. Metadata first Client 1 tells the API servers (via the load balancer) about the new version. The API server writes a new file_version row with status "pending", invalidates the cached entry, and tells the notification service. Her phone (client 2), holding a long poll connection, hears "file is being updated."
  3. Content in parallel Client 1 sends the content to block servers, which detect via hashes that only blocks 2 and 5 changed, compress and encrypt those two blocks, and store them in S3 (replicated to another region). Unchanged blocks are de-duplicated: the new version simply references the existing ones.
  4. Done S3's completion callback reaches the API servers, which set status "uploaded" and notify the notification service again.
  5. Download on phone The phone's long poll returns; it asks the API servers for the latest metadata (the ordered list of block hashes), downloads only blocks 2 and 5 through block servers, and rebuilds the file.
  6. Offline tablet Maya's tablet is off. The change waits in the offline backup queue; when the tablet comes online, it pulls the changes.
  7. Conflict case If her colleague edited the same file at the same moment and was processed second, the colleague would get a conflict and see both copies to merge or override.

"The first version processed wins. The later one gets a conflict. We show that user both their local copy and the server's latest version, and they choose to merge or override. Nothing is silently discarded."

Deep dive
10–25 min
  • Block servers: 4 MB blocks with hashes, delta sync, compression, encryption.
  • Strong consistency: relational DB (ACID), cache invalidation on write.
  • Schema: user, device (push_id), namespace, file, file_version (read-only), block.
  • Upload flow (two parallel requests, pending then uploaded) and download flow.
  • Notification: long polling over WebSocket. Storage savings. Failure handling.
"Block servers split files into blocks of up to 4 MB like Dropbox, each identified by a hash. On edit, we compare hashes and upload only changed blocks, which is delta sync. Each block is compressed and encrypted before going to cloud storage."
"Why a relational database instead of NoSQL?"
"We need strong consistency: two devices must never show different versions of a file. Relational databases support ACID natively, while with most NoSQL stores we'd have to build those guarantees into our sync logic ourselves."
"Why long polling and not WebSocket?"
"Notification traffic is one-way, server to client, and infrequent, with no bursts. WebSocket shines for real-time two-way traffic like chat. Long polling is simpler and enough here, and it's what Dropbox uses."
"Storage costs are exploding. Ideas?"
"Three: de-duplicate blocks with the same hash at the account level; limit the number of stored versions and keep only valuable ones, weighted to recent edits; and move data untouched for months to cold storage like S3 Glacier, which is much cheaper."
"A notification server dies. What's the impact?"
"All its long poll connections drop, potentially over a million. Clients reconnect to other servers, but a server can't re-accept all of them at once, so recovery is relatively slow. Meanwhile clients can still sync once reconnected, and missed changes are not lost."

Wrap up
3–5 min
  • Summarize: metadata flow, file sync flow, notification service.
  • Alternatives: direct-to-cloud uploads (faster but logic duplicated per platform; client-side encryption risky) and a separate presence service.
"Why not let clients upload straight to S3?"
"It's faster since the file is transferred once. But chunking, compression and encryption would need to be built for iOS, Android and web separately, which is error-prone, and clients can be hacked, so putting encryption on the client is risky. Block servers keep that logic in one trusted place."

Common mistakes

Uploading the whole file on every change

Without blocks and delta sync, a one-line edit to a 1 GB file re-sends 1 GB. Split into blocks and sync only the changed ones.

Choosing eventual consistency for metadata

Different devices showing different versions of the same file breaks trust. Use strong consistency: relational DB with ACID, invalidate cache on write.

Storing files in one region or one server

"Data loss is unacceptable." Replicate files across regions (S3 cross-region replication).

Silently overwriting on conflicts

Last-writer-wins without telling anyone loses work. The book's approach: first processed wins, the later one gets a conflict and sees both copies.

Defaulting to WebSocket for notifications

WebSocket isn't wrong, but you should justify the choice. Here traffic is one-way and infrequent, so long polling fits.

Forgetting offline devices

If a device is off when a change happens, the change must be kept (offline backup queue) and synced when it reconnects.

Mixing up metadata and file content

The metadata DB stores only metadata. File bytes live in cloud storage. Keep the two paths separate.

Test yourself

How is the 500 PB total storage figure calculated?

50 million signed-up users × 10 GB free space each = 500 PB. It uses all signed-up users (not just DAU) because every account is allocated space.

What is the upload QPS and peak QPS, and how do you get them?

10 million DAU × 2 uploads / 24 hours / 3600 seconds ≈ 240 QPS. Peak is assumed 2×, so 480 QPS.

What are the three steps of a resumable upload?

1) Send the initial request to get the resumable URL. 2) Upload the data and monitor the upload state. 3) If the upload is disturbed, resume it.

What do block servers do with a file, and what is the max block size the book uses?

They split the file into blocks (max 4 MB, following Dropbox), give each block a hash, compress and encrypt each block, and upload them to cloud storage.

Scenario: a user changes one slide in a 40 MB file split into 10 blocks. How much data is uploaded?

Only the block(s) containing that slide, thanks to delta sync. Hashes are compared to find changed blocks, so maybe 1 block (up to 4 MB, before compression) instead of 40 MB.

Why does the design use a relational database for metadata?

The system needs strong consistency. Relational databases natively support ACID properties; NoSQL databases don't by default, so ACID would need to be built into the sync logic.

Why are rows in the file_version table read-only?

To keep the integrity of the file revision history. A new edit creates a new row; old versions never change, so "see revisions" is trustworthy.

In the upload flow, when does the file status change from "pending" to "uploaded"?

Request A sets status "pending" when metadata is added. After block servers upload all blocks to cloud storage, cloud storage triggers a completion callback to API servers, which change the status to "uploaded" and notify other clients.

Scenario: a user's tablet is offline when a file changes. How does it eventually get the update?

The change is stored in the offline backup queue. When the tablet comes back online, it pulls the latest changes: fetch metadata from API servers, then download the needed blocks and rebuild the file.

Why is losing a notification server painful even though clients just reconnect?

Each server can hold over 1 million long poll connections. When it dies, all of them drop at once, and other servers can't re-accept all those connections at the same time. Reconnecting all lost clients is relatively slow.

Cheat sheet

  • Scope: upload/download, sync, notifications, revisions, sharing; mobile + web; any file type; encrypted; max 10 GB; 10M DAU. No collaborative editing.
  • Estimates: 500 PB (50M × 10 GB); ~240 upload QPS; 480 peak.
  • Evolution: single server (Apache, MySQL, drive/ namespaces) → shard by user_id → S3 with cross-region replication → LB + web servers + separate metadata DB.
  • APIs: upload (simple or resumable: get URL, upload, resume), download (path), list_revisions (path, limit). All authenticated over HTTPS.
  • Conflicts: first processed wins; later one sees both copies and merges or overrides.
  • Block servers: 4 MB blocks with hashes; delta sync; compression (gzip/bzip2 for text); encryption; then cloud storage.
  • Strong consistency: relational DB (ACID), invalidate cache on write.
  • Schema: user, device (push_id), namespace, file, file_version (read-only), block.
  • Upload: two parallel requests: metadata (pending, notify) + content (blocks, callback, uploaded, notify). Download: notify, get metadata, get blocks, rebuild.
  • Notifications: long polling (one-way, infrequent), offline backup queue for offline clients.
  • Save space: de-dupe blocks by hash, limit and choose versions, move cold data to S3 Glacier.
  • Failures: secondary LB via heartbeat; block/API servers replaceable; S3 multi-region; cache + DB replicas; notification reconnects are slow (1M+ connections/server); replicated queues.
