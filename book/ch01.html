Chapter 1

Scale From Zero to Millions of Users

Every large website started as one small computer. This chapter walks you through how a system grows, one problem at a time, from a single server serving a handful of users to a multi-data-center setup serving millions. Each step adds exactly one new building block and explains which pain it removes.

~35 min readBeginnerPrerequisites: none (knowing what a website and a database are helps)

The big picture

Designing a system that supports millions of users is hard, and nobody gets it right in one go. It is a journey of continuous refinement. You build something simple, wait for it to break (or predict where it will break), and then add the one piece that fixes that weakness.

This chapter is the foundation of the whole book. Almost every later chapter (rate limiter, chat system, news feed, YouTube...) reuses the building blocks introduced here: load balancers, replicated databases, caches, CDNs, stateless servers, message queues, multiple data centers and sharding. If you understand why each one exists, you can design almost anything.

Real-world analogy

Think of a small restaurant that grows into a chain. On day one, a single cook takes orders, cooks, washes dishes and keeps the recipe book (one server doing everything). When customers multiply, the owner hires more cooks and a host at the door who sends each customer to a free table (load balancer). The recipe book gets photocopied so many cooks can read it at once, but only the head chef may change the original (database replication). Popular dishes are pre-prepared and kept warm (cache). A frozen-dessert supplier opens kiosks across town so people do not have to travel to the main kitchen (CDN). Eventually the chain opens a second kitchen in another city (multiple data centers), and finally splits its giant customer ledger into several smaller ledgers by customer surname (sharding).

The method

Start with the simplest thing that works. Find the bottleneck or single point of failure. Add one component to fix it. Repeat.

The goal

Handle more traffic (scalability), survive failures (availability and reliability), and stay fast (low latency).

Why it matters for interviews

Interviewers expect you to know these components by heart and to justify each one with the problem it solves, not just name it.

Key terms

Server
A computer that waits for requests over the network and sends back responses. A web server runs your application code.
Client
The thing that sends requests: a web browser or a mobile app.
DNS (Domain Name System)
The internet's phone book. Turns a name like api.mysite.com into an IP address like 15.125.23.214. Usually a paid service run by a third party, not something you host yourself.
IP address
A numeric address that identifies a machine on a network. A public IP is reachable from the internet; a private IP is reachable only by machines inside the same network.
HTTP
HyperText Transfer Protocol: the language browsers and servers use to ask for and send web pages and data.
HTML / JSON
HTML is the format of web pages that browsers display. JSON (JavaScript Object Notation) is a simple text format for data, commonly used by APIs that mobile apps call.
API
Application Programming Interface: a set of URLs (endpoints) that programs call to read or change data, e.g. GET /users/12.
Relational database (RDBMS / SQL)
Stores data in tables with rows and columns, supports joins across tables. Examples: MySQL, Oracle, PostgreSQL.
NoSQL database
A non-relational database. Four families: key-value stores, graph stores, column stores, document stores. Examples: CouchDB, Neo4j, Cassandra, HBase, Amazon DynamoDB. Joins are generally not supported.
Vertical scaling (scale up)
Making one machine more powerful: more CPU, RAM, disk.
Horizontal scaling (scale out)
Adding more machines to share the work.
Load balancer (LB)
A component that sits in front of a group of servers and spreads incoming traffic evenly among them.
Failover
Automatically switching to a backup component when the main one fails.
Single point of failure (SPOF)
Any part of the system whose failure stops the whole system from working.
Replication
Keeping copies of the same data on multiple database servers.
Master / slave (primary / replica)
In replication, the master accepts writes; slaves receive copies of the data from the master and serve reads only.
Latency
How long a single request takes, end to end.
Cache
A temporary, fast storage (usually in memory) that keeps results of expensive work or frequently used data so you can serve them quickly next time.
Cache hit / miss
A hit means the data was found in the cache. A miss means it was not, so you must go to the database.
TTL (Time-To-Live)
How long a cached item is allowed to live before it is considered stale and removed or refreshed.
Eviction
Removing items from a full cache to make room for new ones. Policies: LRU, LFU, FIFO.
CDN (Content Delivery Network)
A network of servers spread around the world that store copies of static files (images, videos, CSS, JavaScript) close to users.
Static vs dynamic content
Static content is the same for everyone (a logo image). Dynamic content is generated per request (your personal news feed).
Origin server
The "real" source of a file that a CDN copies from, such as your web server or Amazon S3.
State / session data
Information a server remembers about a user between requests, e.g. "this user is logged in" or a profile picture choice.
Stateful vs stateless server
A stateful server keeps user state in its own memory. A stateless server keeps none; state lives in a shared data store.
Sticky sessions
A load balancer feature that always sends a given user to the same server. Needed for stateful servers; adds overhead.
Data center (DC)
A building full of servers. Big companies run several in different regions.
geoDNS
A DNS service that returns different IP addresses depending on where the user is located, so users are routed to the nearest data center.
Message queue
A durable, in-memory buffer that stores messages so one component (producer) can hand off work to another (consumer) asynchronously.
Asynchronous
"Do it later, do not wait." The sender continues without waiting for the work to finish.
Metrics
Numbers collected over time about the system: CPU usage, requests per second, daily active users, revenue.
CI (Continuous Integration)
Automatically building and testing every code change so problems are caught early.
Sharding
Splitting a large database into smaller pieces (shards) that live on different servers. Each shard has the same schema but different rows.
Sharding key (partition key)
The column(s) used to decide which shard a row belongs to, e.g. user_id.
Resharding
Moving data around when you change the number of shards or the way data is split.
Hotspot / celebrity problem
One shard getting far more traffic than the others, e.g. because it holds a very popular user.
Denormalization
Deliberately storing duplicate data so a query can be answered from one table without joins.
QPS
Queries (requests) per second.

Stage 1: Single server setup

A journey of a thousand miles begins with a single step. At the very start, everything runs on one server: the web application, the database, and the cache. This is perfectly fine for a hobby project or a brand-new product with a few users.

Users reach the single server by its domain name. The server runs the app, the database and the cache all together.

How a request flows, step by step

  1. User types a domain name. They access the website through a domain name such as api.mysite.com. DNS is normally a paid service provided by a third party, not hosted on our servers.
  2. DNS returns an IP address. The browser or app asks DNS, "where is api.mysite.com?" and gets back an IP address, for example 15.125.23.214.
  3. An HTTP request is sent to that IP. Now that the client knows the address, it sends an HTTP request directly to the web server.
  4. The server responds. The web server returns HTML pages (for browsers) or JSON (for mobile apps) for rendering.
Request flow (sequence)
Two round trips: first to DNS for the address, then to the web server for the content.

Where does the traffic come from?

The web server gets traffic from two sources:

Web application

Uses a combination of server-side languages (Java, Python, etc.) to handle business logic and storage, and client-side languages (HTML and JavaScript) for presentation in the browser.

Mobile application

Talks to the server using HTTP. The response format is usually JSON because it is simple and lightweight.

Pros of a single server

  • Very simple to build, deploy and debug.
  • Cheap.
  • No network calls between components, so it is fast at low traffic.

Cons

  • If the server dies, the whole site is down (single point of failure).
  • The app and database compete for the same CPU and memory.
  • There is a hard ceiling on how much one machine can handle.

Stage 2: Separate the database

As the user base grows, one server is not enough. The first split is to move the database onto its own server. Now we have two tiers: a web tier (handles web and mobile traffic) and a data tier (the database). Separating them allows each to be scaled independently: you can give the database a machine with lots of disk and RAM, and the web server a machine with more CPU.

Which database to use?

You choose between a traditional relational database and a non-relational (NoSQL) database.

Relational (SQL)Non-relational (NoSQL)
ExamplesMySQL, Oracle, PostgreSQLCouchDB, Neo4j, Cassandra, HBase, Amazon DynamoDB

The book's advice: relational databases are the best choice for most developers because they have been around for over 40 years and historically they have worked well. If they do not fit your use case, explore beyond them. A non-relational database might be the right choice if:

  • Your application requires super-low latency.
  • Your data is unstructured, or you do not have any relational data.
  • You only need to serialize and deserialize data (JSON, XML, YAML, etc.), i.e. store and fetch blobs.
  • You need to store a massive amount of data.
Beginner tip

"Serialize" means turning an in-memory object into text or bytes so it can be stored or sent. If all your app ever does is "save this user's settings blob" and "load it back by user id", a key-value NoSQL store is a natural fit.

Vertical vs horizontal scaling

When traffic grows, you have two ways to get more capacity.

Scale up vs scale out
Vertical scaling makes one machine bigger. Horizontal scaling adds more machines.

Vertical scaling: good when

  • Traffic is low. Its main advantage is simplicity: no code changes, no new components.

Vertical scaling: serious limits

  • Hard limit: you cannot add unlimited CPU and memory to one server.
  • No failover or redundancy: if that one server goes down, the website goes down with it.

Because of these limits, horizontal scaling is more desirable for large-scale applications. But with several servers, how do users know which one to talk to? And with our current design, users connect directly to the web server: if it is offline, users cannot reach the site; if too many users arrive at once, responses get slow or fail. The answer is a load balancer.

Real-world analogy

Vertical scaling is buying a faster delivery truck. Horizontal scaling is buying more trucks. Eventually no faster truck exists, and if your one truck breaks, nothing gets delivered. A fleet keeps going even if one truck is in the shop.

Stage 3: Load balancer

A load balancer evenly distributes incoming traffic among the web servers that are defined in a load-balanced set.

Adding a load balancer

↓DNS returns the LB's public IP: 88.88.88.1
Load balancerpublic IP 88.88.88.1
↓private IPs (internal network only)
Server 1192.168.0.2

Users connect only to the load balancer's public IP. The web servers have private IPs and cannot be reached directly from the internet.

How it works

  1. Users connect to the LB's public IP. DNS now returns the load balancer's address, not a web server's. The web servers are unreachable directly by clients anymore.
  2. The LB talks to servers via private IPs. A private IP is reachable only between servers in the same network; it is not reachable over the internet. This improves security.
  3. Traffic is spread evenly. Each request goes to one of the servers in the pool.

What problems it fixes

Failover

If server 1 goes offline, all traffic is routed to server 2. The website stays up. We can then add a new healthy server to the pool.

Handling growth

If traffic grows rapidly and two servers are not enough, just add more servers to the pool. The LB automatically starts sending requests to them.

Security

Only the LB is exposed to the internet. Web servers hide behind private IPs.

Failover: server 1 goes down
The load balancer notices server 1 is unhealthy and sends everything to server 2.

The web tier now looks good. But there is still only one database, which does not support failover or redundancy. Database replication solves that.

Stage 4: Database replication

Quoted from Wikipedia in the book: "Database replication can be used in many database management systems, usually with a master/slave relationship between the original (master) and the copies (slaves)."

  • The master database generally only supports write operations. All data-modifying commands (insert, delete, update) go to the master.
  • A slave database gets copies of the data from the master and only supports read operations.
  • Most applications need a much higher ratio of reads to writes, so there are usually more slaves than masters.
Master / slave replication
Writes go to the master. The master copies changes to the slaves. Reads are spread across the slaves.

Advantages

Better performance

All writes and updates happen on the master; reads are distributed across slaves. More queries can be processed in parallel.

Reliability

If one database server is destroyed by a natural disaster (typhoon, earthquake), data is still preserved. Data is replicated across multiple locations, so you do not lose it.

High availability

Because data lives on several machines, the website keeps working even if one database goes offline: you access data from another server.

What if a database goes offline?

ScenarioWhat happens
Only one slave exists and it goes offlineRead operations are temporarily directed to the master. As soon as the problem is found, a new slave replaces the old one.
Multiple slaves, one goes offlineReads are redirected to the other healthy slaves. A new database server replaces the old one.
The master goes offlineA slave is promoted to be the new master. All database operations are temporarily executed on that new master. A new slave replaces the old one for data replication immediately.
The catch with promoting a slave

In production, promoting a new master is more complicated: the data in a slave might not be up to date (replication takes time). Missing data must be recovered by running data recovery scripts. Other approaches like multi-masters and circular replication could help, but they are more complicated and beyond the scope of the book.

Now that the web and data tiers are solid, it is time to improve load and response time. We do that with a cache and a CDN.

Stage 5: Cache

A cache is a temporary storage area that stores the result of expensive responses or frequently accessed data in memory so that subsequent requests are served more quickly. Every time a new web page loads, one or more database calls are executed. Calling the database repeatedly hurts performance. A cache fixes this.

The cache tier

The cache tier is a temporary data store layer, much faster than the database. Benefits of having a separate cache tier:

  • Better system performance.
  • Reduced database workload.
  • The cache tier can be scaled independently.
Read-through cache
The web server first checks the cache. On a hit it returns data straight away. On a miss it queries the database, stores the result in the cache, and returns it to the client.

This caching strategy is called a read-through cache. Other strategies exist depending on data type, size and access patterns. Interacting with cache servers is simple because most provide APIs for common languages. A typical Memcached example:

SECONDS = 1
cache.set('myKey', 'hi there', 3600 * SECONDS)   # store for 1 hour (TTL = 3600 s)
cache.get('myKey')                               # returns 'hi there' until it expires

Considerations for using a cache

Decide when to use it

Use a cache when data is read frequently but modified infrequently. Cached data lives in volatile memory, so a cache server is not ideal for persisting data. If a cache server restarts, all data in memory is lost. Important data should be saved in persistent data stores.

Expiration policy

Once cached data expires, it is removed. Without a policy, data stays forever. Not too short (the system reloads from the DB too often) and not too long (data becomes stale).

Consistency

Keeping the data store and cache in sync. Inconsistency happens because data-modifying operations on the DB and cache are not in a single transaction. Across multiple regions, this is a big challenge (see Facebook's paper "Scaling Memcache at Facebook").

Mitigating failures

A single cache server is a potential SPOF. Recommendation: multiple cache servers across different data centers. Also overprovision memory by a certain percentage to give a buffer as usage grows.

Eviction policy

When the cache is full, adding items may evict existing ones. LRU (least recently used) is the most popular. Others: LFU (least frequently used) and FIFO (first in, first out).

Key idea

A cache trades freshness for speed. You accept that data might be a little out of date in exchange for not hitting the database every time.

Stage 6: Content delivery network (CDN)

A CDN is a network of geographically dispersed servers used to deliver static content: images, videos, CSS, JavaScript files, etc. (Dynamic content caching, which caches HTML pages based on request path, query strings, cookies and headers, is a newer idea and beyond this chapter.)

At a high level: when a user visits a website, a CDN server closest to the user delivers static content. The further users are from CDN servers, the slower the site loads. For example, if CDN servers are in San Francisco, users in Los Angeles get content faster than users in Europe.

How a CDN works

CDN request flow
The first user triggers a fetch from the origin. Later users get the cached copy from the CDN until the TTL expires.
  1. User A requests image.png using a URL provided by the CDN provider, e.g. https://mysite.cloudfront.net/logo.jpg (Amazon CloudFront) or https://mysite.akamai.com/image-manager/img/logo.jpg (Akamai).
  2. If the CDN does not have it in its cache, the CDN requests the file from the origin, which can be a web server or online storage like Amazon S3.
  3. The origin returns image.png to the CDN, including an optional HTTP header Time-to-Live (TTL) that describes how long the image is cached.
  4. The CDN caches the image and returns it to User A. It stays cached until the TTL expires.
  5. User B sends a request for the same image.
  6. The image is returned from the cache as long as the TTL has not expired.

Considerations of using a CDN

Cost

CDNs are run by third parties and you are charged for data transfers in and out. Caching infrequently used assets gives no significant benefit, so consider moving them out of the CDN.

Appropriate cache expiry

For time-sensitive content, set the expiry carefully. Too long and content may no longer be fresh. Too short and you cause repeated reloading from origin servers.

CDN fallback

Consider how your site copes with CDN failure. During a temporary CDN outage, clients should detect the problem and request resources from the origin.

Invalidating files

Remove a file before it expires by (1) invalidating the CDN object using APIs provided by CDN vendors, or (2) object versioning: serve a different version by adding a parameter to the URL, e.g. image.png?v=2.

Stage 7: Stateless web tier

Now it is time to scale the web tier horizontally. To do that, we need to move state (for instance user session data) out of the web tier. A good practice is to store session data in a persistent storage such as a relational database or NoSQL. Each web server in the cluster can then access state data from the database. This is called a stateless web tier.

Stateful architecture (the problem)

A stateful server remembers client data (state) from one request to the next. In the example below, User A's session data and profile image are stored on Server 1. To authenticate User A, HTTP requests must be routed to Server 1. If a request goes to Server 2, authentication fails because Server 2 does not have User A's session data.

Stateful: each user is tied to one server
Every request from the same client must go to the same server. Routing User A to Server 2 fails authentication.

This can be done with sticky sessions in most load balancers, but this adds overhead. Adding or removing servers is much more difficult with this approach, and handling server failures is a challenge.

Stateless architecture (the fix)

HTTP requests from users can be sent to any web server, which fetches state data from a shared data store. State is kept out of web servers. A stateless system is simpler, more robust, and scalable.

Stateless: any server can handle any user

↓any request can go to any server
Server 1
Server 2
Server 3
↓fetch state
Shared storagesessions (NoSQL / Redis / RDBMS)
Session data lives in a shared store. Web servers hold no user state, so they are interchangeable.

The shared data store could be a relational database, Memcached/Redis, or NoSQL. The book chooses NoSQL because it is easy to scale. Once state is removed, autoscaling becomes possible: web servers are added or removed automatically based on traffic load.

Real-world analogy

A stateful bank teller keeps your file in their desk drawer, so you must always queue at that one teller. A stateless bank keeps every file in a central records room. Any free teller can serve you, and if a teller goes home sick, nobody is stuck.

Technical challenges of multi-data-center setups

Traffic redirection

Effective tools are needed to direct traffic to the correct data center. geoDNS can direct traffic to the nearest DC depending on where a user is located.

Data synchronization

Users from different regions could use different local databases or caches. In failover cases, traffic might be routed to a DC where data is unavailable. A common strategy is to replicate data across multiple data centers. Netflix's study shows how it implements asynchronous multi-data center replication.

Test and deployment

With a multi-DC setup, it is important to test your website/application at different locations. Automated deployment tools are vital to keep services consistent across all data centers.

To further scale, we need to decouple different components of the system so they can be scaled independently. Messaging queues are a key strategy used by many real-world distributed systems for this.

Stage 9: Message queue

A message queue is a durable component, stored in memory, that supports asynchronous communication. It serves as a buffer and distributes asynchronous requests.

The basic architecture is simple. Input services, called producers/publishers, create messages and publish them to a message queue. Other services or servers, called consumers/subscribers, connect to the queue and perform actions defined by the messages.

Producer, queue, consumer
Producerpublishes
→publish
Message queue[msg][msg][msg]
→consume
Consumersubscribes
The producer drops messages in the queue and moves on. The consumer pulls them out and processes them at its own pace.

Why decoupling matters

Decoupling makes the message queue a preferred architecture for building a scalable and reliable application:

  • The producer can post a message when the consumer is unavailable to process it.
  • The consumer can read messages even when the producer is unavailable.
  • Producer and consumer can be scaled independently.

Example: photo processing

Your app supports photo customization: cropping, sharpening, blurring, etc. These tasks take time to complete. Web servers publish photo processing jobs to the message queue. Photo processing workers pick up jobs from the queue and asynchronously perform the customization tasks.

Photo processing with a queue
Producers (web servers) and consumers (photo workers) are scaled independently.

When the queue becomes large, more workers are added to reduce processing time. If the queue is empty most of the time, the number of workers can be reduced.

Real-world analogy

A coffee shop cashier takes your order, writes it on a cup, and puts the cup in a line for the baristas. The cashier does not wait for your drink to be made before taking the next order. If the cup line gets long, the manager adds a barista.

Stage 10: Logging, metrics, automation

For a small website on a few servers, logging, metrics and automation are good practices but not a necessity. Once your site grows to serve a large business, investing in these tools is essential.

Logging

Monitoring error logs is important because it helps identify errors and problems. You can monitor logs per server, or use tools to aggregate them to a centralized service for easy search and viewing.

Metrics

Collecting different types of metrics helps gain business insights and understand the health of the system.

Automation

When a system gets big and complex, build or use automation tools to improve productivity. Continuous integration automatically verifies each code check-in, so teams detect problems early. Automating build, test and deploy improves developer productivity significantly.

As data grows every day, your database gets more overloaded. It is time to scale the data tier.

Stage 11: Database scaling

There are two broad approaches: vertical scaling and horizontal scaling.

Vertical scaling of the database

Also known as scaling up: adding more power (CPU, RAM, DISK, etc.) to an existing machine. There are some powerful database servers. According to Amazon RDS, you can get a database server with 24 TB of RAM. This kind of server can store and handle lots of data. For example, stackoverflow.com in 2013 had over 10 million monthly unique visitors, but it only had 1 master database.

Why it is tempting

  • Simple: no application changes.
  • Huge machines exist.

Serious drawbacks

  • You can add more CPU, RAM, etc., but there are hardware limits. With a large user base, one server is not enough.
  • Greater risk of single point of failure.
  • High overall cost. Powerful servers are much more expensive.

Horizontal scaling: sharding

Horizontal scaling, also known as sharding, is the practice of adding more servers. Sharding separates large databases into smaller, more easily managed parts called shards. Each shard shares the same schema, though the actual data on each shard is unique to the shard.

The book's example: user data is allocated to a database server based on user IDs. Any time you access data, a hash function finds the corresponding shard. Here, user_id % 4 is used as the hash function. If the result equals 0, shard 0 stores and fetches the data; if it equals 1, shard 1, and so on.

Sharding users by user_id % 4
Every shard has the same "users" table schema, but different rows. Example: user_id 10 gives 10 % 4 = 2, so it lives on shard 2.

Choosing the sharding key

The most important factor is the choice of the sharding key (also called a partition key). It consists of one or more columns that determine how data is distributed. In the example, user_id is the sharding key. A sharding key lets you retrieve and modify data efficiently by routing queries to the correct database. When choosing one, a key criterion is to pick a key that can evenly distribute data.

The challenges sharding introduces

Resharding data

Needed when (1) a single shard can no longer hold more data due to rapid growth, or (2) certain shards experience shard exhaustion faster than others due to uneven data distribution. You must update the sharding function and move data around. Consistent hashing (Chapter 5) is a commonly used technique to solve this.

Celebrity (hotspot) problem

Excessive access to a specific shard can overload a server. Imagine data for Katy Perry, Justin Bieber and Lady Gaga all ending up on the same shard. For social applications, that shard will be overwhelmed with reads. A fix: allocate a shard for each celebrity, and each shard might even require further partitioning.

Join and de-normalization

Once a database is sharded across servers, it is hard to perform join operations across shards. A common workaround is to de-normalize the database so queries can be performed in a single table.

Walkthrough: a user uploads a photo

  1. DNS. The mobile app resolves api.mysite.com. geoDNS sees the user is on the US West coast and returns the public IP of the US-West data center's load balancer.
  2. Static assets. The app's images, CSS and JavaScript are already coming from the nearest CDN edge, not from our servers.
  3. Load balancer. The request arrives at the LB, which forwards it over a private IP to any healthy web server.
  4. Stateless web server. The server reads the user's session from the shared NoSQL store to confirm they are logged in. Any server could have done this.
  5. Cache, then database. To show the user's profile, the server checks the cache first. On a miss it computes the shard (user_id % N), reads from a replica of that shard, and populates the cache.
  6. Write. The photo's metadata is written to the master of the user's shard; the master replicates to its slaves (and to the other data center).
  7. Queue. The server publishes a "resize and filter this photo" job to the message queue and immediately replies "upload received" to the user.
  8. Workers. Photo workers pick up the job asynchronously, process the image, and store the results.
  9. Observe. Every step emits logs and metrics; dashboards and alerts watch for errors, and automation adds web servers or workers when load climbs.

The book's summary: how to scale to millions of users

1. Keep the web tier stateless

Store sessions in a shared store so any server can handle any request.

2. Build redundancy at every tier

No single points of failure: multiple servers, replicas, cache nodes.

3. Cache data as much as you can

Serve hot, rarely-changing data from memory.

4. Support multiple data centers

For availability and lower latency worldwide.

5. Host static assets in CDN

Closer to users, less load on your servers.

6. Scale your data tier by sharding

Split data horizontally across servers.

7. Split tiers into individual services

Decouple with message queues so parts scale independently.

8. Monitor and automate

Monitor your system and use automation tools.

How to answer this in an interview

The question usually sounds like "Design a system that can scale to millions of users" or it is hidden inside another problem ("How would you scale this?"). Your job is to show the evolution and justify every component.

1
Clarify scope and scale
3–5 min
  • Ask: web, mobile, or both? Expected users now and in a year? Read-heavy or write-heavy? Global or one region?
  • Write down the answers; they drive every later decision.
"Before I draw anything, I want to confirm a few things. Are we serving both web and mobile clients? Roughly how many daily users should we plan for, and is the traffic mostly reads? Are users global or in one region?"
2
Start simple, then remove single points of failure
5–10 min
  • Draw one server with DNS. Then split web and data tiers.
  • Add a load balancer and multiple web servers. Add master/slave replication.
"I'll start with one server so we agree on the request flow: DNS gives the client an IP, the client sends HTTP, and gets HTML or JSON back. The obvious problem is that one machine is a single point of failure, so I'll separate the database, put a load balancer with a public IP in front of two or more web servers on private IPs, and replicate the database: writes go to the master, reads to slaves."
"What happens if the master database dies?"
"A slave gets promoted to be the new master and we add a new slave. The risk is that the slave may be slightly behind, so some recent writes could be missing and we'd run recovery scripts. If that's unacceptable, multi-master or synchronous replication are options, but they add complexity."
3
Improve latency: cache and CDN
5–8 min
  • Cache for read-heavy, rarely-modified data. Mention TTL, consistency, eviction, and multiple cache nodes.
  • CDN for static assets. Mention TTL, cost, fallback, and versioned URLs.
"Most of our traffic is reads, so I'll add a read-through cache in front of the database with a TTL and LRU eviction, running several cache nodes so it is not a SPOF. Images, CSS and JavaScript go to a CDN so users fetch them from a nearby edge."
"How do you deal with stale data in the cache?"
"I'd pick a TTL that matches how fresh the data must be, and on writes either delete the cache key or update it after writing to the database. The cache and DB writes aren't one transaction, so there can be a short window of inconsistency; for data that must be exact, like account balances, I'd read straight from the database."
4
Scale out: stateless tier, data centers, queues
5–10 min
  • Move sessions to a shared NoSQL store; enable autoscaling.
  • geoDNS plus two data centers with replicated data; failover story.
  • Message queue for slow, asynchronous work.
"To autoscale web servers, they must be stateless, so sessions go to a shared NoSQL store. For global users and disaster tolerance I'd run two data centers behind geoDNS and replicate data asynchronously between them. Slow tasks like photo processing go through a message queue so web servers reply immediately and workers scale on queue length."
"Why not just use sticky sessions?"
"They work, but they add overhead at the load balancer, make adding or removing servers harder, and when a server dies its users lose their sessions. A shared session store avoids all three."
5
Scale the data tier and wrap up
5 min
  • Vertical first if it is enough, then sharding with a well-chosen key.
  • Name the challenges: resharding, hotspots, cross-shard joins.
  • Close with monitoring, logging and automation.
"When one database can't keep up, I'd shard by user_id, since most queries are per user and it spreads data evenly. The trade-offs are resharding as we grow, which consistent hashing helps with, hotspots for celebrity accounts, which may need dedicated shards, and no cross-shard joins, so I'd denormalize hot queries."
"How would you pick a sharding key for an e-commerce orders table?"
"I'd look at the most common query. If it's 'show my orders', sharding by customer_id keeps a customer's orders on one shard and spreads load evenly. I'd avoid something like order date, because all of today's writes would land on one shard and create a hotspot."

Common mistakes

Jumping straight to the final diagram

Drawing sharded multi-region microservices in the first minute tells the interviewer nothing about your reasoning. Show the evolution and tie each component to the problem it solves.

Using the cache as the source of truth

Cache memory is volatile. If the cache server restarts, its data is gone. Important data must live in a persistent database.

Forgetting that new components can be SPOFs

A single load balancer, a single cache node, or a single message queue broker is just a new single point of failure. Mention redundancy for each.

Keeping sessions on web servers and then "autoscaling"

Autoscaling only works cleanly if the web tier is stateless. If sessions live in server memory, removing a server logs users out.

Choosing a sharding key that creates hotspots

Keys like timestamps or country can concentrate traffic on one shard. Pick a key that evenly distributes data and matches the main query pattern.

Ignoring replication lag

Saying "promote a slave" without mentioning that it may be behind the master misses a key trade-off.

Putting everything on a CDN

CDNs charge for data transfer. Rarely accessed assets bring little benefit; keep the CDN for popular static content.

Test yourself

1. Describe what happens, step by step, when a user opens api.mysite.com on a single-server setup.

The client asks DNS (a third-party service) for the IP of the domain, DNS returns an IP such as 15.125.23.214, the client sends an HTTP request to that IP, and the web server returns HTML (browser) or JSON (mobile app). Two lookups: one for the address, one for the content.

2. When would you pick a NoSQL database over a relational one?

When you need super-low latency, the data is unstructured or non-relational, you only need to serialize/deserialize data (JSON, XML, YAML), or you must store a massive amount of data. Otherwise relational is the safe default because of its long track record.

3. Why is horizontal scaling preferred for large systems?

Vertical scaling hits a hard hardware limit and has no failover or redundancy: if the one server dies, the site dies. Horizontal scaling lets you keep adding machines and survive individual failures.

4. Your only slave database goes offline. What happens to reads? What if the master goes offline instead?

With one slave down, reads go temporarily to the master until a new slave is set up. If the master goes down, a slave is promoted to master and handles all operations temporarily while a new slave is added. The promoted slave may be missing recent writes, which need recovery scripts.

5. Your product's prices change every few seconds. Should you cache them with a long TTL?

No. Caches suit data that is read often and modified rarely. With fast-changing data, a long TTL serves stale prices; a very short TTL gives little benefit. Read from the database, or cache with a very short TTL only if slight staleness is acceptable.

6. You updated your logo but users still see the old one from the CDN. What are your options?

Either invalidate the object using the CDN vendor's API, or use object versioning by changing the URL, e.g. logo.png?v=2, so the CDN treats it as a new file.

7. What should happen if the CDN has an outage?

Plan a CDN fallback: clients should detect the problem and request the resources directly from the origin server.

8. Why does a stateless web tier make autoscaling easy?

Because no server holds user data, any request can go to any server. You can add or remove servers freely without losing sessions or needing sticky sessions.

9. One of your four shards is overloaded because three celebrities are on it. What would you do?

This is the celebrity/hotspot problem. Allocate a dedicated shard to each celebrity (and partition those further if needed), so their heavy read traffic does not crush other users on the same shard.

10. Image filters take 10 seconds and users complain uploads feel slow. How do you fix it?

Make it asynchronous with a message queue. Web servers publish a processing job and reply immediately; photo workers consume jobs and process them. Add workers when the queue grows, remove them when it is empty.

11. After sharding, a report needs to join users with orders across shards. What is the common fix?

Denormalize: store the needed fields together so the query runs against a single table on one shard, avoiding cross-shard joins.

Cheat sheet

  • Flow: DNS gives IP, client sends HTTP, server returns HTML (web) or JSON (mobile).
  • Default to relational; choose NoSQL for super-low latency, unstructured data, pure serialization, or massive data.
  • Vertical scaling is simple but has a hard limit and no failover; prefer horizontal scaling.
  • Load balancer: public IP to users, private IPs to servers; gives failover and easy growth.
  • Replication: master takes writes, slaves take reads; promote a slave if the master dies (watch for missing data).
  • Cache: read-through; use for read-heavy, rarely-modified data; set TTL; avoid SPOF; overprovision; evict with LRU/LFU/FIFO.
  • CDN: static assets near users; consider cost, TTL, fallback to origin, invalidation via API or versioned URLs.
  • Stateless web tier: sessions in a shared store (NoSQL); enables autoscaling; avoids sticky sessions.
  • Multi-DC: geoDNS routing, failover to healthy DC, replicate data, test and deploy with automation.
  • Message queue: producers publish, consumers process asynchronously; decouples and scales parts independently.
  • Sharding: same schema, different rows; pick a key that distributes evenly; challenges are resharding, hotspots, joins (denormalize).
  • Summary: stateless web tier, redundancy everywhere, cache a lot, multiple DCs, CDN for static, shard data, split into services, monitor and automate.
