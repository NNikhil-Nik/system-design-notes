Chapter 5

Design Consistent Hashing

When data is spread over many servers, you need a rule for "which server holds this key?" The simple rule breaks badly whenever a server is added or removed. Consistent hashing is a clever rule that moves only a small fraction of keys when the set of servers changes, and it powers systems like Amazon Dynamo, Cassandra and Discord.

~30 min readIntermediatePrerequisites: Chapter 1 (sharding, caches), basic idea of a hash function

The big picture

To scale horizontally (add more machines instead of buying a bigger one), we split data across many servers. Each piece of data has a key, such as a user ID or a cache key, and we need a fast, deterministic way to decide which server stores it. Every client must reach the same answer without asking a central directory.

The obvious approach is "hash the key and take the remainder when divided by the number of servers." It works perfectly as long as the number of servers never changes. But servers crash, and we add servers as traffic grows. When that happens, the obvious approach reshuffles almost every key, which for a cache means a sudden flood of misses, and for a database means moving most of your data over the network.

Consistent hashing is the fix. The book quotes the definition from Wikipedia: "Consistent hashing is a special kind of hashing such that when a hash table is re-sized and consistent hashing is used, only k/n keys need to be remapped on average, where k is the number of keys, and n is the number of slots."

Real-world analogy

Imagine a round table with seats for several waiters, and diners sitting all around it. Rule: each diner is served by the first waiter found walking clockwise from where the diner sits. If a new waiter sits down, he only takes over the diners between himself and the previous waiter; everyone else keeps their waiter. If a waiter leaves, only his diners shift to the next waiter clockwise. Compare that with the "modulo" approach, which is like renumbering every waiter and reassigning every diner whenever anyone joins or leaves.

The one-sentence version

Put both servers and keys on the same circle using a hash function; each key belongs to the first server clockwise from it. Adding or removing a server only affects the keys in one neighbouring slice of the circle.

Key terms

Key
The identifier of a piece of data, e.g. user:42 or a cache key. We use it to decide where the data lives.
Hash function
A function that turns any input (a string, a number) into a fixed-size number. The same input always gives the same output, and outputs look randomly spread. Examples: SHA-1, MD5, MurmurHash.
Hash value
The number a hash function outputs for a given input.
Modulo (%)
The remainder after division. 10 % 4 = 2, because 10 = 2×4 + 2.
Server pool
The set of servers currently storing data. Its size is often called N.
Horizontal scaling
Handling more load by adding more machines rather than making one machine bigger.
Rehashing
Recomputing which server each key belongs to after the number of servers changes.
Cache miss
When a client looks for data in a cache and it is not there, so it must go to the slower database.
SHA-1
A hash function whose output is a 160-bit number, i.e. between 0 and 2160 − 1.
Hash space
The full range of possible hash values, from the smallest (0) to the largest (2160 − 1 for SHA-1).
Hash ring
The hash space drawn as a circle by joining its two ends, so that after the largest value comes 0 again.
Partition
The slice of the ring between two adjacent servers. All keys in a server's partition are stored on that server.
Virtual node (vnode / replica)
One of several positions on the ring that belong to the same real server. A server with 3 virtual nodes appears at 3 places on the ring.
Standard deviation
A measure of how spread out numbers are. Here: how much each server's share of keys differs from the average share. Smaller means more even.
Hotspot
A server that gets far more traffic or data than the others and becomes overloaded.
Binary search
Finding an item in a sorted list by repeatedly halving the search range. Takes about log2(n) steps: around 17 steps for 100,000 items.
Sharding
Splitting a large dataset across multiple servers (shards), each holding part of the data.

The rehashing problem

If you have n cache servers, a common way to balance the load is:

serverIndex = hash(key) % N      # N = size of the server pool

Why is this so bad? In a cache cluster, a key that "moved" is not really moved; clients just look on the new server, find nothing, and get a cache miss. When most keys move at once, a storm of cache misses hits the database at the same moment. In a storage cluster, the data must physically be copied across the network. Consistent hashing is an effective technique to mitigate this problem.

Hash space and hash ring

Now that we understand the problem, let us build consistent hashing step by step.

  1. Pick a hash function. The book assumes SHA-1. Its output range, the hash space, goes from 0 to 2160 − 1. Call the first value x0 and the last value xn.
  2. Draw the hash space as a line from x0 = 0 to xn = 2160 − 1.
  3. Bend the line into a circle by connecting both ends. This is the hash ring. Moving clockwise past the largest value brings you back to 0.
From hash space to hash ring
The line of possible hash values is joined end to end. Every point on the circle is one possible hash value.
How big is 2160?

About 1.46 × 1048. The ring has so many positions that two different servers or keys practically never land on the exact same point. In the diagrams we draw positions as angles (0 to 360 degrees) for readability; the idea is identical.

Hashing servers and keys onto the ring

Step 1: Place the servers

Using the same hash function f, we map servers onto the ring based on the server IP address or name. For example, f("10.0.0.1") gives one position, f("10.0.0.2") another.

Step 2: Place the keys

Cache keys are hashed with the same function and placed on the same ring. One important difference from the modulo approach: there is no modular operation. The hash value is the position.

4 servers (circles) and 4 keys (squares) on the ring
Servers s0–s3 and keys k0–k3 are positioned by their hash values. Position 0 is at the top; values increase clockwise.

Server lookup: go clockwise

To determine which server a key is stored on, we go clockwise from the key position on the ring until a server is found. That is the whole rule.

Each key walks clockwise to its server
Going clockwise, key0 is stored on server 0, key1 on server 1, key2 on server 2, and key3 on server 3.

Worked numeric example (a tiny ring from 0 to 99)

Pretend the hash space is only 0–99. Servers hash to positions A = 10, B = 40, C = 70.

Key hashWalk clockwise...Server
5next server position ≥ 5 is 10A
25next server position ≥ 25 is 40B
40exactly on 40B
55next is 70C
85nothing ≥ 85, so wrap around to the start: 10A

So A owns positions 71–99 and 0–10, B owns 11–40, and C owns 41–70. The wrap-around is why we use a ring rather than a line.

Implementation: sorted list + binary search

A computer does not literally "walk" around a circle. It keeps the server positions in a sorted list and uses binary search to find the first position that is greater than or equal to the key's hash. If there is none, it wraps to the first element.

import bisect, hashlib

def h(s):                                  # position on the ring
    return int(hashlib.sha1(s.encode()).hexdigest(), 16)

class ConsistentHashRing:
    def __init__(self, vnodes=100):
        self.vnodes = vnodes               # virtual nodes per server
        self.positions = []                # sorted ring positions
        self.owner = {}                    # position -> real server

    def add_server(self, server):
        for i in range(self.vnodes):
            p = h(f"{server}#{i}")         # e.g. "10.0.0.1#7"
            bisect.insort(self.positions, p)
            self.owner[p] = server

    def remove_server(self, server):
        for i in range(self.vnodes):
            p = h(f"{server}#{i}")
            self.positions.remove(p)
            del self.owner[p]

    def get_server(self, key):
        p = h(key)
        i = bisect.bisect_left(self.positions, p)   # first position >= p
        if i == len(self.positions):                 # past the end?
            i = 0                                    # wrap around the ring
        return self.owner[self.positions[i]]

Lookup costs O(log V), where V is the total number of virtual nodes. With 10 servers × 200 virtual nodes = 2,000 positions, that is about 11 comparisons per lookup: extremely fast.

Adding a server

Using the logic above, adding a new server only requires redistributing a fraction of keys. Suppose server 4 (s4) is added to the ring between k0 and s0.

Add s4: only k0 moves
After s4 is added, only key0 needs to be redistributed. k1, k2 and k3 remain on the same servers.

Before s4 was added, key0 was stored on s0. Now key0 is stored on s4, because s4 is the first server it meets going clockwise from key0's position. The other keys are not redistributed. Compare that to the modulo approach, where adding a fifth server would change hash % 4 to hash % 5 and move most keys.

Removing a server

When a server is removed, only a small fraction of keys need redistribution. Suppose s1 is removed.

Remove s1: only k1 moves
When s1 is removed, only key1 must be remapped, to s2. The rest of the keys are unaffected.

k1 used to walk clockwise and hit s1 first. With s1 gone, it keeps walking and reaches s2. Keys that belonged to s0, s2 and s3 never noticed anything happened.

Remember the direction

Keys always move to the clockwise neighbour of a removed server. When a server is added, it takes keys from its clockwise neighbour (the server that used to own them).

Two issues in the basic approach

The consistent hashing algorithm was introduced by Karger et al. at MIT. The basic steps are:

  • Map servers and keys onto the ring using a uniformly distributed hash function.
  • To find out which server a key is mapped to, go clockwise from the key position until the first server on the ring is found.

Two problems are identified with this approach.

Issue 1: Partition sizes can be very uneven

It is impossible to keep the same size of partitions on the ring for all servers once servers can be added or removed. A partition is the hash space between adjacent servers. In the example below, after s1 is removed, s2's partition is twice as large as the partitions of s0 and s3.

Uneven partitions after removing s1
Each coloured arc is the slice of the ring a server owns. s2 inherited s1's slice and now owns half of the ring.

Half of all keys going to one of three servers means that server needs about twice the memory and handles about twice the traffic of the others.

Issue 2: Keys can be non-uniformly distributed

Even without removals, servers hashed to random positions can end up bunched together. In the example below, s0, s1 and s3 sit close together, so most keys are stored on s2, while s1 and s3 have no data.

Non-uniform key distribution
With only four random positions, there is a real chance of large gaps. The server at the end of the largest gap becomes a hotspot.

A technique called virtual nodes (or replicas) is used to solve both problems.

Virtual nodes

A virtual node refers to a real node, and each server is represented by multiple virtual nodes on the ring. Instead of hashing "server 0" once, we hash "s0_0", "s0_1", "s0_2", ... and place every result on the ring. All of those points belong to the same physical machine.

Real-world analogy

If you drop 4 coins on a long track at random, the gaps between them will be very uneven. If you drop 400 coins, the gaps will be small and fairly regular. Give each server many coins (virtual nodes) and every server ends up with roughly the same total length of track.

How it works

In the book's example, both server 0 and server 1 have 3 virtual nodes. The number 3 is arbitrarily chosen; in real-world systems the number is much larger.

Two servers, three virtual nodes each
Instead of s0 owning one big partition, it owns three smaller ones (blue arcs), interleaved with s1's three (green arcs). Each server is responsible for many partitions.
  1. Create virtual nodes. s0_0, s0_1, s0_2 represent server 0; s1_0, s1_1, s1_2 represent server 1.
  2. Hash each virtual node onto the ring. They scatter around the circle.
  3. Look up keys exactly as before. Go clockwise from the key to the first virtual node. In the diagram, k0 finds virtual node s1_1 first.
  4. Map virtual node to real server. s1_1 belongs to server 1, so k0 is stored on server 1.

How many virtual nodes?

As the number of virtual nodes increases, the distribution of keys becomes more balanced, because the standard deviation (how far each server's load is from the average) gets smaller. The book cites an experiment:

~10%std. deviation of the mean with 100 virtual nodes
~5%std. deviation of the mean with 200 virtual nodes
↑ vnodesmore balance, more metadata

In plain terms: with 200 virtual nodes per server, a typical server holds within about 5% of the average amount of data. If the average is 1,000,000 keys per server, most servers hold roughly 950,000 to 1,050,000 keys.

More virtual nodes

  • More balanced data distribution.
  • When a server leaves, its load spreads over many servers instead of dumping onto one neighbour.
  • Lets you give a powerful server more vnodes than a weaker one (weighted capacity).

The cost

  • More space is needed to store data about virtual nodes (the sorted list of positions grows).
  • Slightly more work when adding or removing servers.

This is a tradeoff, and we can tune the number of virtual nodes to fit our system requirements.

Why virtual nodes fix both issues

Uneven partitions: each server's total share is the sum of many small random slices, which averages out. Removing a server: its many slices each go to a different clockwise neighbour, so the load is shared among all remaining servers instead of doubling one.

Finding affected keys

When a server is added or removed, a fraction of data needs to be redistributed. How do we find exactly which range of keys to move?

The affected range when adding or removing a server
Left: s4 is added; the red arc between s3 and s4 is the affected range. Right: s1 is removed; the red arc between s0 and s1 is the affected range.

Adding a server (s4)

The affected range starts from s4 (the newly added node) and moves anticlockwise around the ring until a server is found (s3). Keys located between s3 and s4 need to be redistributed to s4.

Removing a server (s1)

The affected range starts from s1 (the removed node) and moves anticlockwise around the ring until a server is found (s0). Keys located between s0 and s1 must be redistributed to s2.

In code terms: for a new node at position p, find its predecessor position q in the sorted list. All keys with hash in (q, p] move from p's clockwise successor to the new node. With virtual nodes, repeat this for every virtual node of the new server; each one steals a small range from a different neighbour.

Benefits and real-world uses

Benefits (from the book's wrap-up)

  • Minimized keys are redistributed when servers are added or removed: about k/n instead of nearly all.
  • It is easy to scale horizontally because data are more evenly distributed.
  • Mitigate the hotspot key problem. Excessive access to a specific shard could cause server overload. Imagine data for Katy Perry, Justin Bieber, and Lady Gaga all ending up on the same shard. Consistent hashing helps mitigate the problem by distributing the data more evenly.

Walkthrough

  1. Hash the key. The web server computes h("user:42"), a position on the ring.
  2. Binary search. It finds the first virtual node at or after that position in its sorted list, wrapping to the start if needed. Say it is s1_57.
  3. Map to a real server. s1_57 belongs to Cache B, so the request goes to Cache B.
  4. Serve. Cache B returns the profile, or on a miss the web server reads the database and stores the result in Cache B.
  5. Scale out. Ops adds Cache D. Its 200 virtual nodes are inserted into every client's ring. Only keys falling in D's new slices change owner (about 1/4 of keys, since there are now 4 servers), causing a modest, spread-out set of cache misses, instead of most of the cache missing at once as with hash % N.
  6. Failure. If Cache A dies, its 200 slices each fall to their clockwise neighbours, which belong to B, C and D roughly equally, so no single server is overwhelmed.

How to answer this in an interview

Consistent hashing usually comes up as a building block inside a bigger question ("how do you partition the data?"), or as a direct "explain consistent hashing" question. Either way, this structure works.

State the problem it solves

  • Explain hash(key) % N and show what happens when N changes.
"The naive way to shard is hash of the key modulo the number of servers. That's balanced, but if a server dies and N goes from 4 to 3, almost every key maps to a different server. For a cache, that's a flood of misses hitting the database at once."
2
Draw the ring
5 min
  • Hash space 0 to 2160 − 1 (SHA-1) bent into a ring.
  • Servers and keys hashed onto it; key goes to first server clockwise.
  • Show adding and removing a server.
"I hash both servers and keys onto the same ring. A key belongs to the first server clockwise from it. If I add a server, it only takes keys from the slice between it and the previous server. On average only k over n keys move."
"How would you actually implement the clockwise lookup?"
"Keep the server positions in a sorted array. Hash the key, binary-search for the first position greater than or equal to it, and wrap to index 0 if I run off the end. That's O(log n) per lookup."
3
Point out the flaws and fix them with virtual nodes
5 min
  • Uneven partitions, non-uniform key distribution.
  • Virtual nodes: many positions per server; std. dev. ~10% at 100, ~5% at 200; costs metadata.
"With few servers, random positions give uneven slices, and when a server leaves, its whole slice lands on one neighbour. So each server gets many virtual nodes, say 100 to 200. With 200 the load per server is within about 5% of the mean. The trade-off is more metadata to store."
"Some of your servers have twice the RAM. How do you use that?"
"Give them proportionally more virtual nodes. A server with twice the vnodes owns roughly twice the hash space, so it stores roughly twice the keys."
"What about a single very hot key, like a celebrity's profile?"
"Consistent hashing spreads keys evenly, but one key still lives on one server. For a truly hot key I'd add replication of that key or a local cache in front, on top of consistent hashing."

Common mistakes

Applying modulo to the ring position

In consistent hashing there is no % N. The hash value is the position on the ring. If you take a modulo by the server count, you are back to the rehashing problem.

Forgetting the wrap-around

A key whose hash is larger than every server position belongs to the first server on the ring. Missing this in code gives an index-out-of-range bug.

Presenting the basic ring as the final answer

Interviewers expect you to spot uneven partitions and non-uniform distribution yourself, then introduce virtual nodes.

Getting the direction wrong

Lookups go clockwise. The affected range when adding or removing a node is found by going anticlockwise from that node to the previous server.

Claiming virtual nodes are free

More vnodes mean more balance but more metadata to store and update. Say it is a tunable trade-off.

Thinking consistent hashing solves a single hot key

It evens out the distribution of many keys. One extremely popular key still maps to one server and needs extra measures.

Test yourself

1. With hash % N and 4 servers, server 1 goes down. Why do keys on servers 0, 2 and 3 move too?

Because the divisor changes from 4 to 3, so hash % 3 differs from hash % 4 for most hash values. The server assignment depends on N, not just on the key. In the book's example, 6 of 8 keys moved even though only 2 lived on the failed server.

2. What is the hash space when using SHA-1, and how does it become a ring?

0 to 2160 − 1. Connect the two ends so that after the largest value comes 0 again.

3. On a 0–99 ring, servers are at 15, 50 and 80. Which server stores keys hashing to 20, 80 and 95?

20 → 50 (first server clockwise). 80 → 80 (it lands exactly on that server). 95 → 15, because nothing is ≥ 95 so we wrap around to the first server.

4. A new server s4 is added between s3 and s0. Which keys move, and where do they come from?

Only the keys between s3 and s4 (going anticlockwise from s4 until the first server, s3). They move to s4 from s0, which used to own them as their first clockwise server.

5. Server s1 is removed. Which keys move and to where?

Keys between s0 (anticlockwise neighbour) and s1. They move to s2, the next server clockwise.

6. What are the two problems with the basic consistent hashing approach?

(1) Partition sizes are uneven, especially after servers are added or removed (e.g. one server ends up owning half the ring). (2) Keys can be non-uniformly distributed, so some servers get most keys and others almost none.

7. How do virtual nodes help, and what does the book say about 100 vs 200 of them?

Each server appears at many points, so its total share is the sum of many small slices, which averages out. The book notes a standard deviation of about 10% of the mean with 100 virtual nodes and about 5% with 200. The cost is more space for virtual node metadata.

8. You have 5 servers but one has double the CPU and memory. How do you route more data to it?

Give it about twice as many virtual nodes as the others. It then owns roughly twice the ring and stores roughly twice the keys.

9. Why use binary search in the implementation?

Ring positions are stored in a sorted list. Finding the first position ≥ the key's hash with binary search takes O(log n) time, e.g. about 11 steps for 2,000 virtual nodes, instead of scanning the whole list.

10. Name three real systems that use consistent hashing.

Any three of: Amazon Dynamo (partitioning), Apache Cassandra (data partitioning), Discord, Akamai CDN, Google Maglev load balancer.

Cheat sheet

  • hash(key) % N is balanced but breaks when N changes: most keys remap (6 of 8 in the book's example).
  • Consistent hashing: only about k/n keys remap on resize (k keys, n servers).
  • Hash space: SHA-1, 0 to 2160 − 1, bent into a hash ring.
  • Hash servers (by IP/name) and keys with the same function onto the ring. No modulo.
  • Lookup: go clockwise from the key to the first server. Implement with sorted list + binary search; wrap to index 0.
  • Add server: it takes the keys between it and its anticlockwise neighbour. Remove server: its keys go to the clockwise neighbour.
  • Problems with basic ring: uneven partition sizes; non-uniform key distribution.
  • Fix: virtual nodes, many ring positions per server. Std. dev. ~10% of mean at 100 vnodes, ~5% at 200.
  • Trade-off: more vnodes = better balance but more metadata storage.
  • Benefits: minimal redistribution, easy horizontal scaling, mitigates hotspots.
  • Used by Dynamo, Cassandra, Discord, Akamai CDN, Maglev.
