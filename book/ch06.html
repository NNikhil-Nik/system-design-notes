Chapter 6

Design a Key-Value Store

A key-value store is the simplest kind of database: you hand it a key, it hands you back a value. Making one that runs on a single computer is easy. Making one that runs on hundreds of computers, never goes down, and survives broken networks is one of the classic hard problems of system design, and this chapter walks through every piece of it.

~45 min readAdvancedPrerequisites: Ch 1 (scaling basics), Ch 5 (consistent hashing)

The big picture

Almost every large website needs somewhere to keep small pieces of data that it can look up very quickly by a name. A shopping cart is looked up by a user ID. A login session is looked up by a session token. A user's settings are looked up by their account ID. In all of these cases the program does not need fancy search or joins. It just needs: "give me the thing stored under this name".

That is exactly what a key-value store does. Famous real-world examples are Amazon DynamoDB, memcached and Redis. The book's design in this chapter is heavily inspired by Amazon's Dynamo paper and by Apache Cassandra.

The interesting part is not the "store a value" part. It is everything that happens when you need so much data and so much traffic that one machine is not enough. Then you must answer questions like:

  • Which machine holds which key?
  • How many copies of each key do we keep, and where?
  • If two copies disagree, which one is right?
  • How do we notice that a machine has died, and what do we do about it?
  • How do we write and read data on each machine efficiently?
Real-world analogy

Think of a huge coat-check service at a stadium. You hand over your coat (the value) and get a ticket number (the key). With one small desk and one attendant, it is simple. But with 80,000 fans, you need many desks. Now you need rules: ticket numbers 1 to 10,000 go to desk A, and so on (partitioning). In case a desk catches fire, you keep a photo of every coat at two other desks (replication). Desks constantly shout "I'm still open!" to each other so everyone knows which desks are alive (failure detection). If desk A is briefly closed, desk B temporarily holds coats meant for A and passes them back when A reopens (hinted handoff). This chapter is basically the rulebook for that coat-check service.

What you will learn

The CAP theorem, consistent hashing for partitioning, replication, quorum consensus (N, W, R), consistency models, vector clocks for conflict detection, gossip protocols, sloppy quorum and hinted handoff, Merkle trees, and the read/write path inside a single storage node (commit log, memtable, SSTables, Bloom filters).

Key terms

Key-value pair
One record in the store: a unique key (the name) and the value (the data) attached to it. Example: key user:42:cart, value ["book","pen"].
Node / server
One computer in the cluster that stores part of the data. The book uses "node" and "server" interchangeably.
Cluster
A group of nodes working together so they look like one big system to the user.
Distributed system
A system whose parts run on several computers that talk over a network.
Partition (data)
Splitting the data into smaller pieces so each node only stores a slice. Also called sharding.
Network partition
A different meaning: the network breaks so that some nodes cannot talk to others, even though they are all still running. The "P" in CAP.
Replication / replica
Keeping several copies of the same data on different nodes. Each copy is a replica.
Consistency
Everyone who reads the data sees the same, latest value, no matter which node they ask.
Availability
Every request gets a response, even if some nodes are broken.
Partition tolerance
The system keeps working even when the network splits the nodes into groups that cannot communicate.
CAP theorem
The rule that a distributed system cannot guarantee Consistency, Availability and Partition tolerance all at the same time. It can pick two.
Consistent hashing
A way to map keys and servers onto a circle ("hash ring") so that adding or removing a server only moves a small fraction of keys. Covered in Chapter 5.
Virtual node
One physical server appearing at several spots on the hash ring. More powerful servers get more virtual nodes.
Coordinator
The node that receives a client's request and acts as a middleman, forwarding it to the replicas and collecting their answers.
Quorum
The minimum number of replicas that must agree (acknowledge) before an operation is considered successful.
N, W, R
N = number of replicas. W = how many must confirm a write. R = how many must answer a read.
Strong / weak / eventual consistency
How fresh reads are guaranteed to be: always latest / maybe not latest / latest after enough time passes.
Versioning
Treating each change as a new, immutable version of the data instead of overwriting it.
Vector clock
A list of [server, counter] pairs attached to each version, used to tell whether one version came after another or whether they conflict.
Sibling / conflict
Two versions that were created independently (neither came from the other). The system cannot automatically pick one.
Heartbeat
A small "I'm alive" signal a node sends regularly.
Gossip protocol
A failure-detection method where each node periodically shares its list of heartbeats with a few random nodes, so information spreads like gossip.
Sloppy quorum
When some replicas are down, use the first W (or R) healthy servers on the ring instead of insisting on the exact replicas.
Hinted handoff
A stand-in server stores writes for a down server along with a "hint", then hands them back when that server recovers.
Anti-entropy
A background process that compares replicas and repairs any differences. "Entropy" here means disorder.
Merkle tree
A tree of hashes where each parent is the hash of its children. Lets two servers find which data differs by comparing only a few hashes.
Hash
A function that turns any input into a fixed-size fingerprint. Same input, same fingerprint; tiny change, totally different fingerprint.
Commit log
An append-only file on disk where every write is recorded first, so it can be recovered after a crash.
Memory cache / memtable
An in-memory table holding recent writes before they are flushed to disk.
SSTable
Sorted String Table: an immutable file on disk containing key-value pairs sorted by key.
Bloom filter
A tiny data structure that can answer "is this key definitely not here, or possibly here?" very quickly.
Latency
How long one request takes, usually measured in milliseconds.

What is a key-value store?

A key-value store (also called a key-value database) is a non-relational database. "Non-relational" means there are no tables with columns, no SQL joins, no foreign keys. Each record is just a unique key and the value that goes with it.

  • The key must be unique. It can be plain text or a hashed value. Examples from the book: plain text key "last_logged_in_at", hashed key 253DDEC4.
  • Short keys work better because they are faster to compare and take less space.
  • The value can be anything: a string, a list, an object. The store usually treats it as an opaque blob, meaning it does not care what is inside.
keyvalue

The whole interface is just two operations:

put(key, value)   // insert "value" associated with "key"
get(key)          // get the "value" associated with "key"
Why not just use a normal SQL database?

A relational database can do much more (joins, complex queries, transactions), but that power costs speed and makes it harder to spread across many machines. When all you need is "look up by key", a key-value store is simpler, faster, and much easier to scale horizontally (by adding more machines).

Understand the problem and design scope

No design is perfect. Every design balances trade-offs between how much memory you use, how fresh reads are, how available the system is, and how fast it responds. So the first step in an interview is to agree on the requirements. The book settles on these characteristics:

Small pairs

The size of a key-value pair is small: less than 10 KB.

Big data

It must be able to store a lot of data, far more than fits on one machine.

High availability

The system responds quickly, even during failures.

High scalability

It can grow to support very large data sets and traffic.

Automatic scaling

Servers can be added or removed automatically based on traffic.

Tunable consistency

The operator can choose how strict consistency should be, trading it against speed.

Low latency

Reads and writes must be fast.

Interview tip

Always say these requirements out loud and get the interviewer to agree. "Tunable consistency" in particular is the hook for the whole quorum discussion later. If the interviewer instead says "this is for bank balances", you would lean towards strong consistency, and the design changes.

Single server key-value store

Before going distributed, start simple. On one server, the most intuitive approach is to keep everything in a hash table in memory.

A hash table is a data structure that stores key-value pairs and can find any key in roughly constant time, no matter how many keys there are. It works by running the key through a hash function to compute which "bucket" (slot in an array) the value lives in. Memory (RAM) is extremely fast, so this gives very low latency.

The whole store is one hash table in RAM on one machine. Fast, but limited by how much RAM one machine has.

The problem: memory is limited and expensive. Once the data grows past what fits in RAM, you are stuck. The book suggests two optimizations to stretch one server further:

  1. Data compression. Compress values so they take less space. You trade a little CPU time for more storage.
  2. Keep only hot data in memory. "Hot" means frequently accessed. Store the rest on disk. Most systems have a small set of popular keys, so this works well.

Even with these tricks, a single server reaches its capacity very quickly, and if that one server dies, everything is gone or unavailable. To support big data and high availability, we need a distributed key-value store.

Distributed key-value store

A distributed key-value store (also called a distributed hash table) spreads key-value pairs across many servers. As soon as you have more than one server, a new problem appears: the servers must communicate over a network, and networks can fail. The rules for what you can and cannot guarantee in that situation are captured by the CAP theorem. It is the single most important idea for this chapter, so we will go slowly.

The CAP theorem, explained slowly

The CAP theorem says it is impossible for a distributed system to simultaneously provide more than two of these three guarantees:

C - Consistency

All clients see the same data at the same time, no matter which node they connect to.

A - Availability

Any client that requests data gets a response, even if some of the nodes are down.

P - Partition tolerance

The system keeps operating even when the network breaks communication between nodes.

A "partition" here means a communication break between two nodes. Partition tolerance means the system continues to work despite such breaks.

Three replicas: n1, n2, n3
Data is replicated on three nodes. In a healthy network, a write to any node is copied to the other two, so all three agree.

Picking two out of three

Key-value stores are classified by which two of the three properties they support:

TypeGuaranteesGives upTypical example
CPConsistency + Partition toleranceAvailabilityBank balances, anything where a wrong answer is worse than no answer
APAvailability + Partition toleranceConsistency (reads may be stale)Shopping carts, social feeds, the Dynamo/Cassandra style
CAConsistency + AvailabilityPartition toleranceDoes not exist in real-world distributed systems
Why CA cannot exist in practice

Network failures are unavoidable. Cables get cut, switches crash, a data center loses connectivity. A distributed system therefore must tolerate network partitions; it has no choice. Since P is mandatory, the only real choice is what to do when a partition happens: keep consistency (CP) or keep availability (AP). A "CA" system would be one that simply assumes the network never breaks, which is not realistic once you have more than one machine.

The ideal world

In an ideal world, network partitions never occur. Data written to n1 is automatically replicated to n2 and n3, and both consistency and availability are achieved. Nothing to choose.

The real world: n3 goes down

Now suppose n3 goes down (or the network to it breaks) and cannot communicate with n1 and n2.

Network partition: n3 is cut off
If clients write to n1 or n2, the data cannot be propagated to n3. If data was written to n3 but not yet copied out, n1 and n2 have stale data. The system must now choose.

If we choose CP (consistency)

We must block all write operations to n1 and n2 to avoid data inconsistency among the three servers. This makes the system unavailable. Banks typically choose this: if a balance is not up to date, showing it could lead to wrong transactions. Until the partition is resolved, the bank returns an error rather than a possibly wrong answer.

If we choose AP (availability)

The system keeps accepting reads, even though it might return stale data. n1 and n2 keep accepting writes, and the data is synced to n3 when the partition is resolved. Users always get a response; they just might briefly see old data.

Real-world analogy

Imagine three bank branches that share one ledger by phone. The phone lines to branch 3 go dead. A CP bank says "Sorry, no withdrawals until the phones work again" because branch 3 might have just paid out the same money. An AP coffee-shop loyalty program says "Sure, here's your stamp" at every branch and reconciles the stamp cards later. Being briefly wrong about loyalty stamps is fine; being wrong about money is not.

Choosing the right CAP guarantee for your use case is an important step. Discuss it with the interviewer and design accordingly. For the rest of this chapter, the book's design leans towards an AP system with tunable consistency, like Dynamo and Cassandra.

Data partition

For large applications it is infeasible to fit the complete data set on one server. The simplest fix is to split the data into smaller partitions and store them on multiple servers. Two challenges come up:

  • Distribute data evenly across multiple servers, so no single server is overloaded.
  • Minimize data movement when nodes are added or removed.

Consistent hashing (Chapter 5) solves both. A quick refresher:

  1. Make a ring. Imagine the whole range of possible hash values bent into a circle.
  2. Place servers on the ring. Hash each server's name or IP to get its position.
  3. Place keys on the ring. Hash each key to get its position.
  4. Walk clockwise. A key belongs to the first server you meet walking clockwise from the key's position.
Consistent hashing ring with 8 servers
Eight servers (s0 to s7) are placed on the ring by hashing. key0 hashes to a point between s0 and s1; walking clockwise, the first server reached is s1, so s1 stores key0.

Using consistent hashing to partition data has two big advantages called out by the book:

Automatic scaling

Servers can be added and removed automatically depending on load. When a server joins, it only takes over keys from its clockwise neighbour; the rest of the ring is untouched. So only a small fraction of keys move.

Heterogeneity

The number of virtual nodes for a server is proportional to its capacity. A server with twice the disk and CPU gets twice as many virtual nodes, so it receives roughly twice as many keys.

Why not just hash(key) mod number_of_servers?

With modulo hashing, if you go from 4 servers to 5, almost every key maps to a different server and has to move. That is a disaster for a store holding terabytes. Consistent hashing moves only about 1/n of the keys.

Data replication

To achieve high availability and reliability, data must be replicated asynchronously over N servers, where N is a configurable parameter (3 is a very common choice).

How replicas are chosen: after a key is mapped to a position on the hash ring, walk clockwise from that position and choose the first N servers on the ring to store copies.

Replicating key0 with N = 3
Walking clockwise from key0, the first three servers are s1, s2 and s3. Each of them stores a replica of key0.

Two important refinements

  1. Pick unique physical servers. With virtual nodes, the first N nodes on the ring might belong to fewer than N physical machines (for example, two virtual nodes of the same server sit next to each other). Then losing one machine loses two "copies". To avoid this, when walking clockwise we only choose unique servers, skipping virtual nodes of a server we already picked.
  2. Spread across data centers. Nodes in the same data center often fail at the same time due to power outages, network issues or natural disasters. For better reliability, replicas are placed in distinct data centers, and data centers are connected through high-speed networks.

Consistency: quorum consensus

Since data is replicated on multiple nodes, it must be synchronized across replicas. If one replica has a new value and another still has the old one, a reader might see the wrong thing. Quorum consensus lets us guarantee consistency for both reads and writes, and lets us tune how strict we want to be.

The three knobs

Nnumber of replicas
Wwrite quorum: acks needed for a write to succeed
Rread quorum: responses needed for a read to succeed
  • W of size W: for a write to be considered successful, it must be acknowledged by W replicas.
  • R of size R: for a read to be considered successful, the read must wait for responses from at least R replicas.

The coordinator

The client does not talk to all replicas itself. Instead, one node acts as the coordinator: a proxy between the client and the replica nodes. It forwards the request and counts the replies.

Quorum write with N = 3
The coordinator sends the write to all N = 3 replicas in parallel. With W = 1, it reports success to the client as soon as the first ack comes back. With W = 2 it waits for two acks; with W = 3, all three.

Walking through W = 1

  1. Client sends put(key0, v1) to the coordinator.
  2. Coordinator forwards the write to s0, s1 and s2 at the same time.
  3. First ack arrives, say from s1. Because W = 1, one ack is enough.
  4. Coordinator replies "success" to the client immediately. It does not wait for s0 and s2.
  5. Data is still sent to s0 and s2 in the background. W = 1 does not mean the data is written to only one server; it means the coordinator only waits for one acknowledgment.
The core trade-off

The configuration of W, R and N is a trade-off between latency and consistency. If W = 1 or R = 1, an operation returns quickly because the coordinator only waits for the fastest replica. If W or R is larger than 1, the system offers better consistency, but the query is slower because the coordinator must wait for the slowest of the required replicas.

Why W + R > N guarantees strong consistency

If W + R > N, strong consistency is guaranteed because there must be at least one overlapping node that has the latest data. Concretely, with N = 3, W = 2, R = 2:

Overlap between write set and read set (N=3, W=2, R=2)
The write was confirmed by s0 and s1. A later read asks s1 and s2. Because 2 + 2 > 3, the two groups must share at least one node (s1), so the read is guaranteed to see the latest write. (Versioning, below, tells the reader which of the answers is newer.)

Possible configurations

SettingWhat it meansGood for
R = 1, W = NWrites must reach all replicas; reads ask just one.The system is optimized for a fast read.
W = 1, R = NWrites need one ack; reads must ask every replica.The system is optimized for fast write.
W + R > NWrite and read sets always overlap. Typical: N = 3, W = R = 2.Strong consistency is guaranteed.
W + R <= NSets may not overlap; a read might hit only stale replicas.Strong consistency is not guaranteed, but latency is lower.

Depending on the requirement, we tune the values of W, R and N to reach the desired level of consistency. That is what "tunable consistency" in the requirements means.

Consistency models

A consistency model defines the degree of data consistency the system promises. There is a wide spectrum. The book highlights three:

Strong consistency

Any read returns the value of the most recent write. A client never sees out-of-date data.

Weak consistency

Subsequent reads may not see the most updated value.

Eventual consistency

A specific form of weak consistency. Given enough time, all updates are propagated and all replicas become consistent.

How strong consistency is usually achieved: force a replica to not accept new reads or writes until every replica has agreed on the current write. This approach is not ideal for highly available systems because it can block new operations.

What the book's design uses: Dynamo and Cassandra adopt eventual consistency, and so does our key-value store. With eventual consistency, concurrent writes can allow inconsistent values to enter the system, and the client is forced to read the values and reconcile them. The next section explains how reconciliation works with versioning.

Real-world analogy

Eventual consistency is like updating your profile picture on a social network. Your friend in another country might still see your old picture for a few seconds. Nobody is harmed, and soon everyone sees the new one. Strong consistency is like an ATM: it must never show a balance that ignores your last withdrawal.

Inconsistency resolution: versioning and vector clocks

Replication gives high availability, but it causes inconsistencies among replicas. Versioning and vector clocks are used to solve these problems.

Versioning means treating each data modification as a new, immutable version of the data. Instead of overwriting, we produce version 1, version 2, and so on.

How a conflict happens

  1. Start state. Both replica nodes n1 and n2 have the same value for key name: "john". Call this the original value.
  2. Server 1 updates the name to "johnSanFrancisco" via n1.
  3. At the same time, server 2 updates the name to "johnNewYork" via n2.
  4. Now we have two versions, v1 and v2, both created from the original. Neither is "obviously" newer. These are conflicting values.

n2: "johnNewYork"v2, written by server 2

Conflictwe need a way to detect and resolve it
It is easy to throw away the original once we know it is older. But v1 and v2 were made independently. We need a mechanism that can detect such conflicts and help reconcile them.

What is a vector clock?

A vector clock is a [server, version] pair associated with a data item. It can be used to check whether one version precedes, succeeds, or is in conflict with others.

Written as D([S1, v1], [S2, v2], ..., [Sn, vn]), where D is a data item, v1 is a version counter and S1 is a server number. If data item D is written to server Si, the system does one of these:

  • Increment vi if [Si, vi] already exists.
  • Otherwise, create a new entry [Si, 1].

Think of it as each server keeping its own tally of "how many times I have handled updates to this item", and the item carrying everyone's tally with it.

The book's example, step by step

Vector clock example: D1 to D5
D3 and D4 both descend from D2 but were created independently on different servers, so they conflict. A client reconciles them into D5.
  1. D1. A client writes data item D1 to the system. The write is handled by server Sx. Sx has no entry yet, so it creates one: vector clock D1([Sx, 1]).
  2. D2. Another client reads the latest D1, updates it to D2 and writes it back. D2 overwrites D1. Assume the write is handled by the same server Sx, which now increments its counter: D2([Sx, 2]).
  3. D3. Another client reads the latest D2, updates it to D3 and writes it back. Assume this write is handled by server Sy. Sx's counter stays at 2; Sy adds its own entry: D3([Sx, 2], [Sy, 1]).
  4. D4. Another client also reads the latest D2 (not D3), updates it to D4 and writes it back. This write is handled by server Sz: D4([Sx, 2], [Sz, 1]).
  5. Conflict detected. When another client reads D3 and D4, it discovers a conflict, caused by data item D2 being modified by both Sy and Sz. Neither D3 nor D4 includes the other's change.
  6. D5. The client resolves the conflict (for example, by merging the two values) and sends the updated data to the server. Assume the write is handled by Sx, so Sx increments to 3, and the other entries are kept: D5([Sx, 3], [Sy, 1], [Sz, 1]).

How to tell "ancestor" from "conflict"

Using vector clocks, it is easy to tell whether version X is an ancestor of version Y (meaning no conflict, Y simply came later) or a sibling (conflict).

X is an ancestor of Y (no conflict)

If the counter of every participant in Y's vector clock is greater than or equal to the matching counter in X. Example: D([s0,1],[s1,1]) is an ancestor of D([s0,1],[s1,2]). Safe to discard X.

X and Y are siblings (conflict)

If there is any participant in Y's vector clock whose counter is less than its counter in X (and vice versa). Example: D([s0,1],[s1,2]) and D([s0,2],[s1,1]) conflict: each is ahead on one server.

Apply this to the example: compare D3 [Sx,2],[Sy,1] with D4 [Sx,2],[Sz,1]. D3 has Sy = 1 but D4 has Sy = 0 (missing means 0). D4 has Sz = 1 but D3 has Sz = 0. Each is ahead on something, so they are siblings: conflict. Compare D2 [Sx,2] with D3: D3 is >= D2 everywhere, so D2 is simply an ancestor and can be thrown away.

// Is clock a an ancestor of (or equal to) clock b?
function isAncestor(a, b):
    for each server s in union(keys(a), keys(b)):
        if a.get(s, 0) > b.get(s, 0):
            return false
    return true

function compare(a, b):
    if isAncestor(a, b): return "a happened before b (keep b)"
    if isAncestor(b, a): return "b happened before a (keep a)"
    return "conflict: siblings, client must reconcile"

Downsides of vector clocks

What they give us

  • Precise detection of conflicts versus simple overwrites.
  • No need for synchronized wall clocks across servers.
  • Lets an AP system accept writes everywhere and sort it out later.

Downsides (from the book)

  • Client complexity: vector clocks add complexity to the client because it needs to implement conflict resolution logic.
  • Size can grow rapidly: the [server: version] pairs could grow quickly. The fix is to set a threshold for the length; if it exceeds the limit, the oldest pairs are removed. This can make reconciliation inefficient because the descendant relationship cannot be determined accurately. However, based on the Dynamo paper, Amazon has not yet encountered this problem in production, so it is probably an acceptable solution for most companies.

Handling failures: failure detection

In any large system at scale, failures are not only inevitable but common. Handling failure scenarios is very important. First, we need to detect failures.

In a distributed system, it is insufficient to believe a server is down just because one other server says so. Maybe the problem is just the network between those two. Usually it requires at least two independent sources of information to mark a server down.

Option 1: all-to-all multicasting

Every node sends heartbeats directly to every other node. This is straightforward, but it is inefficient when many servers are in the system: with n servers, the number of messages grows roughly with n squared.

Option 2: gossip protocol (the better choice)

A decentralized failure detection method like the gossip protocol is better. Here is how it works, following the book:

  1. Each node maintains a node membership list, which contains member IDs and heartbeat counters.
  2. Each node periodically increments its own heartbeat counter. A counter that keeps going up means "I'm alive".
  3. Each node periodically sends heartbeats to a set of random nodes, which in turn propagate to another set of nodes. Like a rumour spreading through a school.
  4. Once nodes receive heartbeats, the membership list is updated to the latest info (take the higher counter, note the local time).
  5. If the heartbeat has not increased for more than a predefined period, the member is considered offline.
All-to-all multicast vs gossip
Left: every pair exchanges heartbeats, which explodes with hundreds of nodes. Right: s0 gossips its membership list to two random nodes (solid), and s3 later forwards it onwards (dashed). Information still reaches everyone, with far fewer messages.

  2. s0 gossips heartbeats that include s2's info to a set of random nodes.

Why this is clever

No central "monitor" server is needed (which could itself fail). And because several nodes independently notice s2's stale counter, we satisfy the "at least two independent sources" rule before declaring s2 dead.

Handling temporary failures: sloppy quorum and hinted handoff

After failures have been detected through gossip, the system needs to keep working. Under a strict quorum approach, reads and writes could be blocked: if key0's three replicas are s1, s2, s3 and W = 2, but s2 and s3 are down, the write cannot succeed. That hurts availability.

Sloppy quorum

A technique called sloppy quorum is used to improve availability. Instead of enforcing the quorum requirement on the exact replica set, the system chooses the first W healthy servers for writes and the first R healthy servers for reads on the hash ring. Offline servers are ignored.

Hinted handoff

If a server is unavailable due to network or server failures, another server will process requests temporarily. When the down server is up again, changes are pushed back to it to achieve data consistency. This process is called hinted handoff: the stand-in stores the data with a "hint" saying who it really belongs to.

Following the book's figure: s2 is unavailable, so reads and writes are temporarily handled by s3. When s2 comes back online, s3 hands the data back to s2.
Real-world analogy

Your neighbour is on holiday, so the mail carrier leaves their parcel with you, with a sticky note "for house 12". When they return, you hand it over. You never pretend the parcel is yours.

Trade-off

Sloppy quorum favours availability over consistency. While s2 is down, a read that happens to hit s2's old data elsewhere could be stale. This fits an AP design; you would not do this in a bank ledger.

Handling permanent failures: anti-entropy with Merkle trees

Hinted handoff handles temporary failures. But what if a replica is permanently unavailable, or a stand-in also dies before handing data back? Replicas drift apart. To fix this, we implement an anti-entropy protocol to keep replicas in sync. Anti-entropy involves comparing each piece of data on replicas and updating each replica to the newest version.

The naive approach, sending every key from server A to server B to compare, would move enormous amounts of data. A Merkle tree is used to detect inconsistencies and minimize the amount of data transferred.

What is a Merkle tree?

A hash tree or Merkle tree is a tree in which every non-leaf node is labelled with the hash of the labels or values of its child nodes. Hash trees allow efficient and secure verification of the contents of large data structures. Key property: if anything underneath changes, every hash above it, all the way to the root, changes too.

Building a Merkle tree, step by step (book example: key space 1 to 12)

  1. Divide the key space into buckets. In the example, 4 buckets: keys 1-3, 4-6, 7-9, 10-12. A bucket is used as the root-level node to maintain a limited depth of the tree.
  2. Hash each key in a bucket using a uniform hashing method.
  3. Create a single hash node per bucket by hashing together the hashes of all keys in it.
  4. Build the tree upwards to the root by calculating hashes of children: two bucket hashes combine into a parent, two parents combine into the root.
Comparing two replicas with Merkle trees
Server 2 has a different value for one key in bucket 3 (keys 7-9). That changes bucket 3's hash, its parent's hash, and the root hash (red). Matching hashes elsewhere prove those parts are identical.

Comparing two trees

  1. Compare root hashes. If the root hashes match, both servers have the same data. Done, having exchanged a single hash.
  2. If they disagree, compare the children. The left child hashes match (91ab = 91ab), so keys 1-6 are identical; skip that whole half. The right child hashes differ (e04d vs 7a65), so go down that side.
  3. Keep descending until you reach the leaves. Bucket 4 matches (58e1); bucket 3 differs (c2d9 vs 0e44).
  4. Synchronize only the differing buckets. Exchange just the keys 7-9 and update to the newest versions.

Using Merkle trees, the amount of data that needs to be synchronized is proportional to the differences between the two replicas, not the amount of data they contain. In real-world systems the bucket size is quite big. For instance, a possible configuration is one million buckets per one billion keys, so each bucket only contains 1,000 keys.

Handling data center outage

A data center outage could happen due to power outage, network outage, natural disaster, and so on. To build a system capable of handling data center outage, it is important to replicate data across multiple data centers. Even if a data center is completely offline, users can still access data through the other data centers. This is why, in the replication section, we placed replicas in distinct data centers.

Writes are cheap: one sequential append to disk plus an in-memory update. The expensive sorted-file writing happens later in bulk.
  1. The write request is persisted on a commit log file. Appending to the end of a file is the fastest kind of disk write. If the server crashes, it can replay the log on restart so no acknowledged write is lost.
  2. Data is saved in the memory cache. Now reads of this key can be served from RAM.
  3. When the memory cache is full or reaches a predefined threshold, data is flushed to an SSTable on disk. The memory is then cleared for new writes.
What is an SSTable, simply?

A sorted-string table (SSTable) is a sorted list of <key, value> pairs stored in a file. "Sorted" means keys are in order (apple, banana, cherry...), which makes finding a key in the file fast, like looking up a word in a dictionary instead of a shuffled pile of index cards. SSTables are immutable: once written they are never changed. New values for a key go into newer SSTables, so when reading, newer SSTables win.

From memory cache to SSTable
Memory cachecherry=7, apple=2, banana=5
→sort and flush
SSTable fileapple=2 | banana=5 | cherry=7
The flush writes keys in sorted order to a brand-new file in one big sequential write.

Bloom filters, simply

A Bloom filter is a row of bits (0s and 1s), all starting at 0, plus a few hash functions. Each SSTable has its own Bloom filter.

  • Adding a key: run the key through, say, 3 hash functions. Each gives a position in the bit array. Set those 3 bits to 1.
  • Checking a key: run it through the same 3 hashes. If any of those bits is 0, the key is definitely not in this SSTable, so skip it. If all are 1, the key is probably there, so read the file.
Bloom filter with 12 bits and 3 hash functions
"apple" hashes to positions 1, 5 and 9, so those bits become 1. Later, checking "grape" might hash to 1, 3, 9: bit 3 is 0, so "grape" is definitely not in this SSTable and the file is never opened. (Positions are illustrative.)
Why Bloom filters are perfect here

They are tiny (a few bits per key, so they fit in memory) and never give a false "no". They can give a false "maybe" (a false positive), which just costs one unnecessary file read. That is a great deal: we skip almost every SSTable that does not contain the key.

Every technique in the chapter has a job in this one picture.
  1. Partition: the coordinator hashes cart:42 onto the consistent hashing ring.
  2. Replicate: it walks clockwise and picks the first 3 unique servers, located in different data centers.
  3. Handle failures: gossip has already told it Replica 3 is down, so with a sloppy quorum it uses the next healthy server, which stores the write with a hint.
  4. Write path: each replica appends to its commit log and updates its memory cache, then acks.
  5. Quorum: after W = 2 acks, the coordinator tells the client "success".

  7. Conflicts: if the replicas return versions whose vector clocks are siblings, both are returned and the client reconciles them, writing back a merged version.
  8. Repair: when Replica 3 comes back, hinted handoff gives it the data; anti-entropy with Merkle trees catches anything else that drifted.

"Assume availability is more important. Users should always be able to write."
"Then I will design an AP system with eventual consistency by default, like Dynamo or Cassandra, but expose N, W and R so a caller can choose stronger consistency when needed."

  • Explain why it fails: capacity and single point of failure.
  • Introduce CAP and state your choice.
"On one machine, a hash table in memory is enough, and I could compress values and keep only hot data in RAM. But we quickly hit memory limits and have a single point of failure, so we need to distribute. Once we distribute, partitions are unavoidable, so the real choice is CP or AP. We chose AP."
"Why can't you just have CA?"
"CA means assuming the network never fails. In a real multi-machine system network failures happen, so partition tolerance is not optional. When the network splits, I must either reject requests to stay consistent, or answer and risk staleness."

  • Replication: first N unique servers clockwise, across data centers.
  • Quorum: coordinator, N/W/R, the four configurations.
  • Draw the ring and the coordinator diagram.
"Keys are placed on a consistent hashing ring. Each key is stored on the first N = 3 unique physical servers clockwise, spread across data centers. A coordinator forwards each request to all replicas and waits for W acks on writes and R responses on reads. With N = 3, W = R = 2 we get W + R > N, so reads overlap the latest write."
"What if I want the fastest possible reads?"
"Set R = 1 and W = N. Reads only wait for one replica, and every write has reached all replicas, so any single replica is up to date. The cost is slower writes and writes failing if any replica is unreachable."
4
Deep dive: conflicts and failures
10–15 min
  • Vector clocks: walk through the D1 to D5 example; ancestor vs sibling rule; downsides.
  • Gossip protocol with heartbeat counters.
  • Sloppy quorum + hinted handoff for temporary failures.
  • Merkle trees for permanent failures; multi-DC replication for outages.
"Because we accept writes on any replica, two clients can update the same key concurrently. Each version carries a vector clock. If one clock is greater than or equal to the other on every server, it simply supersedes it. Otherwise they are siblings, and we return both to the client to merge."
"How do you know a node is dead, and what happens to its writes?"
"Each node has a membership list of heartbeat counters and gossips it to random peers. If a node's counter does not increase for a set period, and others confirm, it is marked down. Writes for it go to the next healthy node via sloppy quorum, stored with a hint, and handed back when it recovers. If it is gone for good, Merkle-tree anti-entropy finds and repairs only the differing buckets."
"Your vector clocks keep growing. Is that a problem?"
"We cap the length with a threshold and drop the oldest pairs. That can make ancestry detection imprecise, but the Dynamo paper reports Amazon has not run into this in production, so it is an acceptable trade-off."

Storage engine and wrap up
3–5 min
  • Write path: commit log, memory cache, flush to SSTable.
  • Read path: memory cache, Bloom filter, SSTables.
  • Recap with the summary table.
"On each node, writes go to a commit log for durability, then to an in-memory cache, which is flushed to immutable sorted SSTables when full. Reads check memory first, then use per-SSTable Bloom filters to skip files that definitely do not have the key. To recap: consistent hashing for scale, replication across data centers for availability, quorums for tunable consistency, vector clocks for conflicts, gossip, hinted handoff and Merkle trees for failures."
"Why a commit log if the data is going into memory anyway?"
"Memory is lost on a crash. The commit log is an append-only file, so writing to it is fast, and on restart the node replays it to rebuild the memory cache. Without it, acknowledged writes could disappear."

Common mistakes

Claiming a CA distributed system

Saying "my system is consistent and available" without addressing partitions shows you have not understood CAP. Partitions will happen; say which property you sacrifice during one.

Thinking W = 1 means "write to one server"

The write is still sent to all N replicas. W only controls how many acks the coordinator waits for before replying.

Using modulo hashing for partitioning

hash(key) % n remaps almost every key when n changes. Use consistent hashing, and mention virtual nodes for heterogeneity.

Picking the first N ring positions blindly

With virtual nodes, adjacent positions may be the same physical machine. Pick the first N unique servers, ideally in different data centers.

Using wall-clock "last write wins" without saying so

Timestamps from different servers can disagree, silently losing data. The book's answer is vector clocks; if you choose last-write-wins instead, call out the trade-off.

Declaring a node dead from one missed ping

It may just be a network blip between two nodes. Require multiple independent sources, which gossip provides naturally.

Confusing temporary and permanent failure handling

Hinted handoff is for short outages. Merkle-tree anti-entropy is for replicas that are out of sync for longer or permanently. Mention both.

Test yourself

1. What are the three guarantees in CAP, and why must a real distributed system always include P?

Consistency (everyone sees the same data), Availability (every request gets a response), Partition tolerance (keeps working when the network splits). Network failures are unavoidable in practice, so a distributed system must tolerate partitions. The real choice is between C and A during a partition.

2. n3 loses its connection to n1 and n2. Describe what a CP system and an AP system each do.

CP: blocks writes to n1 and n2 (and becomes unavailable) to avoid inconsistency among the three nodes, like a bank. AP: keeps accepting reads (possibly stale) and writes on n1 and n2, then syncs the data to n3 once the partition is resolved.

3. With N = 3, which W and R give strong consistency? Which configuration optimizes reads?

Any W + R > 3, for example W = 2, R = 2, because the read set and write set must overlap in at least one replica holding the latest data. R = 1, W = N (= 3) optimizes reads.

4. With W = 1, is the data only stored on one replica?

No. The coordinator sends the write to all N replicas. W = 1 only means it reports success after the first acknowledgment, which lowers latency but weakens consistency.

5. Version A has clock ([s0,1],[s1,2]) and version B has ([s0,2],[s1,1]). Which one wins?

Neither. B is ahead on s0, A is ahead on s1, so neither is an ancestor of the other. They are siblings in conflict, and the client must reconcile them.

6. In the book's example, D5 is written by Sx after merging D3 and D4. What is D5's vector clock and why?

D5([Sx,3],[Sy,1],[Sz,1]). The merged version keeps the highest counters from both parents ([Sx,2],[Sy,1],[Sz,1]), and since Sx handles the write, it increments its own counter from 2 to 3.

7. Why is gossip preferred over all-to-all multicasting for failure detection?

All-to-all sends heartbeats between every pair of nodes, which becomes inefficient with many servers. Gossip has each node share its membership list with a few random nodes, which spreads information with far fewer messages and is decentralized.

8. A server is down for 2 minutes during a reboot. Which techniques keep writes flowing and bring it back up to date?

Sloppy quorum: writes use the first W healthy servers on the ring, so a stand-in accepts writes. Hinted handoff: the stand-in keeps them with a hint and pushes them back when the server returns.

9. Two replicas each hold a billion keys. How do Merkle trees avoid sending all of them to compare?

Keys are grouped into buckets, each bucket is hashed, and hashes are combined up to a root. Compare roots; if they match, done. If not, descend only into children whose hashes differ, until you find the mismatched buckets. Only those buckets are synced, so the transfer is proportional to the differences, not the data size.

10. A read misses the memory cache. How does the node avoid opening every SSTable?

It checks each SSTable's Bloom filter. If the filter says "definitely not", that SSTable is skipped. Only SSTables whose filter says "maybe" are read. A false positive just costs one extra read; there are no false negatives.

Cheat sheet

  • API: put(key, value), get(key). Requirements: pairs <10 KB, big data, high availability, scalability, auto scaling, tunable consistency, low latency.
  • Single server: in-memory hash table + compression + hot data in memory. Runs out of space fast.
  • CAP: pick two of C, A, P. P is mandatory, so CP (bank: block writes) or AP (accept writes, sync later). CA does not exist in practice.
  • Partition with consistent hashing: even spread, minimal movement, automatic scaling, virtual nodes for heterogeneity.
  • Replicate: walk clockwise, first N unique servers, in distinct data centers.
  • Quorum: coordinator waits for W write acks / R read responses. W + R > N = strong; R=1,W=N = fast reads; W=1,R=N = fast writes.
  • Consistency models: strong, weak, eventual. This design: eventual, like Dynamo and Cassandra.
  • Vector clocks: [server, counter] per version. All counters >= means ancestor; otherwise siblings (conflict, client resolves). Downsides: client complexity, size growth (threshold).
  • Failure detection: gossip with heartbeat counters; mark down if not increased for a period, confirmed by others.
  • Temporary failures: sloppy quorum + hinted handoff. Permanent: anti-entropy with Merkle trees (sync only differing buckets). Data center outage: cross-DC replication.
  • Write path: commit log, then memory cache, then flush to SSTable when full.
  • Read path: memory cache; on miss, Bloom filter picks candidate SSTables; read them; return.
