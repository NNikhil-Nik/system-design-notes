Chapter 11

Design a News Feed System

When you open Facebook, Instagram or Twitter, you see a scrolling list of your friends' latest posts. That list is the news feed. This chapter shows how to build one for 10 million daily users: how a new post reaches friends' feeds, and how a feed loads in a fraction of a second.

~35 min readIntermediatePrerequisites: Ch1 (scaling), Ch4 (rate limiter), Ch10 (queues)

The big picture

The book quotes Facebook's help page: "News feed is the constantly updating list of stories in the middle of your home page. News Feed includes status updates, photos, videos, links, app activity, and likes from people, pages, and groups that you follow on Facebook." Similar products include Facebook's news feed, Instagram's feed and Twitter's timeline.

The system has two jobs, and almost the whole chapter is about doing each one fast:

1. Feed publishing

When you post, the post is saved and made to appear in your friends' feeds.

2. News feed building

When you open the app, the system assembles your friends' posts, newest first, and shows them to you.

The core tension: one post must show up in up to 5,000 friends' feeds, and people read feeds far more often than they post. Do we do the work when someone posts (prepare everyone's feed in advance) or when someone reads (gather posts on demand)? The answer, it turns out, is "it depends on who posted", and that is the heart of this chapter.

Real-world analogy

Imagine a newspaper delivery service. Option A (push): every time a writer publishes an article, a courier immediately drops a copy into the mailbox of every subscriber. Reading is instant: just open your mailbox. But if a famous columnist has 10 million subscribers, the couriers are overwhelmed for hours. Option B (pull): nothing is delivered; each reader walks to every writer's office to collect new articles when they want to read. No wasted deliveries, but reading is slow. Real feed systems mix both: couriers deliver articles from ordinary writers, while the famous columnist's articles are picked up by readers themselves when they open the paper.

A separate program with one responsibility, such as the post service or the fanout service.
Cache
Fast in-memory storage (for example Redis or Memcached) holding copies of frequently used data.

Deliver the post to all friends' feed caches at the moment it is published.
Fanout on read (pull model)
Do nothing at publish time; gather recent posts from friends when a user loads the feed.

When one key or user (for example a celebrity) causes a huge, uneven amount of work or traffic.
Hybrid approach
Use push for most users and pull for celebrities with very many followers.
Consistent hashing
A way to spread data and requests across servers evenly so hot users do not overload one server (Chapter 5).
Graph database
A database built to store relationships, such as "A is friends with B". Good for friend lists and recommendations.
Message queue
A waiting line that holds jobs until workers process them.
Fanout workers
Servers that take jobs from the queue and write post IDs into friends' news feed caches.
Hydrate
Turn bare IDs into full objects: look up the post text, author name, profile picture and so on.
CDN
Content delivery network: servers around the world that store copies of images and videos close to users for fast loading.
Cache miss
When requested data is not in the cache and must be fetched from the slower database.
Sharding
Splitting a database's data across many machines, each holding a part (Chapter 1).
Replication / read replica
Keeping copies of a database on other machines. A master handles writes; replicas serve reads.
Stateless web tier
Web servers that keep no user data between requests, so any server can handle any request.
QPS
Queries per second: how many requests the system handles each second.
Latency
How long a request takes to complete.

Step 2a: Newsfeed APIs

The news feed APIs are the main way clients talk to servers. They are HTTP based and let clients publish a post, retrieve the feed, add friends and so on. The book focuses on two.

Feed publishing API

POST /v1/me/feed
Params:
  content:    content is the text of the post
  auth_token: it is used to authenticate API requests

Newsfeed retrieval API

GET /v1/me/feed
Params:
  auth_token: it is used to authenticate API requests

/v1 is the API version, so the format can change later without breaking old apps. me means "the logged-in user", worked out from the auth_token, so a user cannot post to someone else's feed by changing an ID in the URL.

Example: Alice taps "Post" with "Just finished my first marathon!". Her app sends POST /v1/me/feed with that content and her token. Later Bob opens the app, which sends GET /v1/me/feed with Bob's token and gets back a list of posts as JSON.

Step 2b: Feed publishing, high-level design

Feed publishing
One publish request triggers three things in parallel: save the post, push it into friends' feeds, and alert friends.

Web servers

Notification service
Informs friends that new content is available and sends out push notifications (this is the system from Chapter 10).

Why split publishing and reading?

They have very different loads and speed needs. Reads happen far more often and must feel instant. Keeping them as separate flows lets each be scaled and tuned on its own.

Step 3a: Deep dive into feed publishing: web servers

Besides talking to clients, web servers enforce two protections before any post enters the system:

Authentication

Only users signed in with a valid auth_token are allowed to make posts. A request without a valid token is rejected.

Rate limiting

The system limits the number of posts a user can make within a certain period. This is vital to prevent spam and abusive content. (See Chapter 4.)

Example: a spam bot tries to post 500 times in a minute. The token check identifies the account, and a rate limit of, say, 10 posts per minute (an illustrative value) rejects the rest with an error, so the fanout service never wastes effort pushing spam into millions of feeds.

Step 3b: Fanout service, push vs pull

Fanout is the process of delivering a post to all friends. There are two models, and the choice is the most important decision in the chapter.

Fanout on write (push model)

With this approach, the news feed is pre-computed during write time. A new post is delivered to friends' caches immediately after it is published.

Fanout on read (pull model)

The news feed is generated during read time. It is an on-demand model: recent posts are pulled when a user loads her home page.

Where the work happens: push vs pull
Push does the work once per post, ahead of time. Pull does the work every time a feed is opened.

Push model: pros and cons

Pros

  • The news feed is generated in real time and can be pushed to friends immediately.
  • Fetching the news feed is fast because it is pre-computed during write time.

Cons

  • If a user has many friends, fetching the friend list and generating news feeds for all of them is slow and time consuming. This is called the hotkey problem.
  • For inactive users or those who rarely log in, pre-computing news feeds wastes computing resources.

Pull model: pros and cons

Pros

  • For inactive users or those who rarely log in, it works better: no resources are wasted on them.
  • Data is not pushed to friends, so there is no hotkey problem.

Cons

  • Fetching the news feed is slow because it is not pre-computed.

Step 3c: The celebrity (hotkey) problem, worked example

Let us put numbers on why push breaks for celebrities. These are illustrative figures to show the shape of the problem, not numbers from the book.

Two things jump out:

  1. Delay. If the fanout workers can do 100,000 cache writes per second, one celebrity post takes 100 seconds to reach the last follower. Meanwhile other users' posts queue behind it.
  2. Waste. Most of those writes go into feeds of people who will not even open the app today.

With pull for the celebrity, publishing costs one write (save the post). Each follower who actually opens the app does one small extra lookup ("any new posts from celebrities I follow?"). If 4 million followers open the app, that is 4 million cheap reads of the same, highly cacheable post instead of 10 million writes up front.

One post, millions of feeds
The "hot key": one user's post generates an enormous, lopsided amount of write work.

Step 3d: The hybrid approach

The book adopts a hybrid: since fetching the news feed fast is crucial, use a push model for the majority of users. For celebrities or users who have many friends/followers, let followers pull news content on demand to avoid system overload. Consistent hashing is a useful technique to mitigate the hotkey problem, because it distributes requests and data more evenly.

Hybrid feed: pushed posts + pulled celebrity posts
Ordinary friends' posts are already in Bob's feed cache. Posts from the few celebrities Bob follows are fetched when he opens the app, then merged in reverse chronological order.

Interview tip

Interviewers love asking "what counts as a celebrity?" A good answer: a configurable threshold on follower count. Users above it skip push fanout. You can also skip pushing to inactive followers to cut waste further.

Step 3e: The fanout service, step by step

Fanout service internals
The fanout service figures out who should see the post, then hands the actual writing to workers via a queue.
  1. Fetch friend IDs from the graph database. Graph databases are suited for managing friend relationships and friend recommendations. Example: Alice's friends are u-2, u-3 and 298 others.
  2. Get friends info from the user cache, then filter. The system filters out friends based on user settings. For example, if you mute someone, their posts will not show in your feed even though you are still friends. Posts may also be shared only with a specific group of friends, or hidden from other users.
  3. Send the friends list and new post ID to the message queue. This decouples the fanout service from the slow part, the writing, and absorbs bursts.
  4. Fanout workers fetch data from the message queue and store news feed data in the news feed cache.
  5. Store <post_id, user_id> in the news feed cache. You can think of the cache as a mapping table. Whenever a new post is made, it is appended to the news feed table.

Why store only IDs?

The memory consumption would be very large if we stored entire user and post objects in the cache. If Alice's post (text, author name, profile picture URL) were copied into 300 feeds, that is 300 copies of the same data; and if Alice edited her post, all copies would need updating. Storing only IDs keeps each entry tiny, and the full post lives in one place (the post cache).

Why a configurable limit?

To keep memory size small, a configurable limit is set on how many IDs each user's feed holds. The chance of a user scrolling through thousands of posts in the news feed is slim. Most users are only interested in the latest content, so the cache miss rate is low. If someone does scroll very far back, the system can fall back to the database for older items.

Feel the savings (illustrative)

Suppose one feed entry (two 8-byte IDs) is about 16 bytes and the limit is 500 entries. That is about 8 KB per user, or about 80 GB for 10 million users: it fits comfortably in a cluster of cache servers. Storing full 1 KB posts instead would be 64 times bigger.

Step 6: the fully hydrated feed returns to the client as JSON; the app then loads media files from the CDN.
  1. Request. A user sends a request to retrieve her news feed: /v1/me/feed.
  2. Load balancer redistributes requests to web servers.
  3. Web servers call the news feed service to fetch news feeds.
  4. Get post IDs. The news feed service gets a list of post IDs from the news feed cache.
  5. Hydrate. A user's news feed is more than a list of IDs. It contains username, profile picture, post content, post image and so on. So the news feed service fetches the complete user and post objects from caches (user cache and post cache) to construct the fully hydrated news feed.
  6. Return. The fully hydrated news feed is returned in JSON format to the client for rendering.

Media content (images, videos) is stored in a CDN for fast retrieval. The JSON only contains URLs pointing to the CDN, so the heavy files come from a server near the user.

Example of a hydrated item the client might receive (illustrative):

Why split into tiers?

Different data changes at different speeds and is read in different patterns. Counters change constantly; post content rarely changes; the hot cache needs extra copies to handle viral traffic. Splitting lets each be tuned on its own instead of one giant cache trying to do everything.

Step 4: Wrap up

We designed publishing and retrieval. Like any system design question, there is no perfect answer; every company has unique constraints. The key is to discuss trade-offs. If time remains, the book suggests talking about scalability:

Scaling the database

  • Vertical vs horizontal scaling: a bigger machine versus more machines. Vertical has a hard ceiling; horizontal is how you grow without limit.
  • SQL vs NoSQL: relational databases give strong structure and joins; NoSQL stores scale out more easily for simple access patterns like "feed for user X".
  • Master-slave replication: one master takes writes, copies are kept on slaves.
  • Read replicas: since feeds are read-heavy, serve reads from replicas to spread load.
  • Consistency models: replicas may lag a little behind the master, so a reader might briefly see slightly old data. For a feed, that is usually acceptable (eventual consistency).
  • Database sharding: split data across machines, for example by user ID.

Other talking points

Keep web tier stateless

Any server can serve any request, so you add servers freely behind the load balancer.

Cache data as much as you can

The five cache tiers make reads fast and protect the databases.

Support multiple data centers

Serve users from nearby locations and survive a whole data center failing.

Loosely couple with message queues

The fanout queue lets publishing stay fast while workers catch up.

Monitor key metrics

For example, QPS during peak hours and latency while users refresh their news feed.

Putting it all together

Full news feed system
Left side: publishing. Right side: retrieval. Both share the load balancer, stateless web servers and cache tier.

Walkthrough: Alice posts, Bob reads

  1. Alice posts. POST /v1/me/feed with content and her auth_token goes through the load balancer to a web server, which authenticates her and checks her post rate limit.
  2. Save. The post service stores the post in the post DB and post cache, producing post ID p-901.
  3. Fan out. Alice is not a celebrity, so the fanout service gets her friend IDs from the graph DB, filters out friends who muted her using the user cache, and puts the friend list plus p-901 onto the message queue.
  4. Write IDs. Fanout workers append <p-901, friend_id> to each friend's news feed cache entry, trimming each list to the configured limit.
  5. Notify. In parallel, the notification service may push "Alice shared a post" to friends' phones.
  6. Bob reads. GET /v1/me/feed reaches the news feed service. It reads Bob's post IDs from the news feed cache (p-901 is near the top) and, under the hybrid model, pulls recent posts from celebrities Bob follows, then merges them newest first.
  7. Hydrate and return. It looks up post content, author names and pictures, like counts and whether Bob liked each post from the cache tiers, and returns JSON. Bob's app then downloads Alice's photo from the CDN.

Common mistakes

Choosing pure push without mentioning celebrities

Push-only collapses on accounts with millions of followers. Always raise the hotkey problem and the hybrid fix.

Storing full posts in every feed

Duplicating post and user objects into each follower's feed wastes huge amounts of memory. Store <post_id, user_id> and hydrate on read.

Building the feed with a giant database query on every read

Pure pull with "SELECT posts from all 5,000 friends ORDER BY time" on every refresh is slow. Precompute for most users.

Forgetting filters and privacy

Muted friends and posts shared with only some friends must be filtered during fanout.

Serving images and videos from your web servers

Media belongs in a CDN; the feed JSON just holds URLs.

Skipping auth and rate limiting on publish

Without them, spammers can flood millions of feeds through the fanout service.

Test yourself

1. What are the two main flows of a news feed system?

Feed publishing (saving a post and delivering it to friends' feeds) and news feed building (assembling and returning a user's feed when they open it).

2. What are the two APIs, and what parameters do they take?

POST /v1/me/feed with content and auth_token to publish; GET /v1/me/feed with auth_token to retrieve.

3. Define fanout on write and fanout on read in one sentence each.

Fanout on write precomputes feeds by pushing a new post into friends' feed caches at publish time. Fanout on read builds the feed on demand by pulling friends' recent posts when the user loads it.

4. Give two drawbacks of the push model.

The hotkey problem: users with many friends/followers make fanout slow and expensive. And it wastes resources precomputing feeds for inactive users who rarely log in.

5. Scenario: a pop star with 20 million followers posts. Using pure push at 100,000 cache writes per second, roughly how long until the last follower's feed updates? What should you do instead?

20,000,000 / 100,000 = 200 seconds, while blocking other fanout work. Use the hybrid model: do not push the star's posts; followers pull them at read time, where the post is served from the hot cache.

6. What does the fanout service do in its first two steps?

It fetches friend IDs from the graph database, then gets friends' info from the user cache and filters based on settings, for example muted friends or posts shared only with certain friends.

7. Why does the news feed cache store only IDs, and why is a size limit acceptable?

Full objects would use far too much memory and duplicate data. A configurable limit is fine because most users only look at the latest content; few scroll through thousands of posts, so the cache miss rate stays low.

8. What does "hydrate" mean in step 5 of retrieval?

Turning bare post IDs into full feed items by fetching user objects (name, profile picture) and post objects (content, image) from the user and post caches.

9. Name the five cache tiers and one thing each stores.

News feed (post IDs), content (post data, with a hot cache for popular posts), social graph (followers/following), action (liked, replied), counters (like, reply, follower, following counts).

10. Scenario: feed reads are overloading your post database. Name three remedies from the wrap-up.

Add read replicas (master-slave replication), cache more aggressively (content and hot cache tiers), and shard the database horizontally. Also accept eventual consistency on replicas, since slightly stale feeds are fine.

Cheat sheet

  • Scope: web + mobile, publish + view friends' posts, newest first, up to 5,000 friends, 10M DAU, text + images + video.
  • APIs: POST /v1/me/feed (content, auth_token), GET /v1/me/feed (auth_token).
  • Publishing: LB, web servers, then post service (post cache + DB), fanout service (news feed cache), notification service.
  • Building: LB, web servers, news feed service, news feed cache.
  • Web servers enforce authentication and post rate limiting.
  • Push (fanout on write): fast, real-time reads; hotkey problem and waste on inactive users.
  • Pull (fanout on read): no waste, no hotkey; slow reads.
  • Hybrid: push for most, pull for celebrities; consistent hashing spreads hot keys.
  • Fanout: graph DB friend IDs, user cache filter (muted, restricted), queue, workers write <post_id, user_id>.
  • Store IDs only, cap feed length; low miss rate because people read recent posts.
  • Retrieval: get IDs, hydrate from user + post caches, return JSON; media via CDN.
  • Cache tiers: news feed, content (hot cache), social graph, action, counters. Scale DB with replicas + sharding; stateless web tier; monitor QPS and latency.
