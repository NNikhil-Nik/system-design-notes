Chapter 12

Design a Chat System

Chat apps like WhatsApp, Slack and Discord feel simple: you type, your friend sees it instantly. Under the hood they need a special kind of always-open connection, servers that remember who is connected where, a storage system that can hold billions of messages forever, and a clever way to show who is online. This chapter builds all of that from scratch.

~35 min readAdvancedPrerequisites: Ch1 (scaling basics), Ch6 (key-value store), Ch7 (unique ID generator)

The big picture

Most of the web works like a vending machine: you (the client) press a button (send a request), and the machine (the server) gives you something back (a response). The server never walks up to you on its own. That model breaks down for chat. When your friend sends you a message, the server needs to push it to you right away, even though you did not ask for anything at that exact moment.

So the core problem of this chapter is: how do we let a server push data to millions of phones and browsers in real time, reliably, and store every message forever? Along the way we answer smaller questions:

  • Which network protocol should the client and server use? (Polling, long polling or WebSocket?)
  • Which parts of the system can be "stateless" (any server can handle any request) and which must be "stateful" (a specific server holds your connection)?
  • What database fits chat history, which grows forever and is read mostly from the newest end?
  • How do we generate message IDs that sort by time?
  • How do we keep your phone and laptop in sync?
  • How does the green "online" dot work without flickering every time you go through a tunnel?
Real-world analogy

Think of the chat service as a post office with telephone operators. Two people never hand letters to each other directly; they always go through the post office (the chat service). The post office keeps a copy of every letter in a giant archive (the key-value store). If the recipient currently has an open phone line to the post office (a WebSocket connection), an operator reads the letter to them instantly. If they are not on the line, the post office sends a postcard saying "you have mail" (a push notification). A receptionist (service discovery) decides which operator each caller is connected to, and a notice board (presence servers) shows who is currently on the phone.

There are several kinds of chat apps, and the right design depends on which one you build:

1-on-1 chat

Apps like Facebook Messenger, WeChat and WhatsApp focus on private conversations between two people (plus groups).

Office chat

Apps like Slack focus on group chat inside a company: channels, teams, threads.

Large group / community

Apps like Discord focus on large groups and low-latency voice chat for communities and gamers.

Key idea

Because "chat app" can mean so many things, the very first thing you must do in an interview is pin down exactly what kind of chat app the interviewer wants. Everything else follows from that.

Key terms

Client
The app running on the user's device: a mobile app or a web page in a browser.

The backend system that receives messages from senders, stores them and relays them to recipients. Clients never talk to each other directly.
HTTP
The standard request/response protocol of the web. The client always starts the conversation; the server only answers.
Keep-alive
An HTTP header that tells the server to keep the underlying network connection open for reuse, so the client does not pay the cost of a new TCP handshake for each request.
TCP handshake
The small back-and-forth exchange needed to open a network connection. Doing it over and over is wasteful.
Polling
The client asks the server "anything new?" at a fixed interval (for example every few seconds), even if nothing happened.
Long polling
The client asks "anything new?" and the server holds the request open until a message arrives or a timeout passes, then the client immediately asks again.
WebSocket
A protocol that gives a persistent, two-way (bidirectional) connection between client and server. Either side can send data at any time. It starts life as an HTTP request that is "upgraded".
Bidirectional
Data can flow in both directions (client to server and server to client) over the same connection.
Persistent connection
A connection that stays open for a long time instead of being closed after one request.
Stateless service
A service that does not remember anything about a client between requests. Any server behind the load balancer can handle any request.
Stateful service
A service where a specific server holds information about a client (here: the open WebSocket connection). The client sticks to that server.
Load balancer
A component that spreads incoming requests across many servers.
Service discovery
A component that tells a client which server it should connect to, based on criteria such as location and server load.
Apache ZooKeeper
A popular open-source tool used for service discovery: it keeps a registry of all available chat servers and picks the best one for a client.
Presence
Whether a user is online or offline (the green dot).
Heartbeat
A small periodic "I am still here" message sent by the client so the server knows it is alive.
Push notification
A message delivered to a phone by the operating system (Apple / Google push services) even when the app is not open.
Key-value (KV) store
A database that stores data as key → value pairs, like a giant dictionary. Easy to scale horizontally. Examples: HBase, Cassandra.
Horizontal scaling
Adding more machines to handle more load (as opposed to buying a bigger machine, which is vertical scaling).
Long tail
The rarely accessed older data. In chat, old messages are seldom read but must still be available.
Primary key (PK)
The column (or columns) that uniquely identify a row in a table.
Composite primary key
A primary key made of more than one column, e.g. (channel_id, message_id).

A per-user queue (think "inbox") that collects messages waiting to be delivered to that user.

A 64-bit unique ID format (from Chapter 7) whose first bits are a timestamp, so IDs sort by time.

A variable each device keeps: the largest message ID it has already received. Used to fetch only newer messages.
Fan-out
Sending one event (a message, or a status change) to many recipients.
Publish-subscribe (pub/sub)
A messaging pattern where publishers post events to a channel and every subscriber of that channel receives them.
SPOF
Single point of failure: one component whose failure brings down the whole system.
End-to-end encryption
Encryption where only the sender and recipient can read a message; even the chat service cannot.

Step 2: How clients and the server talk

First principle: clients do not talk to each other directly. Each client connects to the chat service, which supports three jobs:

  1. Receive messages from clients. The sender pushes a message to the chat service.
  2. Find the right recipients and relay the message. The service figures out who should get it and delivers it.
  3. Hold messages for offline recipients. If a recipient is not online, the service stores the message until they come back.

The chat service sits in the middle of every conversation. It stores the message, then forwards it to the receiver (or keeps it until the receiver comes online).

Sending is easy, receiving is hard

Sender side: when you send a message, your client starts the conversation, which is exactly what HTTP is good at. Your app opens an HTTP connection and sends the message. The keep-alive header lets the client reuse this connection so it does not redo the TCP handshake for every message. Many popular chat apps (Facebook, for example) originally used HTTP for sending.

Receiver side: this is the tricky part. HTTP is client-initiated: the server cannot just reach out and hand you a message. We need a way for the server to deliver messages the moment they arrive. Over the years three techniques have been used: polling, long polling and WebSocket.

Option 1: Polling

With polling, the client periodically asks the server: "Are there new messages for me?" The server answers either "yes, here they are" or "no". Then the client waits a few seconds and asks again.

Polling sequence
The client keeps asking on a timer. The more often it asks, the faster it notices messages, but the more server resources it burns on empty answers.

Pros

  • Very simple: just plain HTTP requests on a timer.
  • Works everywhere.

Cons

  • Costly: depending on the polling frequency, most answers are "no", wasting server resources.
  • Trade-off between delay (poll rarely) and waste (poll often).

Option 2: Long polling

Long polling fixes the waste. The client sends a request, and the server holds it open until either a new message arrives or a timeout is reached. When the client gets a response (message or timeout), it immediately sends a new request. So there is almost always one request "waiting" at the server.

Long polling sequence
The server parks the request until something happens. This cuts down empty responses, but the connection is still restarted after each answer.

Long polling still has real drawbacks, and the book lists three:

Sender and receiver may be on different servers

HTTP servers are usually stateless and sit behind a round-robin load balancer. The server that receives the sender's message may not be the server holding the receiver's long-poll request.

Can't tell if a client disconnected

The server has no good way to know whether a client is gone or just quietly waiting for the poll to return.

Inefficient

If a user does not chat much, long polling still makes periodic connections after every timeout.

Option 3: WebSocket (the winner)

WebSocket is the most common solution for sending asynchronous updates from server to client. A WebSocket connection:

  • is initiated by the client, just like HTTP;
  • starts as an HTTP connection and is then "upgraded" to a WebSocket via a well-defined handshake;
  • is bidirectional (both sides can send at any time) and persistent (stays open);
  • works even if a firewall is in place, because it uses port 80 or 443, the same ports used by HTTP/HTTPS.
WebSocket sequence
After one upgrade handshake, the same connection stays open. The server can push to the client whenever it wants, with no repeated requests.

Since WebSocket is bidirectional, there is no strong technical reason not to use it for sending too. Using WebSocket for both sending and receiving simplifies the design and the implementation on both client and server.

Trade-off

WebSocket connections are persistent, so connection management on the server side becomes critical. Each chat server must hold many open connections efficiently, and when a server dies, its users must reconnect elsewhere. This is why chat servers are the one "stateful" part of our design.

Step 2: High-level design

Although WebSocket is the main protocol for chat, not everything needs to be a WebSocket. Signing up, logging in, editing your profile and so on are normal request/response actions and can use plain HTTP. The book splits the system into three categories:

Stateless services

Traditional public-facing request/response services: login, signup, user profile, etc. They sit behind a load balancer which routes requests to the right service. Can be monolithic or microservices. Many can be bought off the shelf.

Stateful service

The chat service. Each client keeps a persistent WebSocket connection to one chat server and normally does not switch servers while that server is available.

Third-party integration

Push notifications. They inform users of new messages even when the app is not running. Covered in depth in Chapter 10.

Stateless services

These are the boring-but-necessary parts. A load balancer receives HTTP requests and routes them to services such as login, signup and user profile. One stateless service deserves special attention: service discovery. Its job is to give the client a list of DNS host names of chat servers that the client could connect to. We dive into it in Step 3.

Stateful service

Each client holds an open WebSocket to exactly one chat server. The service discovery coordinates closely with the chat servers to avoid overloading any one of them.

Third-party integration

For a chat app, push notification is the most important third-party integration. It is how a user learns a new message arrived when the app is closed.

Scalability: why not just one server?

At small scale, all of the services above could fit on one server. Even at our scale, a modern cloud server could in theory hold all user connections in memory. A rough estimate the book makes: with 1M concurrent users and about 10K of memory per connection on the server, you only need about 10GB of memory to hold every connection on one box.

Red flag

Proposing a design where everything lives on one server raises a red flag in an interview. The biggest reason is the single point of failure (SPOF): if that one box dies, nobody can chat. It is fine to start with a single-server design, but say clearly that it is a starting point.

Step 2: Storage

Choosing a database is one of the most important decisions here. Is it a relational database (SQL) or a NoSQL database? To decide, look at what kinds of data we have and how they are read and written.

Two types of data

Generic data

User profiles, settings, user friends lists. Stored in robust, reliable relational databases. Replication and sharding are common techniques to meet availability and scalability needs.

Chat history

The messages themselves. This is unique to chat systems, so we need to understand its read/write pattern before picking a store.

The read/write pattern of chat history

  • The amount of data is enormous. A previous study revealed that Facebook Messenger and WhatsApp process 60 billion messages a day.
  • Only recent chats are accessed frequently. Users usually don't look up old chats.
  • But random access must still work. Search, viewing your mentions, and jumping to a specific message all need to reach older data, so the data layer must support them.
  • The read to write ratio is about 1:1 for 1-on-1 chat apps. Every message written is read about once.
60Bmessages/day (Messenger + WhatsApp)
1:1read:write ratio
Recentchats are the hot data

Why a key-value store

The book recommends a key-value store for chat history, for these reasons:

  1. Easy horizontal scaling. When data grows, add more machines. No painful re-architecture.
  2. Very low latency to access data.
  3. Relational databases do not handle the long tail of data well. When indexes grow large, random access becomes expensive.
  4. Proven in practice. Facebook Messenger uses HBase, and Discord uses Cassandra.
Beginner note

A key-value store is like a giant dictionary spread over many machines: you give it a key (like a message ID) and it returns the value (the message). Because each key lives on one machine chosen by hashing, adding machines simply spreads the keys thinner. See Chapter 6 for how one works inside.

Step 2: Data models and message IDs

Message table for 1-on-1 chat

The primary key is message_id, which also helps decide message order. We cannot rely on created_at to order messages, because two messages can be created at the same moment.

Two message tables
Left: 1-on-1 messages keyed by message_id. Right: group messages keyed by the composite primary key (channel_id, message_id).

Message table for group chat

The composite primary key is (channel_id, message_id). "Channel" and "group" mean the same thing here. channel_id is the partition key because all queries in a group chat operate within one channel: "give me the latest 50 messages of channel 42". Keeping a whole channel's messages together makes that query fast.

Message ID requirements

How do we generate message_id? It must satisfy two requirements:

  • IDs must be unique.
  • IDs should be sortable by time, meaning new rows have higher IDs than old ones.

Three options:

Worked example

In channel 42, messages get local IDs 1001, 1002, 1003. In channel 77, IDs also might be 1001, 1002. That is fine, because the key is (channel_id, message_id): (42, 1001) and (77, 1001) are different rows. All we ever need is "sort messages inside channel 42", and the local counter gives exactly that.

Step 3: Service discovery

The primary role of service discovery is to recommend the best chat server for a client, based on criteria like geographical location and server capacity. Apache ZooKeeper is a popular open-source solution. It registers all available chat servers and picks the best one for each client based on predefined criteria.

How a client gets assigned a chat server
Login goes over HTTP through the load balancer to the API servers. After authentication, service discovery (ZooKeeper) chooses the best chat server and returns its info. The client then opens a WebSocket directly to that server.
  1. User A tries to log in to the app.
  2. The load balancer sends the login request to API servers.
  3. After the backend authenticates the user, service discovery finds the best chat server for User A. In the example, server 2 is chosen and its server info is returned to User A.
  4. User A connects to chat server 2 through WebSocket.
Real-world analogy

Service discovery is like the host at a busy restaurant. You don't pick your own table; the host looks at which waiter has the fewest tables in your section and seats you there. From then on, that waiter serves you.

Step 3: Message flows

Now the core of the chapter: what happens, step by step, when a message is sent. We look at 1-on-1 chat, multi-device sync, and small group chat.

1-on-1 chat flow

1-on-1 message flow
A's message is assigned an ID, queued, stored, and then delivered to B either over B's WebSocket (if online) or as a push notification (if offline).
  1. User A sends a chat message to chat server 1.
  2. Chat server 1 obtains a message ID from the ID generator.
  3. Chat server 1 sends the message to the message sync queue.
  4. The message is stored in a key-value store.
  5. a. If User B is online, the message is forwarded to chat server 2, where User B is connected. b. If User B is offline, a push notification is sent from push notification (PN) servers.
  6. Chat server 2 forwards the message to User B. There is a persistent WebSocket connection between User B and chat server 2.
Why this works

Notice how this solves the long-polling problem "sender and receiver are on different servers". Chat server 1 does not need to hold B's connection; it hands the message to the queue, and the system routes it to whichever chat server B is connected to (chat server 2).

Message synchronization across multiple devices

Many users have several devices. Suppose User A is logged in on a phone and a laptop. Each device has its own WebSocket to chat server 1. How does each device know which messages it is missing?

Each device keeps a variable called cur_max_message_id: the ID of the latest message it has seen. A message is considered new for a device when both conditions hold:

  • The recipient ID equals the currently logged-in user ID.
  • The message ID in the key-value store is larger than cur_max_message_id.

Because each device has its own cur_max_message_id, each device can independently fetch exactly the messages it lacks from the KV store.

Multi-device sync
Each device tracks the highest message ID it has seen and asks only for messages addressed to the user with a larger ID.

Small group chat flow

Group chat is more complicated than 1-on-1. Suppose there are 3 members in a group: User A, User B and User C. When User A sends a message, the message is copied to each group member's message sync queue: one for User B and one for User C. You can think of the message sync queue as an inbox for a recipient.

Group chat: sender side (fan-out on write)
User A's single message is written into the inbox (message sync queue) of every other group member.

This design is good for small group chat because:

  • It simplifies message sync: each client only needs to check its own inbox to get new messages.
  • When the group is small, storing a copy in each recipient's inbox is not too expensive.

WeChat uses a similar approach, and it limits a group to 500 members. For groups with a lot of users, storing a copy of the message for each member is not acceptable (100,000 members would mean 100,000 copies of every message).

On the recipient side, a single user's inbox receives messages from multiple senders: your inbox collects messages from every group and person you talk to.

Group chat: recipient side
User C's inbox collects messages from both User A and User B, even though they are on different chat servers.

Copy-to-every-inbox: pros

  • Simple sync: each client reads one inbox.
  • Fast reads.
  • Cheap when groups are small (here, at most 100 members).

Copy-to-every-inbox: cons

  • Writes multiply by group size.
  • Unacceptable for very large groups: too much storage and write traffic.

Step 3: Online presence

The online indicator (the little green dot next to a friend's name) is an essential feature of many chat apps. In the high-level design, presence servers manage online status and talk to clients over WebSocket. Four things can change a user's status:

1. User login

After the WebSocket connection is built between the client and the real-time service, User A's online status and last_active_at timestamp are saved in the KV store. The presence indicator shows the user is online.

3. User disconnection

We all wish our internet were perfectly stable, but it isn't. When a user disconnects, the persistent connection is lost. A naive approach: mark the user offline the instant the connection drops, and back online when it reconnects. The problem: users disconnect and reconnect to the internet frequently in a short time, for example when driving through a tunnel. Updating status on every disconnect/reconnect would make the green dot flicker constantly and give a bad user experience.

The solution is a heartbeat mechanism. Periodically, an online client sends a heartbeat event to presence servers. If presence servers receive a heartbeat within a certain time, say x seconds, from the client, the user is considered online. Otherwise it is offline. In the book's example, the client sends a heartbeat every 5 seconds; after sending 3 heartbeat events, the client disconnects and does not reconnect within x = 30 seconds, so its status is changed to offline.

Heartbeat timeline: why it avoids flicker
Green dots are heartbeats sent every 5 seconds. A short gap (scenario 1) is forgiven. Only when no heartbeat arrives for 30 seconds (scenario 2: last heartbeat at 10s, offline at 40s) is the user marked offline.
Trade-off

A shorter timeout shows offline status sooner but flickers more on bad networks. A longer timeout is smoother but leaves people looking "online" for a while after they really left. 5-second heartbeats with a 30-second timeout is the book's example balance.

4. Online status fan-out

How do User A's friends learn when A's status changes? Presence servers use a publish-subscribe model, in which each friend pair maintains a channel. When User A's online status changes, it publishes the event to three channels: A-B, A-C and A-D. Those three channels are subscribed by User B, C and D respectively, so it is easy for friends to get online status updates. Communication between clients and servers is through real-time WebSocket.

Presence fan-out with pub/sub channels
A's status change is published once per friend channel; each friend subscribed to their channel with A receives it over WebSocket.

This works well for a small user group. WeChat uses a similar approach because its user group is capped at 500. For larger groups, informing every member about online status is expensive and time consuming. Assume a group has 100,000 members: each status change generates 100,000 events. To solve the performance bottleneck, a possible solution is to fetch online status only when a user enters a group or manually refreshes the friend list.

Worked example

Group of 100,000 members. If each member goes online or offline just twice a day, that's 200,000 status changes, each fanned out to 100,000 people: 20 billion events a day for one group. Pulling status on demand ("show me who is online in this group right now") avoids almost all of that.

Step 4: Wrap up

We built a system that supports 1-on-1 and small group chat, using WebSocket for real-time communication between client and server. If there is extra time, the book suggests these talking points:

Media files

Extend the app to support photos and videos. Media is much bigger than text. Discuss compression, cloud storage, and thumbnails.

End-to-end encryption

WhatsApp supports it for messages. Only the sender and recipient can read messages. Interested readers can look at the references in the book.

Caching messages on the client

Storing messages on the client side reduces data transfer between client and server.

Improve load time

Slack built a geographically distributed network to cache users' data, channels, etc. for better load time.

Error handling: chat server error

There may be hundreds of thousands of persistent connections or more to one chat server. If a chat server goes offline, service discovery (ZooKeeper) provides a new chat server for clients to establish new connections with.

Error handling: message resend

Retry and queueing are common techniques for resending messages.

The complete design: stateless HTTP services for account actions, stateful chat and presence servers for real-time traffic, queues + KV store for messages, and push notifications for offline users.

Walkthrough: User A sends "Hi" to User B

  1. Login. A's app sends a login request over HTTP. The load balancer forwards it to an API server, which authenticates A.
  2. Server assignment. Service discovery (ZooKeeper) picks the best chat server for A, say chat server 1, based on location and load, and returns it.
  3. Connect. A opens a WebSocket to chat server 1. Presence servers write status=online, last_active_at=now to the KV store and publish "A is online" to channels A-B, A-C, ...
  4. Send. A types "Hi" and it travels up the WebSocket to chat server 1.
  5. ID. Chat server 1 gets a time-sortable message ID (Snowflake or a local per-channel sequence).
  6. Queue + store. The message goes into the message sync queue and is persisted in the KV store forever.
  7. Deliver. B is online on chat server 2, so the message is forwarded there and pushed down B's WebSocket. If B were offline, notification servers would send a push notification instead.
  8. Other devices. A's laptop sees its cur_max_message_id is behind and pulls the new message too, so A's own history is in sync everywhere.
  9. Heartbeats. Meanwhile both clients send heartbeats every 5 seconds. If B's phone goes silent for 30 seconds, presence marks B offline and notifies B's friends.

"Why not store messages in MySQL?"
"The volume is huge, for reference Messenger and WhatsApp handle about 60 billion messages a day, and we keep history forever. Reads are mostly recent messages but we still need random access for search and jumping to messages. Relational databases get expensive on random access once indexes grow large. A key-value store scales horizontally with low latency; Facebook uses HBase and Discord uses Cassandra for this."

"Instead of reacting to every connection drop, clients send a heartbeat every 5 seconds. A user is only marked offline if no heartbeat arrives for, say, 30 seconds. Short blips are forgiven."
"What if a group had 100,000 members?"
"Copying each message into 100,000 inboxes and fanning out presence to 100,000 people would be too expensive. That approach is right for small groups, WeChat caps at 500. For huge groups, I'd fetch presence only when a user opens the group or refreshes, rather than pushing every change."

"Not by created_at, since two messages can share a timestamp. message_id must be unique and time-sortable. Common mistakes

Designing everything on one server

Even if the memory math says one machine could hold all connections, it's a single point of failure. Start simple if you like, but scale out before you finish.

Using plain HTTP or polling to receive messages

HTTP is client-initiated; polling wastes resources. Explain the progression to WebSocket and why.

Making every service a WebSocket

Login, signup and profile updates are normal request/response actions. Keep them stateless behind a load balancer.

Ordering messages by created_at

Two messages can be created at the same time. Use a unique, time-sortable message_id.

Assuming auto_increment exists

NoSQL key-value stores usually don't provide it. Propose Snowflake or a local per-channel sequence.

Marking users offline on every disconnect

That causes flicker. Use heartbeats and a timeout.

Applying the small-group fan-out to huge groups

Copying messages to every inbox and pushing every presence change only works for small groups. Call out the limit.

Forgetting offline users and multiple devices

Always say what happens when the recipient is offline (push notification) and how a second device catches up (cur_max_message_id).

Test yourself

1. Why is plain HTTP a poor fit for receiving chat messages?

HTTP is client-initiated: the server can only answer requests, it cannot start a conversation. A chat server needs to push a message to the recipient the moment it arrives, which HTTP alone cannot do.

2. Give the three drawbacks of long polling from the book.

(1) Sender and receiver may be connected to different (stateless, round-robin) chat servers, so the server receiving the message may not hold the receiver's connection. (2) The server can't tell if a client has disconnected. (3) It's inefficient: users who rarely chat still make periodic connections after every timeout.

3. Why does WebSocket usually work even behind corporate firewalls?

It starts as an HTTP connection and is upgraded via a handshake, and it uses ports 80 or 443, the same ports as HTTP/HTTPS, which firewalls normally allow.

4. Which parts of the system are stateful, and why?

The chat servers (the chat service). Each client holds a persistent WebSocket to one specific chat server and normally sticks with it, so that server "holds state" for the client. Login, signup and profile are stateless and can be served by any server behind a load balancer.

5. Why choose a key-value store for chat history over a relational database?

Easy horizontal scaling, very low latency, and relational databases handle the long tail of data poorly: random access becomes expensive as indexes grow. It's proven in practice: Facebook Messenger uses HBase, Discord uses Cassandra.

6. What is the primary key of the group message table, and why is channel_id the partition key?

(channel_id, message_id). All queries in a group chat operate within a channel ("latest messages in channel X"), so partitioning by channel keeps those messages together for fast reads.

7. Scenario: your phone has cur_max_message_id = 500. Messages to you with IDs 480, 510 and 530 are in the KV store. What does the phone fetch?

510 and 530. A message is new for this device if the recipient is the logged-in user and its ID is greater than cur_max_message_id. 480 has already been seen.

8. Scenario: heartbeats every 5 seconds, timeout 30 seconds. A user's last heartbeat is at t = 12s and they never come back. When are they marked offline? What if they reconnect at t = 30s?

Offline at about t = 42s (12 + 30). If they reconnect and send a heartbeat at t = 30s, only 18 seconds passed, so they stay online the whole time with no flicker.

9. Why does copying each message into every member's inbox work for this design but not for a 100,000-member group?

With at most 100 members, storing a copy per recipient is cheap and makes sync simple (each client reads only its inbox). With 100,000 members, every message becomes 100,000 writes, which is unacceptable. WeChat uses the inbox approach but limits groups to 500.

10. A chat server crashes. Walk through recovery.

Clients detect the lost connection, go back to service discovery (ZooKeeper), which provides a new chat server. Clients reconnect via WebSocket and pull any missed messages using cur_max_message_id. Undelivered messages are resent using retry and queueing.

Cheat sheet

  • Scope: 1-on-1 + groups up to 100, mobile + web, 50M DAU, text < 100,000 chars, history forever, multi-device, push notifications, presence.
  • Clients never talk directly; the chat service receives, relays and stores messages for offline users.
  • Polling = wasteful; long polling = different-server problem, can't detect disconnects, inefficient; WebSocket = bidirectional, persistent, HTTP upgrade, ports 80/443.
  • Use WebSocket for both sending and receiving; HTTP for login/signup/profile.
  • Stateless services behind a load balancer; stateful chat servers; push notification as third-party integration.
  • One server = SPOF. Scale out chat, presence, API and notification servers.
  • Generic data in relational DB; chat history in a KV store (HBase at Facebook, Cassandra at Discord). 60B messages/day, read:write about 1:1, recent data is hot.
  • 1-on-1 table PK: message_id. Group table PK: (channel_id, message_id), channel_id is the partition key.
  • message_id must be unique and time-sortable: no auto_increment in NoSQL; use Snowflake or a local per-channel sequence.
  • ZooKeeper service discovery picks the best chat server after login; client connects via WebSocket.
  • 1-on-1 flow: chat server, ID generator, message sync queue, KV store, then WebSocket (online) or push notification (offline). Devices sync with cur_max_message_id.
  • Presence: heartbeat every 5 s, offline after 30 s silence; pub/sub channel per friend pair; for huge groups fetch status on enter/refresh.
