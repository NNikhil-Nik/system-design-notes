Chapter 8

Design a URL Shortener

A URL shortener turns a long, ugly web address into a tiny one like https://tinyurl.com/y7keocwj. When someone clicks the short link, they are sent on to the original page. It sounds simple, but designing one teaches you hashing, base 62 encoding, HTTP redirects, caching and how to handle a database with hundreds of billions of rows.

~30 min readBeginnerPrerequisites: Ch 1 (scaling basics), Ch 2 (estimation), Ch 7 (unique ID generator)

The big picture

Long URLs are hard to share. They break across lines in emails, they do not fit in a text message, and nobody can remember them. A URL shortener solves this with two jobs:

  1. Shortening. You give it a long URL. It gives you back a short alias (a short URL).
  2. Redirecting. When anyone visits the short URL, the service looks up the long URL and tells the browser to go there.

That is the whole product. The interesting part is doing it for 100 million new URLs every day, keeping the short part as short as possible, and answering every click quickly.

Real-world analogy

Think of a coat check at a theatre. You hand over a big, bulky coat (the long URL) and get back a small numbered ticket (the short URL). Later, anyone holding that ticket can walk up to the counter, and the attendant looks up the number and hands back the coat (the redirect). The ticket is tiny, but it reliably points at something big. The coat check needs two things to work: a way to hand out unique ticket numbers, and a fast way to find a coat given a number. This chapter is about exactly those two things.

Why interviewers love it

The scope is small enough to finish in 45 minutes, yet it touches estimation, API design, HTTP, hashing, databases and caching.

What you will learn

How 301/302 redirects work, how to pick a short-code length with math, two ways to generate codes (hash vs base 62), and how to scale reads with a cache.

Key insight

Reads outnumber writes 10 to 1. Almost every design decision is about making the redirect (read) path fast.

Key terms

URL
Uniform Resource Locator, a web address such as https://www.example.com/page.
Long URL
The original address a user wants to shorten.
Short URL / alias
The compact address the service hands back, e.g. https://tinyurl.com/zn9edcu.
Hash value / short code
The few characters after the domain (zn9edcu) that identify one long URL.
Hash function
A function that turns any input (like a long URL) into a fixed-size output. The same input always gives the same output.
Collision
When two different inputs produce the same hash output. Two long URLs would then fight over one short code.
CRC32, MD5, SHA-1
Well-known hash functions. CRC32 outputs 8 hex characters, MD5 outputs 32, SHA-1 outputs 40.
Base 62
A way of writing numbers using 62 symbols (0-9, a-z, A-Z) instead of the usual 10 digits. Bigger base means shorter strings.
HTTP redirect
A server response telling the browser "the thing you want is somewhere else; go here instead".
301 Moved Permanently
A redirect status meaning the move is permanent. Browsers cache it and stop asking the shortener.
302 Found
A redirect status meaning the move is temporary. Browsers keep asking the shortener every time.
Location header
The part of a redirect response that contains the address the browser should go to.
API endpoint
A URL on the server that clients call to perform an action, like POST api/v1/data/shorten.
REST
A common style for web APIs where you use HTTP verbs (GET, POST) on resource URLs.
QPS
Queries per second, how many requests the system handles each second.
Bloom filter
A compact, space-efficient data structure that answers "is X definitely not in the set, or maybe in it?". Fast, but can give false positives.
Cache
Fast memory storage (e.g. Redis, Memcached) that keeps popular data so you avoid slow database lookups.
Load balancer
A machine that spreads incoming requests across many web servers.
Stateless web tier
Web servers that keep no user data locally, so you can add or remove them freely.
Replication
Keeping copies of a database on several machines for safety and read speed.
Sharding
Splitting one big database into smaller pieces (shards), each holding part of the data.
Rate limiter
A component that blocks clients sending too many requests (Chapter 4).
Unique ID generator
A service that hands out globally unique numbers, e.g. Twitter Snowflake (Chapter 7).

Basic use cases

  1. URL shortening - given a long URL, return a much shorter URL.
  2. URL redirecting - given a short URL, redirect to the original URL.
  3. High availability, scalability and fault tolerance - the usual non-functional goals.

Back-of-the-envelope estimation

"Back-of-the-envelope" means rough math you could do on scrap paper. The goal is not precision; it is to know the scale so you pick sensible technology. Let us do it one step at a time.

  1. Write operations per day. Given: 100 million URLs are shortened per day.
  2. Writes per second. A day has 24 x 3600 = 86,400 seconds. 100,000,000 / 86,400 = about 1,160 writes per second. (The exact result is 1,157; the book rounds to 1,160.)
  3. Reads per second. Assume the read-to-write ratio is 10:1, meaning each short URL is clicked about 10 times for every time one is created. 1,160 x 10 = 11,600 reads per second.
  4. Total records over 10 years. Assume the service runs for 10 years. 100 million x 365 days x 10 years = 365 billion records.
  5. Storage. Assume an average URL is 100 bytes long. 365 billion x 100 bytes = 36.5 trillion bytes, which is 365 TB.
Checking the storage unit

The book writes the storage as 365 billion x 100 bytes x 10 years = 365 TB. Note that the "10 years" is already inside the 365 billion figure, so the clean computation is 365 x 109 x 100 bytes = 3.65 x 1013 bytes, roughly 36.5 TB. The book's 365 TB is a deliberately generous (rounded-up) figure. In an interview, show your working and say which one you mean; the point is "tens to hundreds of terabytes - far too big for one machine's memory".

What the numbers tell us

365 billion records will not fit in memory, so we need a real database. 11,600 reads per second is much larger than 1,160 writes per second, so the read path (redirecting) deserves a cache. And 365 billion distinct codes tells us how long the short code must be.

Step 2 - High-level design

We will look at three things: the API endpoints, how redirecting works, and how shortening works.

API endpoints

An API endpoint is the "door" that clients knock on. We follow REST style and need just two:

PurposeRequestParametersReturns

RedirectGET api/v1/shortUrlThe short URL in the pathThe longURL for HTTP redirection

We use POST for shortening because it creates something new on the server. We use GET for redirecting because it only reads.

POST /api/v1/data/shorten
Content-Type: application/json

{ "longUrl": "https://en.wikipedia.org/wiki/Systems_design" }

--- response ---
200 OK
{ "shortUrl": "https://tinyurl.com/zn9edcu" }

URL redirecting

When you type a tinyurl link into a browser, here is what happens. The shortener server does not send you the page. Instead, it sends back a tiny response saying "go over there", with the long URL in the Location header. The browser then makes a second request to the real site.

The redirect exchange
The shortener only answers step 2. It returns a status code (301 or 302) and a Location header. The browser follows the Location header on its own.

301 vs 302: which redirect to use?

Both codes redirect the user, but they differ in one important way: does the browser remember the answer?

301 Moved Permanently

"This URL has moved for good." The browser caches the response. The next time the user clicks the same short URL, the browser goes straight to the long URL and never contacts the shortener again.

302 Found

"This URL has moved temporarily." The browser does not cache it. Every click goes back to the shortener first, which then redirects again.

301 (permanent)302 (temporary)

Choose it whenPriority is reducing server loadAnalytics are important (click rate, source of clicks)
Interview tip

There is no single "right" answer. Say: "If the goal is to reduce server load, I would pick 301. If analytics such as click rate and source tracking matter, I would pick 302." Stating the trade-off is what earns credit.

The simplest way to implement redirecting is with a hash table that stores <shortURL, longURL> pairs:

  1. Get longURL: longURL = hashTable.get(shortURL)
  2. Redirect: once you have the longURL, perform the URL redirect.

URL shortening

Suppose the short URL looks like www.tinyurl.com/{hashValue}. To support shortening, we need a hash function fx that maps a long URL to the hashValue.

The hash function idea

The function must satisfy two rules: each longURL maps to exactly one hashValue, and each hashValue can be mapped back to its longURL.

The requirements for the hash function are:

  • Each longURL must be hashed to one hashValue.
  • Each hashValue can be mapped back to the longURL.

How to actually build that function is the main topic of the deep dive.

Step 3 - Deep dive: data model

In the high-level design, everything lived in a hash table. A hash table in memory is a great starting point, but it fails in real life for two reasons:

In-memory hash table: good

  • Very simple to code
  • Extremely fast lookups

In-memory hash table: bad

  • Memory is limited and expensive - hundreds of TB will not fit
  • If the server restarts, everything in memory is lost

The better option is to store the <shortURL, longURL> mapping in a relational database. The table is simple, with three columns:

The url table
One row per shortened URL. "PK" means primary key: a column whose value uniquely identifies the row. In the base 62 approach, shortURL is derived from id.

Hash value length

The hashValue is made of characters from [0-9, a-z, A-Z]: 10 + 26 + 26 = 62 possible characters. How long must it be?

Think about it like a combination lock. A lock with 1 dial of 10 digits has 10 combinations. 2 dials give 10 x 10 = 100. With n dials and 62 symbols per dial, there are 62n combinations. We need enough combinations to give every one of our 365 billion URLs its own code. So we find the smallest n such that 62n ≥ 365 billion.

Answer: 7 characters

With n = 6 we can only make about 56.8 billion codes, which is not enough. With n = 7 we can make about 3.5 trillion, comfortably above 365 billion. So the hashValue length is 7.

Now we look at two ways to produce that 7-character value: hash + collision resolution, and base 62 conversion.

Approach 1: hash + collision resolution

The first idea is to use a well-known hash function. Here is what three of them output for the same input, https://en.wikipedia.org/wiki/Systems_design:

Hash functionHash value (hexadecimal)Length
CRC325cb540548 chars
MD55a62509a84df9ee03fe1230b9df8b84e32 chars
SHA-10eeae7916c06853901d9ccbefbfcaf4de57ed85b40 chars

Even the shortest one, CRC32, is longer than 7 characters. The obvious fix is to take the first 7 characters (for CRC32: 5cb5405). But chopping a hash makes collisions more likely: two different long URLs might start with the same 7 characters.

Resolving collisions

When a collision happens, we append a new predefined string to the long URL and hash again, repeating until there is no collision.

Hash + collision resolution flow
Hash, cut to 7 characters, check the database. If the code is already taken, add a predefined string to the long URL and hash again. If it is free, save it.

Worked example. Hash https://en.wikipedia.org/wiki/Systems_design with CRC32, take 5cb5405. Suppose that code already belongs to another URL. We append a predefined string (call it X) to get https://en.wikipedia.org/wiki/Systems_designX, hash that, take the first 7 characters, and check again. Because the input changed, the output is completely different, and it is very likely free.

The cost: a database lookup per write - and the Bloom filter fix

This method removes collisions, but it is expensive: every time we create a short URL we must query the database to check whether the code already exists. A Bloom filter can speed this up.

What is a Bloom filter?

A Bloom filter is a long row of bits (all 0 at first) plus a few hash functions. To add an item, you hash it with each function and set those bit positions to 1. To check an item, you hash it again and look at those positions. If any bit is 0, the item is definitely not in the set. If all are 1, it is probably in the set (it might be a false positive). It uses far less memory than storing the actual items, so it fits in RAM. For the shortener: if the Bloom filter says "definitely not seen", we skip the database check entirely.

Bloom filter in a nutshell
Any 0 among the checked bits means "definitely new". All 1s means "maybe exists - go confirm with the database".

Approach 2: base 62 conversion

Base conversion means writing the same number using a different set of digits. We normally count in base 10 (digits 0-9). Computers also use base 2 (0-1) and base 16 (0-9, a-f). Base 62 uses 62 symbols, so each character carries more information and the string gets shorter.

The idea: give every URL a unique number (its id) first, then write that number in base 62. That base 62 string is the short code. Since ids are unique, codes are unique - no collisions possible.

The base 62 alphabet

Value0 ... 910 ... 3536 ... 61
Character0 ... 9a ... zA ... Z

So 0 = '0', 9 = '9', 10 = 'a', 35 = 'z', 36 = 'A', and 61 = 'Z'.

Worked example: convert 11157 to base 62

Convert by repeatedly dividing by 62 and keeping the remainders - exactly how you would convert a number to binary, but dividing by 62 instead of 2.

  1. 11157 / 62 = 179, remainder 59. Check: 179 x 62 = 11098, and 11157 - 11098 = 59. Value 59 maps to X (36 = A, so 59 = A + 23 = X).
  2. 179 / 62 = 2, remainder 55. Check: 2 x 62 = 124, 179 - 124 = 55. Value 55 maps to T (36 + 19).
  3. 2 / 62 = 0, remainder 2. Value 2 maps to 2. The quotient is now 0, so we stop.
  4. Read the remainders bottom to top: 2, 55, 59 → 2 T X = "2TX".
Repeated division by 62
Read the characters from the bottom up: 11157 in base 10 = "2TX" in base 62. The short URL becomes https://tinyurl.com/2TX.

To go back, multiply out: 2 x 622 + 55 x 621 + 59 x 620 = 7688 + 3410 + 59 = 11157.

Pseudocode

ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"

function encode(id):              # number -> short code
    if id == 0: return "0"
    s = ""
    while id > 0:
        s = ALPHABET[id % 62] + s  # prepend the remainder's character
        id = id / 62               # integer division
    return s

function decode(code):            # short code -> number
    id = 0
    for ch in code:
        id = id * 62 + ALPHABET.indexOf(ch)
    return id

encode(11157)  # "2TX"
decode("2TX")  # 11157

Why "guessable" matters

If ids go 11157, 11158, 11159..., the codes go 2TX, 2TY, 2TZ... Anyone can enumerate them and visit every link people have shortened, including private ones. In an interview, mention this and suggest a mitigation such as non-sequential IDs.

The book uses base 62 conversion in its design.

URL shortening deep dive

As one of the core parts of the system, the shortening flow should be logically simple and functional. Here is the flow using base 62:

URL shortening flow
If the long URL was already shortened, return the existing short URL. Otherwise get a fresh unique ID, encode it in base 62, and store the new row.
  1. Input longURL. The client calls POST api/v1/data/shorten.
  2. Check the database. Is this longURL already stored?
  3. If yes, it was converted before. Fetch its shortURL from the database and return it. (This avoids creating many codes for the same page.)
  4. If no, the longURL is new. The unique ID generator creates a new unique ID (primary key).
  5. Convert the ID to a shortURL with base 62.
  6. Create a new row in the database with the ID, shortURL and longURL.

Worked example from the book

  • Input longURL: https://en.wikipedia.org/wiki/Systems_design
  • Unique ID generator returns: 2009215674938
  • Convert the ID to base 62: zn9edcu
  • Save to the database: id = 2009215674938, shortURL = zn9edcu, longURL = https://en.wikipedia.org/wiki/Systems_design
Why we need a distributed ID generator

The ID must be globally unique even when many web servers are creating URLs at the same time across machines. A simple auto-increment column on one database does not work well in a distributed environment. That is why we use a generator like Twitter's Snowflake from Chapter 7.

URL redirecting deep dive

Since there are 10 times more reads than writes, the <shortURL, longURL> mapping is stored in a cache to improve performance. Popular links (say, one shared in a viral tweet) are read over and over; serving them from memory avoids hitting the database each time.

URL redirecting flow
Check the cache first. Only on a cache miss do we query the database, then put the result in the cache so the next click is fast.
  1. A user clicks a short URL link: https://tinyurl.com/zn9edcu.
  2. The load balancer forwards the request to one of the web servers.
  3. If the shortURL is already in the cache, return the longURL directly.
  4. If it is not in the cache, fetch the longURL from the database. If it is not in the database either, the user probably entered an invalid short URL (return an error such as 404).
  5. The longURL is returned to the user (as a redirect) - and stored in the cache for next time.
Why caching works so well here

The data never changes (no updates or deletes allowed), so cached entries never go stale. That removes the hardest part of caching - invalidation. This is a nice point to raise in an interview.

Step 4 - Wrap up

If there is extra time at the end of the interview, here are talking points the book suggests:

Rate limiter

A malicious user could send an overwhelming number of shortening requests. A rate limiter (Chapter 4) filters out requests based on IP address or other rules.

Web server scaling

The web tier is stateless, so it is easy to scale by adding or removing web servers behind the load balancer.

Database scaling

Replication (copies for reads and safety) and sharding (splitting the 365 billion rows across machines) are common techniques.

Analytics

Data is increasingly important. Integrating an analytics solution answers questions like how many people click a link and when. (Remember 302 helps here.)

Availability, consistency, reliability

These are core to any large system's success. Revisit Chapter 1 for the techniques (redundancy, failover, multiple data centers).

Walkthrough 1: shortening a URL

  1. Client sends POST api/v1/data/shorten with longUrl = https://en.wikipedia.org/wiki/Systems_design.
  2. Rate limiter checks the client is not flooding us, and the load balancer picks a web server.
  3. Web server checks the database: has this longURL been shortened before? No.
  4. ID generator returns 2009215674938.
  5. Base 62 encode gives zn9edcu.
  6. Save the row and return https://tinyurl.com/zn9edcu.

Walkthrough 2: clicking the short URL

  1. Browser sends GET https://tinyurl.com/zn9edcu.
  2. Load balancer routes it to any web server (they are all identical).
  3. Web server checks the cache for zn9edcu. First click: miss. It reads the database and fills the cache.
  4. Server responds with a 301 or 302 and Location: https://en.wikipedia.org/wiki/Systems_design.
  5. Browser follows the Location header to Wikipedia. Later clicks by others hit the cache directly; with 301, repeat clicks by the same browser skip us entirely.

Common mistakes

Skipping the length math

Saying "I'll use 6 or 7 characters" without justifying it. Always show 62n ≥ 365 billion and conclude n = 7.

Ignoring collisions

Proposing "MD5 and take 7 characters" without saying what happens when two URLs share a prefix. Truncated hashes collide; you must check and resolve.

Picking 301 or 302 without a reason

Both are valid. The interviewer wants to hear the trade-off: server load (301) vs analytics accuracy (302).

Storing everything in memory

A hash table is fine for the high-level sketch, but with 365 billion records you need a durable database plus a cache.

Using a single auto-increment column for IDs

It becomes a bottleneck and single point of failure across many servers. Reference the distributed ID generator from Chapter 7.

Forgetting the read-heavy ratio

Designing only the write path. The 10:1 ratio means the redirect path and its cache matter most.

Test yourself

1. With 100 million new URLs per day, roughly how many writes per second is that?

About 1,160. A day has 86,400 seconds, and 100,000,000 / 86,400 is about 1,157, rounded to 1,160.

2. Why is the short code 7 characters long?

We need at least 365 billion unique codes. With 62 symbols, 626 is about 56.8 billion (too few) and 627 is about 3.5 trillion (enough). So 7 is the smallest length that works.

3. Convert 11157 to base 62.

11157 / 62 = 179 r 59 ('X'); 179 / 62 = 2 r 55 ('T'); 2 / 62 = 0 r 2 ('2'). Reading remainders bottom-up gives "2TX".

4. The marketing team wants to know how many times each link is clicked. Which redirect code do you choose?

302. With 301, browsers cache the redirect, so repeat clicks never reach the server and are not counted. 302 sends every click through the shortener, making tracking accurate - at the cost of more server load.

5. What happens to the browser's later requests after it receives a 301?

The browser has cached the permanent redirect, so it goes directly to the long URL without contacting the shortener.

6. Why can CRC32 + "take first 7 chars" produce collisions, and how does the book resolve them?

Truncating a hash throws away information, so two different URLs can share the same first 7 characters. The fix is to append a predefined string to the long URL and hash again, repeating until the code is unused in the database.

7. How does a Bloom filter help the hash approach?

Checking the database for every new code is expensive. A Bloom filter in memory can say "definitely not present" quickly, letting us skip the database query in most cases. It may give false positives ("maybe present"), in which case we confirm with the database.

8. Name one advantage and one disadvantage of base 62 conversion versus hashing.

Advantage: collisions are impossible because each ID is unique. Disadvantage: it depends on a unique ID generator, and if IDs increase by 1 the next short URL is easy to guess (security concern). Also, the length is not fixed.

9. A user submits a long URL that was already shortened last week. What does the system do?

The shortening flow first checks whether the longURL is in the database. It is, so the service returns the existing shortURL instead of generating a new ID.

10. Why is caching especially easy in this system?

Short URLs cannot be updated or deleted, so a cached mapping is always correct. There is no cache invalidation problem, and the 10:1 read ratio means the cache absorbs most traffic.

Cheat sheet

  • Two features: shorten (POST api/v1/data/shorten) and redirect (GET api/v1/shortUrl).

  • 10 years → 365 billion records; at 100 bytes each the book estimates 365 TB.
  • 62 characters (0-9, a-z, A-Z); 627 ≈ 3.5 trillion ≥ 365 billion → 7 chars.
  • 301 = permanent, browser caches, less load. 302 = temporary, every click hits us, better analytics.
  • Redirect response carries the long URL in the Location header.
  • Store mappings in a relational DB table (id, shortURL, longURL), not just memory.
