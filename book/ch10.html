Chapter 10

Design a Notification System

Almost every app you use sends you alerts: a bank text when money leaves your account, an email receipt after a purchase, a push banner when a friend messages you. This chapter shows how to build one system that sends millions of those alerts every day, through several different channels, without losing them and without spamming people.

~30 min readIntermediatePrerequisites: Ch1 (scaling basics), Ch4 (rate limiter)

The big picture

A notification is a short message that a system sends to a user to tell them something important happened, such as "Your order has shipped" or "Payment of $40 received". The message is not something the user asked for right now; the system decides to send it.

The book focuses on three kinds of notification:

Mobile push notification

The banner that pops up on your phone's lock screen, even when the app is closed. Works on iOS and Android.

SMS message

A plain text message sent to a phone number. Works on any phone, even without an app or internet data.

Email

A message delivered to an inbox. Good for longer content like receipts, newsletters and reports.

Why is this a design problem at all? Sending one email is easy. Sending 16 million messages a day across three channels, reliably, while respecting users who opted out, without sending duplicates, and without one slow provider holding up everything else, is hard. That is what we design here.

One important idea runs through the whole chapter: we do not deliver the messages ourselves. Apple delivers iOS pushes, Google delivers Android pushes, companies like Twilio deliver SMS and companies like SendGrid deliver email. Our job is to be a reliable "dispatcher" that hands each message to the right delivery company.

Real-world analogy

Think of a company's mailroom. Departments (billing, shipping, marketing) drop off letters. The mailroom does not drive trucks across the country. Instead it sorts the letters into bins: one for FedEx, one for the postal service, one for a courier. Each bin has its own clerk who hands letters to that carrier. If FedEx is slow today, only the FedEx bin piles up; the postal letters still go out. The mailroom also keeps a log book of every letter, so if a carrier loses one it can be sent again. Our notification system is that mailroom: services are the departments, message queues are the bins, workers are the clerks, and APNs, FCM, Twilio and SendGrid are the carriers.

Key terms

Notification
A short message sent by a system to a user to alert them about an event.
Push notification
A message shown on a phone or computer by the operating system, even when the app is not open.
Provider
In this chapter, the server that builds a notification request and sends it to Apple or Google. Our notification servers play this role.
APNs
Apple Push Notification service. Apple's service that delivers push notifications to iPhones and other Apple devices.
FCM
Firebase Cloud Messaging. Google's service that delivers push notifications to Android devices.
Device token
A unique ID string that identifies one app installed on one device. Needed to send a push to that exact device.
Payload
The actual content of a message, usually written in JSON (a simple text format of keys and values).
Third-party service
A company outside ours whose service we use, for example Twilio for SMS or SendGrid for email.
Soft real-time
The message should arrive quickly, but a small delay (seconds, occasionally more) under heavy load is acceptable.
API server
A server that accepts requests over the network through a defined interface (an API) and responds to them.
Message queue
A waiting line for messages. Producers put messages in, consumers take them out later. It lets two parts of a system work at different speeds.
Worker
A server process that pulls jobs from a queue and does the work, here: sending a notification to a third-party service.
Decouple
To separate two components so that a slowdown or failure in one does not directly break the other.
Single point of failure (SPOF)
One component whose failure brings down the whole system.
Auto scaling
Automatically adding or removing servers based on load.
Cache
Fast, in-memory storage holding copies of frequently read data so we do not hit the slower database every time.
Notification log
A database table where every notification is stored before sending, so it can be retried if something fails.
At-least-once delivery
A guarantee that a message will be delivered one or more times. It will not be lost, but it might occasionally be duplicated.
Exactly-once delivery
Each message is delivered one time, never zero, never twice. Very hard to guarantee in distributed systems.
Dedupe (deduplication)
Detecting and dropping repeated copies of the same message, usually by checking a unique event ID.
Template
A pre-written message format with blanks (parameters) filled in for each user, like a form letter.
Opt in / opt out
A user choosing to receive (opt in) or not receive (opt out) a type of notification.
Rate limiting
Capping how many requests or messages are allowed in a time window (see Chapter 4).
appKey / appSecret
A pair of credentials (like a username and password for software) that a client service must present to use our API.
Metrics / monitoring
Numbers collected about the system (for example queue length) and watched so we can react to problems.
Analytics service
A system that records events such as "opened" or "clicked" to measure how users respond.

A quick back-of-the-envelope estimate

The book does not dwell on this, but it helps you feel the scale. A day has 86,400 seconds.

  • 16,000,000 / 86,400 is about 185 notifications per second on average.
  • Traffic is never flat. If peak is, say, 5 times the average, that is roughly 1,000 per second at peak (an illustrative assumption, not a book number).
  • Push alone: 10,000,000 / 86,400 is about 116 per second on average.
What these numbers tell us

A few hundred messages per second is not enormous for a modern server, but bursts matter. A marketing campaign could ask for 5 million emails in a few minutes. That is why the design leans on queues: they absorb bursts so the system does not fall over.

Step 2a: How each notification type works

Before designing our own system, we need to know how notifications physically reach a device. Each channel has its own chain of parties.

iOS push notification

Three parties are involved:

  1. Provider This is us. A provider builds the notification request and sends it to Apple. To do that it needs two things: a device token (who to send to) and a payload (what to send).
  2. APNs Apple's remote service. It receives our request and pushes the notification to the iPhone. Only Apple can wake up an iPhone to show a banner, so we must go through APNs.
  3. iOS device The end client, the user's iPhone or iPad, which displays the notification.

The device token is a unique identifier for "this app on this phone". When the user installs the app and allows notifications, the app gets the token from Apple and sends it to our servers, which store it. Without it, we cannot address a push.

The payload is a JSON dictionary describing the notification. The book shows an example like this:

Step 2c: Initial high-level design (and why it is not enough)

Now the sending flow. Start with the simplest thing that works, then improve it. That is exactly what interviewers want to see.

Initial design: one notification system
Services (billing, shipping, alerts...) call one notification server, which builds payloads and calls each provider directly. The red box is the weak spot.

Pieces of the initial design:

  • Service 1 to N: any internal service that wants to notify users. Examples: a micro-service, a cron job (a task that runs on a schedule), or a distributed system. A billing service that sends payment-due reminders, or a shopping site that tells customers their package arrives tomorrow.
  • Notification system: the centerpiece. It offers APIs for services to call and builds the payload for each third-party service. In this first version it is a single server.
  • Third-party services: APNs, FCM, SMS and email providers. A design point the book stresses: build with extensibility in mind so a provider can be plugged in or swapped out easily. Also, a provider might not be available in some markets; the book's example is that FCM is unavailable in China, where alternatives such as Jpush or PushY are used.
  • iOS, Android, SMS, email: where the user receives the message.

Three problems with the initial design

Single point of failure

There is only one notification server. If it crashes, no notification goes out, for any service, on any channel.

Hard to scale

The one server handles everything: it talks to the database, the cache, and does all the sending. You cannot scale those parts independently.

Performance bottleneck

Processing and sending is slow and resource heavy: building HTML pages, waiting for third-party responses. Doing it all in one box overloads it, especially at peak hours.

Why waiting on third parties hurts

Calling Twilio or APNs is a network round trip. If a call takes 200 ms and the server handles requests one after another while waiting, it is mostly idle-but-busy. If one provider gets slow (say email takes 5 seconds), and push and email share the same server threads, push messages get stuck behind slow emails. One slow channel drags down all channels.

Step 2d: Improved high-level design

The book makes three changes to fix those problems:

  1. Move the database and cache out of the notification server. Storage becomes its own layer, shared by all notification servers. Now servers are interchangeable and hold no unique data.
  2. Add more notification servers and set up automatic horizontal scaling. Several identical servers behind a load balancer remove the single point of failure. When load rises, auto scaling adds more.
  3. Introduce message queues to decouple the system components. Servers do not send directly. They drop each notification into a queue, and separate workers do the slow sending.

Example API for sending an email

The book gives an example of the API a service calls. It is an internal HTTP endpoint (something like POST https://api.example.com/v/email/send; the exact path is not important) with a JSON request body similar to:

{
  "to": [
    { "user_id": 123456 }
  ],
  "from": {
    "email": "from_address@example.com"
  },
  "subject": "Hello, World!",
  "content": [
    { "type": "text/plain", "value": "Hello, World!" }
  ]
}

Notice the caller sends a user_id, not an email address. The notification server looks up the address itself. That keeps contact info in one place and lets the server check opt-out settings.

Walking through the flow, steps 1 to 6

  1. A service calls the API. For example, the shipping service calls the notification server: "tell user 123456 their package shipped".
  2. Fetch metadata. The notification server fetches user info, device tokens and notification settings from the cache, falling back to the database if the cache does not have them.
  3. Put an event in the queue. The server builds a notification event and puts it on the right queue, for example the iOS PN queue. The API can now reply "accepted" to the service immediately, without waiting for Apple.
  4. Workers pull. iOS workers pull notification events from the iOS queue whenever they are free.
  5. Send to the third party. The worker sends the notification to APNs.
  6. Delivered. APNs delivers the notification to the user's iPhone.
Why the queue changes everything

Before: the service waits for the whole chain, including slow third parties. After: the service waits only for "saved to queue", which takes milliseconds. If 5 million emails arrive at once, they simply wait in the email queue while workers drain it at a steady pace. If SendGrid is down, emails pile up in their queue, but iOS pushes keep flowing through their own queue. The queue is the "bin" in our mailroom analogy.

What we gained

  • No single point of failure: many servers, many workers.
  • Each layer scales independently (more workers for email only, if needed).
  • Bursts are absorbed by queues.
  • One provider's outage is isolated to its own queue.

What we paid

  • More moving parts to run and monitor.
  • A small added delay (fine: we only need soft real-time).
  • Messages are now "fire and forget" from the caller's view, so we need tracking to know what happened.

Step 3a: Deep dive into reliability

When notifications matter (a password reset code, a fraud alert), losing them is not acceptable. The book asks two reliability questions.

Question 1: How do we prevent data loss?

One of the most important requirements: notifications can be delayed or re-ordered, but they must never be lost. To achieve this, the notification system persists notification data in a database (a notification log) and implements a retry mechanism.

Notification log + retry
The worker records each notification in the log. If the send fails, the notification is still known and can be retried instead of vanishing.

Concrete example: a worker takes "Your code is 482913" from the SMS queue, writes it to the notification log with status "pending", then calls Twilio. Twilio times out. Because the message is in the log, the system knows it was not sent and tries again. If the worker itself crashed mid-send, a new worker can find the unsent entry in the log.

Question 2: Will recipients receive a notification exactly once?

The short answer is no. Although notifications are delivered exactly once most of the time, the distributed nature of the system could result in duplicates.

Why? Imagine a worker sends an email, SendGrid accepts it, but the "OK" reply is lost on the network. The worker cannot tell "never sent" from "sent but no reply", so it retries. Now the user gets two emails. This is at-least-once delivery: never lost, sometimes doubled.

To reduce duplicates, the book introduces a dedupe mechanism and handles each failure case carefully. A simple dedupe logic:

Dedupe logic from the book

When a notification event first arrives, we check whether it has been seen before by checking the event ID. If it has been seen before, it is discarded. Otherwise, we send out the notification.

Dedupe by event ID
Every event carries a unique ID chosen by the system. A retried copy has the same ID, so it can be caught and dropped.
Dedupe is not perfect

Dedupe greatly reduces duplicates but does not make them impossible. In the lost-reply case above, the third party already delivered the first copy before we knew it. That is why we say "at least once, with best-effort dedupe", never "exactly once". The book points to further reading on why exactly-once delivery is so hard.

Step 3b: Additional components and considerations

Sending is only part of the job. A real notification system also needs templates, settings, rate limits, retries, security, monitoring and tracking.

Notification template

A large notification system sends millions of notifications a day, and many of them look almost identical. A template is a preformatted notification with customizable parameters, styling and tracking links. It avoids building every message from scratch, keeps the format consistent, reduces errors, and saves time. The book's example:

BODY:
You dreamed of it. We dared it. [ITEM NAME] is back — only until [DATE].

CTA:
Order Now. Or, Save My [ITEM NAME]

[ITEM NAME] and [DATE] are blanks filled per message. CTA means "call to action": the button text. Templates live in the database and are cached because they are read constantly.

Notification setting

Users receive far too many notifications and can easily feel overwhelmed. So many sites and apps give users fine-grained control. This information is stored in a notification setting table:

FieldTypeMeaning
user_idbigIntWhich user this setting belongs to.
channelvarcharPush notification, email or SMS.
opt_inbooleanTrue if the user wants to receive notifications on this channel.

Before any notification is sent, we first check whether the user has opted in to receive this type. Example: user 42 has (42, "sms", false). The billing service asks to SMS user 42; the server sees opt_in is false and does not send.

Rate limiting

To avoid overwhelming users with too many notifications, we can limit the number of notifications a user can receive. The book stresses why: if we send too often, users may turn notifications off completely. Example policy: "at most 3 marketing pushes per user per day". This uses the techniques from Chapter 4 (Design a Rate Limiter).

Retry mechanism

When a third-party service fails to send a notification, the notification is added back to the message queue for retrying. If the problem continues, an alert is sent out to developers. In practice, retries are usually spaced out (wait 1 s, then 2 s, then 4 s, known as exponential backoff) so we do not hammer a struggling provider.

Security in push notifications

For iOS or Android apps, appKey and appSecret are used to secure push notification APIs. Only authenticated or verified clients are allowed to send push notifications through our APIs. Without this, anyone who found the endpoint could send spam to all our users.

Monitor queued notifications

A key metric to monitor is the total number of queued notifications. If the number is large, the notification events are not processed fast enough by workers. To avoid delay in delivery, more workers are needed.

Queue depth over time tells you when to add workers
Illustrative: a marketing burst pushes queue depth past the threshold; adding workers drains it back down.

Events tracking

Notification metrics such as open rate, click rate and engagement are important for understanding customer behavior. An analytics service implements events tracking, so integration between the notification system and the analytics service is usually required. The book shows the events a notification can go through:

Each transition is sent to the analytics service. Counting "delivered" vs "click" gives a click rate; "unsubscribe" tells you if you are annoying people. The error-to-pending loop is the retry path (a simplification for clarity).

Step 3c: Updated design

Putting all the extra components together gives the book's updated design. Compared with the improved design, it adds:

  • Authentication and rate limiting in front of the notification servers.
  • Notification templates in the cache/DB, used to render messages.
  • Notification log and a retry path: if a third party fails, the event goes back into the queue.
  • Notification settings checked before sending.
  • Analytics service receiving tracking events from servers, workers and devices (for example clicks).
Updated design (book Step 3)
Servers authenticate and rate limit callers, read settings and templates, then enqueue per channel. Workers send, log, and re-queue failures. Tracking events flow to analytics.

Step 4: Wrap up

Notifications keep users informed about important information. The book's summary of what we built:

  • Reliability: a robust retry mechanism minimizes the failure rate, with a notification log so nothing is lost.
  • Security: appKey/appSecret pairs ensure only verified clients can send notifications.
  • Tracking and monitoring: implemented at every stage of a notification flow to capture important stats.
  • Respect user settings: users may opt out; we check settings before sending.
  • Rate limiting: users appreciate a frequency cap on the notifications they receive.

Throughout, the design leans on message queues to decouple components, absorb bursts and isolate each channel.

  1. Call. The shopping service calls the notification API with its appKey and appSecret and a body containing user_id: 123456 and the order details.
  2. Guard. The server verifies the credentials (security) and checks the caller is within its rate limit.
  3. Look up. It reads user 123456's email address and the "receipt" template from the cache (DB on a miss), and checks the setting row (123456, email, opt_in). Opted in, so continue.
  4. Render and enqueue. It fills in the template, assigns a unique event ID, and puts the event on the email queue. It replies to the shopping service right away. Tracking state: pending.
  5. Work. An email worker pulls the event, checks the event ID has not been seen (dedupe), records it in the notification log, and calls SendGrid. State: sent.
  6. Failure path. If SendGrid errors, the event goes back into the queue for retry; persistent errors alert developers.
  7. Deliver and track. SendGrid delivers it. Delivered, opened and clicked events flow to the analytics service.

Common mistakes

Promising exactly-once delivery

Saying "each user gets every notification exactly once" is a red flag. Say at-least-once with dedupe by event ID, and explain why duplicates can still slip through.

Calling third parties synchronously from the API server

If the API waits on APNs or SendGrid, a slow provider ties up your servers and the calling services. Put a queue in between.

One shared queue for every channel

A single queue means an email outage blocks pushes and SMS. Use one queue per notification type.

Forgetting user settings and rate limits

A design that technically works but ignores opt-outs and frequency caps will annoy users into disabling notifications entirely, which defeats the purpose.

Leaving the API open

Without appKey/appSecret (or similar authentication), anyone who discovers the endpoint can spam your whole user base.

Keeping state inside notification servers

If the server holds the DB or cache locally, you cannot add servers freely. Keep servers stateless and storage separate.

Test yourself

1. What two things does a provider need to send an iOS push notification?

A device token (identifies the app on a specific device, so APNs knows where to deliver) and a payload (the JSON describing the notification content, such as title, body and badge).

2. Why are the user and device tables separate?

Because one user can have multiple devices. Each device has its own token, so the device table has many rows per user linked by user_id, and a push can go to all of them.

3. Name the three problems of the initial single-server design.

Single point of failure (one server down means no notifications), hard to scale (DB, cache and sending are bundled together), and performance bottleneck (slow, resource-heavy processing and waiting on third parties all in one place).

4. What do message queues give us in the improved design?

They decouple notification servers from workers, act as buffers when large volumes are sent, and, with one queue per type, isolate an outage in one third-party service from the other channels.

5. Scenario: SendGrid starts timing out. Walk through what happens to an email notification.

The worker records the notification in the log and attempts the send. On failure the event is put back into the email queue for retry. If the problem persists, developers are alerted. Queue depth grows and monitoring shows it. Push and SMS are unaffected because they use separate queues and workers.

6. Can we guarantee a recipient gets a notification exactly once? Why or why not?

No. If a provider accepts a message but the acknowledgement is lost, the worker cannot tell and retries, causing a duplicate. We aim for at-least-once and reduce duplicates by checking the event ID and discarding events already seen.

7. Which three fields are in the notification setting table, and when is it checked?

user_id, channel and opt_in. It is checked before any notification is sent, so opted-out users never receive that channel.

8. Your dashboard shows the total queued notifications climbing steadily. What does it mean and what do you do?

Workers are not processing events fast enough, so delivery is being delayed. Add more workers (ideally via auto scaling on queue depth). Also check whether a third-party provider is slow, since that also makes the queue grow.

9. Why use notification templates?

Many notifications share the same format. Templates keep formatting consistent, reduce errors and save time; only parameters like [ITEM NAME] and [DATE] change per message.

10. What are the main event states tracked for a notification, and why track them?

Start, pending, sent, delivered, click, plus error and unsubscribe. They feed the analytics service so you can measure open rate, click rate and engagement, and spot when notifications annoy users (unsubscribes).

Cheat sheet

  • Scope: push, SMS, email; soft real-time; iOS, Android, desktop; 10M push + 1M SMS + 5M email per day.
  • We never deliver directly: iOS via APNs, Android via FCM, SMS via Twilio/Nexmo, email via SendGrid/Mailchimp.
  • iOS push needs a device token + JSON payload. One user, many devices: separate user and device tables.
  • Initial single server fails on: single point of failure, hard to scale, performance bottleneck.
  • Fix: DB and cache out of the server, many auto-scaled stateless servers, one message queue per channel, workers.
  • Flow: service calls API, fetch metadata from cache/DB, enqueue, workers pull, send to third party, delivered.
  • Never lose notifications: notification log + retry. Delays and reordering are acceptable.
  • Delivery is at-least-once, not exactly-once; dedupe by event ID.
  • Templates for consistent formatting; settings table (user_id, channel, opt_in) checked before send.
  • Rate limit per user so people do not turn notifications off; appKey/appSecret so only verified clients send.
  • Monitor total queued notifications; add workers when it grows.
  • Track pending, sent, delivered, click, unsubscribe (and errors) in an analytics service.
