Chapter 4

Design a Rate Limiter

A rate limiter is a gatekeeper that decides how many requests a client may send in a given amount of time. Anything above the limit is blocked. This chapter walks through where to put one, the five classic counting algorithms, and how to make it work across many servers at once.

~35 min readIntermediatePrerequisites: Chapters 1 and 3 (servers, caches, the 4-step interview method)

The big picture

Every public web service receives requests: a phone app asks for your feed, a script calls an API, a browser submits a login form. Most clients behave well. Some do not. A buggy script might call the same endpoint thousands of times a second. An attacker might try millions of passwords. A popular partner might accidentally send ten times the normal traffic.

If the service simply accepts everything, one noisy client can slow down or crash the service for everyone. A rate limiter stops that. It counts how many requests each client has sent recently, and once the client passes a threshold, it rejects further requests until enough time has passed.

Some everyday examples of rate limits:

  • A user can write no more than 2 posts per second.
  • You can create a maximum of 10 accounts per day from the same IP address.
  • You can claim rewards no more than 5 times per week from the same device.
Real-world analogy

Think of a popular nightclub with a bouncer at the door. The club can only hold so many people safely, so the bouncer lets in, say, 10 people per minute. If a crowd of 50 shows up at once, the first 10 get in and the rest are told "not right now, try again in a minute." The bouncer does not care who is nice or rude; he just counts. The rate limiter is that bouncer, the club is your API servers, and the crowd is the incoming HTTP requests.

Why bother? The three benefits the book lists

1. Prevent resource starvation from DoS

A Denial of Service (DoS) attack floods a service with requests so real users cannot get through. Almost every big public API enforces limits. For example, Twitter limits the number of tweets to 300 per 3 hours, and Google Docs APIs have a default limit of 300 per user per 60 seconds for read requests. A rate limiter blocks excess calls, whether they are intentional (attacks) or unintentional (bugs).

2. Reduce cost

Fewer excess requests means fewer servers needed, and more resources go to high-priority APIs. This matters a lot when you pay per call to a third-party API, such as checking credit, making a payment, or retrieving health records. Every blocked duplicate call is money saved.

3. Prevent servers from being overloaded

Bots and misbehaving users can generate a huge amount of traffic. A rate limiter filters out the excess so the servers stay healthy for everyone else.

The one-sentence version

A rate limiter answers one question for every incoming request: "Has this client already used up its allowance for this time period?" If yes, reject (HTTP 429). If no, let it through and count it.

Step 1: Understand the problem and establish scope

Rate limiting can be built many different ways, each with its own pros and cons. So, like every design question, we start by asking the interviewer questions. The book's conversation goes roughly like this:

Candidate asksInterviewer answersWhy the question matters

The requirements list

  1. Accurately limit excessive requests. If the rule says 5 per minute, the 6th request must be blocked.
  2. Low latency. Every request passes through the limiter, so it must not slow down HTTP response time noticeably.
  3. Use as little memory as possible. We may track millions of users; each counter must be tiny.
  4. Distributed rate limiting. The limiter can be shared across multiple servers or processes.
  5. Exception handling. Show clear exceptions to users when their requests are throttled.
  6. High fault tolerance. If the limiter has a problem (for example, a cache server goes offline), it must not take the whole system down.
Interview tip

Write these six requirements on the whiteboard. Later, when you pick an algorithm or a storage choice, point back at them: "I'm choosing Redis because of requirement 2, low latency."

The API gateway

In cloud microservice architectures, rate limiting is usually implemented inside a component called an API gateway. An API gateway is a fully managed service that supports rate limiting, SSL termination, authentication, IP whitelisting, serving static content, and more. For now, you only need to know that the API gateway is a middleware that supports rate limiting.

How to choose? The book's guidelines

There is no absolute answer; it depends on your company's tech stack, engineering resources, priorities and goals. The book offers these general guidelines:

  • Evaluate your current technology stack, such as the programming language and cache service. Make sure your language is efficient enough to implement rate limiting on the server side.
  • Pick an algorithm that fits your business needs. If you build it yourself on the server side, you have full control of the algorithm. With a third-party gateway, your choice may be limited.
  • If you already use microservices and have an API gateway for authentication, IP whitelisting and so on, you may add a rate limiter to the gateway.
  • Building your own rate limiting service takes time. If you do not have enough engineering resources, a commercial API gateway is a better option.

Step 2 (continued): The five rate-limiting algorithms

The heart of a rate limiter is the algorithm: the rule for counting requests over time. The book covers five popular ones. They all answer "allow or reject?", but differ in accuracy, memory use and how they treat bursts.

Token bucket

Tokens drip into a bucket; each request spends one. Allows short bursts.

Leaking bucket

Requests wait in a queue and leave at a fixed steady rate.

Fixed window counter

Count requests per clock-aligned window (e.g. each minute).

Sliding window log

Remember the timestamp of every request; count the ones in the last N seconds.

Sliding window counter

Blend the current and previous window counts with a weighted formula.

Algorithm 1: Token bucket

The token bucket algorithm is widely used and simple to understand. The book notes that both Amazon and Stripe use it to throttle their API requests.

How it works

  1. A bucket has a fixed capacity of tokens. Think of tokens as "permission slips."
  2. A refiller adds tokens at a preset rate, for example 2 tokens every second. Once the bucket is full, extra tokens overflow and are thrown away.
  3. Each request consumes one token. When a request arrives, we check whether there is at least one token in the bucket.
  4. If there is a token, we take one out and the request goes through.
  5. If the bucket is empty, the request is dropped.
Token bucket: capacity 4, refiller adds 2 tokens per second
Tokens drip in from the top. A request that finds a token takes it and is forwarded; a request that finds the bucket empty is dropped.

Worked example (the book's timeline)

Bucket size = 4, refill rate = 4 tokens per minute. The bucket starts full.

Token bucket over one minute
Grey squares are empty token slots. Four requests in 20 seconds were fine (a burst), but the 5th within the minute was dropped until the refill.

Notice that the client could send 4 requests almost at once. That is the burst behaviour: as long as tokens are saved up, a quick burst is allowed.

Parameters

  • Bucket size: the maximum number of tokens allowed in the bucket (the biggest burst you accept).
  • Refill rate: the number of tokens put into the bucket every second (the long-run average rate).

How many buckets do we need?

It depends on the rules. The book's examples:

  • It is usually necessary to have different buckets for different API endpoints. If a user may make 1 post per second, add 150 friends per day, and like 5 posts per second, then 3 buckets are required for each user.
  • If we throttle based on IP addresses, each IP address requires a bucket.
  • If the system allows a maximum of 10,000 requests per second overall, it makes sense to have a global bucket shared by all requests.
Implementation detail beginners ask about

No real program has a timer "dripping" tokens. Instead, store two numbers per bucket: tokens and last_refill_time. When a request arrives, compute how much time has passed, add elapsed × refill_rate tokens (capped at bucket size), then try to subtract one. This is cheap and needs no background job.

def allow(bucket, now):
    elapsed = now - bucket.last_refill
    bucket.tokens = min(bucket.size, bucket.tokens + elapsed * bucket.refill_rate)
    bucket.last_refill = now
    if bucket.tokens >= 1:
        bucket.tokens -= 1
        return True      # forward the request
    return False         # reject with 429

Pros

  • Easy to implement.
  • Memory efficient (two numbers per bucket).
  • Allows short bursts of traffic: a request goes through as long as tokens are left.

Cons

  • Two parameters (bucket size and refill rate) can be challenging to tune properly.

Algorithm 2: Leaking bucket

The leaking bucket algorithm is similar to the token bucket, except requests are processed at a fixed rate. It is usually implemented with a first-in-first-out (FIFO) queue. The book notes that Shopify, an e-commerce company, uses leaky buckets for rate limiting.

Real-world analogy

Picture a bucket with a small hole in the bottom. You can pour water in as fast as you like, but it only drips out at one steady speed. If you pour too fast, the bucket overflows and the extra water spills on the floor. Requests are the water; the drip rate is how fast your servers process them.

How it works

  1. A request arrives. The system checks whether the queue is full.
  2. If the queue is not full, the request is added to the queue.
  3. Otherwise, the request is dropped.
  4. Requests are pulled from the queue and processed at regular intervals (the outflow rate), no matter how fast they arrived.
Leaking bucket: queue size 5, outflow 1 request per second
Requests enter on the left and wait their turn. They leave on the right at a constant pace. If every slot is taken, new requests are dropped.

Worked example

Queue size 5, outflow 1 request per second. At time 0, 8 requests arrive at once. Requests 1–5 fill the queue; requests 6–8 are dropped. Over the next 5 seconds, the servers see exactly one request per second. At second 2, two queue slots are free again, so if 2 more requests arrive, they are accepted.

Parameters

  • Bucket size: equal to the queue size. The queue holds the requests to be processed at a fixed rate.
  • Outflow rate: how many requests can be processed at a fixed rate, usually per second.

Pros

  • Memory efficient given the limited queue size.
  • Requests are processed at a fixed rate, so it suits cases where a stable outflow rate is needed.

Cons

  • A burst of traffic fills the queue with old requests; if they are not processed in time, recent requests are rate limited.
  • Two parameters, which might not be easy to tune.
Token bucket vs leaking bucket in one line

Token bucket controls how many requests may start (bursts allowed). Leaking bucket controls how fast requests are processed (output is always smooth).

Algorithm 3: Fixed window counter

How it works

  1. Divide the timeline into fixed-size windows, for example one window per second or per minute, aligned to the clock (1:00:00–1:00:59, 1:01:00–1:01:59, ...).
  2. Give each window a counter starting at 0.
  3. Each request increments the counter of the window it falls into.
  4. Once the counter reaches the threshold, new requests are dropped until a new window starts.

Worked example

Limit: 3 requests per second. In each one-second window, the first 3 requests are allowed and any more are dropped.

The edge-burst problem

The major problem is that a burst of traffic at the edges of two windows can let through more requests than the quota. The book's example: the limit is 5 requests per minute and the counter resets on the round minute.

Fixed window: 10 requests slip through in one minute with a 5/min limit
Each window individually respects the limit of 5. But the dashed one-minute span straddling the boundary contains 10 requests: twice the allowed rate.

Pros

  • Memory efficient (one counter per window).
  • Easy to understand.
  • Resetting available quota at the end of a unit time window fits certain use cases ("10 free downloads per day").

Cons

  • A spike in traffic at the edges of a window can allow more requests than the quota (up to 2× in the worst case).

Algorithm 4: Sliding window log

The sliding window log fixes the edge problem. Instead of clock-aligned windows, the window always means "the last 60 seconds from right now."

How it works

  1. Keep a log of request timestamps for each client. The book notes the data is usually kept in cache, such as a Redis sorted set, with the timestamp as the score.
  2. When a new request comes in, remove all outdated timestamps: those older than the start of the current window (now minus window length).
  3. Add the new request's timestamp to the log.
  4. If the log size is the same or lower than the allowed count, the request is accepted. Otherwise, it is rejected.

Worked example (the book's numbers)

Limit: 2 requests per minute. Timestamps shown as human-readable times (in practice they are Unix timestamps).

Sliding window log with a limit of 2 per minute
Request 3 is rejected but its timestamp still stays in the log. At 1:01:40 the window is [1:00:40, 1:01:40), so the two oldest timestamps are removed and the log size drops back to 2.
  1. 1:00:01 The log is empty, so the request is allowed. Log size 1.
  2. 1:00:30 Timestamp inserted. Log size 2, not larger than 2, so allowed.
  3. 1:00:50 Timestamp inserted. Log size 3, larger than 2, so rejected, even though the timestamp remains in the log.
  4. 1:01:40 Requests in the range [1:00:40, 1:01:40) are within the latest window; anything sent before 1:00:40 is outdated. Two outdated timestamps (1:00:01 and 1:00:30) are removed. Log size becomes 2, so the request is accepted.
# Redis sorted set per client; score = timestamp in ms
ZREMRANGEBYSCORE  log:user42  0  (now - 60000)   # 1. drop old entries
ZADD              log:user42  now  now           # 2. add this request
count = ZCARD     log:user42                     # 3. how many in window?
allow = count <= LIMIT

Pros

  • Very accurate. In any rolling window, requests will not exceed the rate limit.

Cons

  • Consumes a lot of memory: even if a request is rejected, its timestamp might still be stored. A limit of 1,000 per hour means up to 1,000+ timestamps per user.

Algorithm 5: Sliding window counter

This is a hybrid that combines the fixed window counter and the sliding window log. It keeps only two counters per client (cheap like fixed window) but smooths out the edge problem (closer to sliding log).

The formula

Imagine a rolling one-minute window that ends right now. Part of it overlaps the current clock minute and part overlaps the previous one. We assume the previous minute's requests were spread evenly, so we take a proportional share of them:

requests in rolling window =
    requests in current window
  + requests in previous window × overlap percentage of the rolling window and previous window

Worked example (the book's numbers)

Limit: 7 requests per minute. There were 5 requests in the previous minute and 3 in the current minute. A new request arrives at a position 30% into the current minute, so the rolling window overlaps 70% of the previous minute.

Sliding window counter: 30% into the current minute
The rolling window covers the last 70% of the previous minute and the first 30% of the current one. We estimate it holds 3 + 70% of 5 requests.

3 + 5 × 0.7 = 6.5. Depending on the use case, the number can be rounded up or down; the book rounds down to 6. Since the limit is 7, the current request can go through. However, the limit will be reached after receiving one more request.

Pros

  • Smooths out spikes in traffic because the rate is based on the average rate of the previous window.
  • Memory efficient: two counters per client.

Cons

  • It only works for not-so-strict look-back windows. It is an approximation, because it assumes requests in the previous window are evenly distributed.

The book notes that this problem may not be as bad as it seems: according to experiments done by Cloudflare, only 0.003% of requests were wrongly allowed or rate limited among 400 million requests.

Step 2 (continued): High-level architecture

The basic idea of every rate-limiting algorithm is simple: we need a counter to keep track of how many requests are sent from the same user, IP address, etc. If the counter is larger than the limit, the request is disallowed.

Where do we keep the counters?

Using a database is not a good idea because disk access is slow, and we check the counter on every request. An in-memory cache is chosen because it is fast and supports time-based expiration. Redis is a popular option for implementing rate limiting. It offers two commands that do exactly what we need:

INCR

Increases the stored counter by 1. Redis runs it atomically, so two simultaneous INCRs both count.

EXPIRE

Sets a timeout for the counter. When the timeout expires, the counter is automatically deleted, which is perfect for "reset after each window."

High-level architecture
The client sends a request to the middleware. The middleware fetches the counter from the right bucket in Redis and checks whether the limit is reached.
  1. The client sends a request to the rate limiting middleware.
  2. The middleware fetches the counter from the corresponding bucket in Redis and checks if the limit is reached.
  3. If the limit is reached, the request is rejected.
  4. If the limit is not reached, the request is sent to API servers. Meanwhile, the system increments the counter and saves it back to Redis.

Worked example: fixed window with INCR and EXPIRE

Rule: 5 requests per minute per user. User 42 sends a request at 10:15:20.

key   = "rl:user42:10:15"     # user + the current minute
count = INCR key              # 1st request this minute -> 1
if count == 1:
    EXPIRE key 60             # auto-delete after 60 seconds
if count > 5:
    return 429                # 6th, 7th ... requests rejected
forward_to_api_servers()

The 5th request in that minute gets count 5 and passes. The 6th gets count 6 and is rejected. At 10:16:00 a new key rl:user42:10:16 is used, and the old one disappears on its own thanks to EXPIRE. No cleanup job is needed.

The high-level design does not answer two questions: How are rate limiting rules created and stored? And how are rate-limited requests handled? First, the rules.

Reading the YAML

Step 3 deep dive: Exceeding the limit and response headers

What happens to a throttled request?

  • The API returns HTTP response code 429 (Too Many Requests) to the client.
  • Depending on the use case, we may enqueue the rate-limited requests to be processed later. For example, if some orders are rate limited due to system overload, we may keep those orders to be processed later rather than losing a customer's purchase.

Step 3 deep dive: Detailed design

Detailed rate limiter design
Rules live on disk; workers copy them into a cache. The middleware reads rules from the cache and counters from Redis, then forwards, rejects with 429, or enqueues the request.
  1. Rules are stored on the disk. Workers frequently pull rules from the disk and store them in the cache.
  2. A client sends a request to the server; it goes to the rate limiter middleware first.
  3. The middleware loads rules from the cache. It fetches counters and last request timestamps from Redis. Based on the response, it decides:
  4. If the request is not rate limited, it is forwarded to API servers.
  5. If the request is rate limited, the rate limiter returns a 429 error to the client. Meanwhile, the request is either dropped or forwarded to the queue.
Why cache the rules?

Rules change rarely (maybe once a week), but are read on every request (maybe a million times a second). Reading a file from disk a million times a second would be slow, so we read it once into memory and refresh it periodically.

Step 3 deep dive: Rate limiting in a distributed environment

Building a rate limiter for a single server is not hard. Scaling it to support multiple servers and concurrent threads is a different story. There are two challenges: race conditions and the synchronization issue.

Challenge 1: Race condition

At a high level, a counter works like this:

  1. Read the counter value from Redis.
  2. Check if (counter + 1) exceeds the threshold.
  3. If not, increment the counter value by 1 in Redis.

The trouble is that "read, then write" is two separate steps. In a highly concurrent environment, two requests can both read before either writes:

Race condition: two requests, but the counter only goes up by one
Both requests read the value 3 before either wrote. Each adds 1 to its own copy and writes 4. One request is effectively invisible to the limiter, so clients can exceed the limit.

How to fix it:

Locks

The most obvious solution: lock the counter so only one request touches it at a time. But locks significantly slow down the system, so the book does not recommend them for a rate limiter.

Lua script

Send the "read, check, increment" logic to Redis as one Lua script. Redis executes it atomically: nothing else can run in the middle.

Sorted sets

Use Redis sorted-set commands (as in the sliding window log), combined in an atomic transaction, so adding and counting happen together.

-- Lua script run inside Redis (atomic): fixed window check
local count = redis.call("INCR", KEYS[1])
if count == 1 then
  redis.call("EXPIRE", KEYS[1], ARGV[2])   -- window length in seconds
end
if count > tonumber(ARGV[1]) then          -- ARGV[1] = limit
  return 0                                 -- reject
end
return 1                                   -- allow

Challenge 2: Synchronization

To support millions of users, one rate limiter server might not be enough. When multiple rate limiter servers are used, they need to share what they know. Web tiers are stateless, so a client may send requests to different rate limiters. If there is no synchronization, rate limiter 1 does not contain any data about client 2, and cannot do its job properly.

Local counters vs a centralized data store
Left: each limiter keeps its own counters, so a client that hops between limiters is undercounted. Right: all limiters read and write counters in one shared Redis.

Step 3 deep dive: Performance optimization and monitoring

Performance optimization

Performance optimization is a common topic in system design interviews. The book suggests two areas to improve:

  1. Multi-data center setup. Latency is high for users far away from the data center. Most cloud service providers build many edge server locations around the world. The book notes that, as of 2020, Cloudflare had 194 geographically distributed edge servers. Traffic is automatically routed to the closest edge server to reduce latency.
  2. Synchronize data with an eventual consistency model. Copies of counters in different data centers do not need to agree instantly; they converge over time. Waiting for perfect agreement on every request would be too slow. (The eventual consistency model is explained in Chapter 6, Design a Key-Value Store.)
The trade-off

With eventual consistency, a client hitting two data centers at the same instant might briefly get a few extra requests through. For rate limiting, a tiny over-allowance is usually acceptable in exchange for low latency.

Monitoring

After the rate limiter is in place, gather analytics data to check whether it is effective. Primarily, we want to make sure:

  • The rate limiting algorithm is effective. For example, if the rate limiter becomes ineffective when there is a sudden increase in traffic like flash sales, we may replace the algorithm to support burst traffic. Token bucket is a good fit here.
  • The rate limiting rules are effective. If rules are too strict, many valid requests are dropped. In this case, relax the rules a little bit.

Step 4: Wrap up and extra talking points

If time allows, the book suggests mentioning these:

Hard vs soft rate limiting

Hard

The number of requests cannot exceed the threshold. Ever.

Soft

Requests can exceed the threshold for a short period.

Rate limiting at different levels

This chapter discussed rate limiting at the application level (HTTP, layer 7 of the OSI model). It is possible to apply rate limiting at other layers. For example, you can apply rate limiting by IP addresses using iptables (a Linux firewall tool), which works at the IP layer (layer 3).

How to avoid being rate limited (client best practices)

  • Use client cache to avoid making frequent API calls.
  • Understand the limit and do not send too many requests in a short time frame.
  • Include code to catch exceptions or errors so your client can gracefully recover from exceptions.
  • Add sufficient back-off time to retry logic. For example, wait 1s, then 2s, then 4s (exponential backoff), and respect X-Ratelimit-Retry-After.

Walkthrough: user 42 tries to log in for the 6th time in a minute

  1. Request arrives. POST /login from user 42 reaches the nearest data center, and the load balancer sends it to rate limiter 2.
  2. Find the rule. Rate limiter 2 looks in its in-memory rules cache and finds auth_type: login → 5 per minute.
  3. Check the counter atomically. It runs the Lua script on Redis for key rl:login:user42:10:15. INCR returns 6.
  4. Decide. 6 > 5, so the request is rate limited.
  5. Respond. The client receives 429 Too Many Requests with X-Ratelimit-Limit: 5, X-Ratelimit-Remaining: 0, and X-Ratelimit-Retry-After: 40.
  6. Client behaves well. The app shows "Try again in 40 seconds" and waits rather than retrying immediately.
  7. Monitoring. The rejection is recorded in metrics, so the team can see if the login rule is too strict.

Had this been the 3rd attempt, INCR would have returned 3, the request would have gone straight to the API servers, and the response would have carried X-Ratelimit-Remaining: 2.

"Before I design anything, I'd like to clarify a few things. Are we building a server-side limiter for an API? Should rules be per user, per IP, or flexible? And roughly how much traffic, and will it run across many servers?"

  • Briefly compare the five algorithms; pick one and justify it.
  • Draw client → rate limiter → API servers, with Redis holding counters (INCR, EXPIRE).
"I'll put the rate limiter in a middleware layer in front of the API servers, so every service gets protection without changing its code. For the algorithm I'd use token bucket: it's simple, memory-efficient, and allows short bursts, which is what Amazon and Stripe use. Counters live in Redis because it's in-memory and supports expiry."
"Why not just store the counters in a database?"
"Every single request needs a counter read and write. A disk-based database would add milliseconds to every call and become a bottleneck. Redis keeps data in memory, gives atomic INCR, and EXPIRE cleans up old windows for free."
"What's wrong with a fixed window counter?"
"Bursts at the window edges. With a limit of 5 per minute, a client can send 5 requests at 2:00:59 and 5 more at 2:01:00, so 10 requests get through in about one minute. Sliding window log or sliding window counter fixes that."

  • Throttled response: 429 plus X-Ratelimit headers; optional queue.
  • Distributed issues: race condition (Lua script / sorted sets) and synchronization (central Redis, not sticky sessions).
  • Performance: edge servers, eventual consistency. Monitoring.
"Rules are stored as YAML on disk, for example 5 logins per minute. Workers load them into an in-memory cache so the middleware never reads disk on the hot path. Rejected requests get a 429 with Limit, Remaining and Retry-After headers."
"Two rate limiter servers handle the same user at the same time. What can go wrong?"
"A race condition: both read the counter as 3, both write 4, and we've under-counted. Locks would fix it but slow everything down. "The requirement says the limiter must not take the system down. Common mistakes

Relying on client-side limiting

Clients can be modified or forged. Client-side limits are a courtesy, never your protection. Always enforce on the server.

Read-then-write counters without atomicity

Doing GET, then checking in your app, then SET creates a race condition under concurrency. Use INCR or a Lua script so the whole check happens atomically.

Storing counters in a disk database

The limiter runs on every request. A slow store violates the low-latency requirement. Use an in-memory store like Redis.

Forgetting the fixed-window edge problem

If you propose fixed windows, say out loud that bursts at the boundary can allow up to twice the limit, and when that is acceptable.

Proposing sticky sessions for synchronization

They are neither scalable nor flexible. A centralized data store is the book's recommended approach.

Rejecting silently

Returning a generic 500 or dropping the connection confuses clients and causes retry storms. Return 429 with X-Ratelimit-Retry-After.

Jumping to an algorithm before asking questions

Whether you need per-user or per-IP limits, bursts or smooth flow, strict or approximate counts, all change the right algorithm.

Test yourself

1. Name the three benefits of rate limiting from the book.

Preventing resource starvation caused by DoS attacks (intentional or not), reducing cost (fewer servers, fewer paid third-party API calls), and preventing servers from being overloaded by bots or misbehaving users.

2. A token bucket has size 4 and is refilled with 4 tokens at the start of every minute (as in the book's example). It is full at 1:00:00. 4 requests arrive at 1:00:10 and 1 more at 1:00:30. What happens?

The first 4 are all allowed: they spend the 4 saved tokens, which shows that token bucket permits bursts. The request at 1:00:30 finds the bucket empty and is dropped. At 1:01:00 the bucket is refilled and requests are allowed again. The bucket size caps the burst; the refill rate caps the long-run average.

3. Your API allows 1 post per second, 150 friend additions per day and 5 likes per second per user. How many token buckets per user?

Three: one bucket per rule (endpoint), because each has a different size and refill rate.

4. Limit is 5 per minute with a fixed window counter. How can a client get 10 requests through in one minute?

Send 5 requests in the last seconds of one window (e.g. 2:00:30–2:01:00) and 5 more at the start of the next (2:01:00–2:01:30). Each window sees only 5, but the one-minute span from 2:00:30 to 2:01:30 contains 10.

5. Limit 7 per minute, sliding window counter. Previous minute had 5 requests, current has 3, we are 30% into the current minute. Is a new request allowed?

Estimate = 3 + 5 × 0.7 = 6.5, rounded down to 6. That is under 7, so yes, it is allowed. One more request would reach the limit.

6. Why does the sliding window log use lots of memory?

It stores a timestamp for every request in the window, and even rejected requests' timestamps stay in the log. Busy users with high limits mean thousands of timestamps each.

7. Your backend can only safely process 100 orders per second, at a steady pace. Which algorithm fits best?

Leaking bucket. Requests wait in a FIFO queue and are processed at a fixed outflow rate, giving the backend a stable load. Token bucket would allow bursts that could overwhelm it.

8. Two limiter servers both read a counter of 3 at the same moment and both write 4. What is this called and how do you fix it without locks?

A race condition. Make the read-check-increment atomic, using a Redis Lua script (or Redis sorted-set operations in an atomic transaction). Locks work but significantly slow the system.

9. What headers tell a client about its rate limit status?

X-Ratelimit-Remaining (requests left in this window), X-Ratelimit-Limit (requests allowed per window), and X-Ratelimit-Retry-After (seconds to wait before retrying). Sent with HTTP 429 when throttled.

10. Users in Asia complain the rate limiter adds latency, as it runs in a US data center. What do you do?

Deploy rate limiters in multiple data centers or edge locations close to users, and synchronize counters with an eventual consistency model rather than waiting for global agreement on every request. Accept that a few extra requests might briefly slip through.

Cheat sheet

  • Rate limiter = counts requests per client per time window; over the limit, reply 429 Too Many Requests.
  • Benefits: stop DoS / resource starvation, cut cost, prevent overload.
  • Requirements: accurate, low latency, low memory, distributed, clear exceptions, fault tolerant.
  • Place it server-side: middleware or API gateway. Client-side can be forged.
  • Token bucket (size + refill rate): bursts OK, memory-light; used by Amazon, Stripe. One bucket per rule/endpoint/IP, or one global.
  • Leaking bucket (queue size + outflow rate): smooth fixed-rate output; used by Shopify.
  • Fixed window: simplest, but edge bursts can let through up to 2× the limit.
  • Sliding window log: exact, but stores every timestamp (Redis sorted set), memory-heavy.
  • Sliding window counter: current + previous × overlap%, e.g. 3 + 5 × 0.7 = 6.5. Cheap and nearly exact.
  • Counters in Redis: INCR + EXPIRE. Rules in YAML on disk, cached by workers.
  • Headers: X-Ratelimit-Remaining, X-Ratelimit-Limit, X-Ratelimit-Retry-After. Optionally queue rejected requests.
  • Distributed: race conditions → Lua script / sorted sets (not locks); sync → centralized Redis (not sticky sessions); edge servers + eventual consistency for latency.
