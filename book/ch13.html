Chapter 13

Design a Search Autocomplete System

When you type "din" into Google and it instantly suggests "dinner ideas", that's search autocomplete. This chapter designs a system that, for every letter you type, returns the 5 most popular matching searches in under 100 milliseconds, for 10 million users a day. The star of the show is a tree-shaped data structure called a trie.

~35 min readAdvancedPrerequisites: Ch1 (scaling, caching, CDN), Ch2 (estimation), Ch5 (sharding / consistent hashing)

The big picture

Search autocomplete is also called typeahead, search-as-you-type or incremental search. It appears in Google's search box, on Amazon, in your phone's contacts, everywhere. The interview question is usually phrased as: "Design a system that returns the top k most searched queries for what the user has typed so far."

This looks simple, but at scale it is hard:

  • Every single keystroke is a request. One search of "dinner" causes 6 lookups.
  • Answers must come back faster than the user types the next letter (about 100 ms).
  • Popularity changes over time, so the data must be refreshed, but refreshing must never slow down lookups.
  • Bad suggestions (hateful, violent, dangerous) must be removable.

The chapter's answer has two halves: a query service that answers "top 5 for this prefix" extremely fast using a pre-computed trie, and a data gathering service that collects what people search for and rebuilds the trie in the background, for example once a week.

Real-world analogy

Imagine a librarian who, every Sunday night, reads the whole week's request log and writes on a set of index cards: "people who start with tr most often want: true, try". During the week, when someone walks in and says "tr...", the librarian doesn't think at all; they just read the card. Writing cards (data gathering) is slow and happens offline. Reading cards (query service) is instant. That separation is the whole design.

Back-of-the-envelope estimation

Let's do the math step by step, the way the book does.

  1. Users and searches. Assume 10 million DAU, and an average person performs 10 searches per day.
  2. Size of a query. 20 bytes of data per query string: assume ASCII encoding (1 byte per character), 4 words per query, and 5 characters per word on average. 4 × 5 = 20 bytes.
  3. Requests per query. For every character entered into the search box, the client sends a request to the backend. So on average about 20 requests are sent per search query. For example, typing "dinner" sends 6 requests:

search?q=dinner
  4. QPS. 10,000,000 users × 10 queries/day × 20 characters / 24 hours / 3,600 seconds ≈ 24,000 QPS.
  5. Peak QPS. QPS × 2 ≈ 48,000.
  6. New storage. Assume 20% of daily queries are new. 10 million × 10 queries/day × 20 bytes per query × 20% = 0.4 GB of new data added to storage daily.

Step 3: The trie data structure

Relational databases are not efficient for fetching the top 5 queries for a prefix. The trie (prefix tree) is. Since it is fundamental to this design, let's build it up from zero.

What is a trie?

The name comes from the word retrieval, and it is designed for string retrieval. The main ideas:

  • A trie is a tree-like data structure.
  • The root represents an empty string.
  • Each node stores a character and has up to 26 children, one for each possible next character (we only allow a–z).
  • Each tree node represents a single word or a prefix string: the characters on the path from the root to that node.

Below is a trie built from the queries tree, try, true, toy, wish, win. Follow any path from the root: each edge adds a letter. The words tree, true and wish share long prefixes, so they share nodes.

A trie for: tree, try, true, toy, wish, win
Each edge is one character; each node is the prefix spelled out on the path from the root. Highlighted (green) nodes are complete search queries. "tr" is shared by tree, try and true.
Real-world analogy

A trie is like a phone menu: "press t, then r, then u...". Each press narrows the options. After you've pressed "t", "r", you are standing in the part of the menu where every remaining option starts with "tr". You never look at anything starting with "w".

How autocomplete works on a trie

Some terms first: p = length of the prefix, n = total number of nodes in the trie, c = number of children (all descendants) of a given node.

Steps to get the top k most searched queries:

  1. Find the prefix. Walk down from the root one character at a time. Time complexity: O(p).
  2. Traverse the subtree from the prefix node to get all valid children (a child is valid if it can form a valid query string). Time complexity: O(c).
  3. Sort the children and get the top k. Time complexity: O(c log c).
Worked example: prefix "tr", k = 2
  1. Find the prefix node "tr": root → t → tr (2 steps, because p = 2).
  2. Traverse the subtree under "tr" and collect all valid queries: tree: 10, true: 35, try: 29.
  3. Sort by frequency: true 35, try 29, tree 10. Take the top 2: true: 35, try: 29.

The time complexity of this algorithm is the sum of the steps: O(p) + O(c) + O(c log c). It is straightforward, but too slow because in the worst case we traverse the entire trie to get the top k results. (Imagine the prefix is "a": the subtree under "a" could contain millions of queries.) Two optimizations fix this.

Optimization 1: limit the max length of a prefix

Users rarely type a long search query into the search box. So it is safe to say p is a small integer, say 50. If we limit the length of a prefix, the time complexity for "find the prefix" drops from O(p) to O(small constant), i.e. O(1).

Optimization 2: cache top search queries at each node

To avoid traversing the whole trie, store the top k most frequently used queries at each node. Since 5 to 10 autocomplete suggestions are enough for users, k is a relatively small number. In our specific case, only the top 5 search queries are cached.

By caching top search queries at every node, we significantly reduce the time complexity to retrieve the top 5 queries. However, this design requires a lot of space to store top queries at every node. Trading space for time is well worth it, as fast response time is very important.

Trie with top-k cached at every node (k = 2 for readability)
Each node stores a small pre-sorted list of the best queries in its subtree. To answer prefix "tr", jump to the "tr" node and read [true:35, try:29]. No traversal, no sorting.

After applying both optimizations:

  1. Find the prefix node: O(1), because the prefix length is capped.
  2. Return the top k: O(1), because the result is already cached at that node.

As the time complexity for each step is reduced to O(1), our algorithm takes only O(1) to fetch the top k queries.

Step 3: Data gathering service (redesigned)

In the first version, whenever a user typed a search query, data was updated in real time. That approach is not practical, for two reasons:

  • Users may enter billions of queries per day. Updating the trie on every query significantly slows down the query service.
  • Top suggestions may not change much once the trie is built. So it is unnecessary to update the trie frequently.

Real-time applications (like Twitter) need fresh suggestions, but for many other use cases like Google keywords, autocomplete suggestions may not change much on a daily basis. Either way, the foundation stays the same: the data used to build the trie usually comes from analytics or logging services.

Workers. A set of servers that perform asynchronous jobs at regular intervals. They build the trie data structure and store it in the trie DB.

Trie cache. A distributed cache system that keeps the trie in memory for fast reads. It takes a weekly snapshot of the DB.

Trie DB. Persistent storage. Two options:

Option 1: Document store

Since a new trie is built weekly, we can periodically take a snapshot of it, serialize it and store the serialized data in the database. Document stores like MongoDB are good fits for serialized data.

Option 2: Key-value store

A trie can be represented in hash table form: every prefix in the trie is mapped to a key in the hash table; data on each trie node is mapped to a value in the hash table.

Mapping a trie to a key-value store
Each trie node becomes one key-value pair: the prefix is the key, and the node's data (its cached top queries) is the value. Looking up a prefix becomes a single hash-table get.

Step 3: Query service (redesigned)

In the high-level design, the query service called the database directly to fetch the top 5 results. The improved design:

Most requests are answered straight from memory. Only cache misses go to the trie DB.
  1. A search query is sent to the load balancer.
  2. The load balancer routes the request to API servers.
  3. API servers get trie data from the trie cache and construct autocomplete suggestions for the client.
  4. If the data is not in the trie cache, we replenish it from the trie DB. This way, all subsequent requests for the same prefix are returned from the cache. A cache miss can happen when a cache server is out of memory or offline.

Query service requires lightning-fast speed. The book proposes these optimizations:

AJAX request

For web applications, browsers usually send AJAX requests to fetch autocomplete results. The main benefit is that sending or receiving a request/response does not refresh the whole web page.

Browser caching

For many applications, suggestions may not change much within a short time, so they can be saved in the browser cache. Subsequent requests get results directly from the cache. Google search uses this: the response header contains cache-control: private, max-age=3600.

Data sampling

For a large-scale system, logging every search query requires a lot of processing power and storage. Data sampling is important: only 1 out of every N requests is logged by the system.

Decoding the Google header

private means results are intended for a single user and must not be cached by a shared cache. max-age=3600 means the cache is valid for 3,600 seconds, i.e. one hour. So if you type "din" twice within an hour, the second time your browser answers by itself, without touching the servers.

Browser cache short-circuits repeat requests
The first request goes to the servers and the response is cached; repeats within max-age are served locally.

Step 3: Trie operations

The trie is the core component of the system. Let's look at how it is created, updated and deleted.

Create

The trie is created by workers using aggregated data. The source of data is the analytics log / database.

Update

There are two ways to update the trie:

Option 1: Update weekly

Once a new trie is created, the new trie replaces the old one. This is the recommended approach.

Option 2: Update each node directly

We try to avoid this because it is slow. If the trie is small, it is an acceptable solution. When we update a trie node, its ancestors all the way up to the root must be updated, because ancestors store the top queries of their children.

Here is an example of why ancestors must change. Suppose the frequency of "try" rises from 29 to 40:

Updating one node ripples up to the root
Changing one query's frequency changes the cached top-k list of every ancestor (shown with k = 2). That is why per-node updates are slow and the weekly rebuild is preferred.

Delete

We have to remove hateful, violent, sexually explicit or dangerous autocomplete suggestions. We add a filter layer in front of the trie cache to filter out unwanted suggestions. Having a filter layer gives us the flexibility of removing results based on different filter rules. Unwanted suggestions are physically removed from the database asynchronously, so the correct data set will be used to build the trie in the next update cycle.

Step 3: Scale the storage

Now that the system brings autocomplete queries to users, it's time to solve the scalability issue when the trie grows too large to fit in one server. Since English is the only supported language, a naive way to shard is based on the first character:

  • If we need two servers for storage, store queries starting with 'a' to 'm' on the first server and 'n' to 'z' on the second.
  • If we need three servers: 'a' to 'i', 'j' to 'r', and 's' to 'z'.

Following this logic, we can split queries up to 26 servers because there are 26 alphabetic characters in English. Let's define sharding based on the first character as first-level sharding. To store data beyond 26 servers, we can shard on the second or even the third level. For example, data queries that start with 'a' can be split into 4 servers: 'aa-ag', 'ah-an', 'ao-au' and 'av-az'.

Naive sharding by first letter and the uneven-load problem
One server per letter gives very uneven load: there are a lot more words that start with 'c' than with 'x'.

At first glance this approach seems reasonable, until you realize that there are a lot more words that start with the letter 'c' than 'x'. This creates uneven distribution.

To mitigate the data imbalance problem, we analyze historical data distribution pattern and apply smarter sharding logic. The shard map manager maintains a lookup database for identifying where rows should be stored. For example, if there are a similar number of historical queries for 's' and for 'u', 'v', 'w', 'x', 'y' and 'z' combined, we can maintain two shards: one for 's' and one for 'u' to 'z'.

Shard map manager
Web servers first ask the shard map manager where a prefix lives, then fetch data from that shard. Ranges are chosen from historical data so each shard gets a similar amount.

Step 4: Wrap up

After the deep dive, the interviewer might ask follow-up questions. The book covers these:

How do you extend the design to support multiple languages?

To support other non-English queries, we store Unicode characters in trie nodes. Unicode is "an encoding standard that covers all the characters for all the writing systems of the world, modern and ancient".

What if top search queries in one country are different from others?

We might build different tries for different countries. To improve response time, we can store tries in CDNs.

How can we support trending (real-time) search queries?

Assume a news event breaks out and a search query suddenly becomes popular. Our original design will not work because:

  • Offline workers are not scheduled to update the trie yet, because they run weekly.
  • Even if scheduled, it takes too long to build the trie.

Building a real-time search autocomplete is complicated and beyond the scope of the book, but a few ideas:

Reduce the working data set

Reduce the working data set by sharding.

Change the ranking model

Assign more weight to recent search queries.

Stream processing

Data may come as streams, so we don't have access to all the data at one time. Streaming data means data is generated continuously. Stream processing requires a different set of systems: Apache Hadoop MapReduce, Apache Spark Streaming, Apache Storm, Apache Kafka, etc.

Walkthrough: a user types "tr"

  1. Keystroke "t". The browser sends an AJAX request search?q=t without reloading the page. If it already asked for "t" within the past hour, the browser cache answers instantly.
  2. Load balancer → API server. The request lands on any API server (they are stateless).
  3. Find the shard. The API server asks the shard map manager which trie cache shard owns the prefix "t".
  4. Read the trie node. Prefix length is capped, so finding the node is O(1). The node already holds its pre-sorted top 5, so returning them is O(1).
  5. Filter. The filter layer drops any suggestion on the block list.
  6. Respond. The client shows e.g. [true, try, toy, tree]. The user types "r" and the same thing happens for "tr", well within 100 ms.
  7. Logging. One in N of these requests is written to the analytics logs.
  8. Weekly rebuild. Aggregators roll the logs into weekly (query, week, frequency) rows; workers build a fresh trie, save it to the trie DB, and the trie cache loads the new snapshot, replacing the old trie.

Common mistakes

Running a SQL LIKE query per keystroke at scale

Fine for a prototype, but at ~24,000 QPS against a huge table it won't meet 100 ms. Move to a trie in memory.

Updating the trie in real time on every search

Billions of writes per day slow down reads, and every update must also update all ancestors' cached top-k lists. Build offline and swap weekly unless real-time is a stated requirement.

Forgetting that each keystroke is a request

The QPS estimate must multiply by characters per query (about 20), not just searches per day.

Stopping at the naive trie

Without capping prefix length and caching top k at each node, the lookup can traverse most of the trie. State the O(1) optimizations and the space-for-time trade-off.

Sharding evenly by letter and calling it done

Letter-based shards are badly imbalanced. Mention historical distribution and a shard map manager.

No plan for removing harmful suggestions

Always include a filter layer and asynchronous physical deletion.

Ignoring client-side wins

AJAX, browser caching (cache-control: private, max-age=3600) and data sampling are cheap, high-impact optimizations.

Test yourself

1. Walk through the QPS estimate. Where does 24,000 come from?

10,000,000 DAU × 10 searches/day × 20 requests per search (one per character, 4 words × 5 chars) / 86,400 seconds ≈ 23,000, rounded to about 24,000 QPS. Peak is about double: 48,000.

2. How much new data per day, and how?

10M × 10 queries × 20 bytes × 20% new = 0.4 GB per day. Storage is modest, so speed, not storage, is the main challenge.

3. What does a node in a trie represent, and what does the root represent?

Each node represents a prefix (or complete word): the characters on the path from the root to it. The root represents the empty string. With lowercase English, each node has up to 26 children.

4. Using the frequencies tree:10, try:29, true:35, toy:14, wish:25, win:50, what are the top 2 for prefix "t"? For "w"?

"t": true:35, try:29 (toy:14 and tree:10 are lower). "w": win:50, wish:25.

5. What is the complexity of the naive top-k algorithm, and why is it too slow?

O(p) + O(c) + O(c log c): find the prefix, traverse all descendants, sort them. For a short prefix like "a", c can be huge, so in the worst case you traverse almost the entire trie per keystroke.

6. Which two optimizations make lookups O(1), and what do they cost?

Limit the max prefix length (e.g. 50) so finding the node is constant time, and cache the top k queries at every node so no traversal or sorting is needed. The cost is extra memory, since every node stores a list; the book argues trading space for time is worth it.

7. Scenario: the frequency of "tree" jumps from 10 to 60 and you update the node in place. Which nodes must change?

The "tree" node and all its ancestors: "tre", "tr", "t" and the root, because each caches the top queries of its subtree. With k = 2, root becomes [tree:60, win:50], "t" and "tr" become [tree:60, true:35]. This ripple is why per-node updates are slow and weekly rebuilds are preferred.

8. What are the two options for the trie DB?

A document store (e.g. MongoDB) holding a serialized snapshot of the weekly trie, or a key-value store where each prefix is a key and the node's data (its top queries) is the value.

9. Scenario: a hateful query starts appearing in suggestions. What do you do right now, and what happens later?

Add a rule to the filter layer between the API servers and the trie cache, so it is hidden immediately. The entry is then physically removed from the database asynchronously, so the next trie rebuild uses a clean data set.

10. Why is sharding by first letter problematic and how do you fix it?

Data is uneven: far more words start with 'c' than 'x', so some shards get overloaded. Use historical data distribution and a shard map manager, e.g. one shard for 's' and another for 'u' through 'z' if their query volumes are similar.

Cheat sheet

  • Scope: prefix-only matching, top 5 by historical frequency, no spell check, English lowercase, 10M DAU, under 100 ms.
  • Estimate: 10M × 10 × 20 / 86,400 ≈ 24,000 QPS, peak ~48,000; 0.4 GB new data/day (20% new).
  • Two services: data gathering (build the data) and query service (answer prefixes).
  • v1: frequency table + LIKE 'prefix%' ORDER BY frequency DESC LIMIT 5; works small, bottlenecks at scale.
  • Trie: root = empty string, each node = prefix, up to 26 children, frequency stored in nodes.
  • Naive top-k: O(p) + O(c) + O(c log c). Optimized: cap prefix (~50) + cache top k per node = O(1). Space traded for time.
  • Offline pipeline: analytics logs → aggregators → aggregated data (weekly) → workers → trie DB → trie cache (weekly snapshot).
  • Trie DB: document store (serialized snapshot, MongoDB) or KV store (prefix → node data).
  • Query path: LB → API servers → trie cache → trie DB on miss. Plus AJAX, browser cache (private, max-age=3600), data sampling (1 in N).
  • Update: replace whole trie weekly; per-node updates must also update all ancestors. Delete: filter layer now, physical removal async.
  • Scale: shard by first letter (26), then deeper levels; fix uneven load with a shard map manager based on history.
  • Extras: Unicode for languages, per-country tries in CDNs, trending via sharding, recency-weighted ranking and stream processing (Kafka, Spark Streaming, Storm, MapReduce).
