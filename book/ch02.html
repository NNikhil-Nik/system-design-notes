Chapter 2

Back-of-the-Envelope Estimation

Before building anything, engineers do quick, rough maths to see whether a design can cope with the expected load. This chapter teaches the numbers you should know by heart (powers of two, latency, availability) and a simple, repeatable method for estimating traffic, storage and servers, worked through with a Twitter example and extra practice problems.

~25 min readBeginnerPrerequisites: Chapter 1, basic multiplication and division

The big picture

In a system design interview, you are sometimes asked to estimate system capacity or performance requirements using a back-of-the-envelope estimation. Jeff Dean, a Google Senior Fellow, describes these as "estimates you create using a combination of thought experiments and common performance numbers to get a good feel for which designs will meet your requirements."

Why does it matter? Because numbers decide designs. If you need to store 50 GB, one database is fine. If you need to store 55 PB, you need a very different architecture. If you get 10 requests per second, one server is fine; at 100,000, you need many servers, caches and probably sharding. Estimation tells you which world you are in before you start drawing boxes.

Real-world analogy

You are planning a party. You do not count every grain of rice. You think: "About 40 guests, each eats roughly 200 g of food, so I need about 8 kg. Maybe 10 kg to be safe." That rough estimate tells you whether to cook at home or call a caterer. Back-of-the-envelope estimation is exactly this, but for servers, storage and network.

What you need

A good sense of scalability basics and a few numbers memorized: powers of two, latency numbers, and availability numbers.

What you produce

Rough answers for QPS, peak QPS, storage, cache size, bandwidth and number of servers.

What is graded

The interviewer cares about your process, not the exact result. Clear assumptions and units matter more than precision.

Key terms

Back-of-the-envelope estimation
A quick, rough calculation (small enough to fit on the back of an envelope) to check if a design is in the right ballpark.
Bit / byte
A bit is a single 0 or 1. A byte is 8 bits. An ASCII character uses one byte of memory.
KB, MB, GB, TB, PB
Kilobyte, megabyte, gigabyte, terabyte, petabyte. Each is about 1,000 times (exactly 1,024 times, a power of two) the previous one.
Latency
How long one operation takes, e.g. reading from memory or sending a packet across the world.
ns, µs, ms
Nanosecond (one billionth of a second, 10-9 s), microsecond (10-6 s = 1,000 ns), millisecond (10-3 s = 1,000 µs).
L1 / L2 cache
Tiny, extremely fast memory built into the CPU. Not the same as an application cache like Redis.
Main memory (RAM)
The computer's working memory. Fast, but lost when the power goes off.
Disk seek
The time a spinning hard disk takes to move its head to the right spot before reading. Slow.
Sequential read
Reading data that sits next to each other in order. Much faster than jumping around (random reads).
Compression
Shrinking data (e.g. with Zippy/Snappy or gzip) so it takes less space and less network time.
Round trip
Sending a message and receiving the reply.
Availability
The percentage of time a system is up and working. Often written as "nines": 99.9% is "three nines".
Downtime
Time when the system is not available.
SLA (Service Level Agreement)
A formal promise from a service provider to customers about uptime (e.g. 99.9%).
MAU / DAU
Monthly active users / daily active users: how many distinct people use the product in a month / day.
QPS
Queries per second: how many requests the system receives each second on average.
Peak QPS
QPS at the busiest time. Often estimated as 2 times the average.
Throughput / bandwidth
How much data moves per second, e.g. 1 GB/s.
Order of magnitude
A factor of 10. "Two orders of magnitude" means about 100 times.

Power of two

Although data volume can become enormous when dealing with distributed systems, calculation all boils down to the basics. To get correct calculations, it is critical to know the data volume unit using the power of 2. A byte is a sequence of 8 bits. An ASCII character uses one byte of memory (8 bits).

2101 Thousand1 Kilobyte1 KB
2201 Million1 Megabyte1 MB
2301 Billion1 Gigabyte1 GB

For estimation, treat 2^10 as 1,000. The 2.4% error does not matter for rough maths.

How to use it

The trick is to convert big numbers into "thousands, millions, billions" and let units do the work:

  • 1 million users x 1 KB each = 106 x 103 bytes = 109 bytes = 1 GB.
  • 1 billion images x 1 MB each = 109 x 106 = 1015 bytes = 1 PB.
  • 100 million rows x 500 bytes = 108 x 5 x 102 = 5 x 1010 bytes = 50 GB.
Memory trick

Thousand, Million, Billion, Trillion, Quadrillion maps to KB, MB, GB, TB, PB. Count the groups of three zeros: 103 = K, 106 = M, 109 = G, 1012 = T, 1015 = P.

The book's conclusions

Memory is fast, disk is slow

Reading 1 MB from memory (250 µs) is over 100x faster than reading it from disk (30 ms). This is why caches live in memory.

Avoid disk seeks if possible

A single seek costs 10 ms, the same as reading a whole MB over the network.

Simple compression algorithms are fast

Compressing 1 KB takes 10 µs. Cheap compared to sending bytes over a network.

Compress data before sending it over the internet if possible

Fewer bytes on the wire means less time and less bandwidth cost.

Data centers are usually in different regions, and it takes time to send data between them

A cross-continent round trip is 150 ms, 300 times a round trip within one data center.

How this shapes designs

These numbers explain choices from Chapter 1: put a cache in memory in front of the database, put content on a CDN near users, and route users to the nearest data center with geoDNS. Every one of these avoids a slow line in the table.

Availability numbers

High availability is the ability of a system to be continuously operational for a desirably long period of time. It is measured as a percentage, with 100% meaning a service that has 0 downtime. Most services fall between 99% and 100%.

A service level agreement (SLA) is a commonly used term for service providers. It is an agreement between you (the service provider) and your customer, and it formally defines the level of uptime your service will deliver. Cloud providers Amazon, Google and Microsoft set their SLAs at 99.9% or above. Uptime is traditionally measured in nines. The more the nines, the better.

Each extra nine cuts downtime by 10x (downtime per year)
Going from "two nines" to "five nines" means going from days of downtime a year to just minutes. Each nine is much harder and more expensive to achieve.

Where the numbers come from

You can rebuild the table yourself. Downtime = (1 - availability) x period.

  • 99.9% per day: 0.001 x 86,400 seconds = 86.4 seconds = 1.44 minutes.
  • 99.99% per year: 0.0001 x 365.25 days x 24 hours x 60 minutes = 0.0001 x 525,960 min = 52.6 minutes.
Availability and design

If you rely on several components in a chain, their availabilities multiply. Two services at 99.9% each give roughly 99.8% together. This is one reason Chapter 1 insists on redundancy at every tier.

Step 1: Write down the assumptions

  • 300 million monthly active users (MAU).
  • 50% of users use Twitter daily.
  • Users post 2 tweets per day on average.
  • 10% of tweets contain media.
  • Data is stored for 5 years.

Step 2: Estimate QPS

  1. Daily active users (DAU) = 300 million x 50% = 150 million.
  2. Tweets QPS = 150 million x 2 tweets / 24 hours / 3600 seconds = 300,000,000 / 86,400 = ~3,500.
  3. Peak QPS = 2 x QPS = ~7,000.
Shortcut: a day is about 100,000 seconds

24 x 3,600 = 86,400 seconds. For fast mental maths, round to 105. Then 300 million / 100,000 = 3,000. That is close to the exact 3,472. Rounding up the divisor makes your answer slightly low, so say "around 3,000 to 3,500".

Step 3: Estimate media storage

Going a bit further (not in the book's example)

Text and IDs are tiny next to media. 300 million tweets/day x (64 + 140) bytes is about 300M x 200 bytes = 60 GB per day, roughly 110 TB in 5 years. Media is about 500 times bigger. Spotting which part dominates is the real insight: storage design for this system is really about media.

Why peak is about 2x average

Traffic over a day
People sleep, so traffic is not flat. Systems must be sized for the busiest hour, not the average. A peak factor of 2 is the common default unless you know better (big events can be much higher).

Tips for back-of-the-envelope estimation

Back-of-the-envelope estimation is all about the process. Solving the problem is more important than obtaining results. Interviewers may test your problem-solving skills. Here are the book's tips:

Rounding and approximation

It is difficult to perform complicated maths in an interview. For example, what is "99987 / 9.1"? No need to spend valuable time on it. Precision is not expected. Use round numbers: "99987 / 9.1" becomes "100,000 / 10" = 10,000.

Write down your assumptions

It is a good idea to write down your assumptions to be referenced later. The interviewer can correct one, and you can redo just that step.

Label your units

When you write down "5", does it mean 5 KB or 5 MB? You might confuse yourself. Write down the units, because "5 MB" helps remove ambiguity.

Know the commonly asked estimations

QPS, peak QPS, storage, cache, number of servers, etc. Practice these calculations when preparing for an interview. Practice makes perfect.

Practice problems (worked step by step)

These extra problems follow the book's method. The numbers are invented assumptions for practice, not real company data. Try each one yourself before reading the solution.

Practice 1: A photo-sharing app

Assumptions: 10 million DAU. Each user uploads 2 photos per day. Average photo size is 500 KB. Each user views 20 photos per day. Keep photos for 5 years.

  1. Upload QPS = 10M x 2 / 86,400 = 20M / ~105 = ~200 (exact: ~231). Peak = ~400–500.
  2. Read (view) QPS = 10M x 20 / 86,400 = 200M / 105 = ~2,000 (exact: ~2,300). Peak = ~4,600. The read:write ratio is 10:1, so this is a read-heavy system.
  3. Storage per day = 20M photos x 500 KB = 107 x 2 x 5 x 105 bytes = 1013 bytes = 10 TB per day.
  4. 5-year storage = 10 TB x 365 x 5 = 18,250 TB = ~18 PB.
  5. Read bandwidth = 2,300 views/s x 500 KB = 1,150,000 KB/s = ~1.2 GB/s on average, ~2.3 GB/s at peak.
What the numbers tell you

18 PB will not fit on one database: use object storage (like Amazon S3) for the photos and keep only metadata in a database. 1–2 GB/s of image traffic should come from a CDN (Chapter 1), not your web servers.

Practice 2: Cache size for a news website

Assumptions: 100 million article reads per day. Average article response is 10 KB. Traffic follows an 80/20 pattern: 20% of the content drives most reads, so we cache 20% of a day's read volume.

  1. Read QPS = 100M / 86,400 = 100M / 105 = ~1,000 (exact: ~1,160). Peak = ~2,300.
  2. Daily read volume = 100M x 10 KB = 108 x 104 bytes = 1012 bytes = 1 TB per day.
  3. Cache memory = 20% x 1 TB = 200 GB. This is an upper bound: many reads hit the same article, so the set of unique hot articles is smaller.
  4. Cache servers: assume 64 GB of usable memory per server. 200 GB / 64 GB = ~3.1, so 4 servers. Overprovision and avoid a single point of failure (Chapter 1): plan for 5–6.

Practice 3: Servers and storage for a chat app

Assumptions: 50 million DAU. Each user sends 40 messages per day. Average message is 100 bytes (text plus metadata). Assume one chat server can handle 5,000 QPS. Keep messages for 1 year.

  1. Messages per day = 50M x 40 = 2 billion.
  2. Message QPS = 2 x 109 / 105 = ~20,000 (exact: ~23,000). Peak = ~46,000.
  3. Servers = 46,000 / 5,000 = ~9.2, so 10 servers at peak. Add headroom so a few failures do not overload the rest: ~12–15.
  4. Storage per day = 2 x 109 x 100 bytes = 2 x 1011 bytes = 200 GB per day.
  5. 1-year storage = 200 GB x 365 = 73,000 GB = ~73 TB. With 3 copies for reliability: ~220 TB.
Chat app numbers at a glance
One assumption list feeds two branches: traffic (top row, to servers) and storage (bottom row).

Practice 4: Bandwidth for a video platform

Assumptions: 5 million DAU. Each user watches 5 videos per day. Creators upload 50,000 new videos per day. Average stored video is 300 MB (after encoding). Average bytes streamed per view is 100 MB (people do not always finish).

  1. Views per day = 5M x 5 = 25 million.
  2. View QPS = 25M / 105 = ~250 (exact: ~290). Peak = ~580.
  3. Egress (outgoing) bandwidth = 290 views/s x 100 MB = 29,000 MB/s = ~29 GB/s average, ~58 GB/s at peak. In bits: 29 GB/s x 8 = ~230 Gbps.
  4. New storage per day = 50,000 x 300 MB = 15,000,000 MB = 15 TB per day; per year 15 TB x 365 = ~5.5 PB.
What the numbers tell you

QPS is tiny (hundreds), but bandwidth is huge (hundreds of Gbps). The bottleneck is network, not CPU. That points straight at a CDN and at bandwidth cost as the main concern, which is exactly what the YouTube chapter later explores.

Sanity check

Always ask "does this feel right?" Two billion messages a day for 50 million people is 40 each, which is plausible for a chat app. If a result looks absurd (say, 1 PB per day for text chat), recheck your units.

Walkthrough using the Twitter numbers

  1. Clarify. "Are we estimating write QPS for tweets and storage for media?" Yes.
  2. Assume. 300M MAU, 50% daily, 2 tweets/day, 10% with media, 1 MB media, 5 years. Written on the board.
  3. Traffic. 150M DAU, ~3,500 QPS, ~7,000 peak.
  4. Storage. 30 TB/day of media, ~55 PB over 5 years.
  5. Derived. At ~1,000 QPS per server (assumption), ~7 servers at peak for writes, so ~10 with headroom.
  6. So what? 7,000 writes/s is manageable, but 55 PB of media must go to distributed object storage and be served via a CDN; tweet text can live in a sharded database.

How to do estimations live in an interview

Estimation usually happens early, right after clarifying requirements. It should take about 5 minutes, not 20. Keep it on the whiteboard where you and the interviewer can both see it.

1
Ask whether estimation is wanted and what matters
~1 min
  • Some interviewers want detailed numbers; others want to skip to the design. Ask.
  • Find out which numbers drive the design: traffic, storage, or both.
"Would you like me to do a quick capacity estimate? I'm thinking traffic and storage are the ones that will shape this design."
2
State and write down assumptions
~1 min
  • Write each assumption as a bullet with units.
  • Invite corrections before calculating.
"Let me assume 300 million monthly users, half of them active daily, two tweets per user per day, 10% of tweets with a 1 MB media file, and we keep data for five years. Do those sound reasonable?"
"Let's say 20% of tweets have media instead."
"Sure, that just doubles media storage: 60 TB per day instead of 30, about 110 PB over five years. QPS doesn't change."
3
Calculate with round numbers, out loud
~2 min
  • Use 105 seconds per day. Use powers of ten. Keep units on every line.
  • Do not aim for precision; aim for the right order of magnitude.
"150 million daily users times 2 is 300 million tweets a day. A day is about 100,000 seconds, so that's roughly 3,000 to 3,500 tweets per second, and I'll double it for peak: about 7,000. For media, 300 million times 10% is 30 million files at 1 MB each, which is 30 TB per day, so about 55 PB over five years."
"Why did you multiply by 2 for peak?"
"Traffic isn't flat across a day. Two times the average is a common rule of thumb for the busiest hour. If we expect spiky events, like a big sports final, I'd plan for a higher factor and rely on autoscaling."
4
Explain what the numbers mean for the design
~1 min
  • Connect each number to a decision: sharding, CDN, cache, number of servers.
"7,000 writes per second is too much for one database long term, so we'll likely shard. And 55 PB of media clearly belongs in object storage behind a CDN, not in the database."
"How many web servers would you need?"
"If one server handles around 1,000 requests per second for this workload, which I'd verify with load tests, 7,000 peak QPS needs about 7 servers. I'd run at least 10 so we can lose a couple and still cope, and autoscale from there."

Common mistakes

Chasing precision

Spending three minutes dividing 99,987 by 9.1 wastes time and impresses nobody. Round to 100,000 / 10 and move on.

Dropping units

Writing "5" instead of "5 MB" is how a 1,000x error sneaks in. Label every number.

Silent assumptions

If you do not say your assumptions out loud and write them down, the interviewer cannot follow or correct you, and you cannot easily redo a step when they change one.

Forgetting peak traffic

Sizing for average QPS means the system falls over at the busiest hour. Always compute peak.

Mixing bits and bytes

Network speeds are usually in bits per second (1 Gbps), storage in bytes. 1 Gbps is about 125 MB/s, not 1 GB/s.

Stopping at the number

"55 PB" on its own is not the point. Say what it implies: object storage, CDN, sharding, more servers.

Treating 2010 latency numbers as exact

The latency table is about relative speed. Hardware has improved, but memory is still far faster than disk and cross-region trips are still slow.

Test yourself

1. Roughly how many bytes are in 1 TB, and which power of two is it?

About 1 trillion (1012) bytes, which is 240. The pattern: 210 KB, 220 MB, 230 GB, 240 TB, 250 PB.

2. Which is faster: reading 1 MB sequentially from memory or from disk? By how much?

Memory: 250 µs vs 30 ms for disk, about 120 times faster. That is why caches keep data in memory.

3. Why is it worth compressing data before sending it between data centers?

Simple compression is fast (about 10 µs per KB with Zippy) while cross-region transfers are slow (150 ms round trip CA to Netherlands). Spending a little CPU to send fewer bytes saves time and bandwidth.

4. A provider promises 99.99% availability. How much downtime is that per year? Per month?

About 52.60 minutes per year and 4.38 minutes per month. Each extra nine reduces downtime by 10x.

5. Redo the Twitter QPS estimate if only 20% of the 300M MAU are active daily.

DAU = 60M. Tweets/day = 120M. QPS = 120M / 86,400 = ~1,400. Peak = ~2,800. This shows why writing assumptions down helps: you just redo one line.

6. In the Twitter example, how much media storage is needed per day, and why?

150M DAU x 2 tweets x 10% with media x 1 MB = 30 million MB = 30 TB per day. Over 5 years: 30 TB x 365 x 5 = ~55 PB.

7. The interviewer gives you "99,987 requests over 9.1 seconds". What do you do?

Round it: 100,000 / 10 = 10,000 requests per second. Precision is not expected; the process matters more.

8. A video service serves 1,000 views per second, each streaming a 50 MB video. What bandwidth is that, and what does it imply?

1,000 x 50 MB = 50 GB per second (if all downloaded within the second, a simplification). That is enormous: video must be served from a CDN close to users, not from your own web servers.

9. Peak QPS is 20,000 and one server handles 2,000 QPS. How many servers do you propose?

20,000 / 2,000 = 10 servers at peak. Propose a few more (for example 12–15) so the system survives server failures and deploys, and mention autoscaling.

10. You computed 1 PB per day for a text-only chat app with 1M users. What went wrong?

That is 1 GB per user per day, which is absurd for text. You almost certainly mixed up units (e.g. used MB instead of bytes). Always sanity-check results and label units.
