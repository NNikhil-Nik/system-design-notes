Design a Rate Limiter

API throttling · Abuse prevention · Distributed counters · Redis atomicity
TL;DR A rate limiter caps requests per user/IP per time window. Use Token Bucket or Sliding Window Counter on Redis for most cases. In distributed systems, centralize state in Redis and use Lua scripts for atomicity.
Why Rate Limit?
  • Prevent DoS/DDoS: Stop single clients from exhausting server resources
  • Cost control: Downstream API calls (ML inference, SMS) are expensive — cap them
  • Tier enforcement: Free plan = 100 req/day, paid = 10K/day
  • Bot prevention: Stop credential stuffing, scraping, spam
Where to Place It
  • Client-side: Unreliable — client can ignore it entirely
  • Server-side middleware: Most flexible; easy to change logic without touching business code
  • API Gateway: Best if you already have one — handles TLS, auth, rate limit, logging all in one
  • Rule: If using microservices with an API Gateway → rate limit there. Otherwise → middleware
5 Algorithms — Quick Reference

Token Bucket

Bucket holds N tokens. Refills at fixed rate r/sec. Each request consumes 1 token. If empty → reject.

✓ Allows bursts up to bucket size
✓ Memory efficient (just 2 vars)
✗ Tricky to tune bucket+refill rate

Leaking Bucket

FIFO queue. Requests enter queue; processed at fixed rate. Full queue → drop request.

✓ Smooth, stable outflow
✗ Queued old requests drain first
✗ Bursty traffic still gets delayed

Fixed Window Counter

Divide time into fixed windows (e.g. 1 min). Count reqs per window. Reset at boundary.

✓ Simple, low memory
✗ 2× traffic at window edge (last 30s of window + first 30s = 2×limit)

Sliding Window Log

Store timestamp of each request in Redis sorted set. Count entries in [now-window, now]. Reject if ≥ limit.

✓ Very accurate, no boundary spike
✗ High memory (stores all timestamps)

Sliding Window Counter ✓

Weight prev window: count = prev_count × overlap% + curr_count. Approximation but very accurate.

✓ Accurate + memory efficient
✓ Industry default (Cloudflare uses this)

Distributed Rate Limiting — Problems & Solutions
  • Race condition: Two servers both read counter=4 (limit=5), both allow request → 6 total requests slip through
  • Fix: Use Redis atomic INCR + Lua script — Lua runs atomically on Redis, no race
  • Synchronization: Multiple rate limiter nodes each have local counts → inconsistent
  • Fix: Centralized Redis cluster as shared state — all rate limiters read/write one store
  • Sticky sessions: Route same user to same rate limiter node. Avoids shared state but limits flexibility.

end
if current > tonumber(ARGV[2]) then
  return 0 -- reject
end
return 1 -- allow

Common Follow-up Questions
How would you handle a DDoS attack where requests come from millions of different IPs?
Rate limit by user agent patterns, geographic regions, or add a CAPTCHA layer. Also consider CDN-level (Cloudflare) protection that absorbs traffic before it hits your servers.
Why Redis over a database for rate limiting?
Redis is in-memory (~sub-millisecond latency), supports atomic operations (INCR), and has built-in TTL expiry. A relational DB would add too much latency to every request.
What if Redis goes down?
Two options: fail open (allow all requests — risk abuse) or fail closed (reject all — risk availability). Most systems fail open with monitoring alerts. Can also have Redis replicas.

Design Consistent Hashing

Hash ring · Virtual nodes · Minimal remapping · Horizontal scaling
TL;DR Consistent hashing places servers and keys on a ring. Adding/removing a server only affects k/n keys (not all). Virtual nodes fix uneven distribution. Used by DynamoDB, Cassandra, CDNs.
The Problem with Naive Hashing
Formula: serverIndex = hash(key) % N
If N changes (server added/removed), almost every key maps to a different server → cache invalidation storm → all requests hit DB simultaneously.
  • Example: 4 servers → 5 servers. ~80% of keys remap. If those were cache keys, 80% become cache misses.
  • This causes a thundering herd problem — DB overload at the moment of scaling
Consistent Hashing — Core Idea
  • Hash space is a ring from 0 to 2³²−1 (wraps around)
  • Both servers and keys are mapped onto the ring using the same hash function
  • A key is stored on the first server clockwise from its position on the ring
  • Add server: only keys between it and its predecessor move → k/n keys remapped
  • Remove server: only keys on that server move to next server → k/n keys remapped
Virtual Nodes — The Fix for Uneven Distribution
  • Problem: With 3 real servers, partition sizes are unequal — one server might get 50% of keys
  • Solution: Each physical server has multiple virtual nodes (100–200) on the ring
  • As more virtual nodes are added, key distribution becomes more uniform (law of large numbers)
  • Trade-off: More virtual nodes = more even distribution but higher memory to store the ring metadata

Step-by-Step: Adding a Server
  • Before: Ring has S0, S1, S2. Key K is clockwise-assigned to S1.
  • Add S3 between S0 and S1 on the ring.
  • Only keys that were between S0 and S3 (previously going to S1) now go to S3.
  • All other keys are completely unaffected — zero remapping for them.
  • Mathematically: ~1/N fraction of keys move on average (N = number of servers)
Replication on the Ring
  • Store key on the first N unique physical servers clockwise from the key's position
  • Skip virtual nodes that map to an already-selected physical server
  • Example: N=3 replication factor → key replicated to 3 different physical servers
  • This is exactly how Cassandra and Dynamo handle replication
Hash Function Choice
  • Use MD5 or SHA-1 for the ring — uniform distribution matters more than security here
  • MurmurHash is popular in practice (faster, still uniform)
  • All servers and keys must use the same hash function

Interview Answer Framework
1
Start with the Problem
With naive hashing — serverIndex = hash(key) % N — adding or removing a server causes almost all keys to remap. In a cache layer, this triggers a cache storm. Consistent hashing solves this by ensuring only k/n keys need to move.
2
Explain the Ring
We map both servers and keys onto a circular ring using the same hash function. A key belongs to the first server clockwise from it. When we add a server, only keys between it and its predecessor get reassigned.
3
Address the Uneven Distribution Problem
With just a few servers, partitions will be unequal. We fix this with virtual nodes — each physical server gets, say, 150 positions on the ring. This makes the distribution much more uniform at the cost of slightly more metadata.
Common Follow-up Questions
How do you find which server a key belongs to efficiently?
Store virtual node positions in a sorted array. Use binary search to find the first position ≥ hash(key). O(log N) lookup. In Java, TreeMap.higherKey() does this natively.
How does Cassandra use consistent hashing?
Cassandra uses a token ring where each node owns a range of tokens. With virtual nodes (vnodes), each physical node owns many token ranges. Data replication copies each row to N consecutive nodes on the ring.
What are the downsides of consistent hashing?
Virtual nodes add complexity to manage. Hot key problem — one key can still overload a server if it gets hammered. Need a separate mechanism (key-based sharding or caching) for hot keys.

Design a Key-Value Store

CAP Theorem · Quorum · Vector Clocks · Gossip · LSM Tree
TL;DR A distributed KV store partitions data via consistent hashing, replicates to N nodes, and uses W+R>N quorum for consistency. Conflicts resolved by vector clocks. Gossip protocol detects failures. Write path: commit log → Memtable → SSTable.
CAP Theorem
A distributed system can guarantee only 2 of 3: Consistency, Availability, Partition tolerance. Since partitions always happen in networks, real choice is CP vs AP.
ChoiceBehavior on PartitionExample Use CaseExample System
CPReturn error or timeout — refuse stale readsBank transfers, inventoryHBase, Zookeeper
APReturn stale data, sync laterSocial feeds, shopping cartsDynamoDB, Cassandra
Core Design Pillars
  • Data Partition: Use consistent hashing to map keys to nodes. Ensures uniform distribution + minimal remapping on scale events.
  • Replication: Copy each key to N clockwise physical servers on the ring. Typical N=3.
  • Quorum Consensus: W + R > N guarantees at least one node has the latest write.
    • N=3, W=1, R=3 → fast writes, slow reads (CP-leaning)
    • N=3, W=3, R=1 → slow writes, fast reads
    • N=3, W=2, R=2 → balanced strong consistency ✓
    • W+R ≤ N → eventual consistency (AP)
  • Consistency model: Strong (all nodes see same data), Eventual (nodes converge over time), Read-your-writes, Monotonic reads
Failure Handling
  • Sloppy Quorum: During partition, write to first W available nodes (not necessarily the correct ones)
  • Hinted Handoff: Temporary node stores the write with a hint; delivers to original node when it recovers
  • Anti-entropy / Merkle Tree: Each node builds a Merkle tree of its data. Compare trees to find divergence without transferring all data.
  • Gossip Protocol: Each node periodically gossips its membership list to k random nodes. Failures propagate in O(log N) rounds.
Vector Clocks — Conflict Resolution
A vector clock is a list of [server, version] pairs. It tracks causality — if clock A dominates B, A is newer. If neither dominates, there's a conflict requiring resolution. 
-- Example timeline
D1([Sx,1])                     -- client writes to server Sx
D2([Sx,2])                     -- same client updates
D3([Sx,2],[Sy,1])              -- client updates via server Sy (branched from D2)
D4([Sx,2],[Sz,1])              -- different client updates via Sz (also branched from D2)
-- D3 and D4 conflict: neither dominates the other → push conflict to client
  • Amazon's Dynamo does this — shopping cart is merged client-side when conflicts occur
  • Downside: Vector clocks grow large if many servers write. Can prune oldest entries with timestamp-based truncation.
Gossip Protocol — Failure Detection
  • Each node maintains a membership list: [nodeId, heartbeat counter, last seen time]
  • Every second, each node increments its own heartbeat and sends its list to k=3 random nodes
  • If a node's heartbeat hasn't updated in threshold time → marked suspicious → then offline
  • Converges in O(log N) rounds — efficient for large clusters
  • Used by: Cassandra, DynamoDB, Riak
LSM Tree — Write & Read Path
  • Write: Append to commit log (durability) → insert into Memtable (in-memory sorted tree) → when Memtable full, flush to SSTable on disk
  • SSTable: Sorted String Table — immutable, sorted file. Multiple levels (L0, L1, L2…) with compaction merging them.
  • Read: Check Bloom filter (probabilistic check — "is this key possibly in this SSTable?") → search Memtable → search SSTables from newest to oldest
  • Bloom filter: Returns false positives but never false negatives. Eliminates disk reads for keys that don't exist.
  • Writes are O(1) (append-only). Reads are O(log N) per SSTable level.

Common Follow-up Questions
Walk me through what happens when W=2, R=2, N=3 and a node goes down.
With 2 nodes still up, W=2 writes still succeed. R=2 reads still succeed. We maintain consistency. If a 2nd node goes down (only 1 left), we can no longer satisfy quorum — system returns error (CP behavior) or switches to sloppy quorum (AP behavior).
Why use a Bloom filter for reads?
SSTables are immutable sorted files on disk. Reading all of them for a missing key wastes I/O. A Bloom filter is a probabilistic structure that tells us "this key is definitely NOT in this SSTable" — we skip those files entirely. It never gives false negatives, only rare false positives (extra disk reads).
How is Cassandra's consistency different from DynamoDB's?
Cassandra lets you tune consistency per query (ONE, QUORUM, ALL). DynamoDB offers eventually consistent reads by default and strongly consistent reads on request (reads from leader only). Both are AP by default but support configurable consistency.

  • Sign bit (1 bit): Always 0 — ensures positive 64-bit signed integer
  • Timestamp (41 bits): Milliseconds since a custom epoch (e.g. Twitter's epoch = Nov 4 2010). Range = 2⁴¹ ms ≈ 69 years of IDs
  • Datacenter ID (5 bits): 2⁵ = 32 datacenters supported
  • Machine ID (5 bits): 2⁵ = 32 machines per DC → 1,024 total machines
  • Sequence (12 bits): Auto-increments per ms, resets to 0 each millisecond. 2¹² = 4,096 IDs per ms per machine = ~4M IDs/sec/machine
Clock Skew Problem & Solution
Problem: NTP adjusts system clocks. If clock moves backward, machine could generate duplicate IDs (same timestamp + same sequence number as a prior ID).

Solution: When currentTimestamp < lastTimestamp, refuse to generate IDs and wait until clock catches up. Log a warning. In severe cases, alert ops.
  • Twitter's Snowflake used NTP with a max drift of 10ms — anything beyond that caused the server to refuse requests
  • Modern systems use Google's TrueTime (with uncertainty bounds) to handle this more elegantly

2
Explain Snowflake Bit Layout
~8 min
The 64-bit ID is composed of: 1 sign bit (always 0), 41 bits of millisecond timestamp since a custom epoch giving us 69 years, 5 bits for datacenter ID (32 DCs), 5 bits for machine ID (32 machines per DC), and 12 sequence bits resetting each ms giving 4096 IDs per ms per machine.

Common Follow-up Questions
What if we run out of sequence numbers in a millisecond?
At 4096 IDs/ms/machine, hitting this limit requires generating more than 4M IDs per second per machine — effectively impossible in normal operation. If somehow hit, we wait for the next millisecond (sleep 1ms).
How do you assign datacenter and machine IDs?
They're set at startup via config or service discovery (e.g. ZooKeeper assigns unique machine IDs). They're hardcoded per deployment, not randomly generated — that's key to why there are no collisions without coordination at runtime.
Can we extend Snowflake for a longer lifespan?
Yes — trade bits between fields. E.g. steal 2 bits from DC and machine fields to add to timestamp → 43-bit timestamp = ~278 years. Or use a different epoch start date to push the expiry further out.

Design a URL Shortener

Base62 Encoding · 301 vs 302 · LRU Cache · DB Schema · Read-heavy
TL;DR Generate a unique 64-bit ID (Snowflake), encode it in base62 to get a 7-char short URL. Store mapping in DB. Cache hot URLs with LRU. Redirect with 302 for analytics, 301 for performance. Read:write ratio ~100:1.
API Design
  • Shorten: POST /api/v1/data/shorten body: {"longUrl":"https://..."} → returns {"shortUrl":"https://short.ly/abc1234"}
  • Redirect: GET /{shortCode} → HTTP redirect to original URL
  • Delete (optional): DELETE /api/v1/{shortCode}

301Permanent redirectYes — after first visit, browser goes directLow (browser handles)Performance matters, don't need analytics

If analytics (click count, geo, device) are important → use 302. If minimizing server load is the priority → use 301.
Two Hashing Strategies
StrategyHowProsCons
Hash + Collision Resolution CRC32/MD5 → take first 7 chars. On collision, append string and rehash. Deterministic (same URL → same short code) Must query DB on every write to detect collision; slower
Base62 Encoding ✓ Generate unique ID (Snowflake) → convert to base62 No collision possible; no DB check needed; time-ordered Different short codes for same long URL (no dedup by default)
Base62 Encoding — How It Works
Alphabet: 0-9a-zA-Z = 62 characters. A 7-character base62 string = 62⁷ ≈ 3.5 trillion unique URLs — enough for centuries. 
-- Convert integer ID to base62 string
def encode(id):
    chars = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"
    result = []
    while id > 0:
        result.append(chars[id % 62])
        id //= 62
    return ''.join(reversed(result)).zfill(7)
-- Example: ID 2009215674938 → "zn9edcu"

Caching Strategy
  • Read:write ratio is ~100:1 — optimize heavily for reads
  • Cache layer (Redis): Store shortCode → longUrl. Evict with LRU.
  • 80/20 rule: 20% of URLs generate 80% of traffic. Cache the hot 20%.
  • If cache miss → query DB → update cache
  • Cache capacity: 10M daily active URLs × 100 bytes avg = ~1 GB — fits in Redis easily

Common Follow-up Questions
How do you handle custom short codes like short.ly/myBrand?
Add a custom_alias column to the DB. On write, check if alias is taken (unique constraint). If not taken, store it. If taken, return a conflict error. Custom aliases bypass base62 encoding — they're stored as-is.
How do you scale reads to 100K+ req/sec?
Multiple layers: CDN for the redirect response itself (if using 301), Redis cache with LRU eviction, read replicas on the DB for cache misses. The cache hit rate should be ~80%+ for hot URLs so DB barely gets touched.
How do you handle URL expiration?
Store expires_at in the DB. On read, check if expired — return 404 if so. Use a background cleanup job (cron) to delete expired rows periodically. Can also use Redis TTL on cached entries.

Design a Web Crawler

BFS · URL Frontier · Politeness · Deduplication · Spider Traps
TL;DR A crawler does BFS from seed URLs. URL Frontier has priority queues (front) + per-domain politeness queues (back). Deduplicate URLs with Bloom filter + hash set. Deduplicate content with SHA-256. Respect robots.txt. Handle spider traps with URL depth limits.
Use Cases & Scale
  • Search engine indexing: Google crawls ~15B pages continuously
  • Web archiving: Internet Archive wayback machine
  • Data mining: Price comparison, research datasets
  • Link checking: Detect broken links, copyright violations
Core Components
  • Seed URLs: Starting points — usually high-PageRank domains or sitemaps
  • URL Frontier: Queue of URLs to crawl. Split into front queues (priority) + back queues (politeness, one per domain)
  • HTML Downloader: Fetches pages. Checks robots.txt cache first. Respects crawl-delay.
  • DNS Resolver: Cached (TTL ~1–5min) to avoid DNS lookup on every page
  • Content Parser: Parse and validate HTML. Reject malformed or non-HTML content.
  • Content Seen? (Dedup): Hash the body (SHA-256). If hash exists in store → skip. Avoids storing duplicate pages with different URLs.
  • Link Extractor: Extract all hrefs. Resolve relative URLs to absolute.
  • URL Filter: Remove blacklisted domains, non-HTML files, already-crawled URLs
  • URL Seen? (Dedup): Bloom filter (fast, probabilistic) + hash set (exact). If URL seen → don't re-enqueue.
Politeness Rules
  • Always check and obey robots.txt — defines disallowed paths per user-agent
  • Cache robots.txt per domain (re-check every few days)
  • Add crawl delay between requests to same domain (e.g. 1–2 seconds)
  • Use a per-domain queue — one back queue per host, ensure only one request in-flight per domain
  • Identify yourself honestly in User-Agent header
URL Frontier — Priority + Politeness
URL Frontier has two tiers: Front queues (prioritization — high PageRank goes to queue 1, low to queue N) and Back queues (politeness — one queue per hostname, ensures crawl delay between requests to same site).
  • Prioritizer: Assigns priority score based on PageRank, update frequency, traffic. High priority → dequeued more often.
  • Back queue router: Maps each hostname to a dedicated queue. Worker picks a non-empty back queue whose domain's next-crawl-time has passed.
  • Queue selector: Maintains a heap sorted by next-allowed-crawl-time per domain.

  • Run multiple crawl servers; partition URLs across servers by domain using consistent hashing

Common Follow-up Questions
Why BFS over DFS for crawling?
DFS can go arbitrarily deep into one branch — perfect for spider traps (infinite /next links). BFS explores breadth-first, ensuring you cover a wide range of pages at each depth level before going deeper. Also easier to implement politeness constraints.
How do you prioritize which pages to crawl first?
Multiple signals: PageRank (linked-to more = more important), update frequency (check HTTP Last-Modified headers), page freshness (when was it last crawled vs when it might have changed), and explicit sitemaps from site owners.
How would you scale to crawl 1 billion pages in 1 month?
1B pages / 30 days / 86400 sec = ~386 pages/sec per worker. With 1 second politeness delay per domain and say 1000 distinct domains queued = 1000 concurrent domain queues. ~400 crawl workers should handle this. Use Kafka for the URL frontier, S3 for content storage, distributed Bloom filter (Redis) for URL dedup.

Design a Notification System

Push · SMS · Email · Message Queues · Reliability · Deduplication
TL;DR One queue per channel (iOS, Android, SMS, Email). Workers call 3rd-party providers (APNs, FCM, Twilio, SendGrid). Persist every notification before queuing. Retry with backoff. Deduplicate with idempotency keys. Respect per-user opt-out settings.

Core Flow
  • Services (order service, auth service, etc.) call Notification Service API to trigger a notification
  • Notification Service validates input, fetches user device tokens and settings, builds payload, persists to DB, then enqueues to appropriate channel queue
  • Workers (one set per channel) pull from queues and call 3rd-party APIs
  • Separate queues per channel so a slow SMS provider doesn't block push notifications
Reliability Principles
  • Persist before enqueue: Save to DB first, then push to queue. On crash, can re-enqueue from DB.
  • Retry on failure: If 3rd-party returns 5xx, retry with exponential backoff (1s, 2s, 4s, 8s…)
  • Idempotency key: Each notification has a unique eventId. Workers check if already delivered before sending — prevents duplicate notifications on retry.
  • At-least-once delivery: May deliver twice on retry. Idempotency at consumer side handles this.
Device Registration Flow
  • On app install, device registers with APNs/FCM and receives a device token
  • App sends token + user_id to your backend → stored in user_devices table
  • Tokens expire or rotate → app must update token on each launch
  • Store multiple tokens per user (multiple devices, multiple apps)

Notification Settings — Opt-Out
  • Every notification should check user's preferences before sending
  • Settings table: (user_id, channel, notification_type, enabled)
  • Types: marketing, transactional, security alerts, social. Users can disable marketing but not security.
  • Never skip opt-out check — violating preferences is a legal and trust issue (GDPR, CAN-SPAM)
Rate Limiting Notifications
  • Cap at e.g. 3 marketing emails/day per user to prevent spam fatigue
  • Use the same Redis Token Bucket or Sliding Window Counter as Ch4
  • Priority tiers: security alerts bypass limits, marketing obeys strict limits
  • Notification templates reduce duplication and allow A/B testing copy
Analytics & Monitoring
  • Track: sent, delivered, opened, clicked, unsubscribed per notification
  • Webhook callbacks from APNs/FCM/Twilio report delivery status → update DB
  • Alert on: delivery failure rate spikes, queue depth growing, 3rd-party latency
  • Dead letter queue (DLQ) for permanently failed notifications — investigate manually

Common Follow-up Questions
How do you handle a 3rd-party provider (e.g. FCM) going down for 2 hours?
Messages accumulate in the Android queue. When FCM recovers, workers process the backlog. Important: use a dead letter queue with max-retry limit (e.g. 5 attempts over 30 min) to avoid infinite retries. Alert ops on DLQ depth. Consider SMS fallback for high-priority notifications.
How do you send 1 billion notifications efficiently?
Fan-out at the worker level: one "broadcast" event triggers a job that writes millions of individual notification records in bulk, then batches them into queue messages. Use batch APIs where supported (FCM supports up to 500 tokens per batch request). Scale workers horizontally.
How do you handle device token refresh (APNs/FCM rotate tokens)?
When a send fails with "invalid token" error from APNs/FCM, delete or mark the token as invalid in DB. The app will register a new token on next launch. For FCM, token rotation is automatic — listen to the token refresh callback in the SDK and update your backend.
