Scale From Zero to Millions of Users

Load balancers · DB replication · Caching · CDN · Sharding
The Big Picture
Analogy — The Lemonade Stand
Day 1: you're the cashier, chef, and waiter. One million customers? You need staff, multiple stands, a warehouse, and delivery trucks. Every technique in this chapter is one more hire or one more stand.
Step-by-Step Scaling Journey
  • Single server: Web app, DB, and cache all on one box. Fine for Day 1. Every outage takes everything down at once.
  • Separate web & DB tiers: Web servers scale independently of the DB. Each does one job. First architectural split.
  • Load balancer: Users hit the LB IP; LB round-robins requests to Web Server 1 and Web Server 2. If one server dies, the LB stops sending traffic to it. No more single-point-of-failure for web tier.
  • DB replication: One master for writes; one or more slaves for reads. Slave fails → promote another slave. Master fails → a slave is promoted to master. Read-heavy workloads scale by adding slave replicas.
  • Cache (Memcached/Redis): Cache-aside pattern: check cache first → if miss, read DB → write result to cache with TTL. Never cache mutable data that must be consistent; set a TTL to prevent stale reads.
  • CDN: Static assets (images, JS, CSS) stored at edge nodes near users. On cache hit, served from edge — fast. On miss, CDN fetches from origin and caches it. Use TTL or versioned filenames for cache invalidation.
  • Stateless web tier: Remove session state from web servers; move to Redis. Now any server can handle any user's request → true horizontal scale without sticky sessions.
  • Message queues: Decouple slow async work (image resize, email send). Producer adds task to queue and returns immediately. Consumer processes at its own pace. If consumers are overwhelmed, scale them horizontally — producer is unaffected.
  • DB sharding: Split rows across multiple DB shards by a shard key (e.g. user_id % N). Each shard holds a subset of data. Enables horizontal DB scale. Downsides: no cross-shard JOINs; resharding is painful when N changes; hotspot keys overload one shard.
  • Multiple data centres: Active-active setup across geographically separated DCs. Users routed to nearest DC. Requires data replication across DCs and a strategy to handle divergent writes.

Interview Questions
When should you add a load balancer?
Click to reveal answer
When a single web server can't handle peak QPS, or when you can't afford a web-tier outage. A load balancer also enables zero-downtime deploys — take servers in/out of rotation one at a time.
What is the difference between vertical and horizontal scaling?
Click to reveal answer
Vertical (scale up): Move to a bigger machine — more CPU, RAM. Simple, no code changes, but has a hardware ceiling and is a single point of failure. Horizontal (scale out): Add more machines. No ceiling in theory. Requires stateless design so any server can handle any request. Horizontal is the approach used at every large-scale system.
Why move session state to Redis instead of keeping it on web servers?
Click to reveal answer
If session data lives on Web Server 1, you need "sticky sessions" (a user must always go to Server 1). This breaks load balancing — one server can be overloaded while others are idle. Moving session state to a shared Redis allows any server to serve any user, enabling true horizontal scale and zero-downtime server replacements.
What are the drawbacks of database sharding?
Click to reveal answer
1) No cross-shard JOINs — data for a join may live on different shards; must do it in application code. 2) Resharding pain — when shard count changes, you must redistribute data, often requiring downtime or a complex migration. 3) Hotspot keys — if one user generates disproportionate load, their shard becomes a bottleneck. 4) Complexity — routing logic, schema changes, and debugging all become harder.

Worked Example — Twitter QPS & Storage
  • Assumptions: 300M MAU, 50% DAU = 150M DAU
  • Write QPS: Each user posts 2 tweets/day → 300M tweets/day ÷ 86,400s ≈ 3,500 QPS; peak ≈ 7,000 QPS
  • Read QPS: Users read ~10× more than they write → ~35,000 QPS read (much higher than write — design for read scale)
  • Storage: 10% of tweets have media (30M/day × 1MB) = 30 TB/day new media storage; text alone ≈ 300M × 280 bytes ≈ 84 GB/day (negligible vs media)
  • Process: State assumptions → derive DAU → estimate QPS (writes first, then read multiplier) → estimate storage (separate text from media)
Interview Questions
What's the read QPS for a system with 10M DAU, each making 5 reads/day?
Click to reveal answer
10M × 5 ÷ 86,400 ≈ 580 QPS average. Peak (assume 2–3×) ≈ 1,200 QPS. Always state your peak multiplier assumption out loud — interviewers want to see the reasoning, not just the number.
How much storage for 1B users uploading one 4MB photo per year?
Click to reveal answer
1B × 4MB = 4 × 10¹⁵ bytes = 4 PB/year. Daily ingest: 4PB ÷ 365 ≈ 11 TB/day. This tells you immediately that you need distributed blob storage (S3 / GCS), not a relational DB, and that a CDN is essential.
Why does knowing latency numbers help in architecture design?
Click to reveal answer
SSD reads take 0.1ms, HDD takes 10ms — 100× difference. If your request budget is 50ms, you can afford ~500 SSD reads but only ~5 HDD reads. This directly tells you whether you need caching and whether to use SSDs over HDDs for your hot data tier. Without these numbers, architecture decisions are guesswork.

A Framework for System Design Interviews

The 4-step recipe · Time budgets · What interviewers actually grade
Why You Need a Framework
Analogy — The Doctor's Appointment
A doctor doesn't start cutting before asking about symptoms, history, and allergies. They clarify, diagnose, propose treatment, then explain trade-offs. Rushing straight to treatment kills patients. Rushing straight to a design without clarifying requirements fails interviews.
The 4 Steps (with Time Budgets for a 45-min Interview)

Step 1 — Clarify (5 min)

  • What are the must-have features?
  • What is the scale? (DAU, QPS)
  • Read-heavy or write-heavy?
  • Consistency or availability priority?
  • Mobile, web, or both?
  • Any existing infra to reuse?

Step 2 — Estimate (5 min)

  • QPS (write, read, peak)
  • Storage (daily ingest × years retained)
  • Bandwidth (QPS × avg payload)
  • State all assumptions out loud
  • Round aggressively — ±1 order of magnitude is fine

Step 3 — High-Level Design (20 min)

  • Draw boxes and arrows first
  • API layer → services → storage
  • Agree with interviewer before diving deep
  • Name your databases by type (SQL, KV, blob)
  • Show the happy path end-to-end

Step 4 — Deep Dive (10 min)

  • Interviewer picks the hard part
  • "I'd choose X because Y; the trade-off is Z"
  • Discuss bottlenecks and how to fix them
  • Talk about failure modes
  • Mention monitoring / alerting
Common Mistakes to Avoid
  • Jumping straight to solutions: The interviewer is grading your process. Spend 5 minutes clarifying even if you think you know the answer.
  • Going too deep too early: Don't spend 20 minutes on the DB schema before drawing the high-level architecture. Agree on scope first.
  • Not explaining trade-offs: Every design choice has a cost. Saying "I'll use Redis" without explaining why is incomplete. "I'll use Redis because it supports sorted sets for the feed, trade-off is it's in-memory so I need persistence config" is the answer.
  • "It depends" without continuing: Say what it depends on, then give your recommendation for this specific scenario.
  • Silence: Think out loud at all times. The interviewer cannot grade what they cannot hear.
  • Ignoring non-functional requirements: Latency SLA, consistency, fault tolerance, and cost are as important as the happy path.
Interview Questions
What should you ask before starting to design?
Click to reveal answer
At minimum: (1) What are the most important features? (2) What is the scale — DAU, peak QPS? (3) What's the latency SLA? (4) Consistency or availability priority? (5) Is this read-heavy or write-heavy? These answers completely change the architecture — a 1,000 QPS read-heavy system looks nothing like a 1M QPS write-heavy one.
How much time should you spend on each step in a 45-minute interview?
Click to reveal answer
Clarify: ~5 min. Estimate: ~5 min. High-level design: ~20 min. Deep dive: ~10 min. Wrap-up / questions: ~5 min. Most candidates spend too long on estimation or get lost in one deep-dive area. Use the interviewer's cues — if they keep asking "what about X?" they want you to move to X.
What's the biggest mistake candidates make in system design interviews?
Click to reveal answer
Jumping straight to a solution. Interviewers want to see how you think: do you gather requirements, make trade-offs explicit, and structure your reasoning? A candidate who dives straight into "I'd use Kafka" without any clarification tells the interviewer nothing useful — the right tool depends entirely on requirements you haven't asked about yet.

Design a Rate Limiter

Throttle API calls · Prevent abuse · Control traffic flow
What is a Rate Limiter?
Analogy — The Nightclub Bouncer
Imagine a nightclub that allows max 100 people per hour. The bouncer counts entries and turns people away once the limit is hit. The rate limiter is that bouncer — it lets a certain number of requests through and rejects the rest with a "429 Too Many Requests" response.
  • Goal: Limit how many API requests a user/IP/service can make in a given time window
  • Prevent DoS/DDoS: Without rate limiting, a single bad actor can flood your servers with millions of requests per second, crashing them for everyone else
  • Reduce costs: Cloud services charge per request — uncontrolled usage = huge bills
  • Enforce fair use: Free tier = 100 req/day, paid tier = unlimited. Rate limiter enforces these tiers
  • Stop bots: Brute-force login attacks try thousands of passwords per second — rate limit stops them cold
Token Bucket — How It Works
Where to Put the Rate Limiter?
  • Client-side: Useless. Attackers simply ignore it. Never rely on client-side limits for security
  • Server-side middleware: Before the request hits your business logic. Clean separation of concerns — your app code doesn't need to know about rate limiting
  • API Gateway: A managed layer that already handles SSL termination, auth, routing. Adding rate limiting here is efficient — one config rules them all (used by AWS API Gateway, Kong, Nginx)
  • Rule of thumb: Already have an API Gateway? Add limits there. Building from scratch? Use server-side middleware. Microservices? Put it at the gateway so each service doesn't re-implement it
Rate Limiter Placement — Architecture
5 Core Algorithms — Explained Simply

1. Token Bucket

  • Imagine a bucket that holds N tokens. Tokens drip in at a fixed rate (e.g. 10/sec). Each request "spends" 1 token. If empty → reject
  • Burst-friendly: can send 50 requests instantly if bucket has 50 tokens
  • ✓ Allows bursts up to bucket size
  • ✓ Simple & memory efficient
  • Used by: AWS, Stripe

2. Leaking Bucket

  • Requests enter a fixed-size FIFO queue. They "leak out" (get processed) at a constant rate. If queue is full → new requests dropped
  • Like a bucket with a small hole — water (requests) drips out steadily regardless of how fast water pours in
  • ✓ Smooth, predictable output rate
  • ✗ Burst of old requests on restart

3. Fixed Window Counter

  • Divide time into fixed windows (e.g. every minute). Count requests per window. Reset counter at window boundary
  • Simple: just increment a Redis counter with TTL
  • ✓ Simple, very memory efficient
  • ✗ Boundary spike: 100 at 00:59 + 100 at 01:01 = 200 in 2 seconds

4. Sliding Window Log

  • Store the exact timestamp of every request. To check limit, count timestamps within the last N seconds. Evict old ones
  • Most accurate — no boundary spike problem
  • ✓ Very accurate, no edge-case spikes
  • ✗ High memory: stores every timestamp even for rejected requests

5. Sliding Window Counter ✓

  • Hybrid: current window count + (previous window count × overlap ratio). E.g. if you're 30% into the current minute, use 70% of last minute's count
  • Formula: prev_count × (1 - overlap%) + cur_count
  • ✓ Accurate and memory efficient
  • ✓ Most widely used in practice
Fixed Window — Boundary Spike Problem
Distributed Rate Limiting — The Hard Part
Analogy — Multiple Ticket Windows
Imagine a concert venue with 5 ticket counters, each independently tracking how many tickets they've sold. Counter A sells 100, Counter B sells 100 — now you've oversold by 400! You need a shared counter that all windows update atomically.
  • Race condition: Two rate limiter nodes both read counter = 99, both see it's under limit of 100, both increment to 100. You now have 101 requests through. Fix: use Redis INCR (atomic) or a Lua script for read-increment-check atomicity
  • Centralized Redis: All rate limiter nodes share a single Redis cluster as the source of truth. Trade-off: Redis is now a bottleneck and single point of failure (mitigate with Redis Cluster / Sentinel)
  • Sticky sessions: Route same user always to same rate limiter node. Works but breaks when a node dies and re-balancing kicks in
  • Local + global: Each node tracks local count + syncs to Redis every N ms. Slightly inaccurate but highly available and fast

Interview Questions
What's the difference between Token Bucket and Leaking Bucket?
Click to reveal answer
Token Bucket allows bursting — if tokens have accumulated, you can send many requests instantly. Leaking Bucket enforces a strict constant output rate — it smooths out traffic like a queue draining at fixed speed. Use Token Bucket for APIs where bursts are acceptable. Use Leaking Bucket for downstream services that can't handle spikes (e.g. payment processors).
Why does Fixed Window Counter have a boundary spike problem?
Click to reveal answer
Suppose limit is 100 req/min. A user sends 100 requests at 00:59 (last second of window 1) and 100 more at 01:01 (first second of window 2). Both windows show 100 — within limit! But in the 2-second span around the boundary, 200 requests got through. Sliding Window Counter fixes this by blending counts from both windows.
How do you handle rate limiting in a distributed system?
Click to reveal answer
Use a centralized Redis store that all rate limiter nodes share. Use Redis's atomic INCR command with a TTL to count requests per key (user ID / IP). Use a Lua script for compound operations (check + increment atomically). For high availability, run Redis in cluster mode. The trade-off is Redis becomes a dependency — add connection pooling and circuit breakers.
How would you rate limit by user ID, IP, and API endpoint simultaneously?
Click to reveal answer
Use composite keys in Redis: ratelimit:{userId}:{endpoint}, ratelimit:{ip}. Check all relevant keys for each request. A request can be blocked if any key exceeds its limit. Endpoint-level limits prevent one expensive endpoint from consuming all quota. Apply limits hierarchically: IP → user → endpoint (most specific wins).
What are the trade-offs between hard vs soft rate limiting?
Click to reveal answer
Hard limit: Strictly block at threshold. Simple, predictable, but jarring — user at 100 requests sees 429 on request 101 instantly. Soft limit: Allow small overages (e.g. 10% burst), throttle with backpressure instead of rejection. Better UX, harder to configure correctly. Most production systems use hard limits with generous thresholds plus burst allowances.

Design Consistent Hashing

Minimize key remapping when servers join or leave
The Problem — Why Normal Hashing Breaks
Analogy — Assigning Rows at a Restaurant
Imagine 4 waiters (servers). Tables are assigned by table_number % 4. Waiter 0 covers tables 0,4,8,12... everything works. Then waiter #3 quits. Now % 3 gives completely different assignments — almost every table gets a new waiter. Chaos. That's what normal modulo hashing does when a server is added/removed.
  • Normal formula: serverIndex = hash(key) % N where N = number of servers
  • Add or remove 1 server → N changes → almost every key maps to a new server
  • In a cache cluster, this means a sudden cache miss storm — all traffic hits the database simultaneously, potentially crashing it
  • Real example: you have 4 Redis cache nodes. Node 2 crashes. With naïve hashing, ~75% of all cache keys now route to wrong nodes → 75% cache miss rate → DB gets hammered
The Solution — Hash Ring
Analogy — Clock with Server Stations
Imagine a clock face (0 to 360°). Servers are placed at positions on the clock. A key is also placed at a position (via hashing). The key "belongs to" the first server you encounter going clockwise. If a server is removed, only the keys between it and its predecessor need to move — everyone else stays put.
  • Hash ring: A circular number line from 0 to 2³²−1 (about 4 billion positions)
  • Server placement: Each server's name/IP is hashed to a position on the ring
  • Key assignment: Hash the key → find position → walk clockwise → first server you hit owns that key
  • Adding a server: Only keys between the new server and its predecessor move. Formally, only k/n keys move (k = total keys, n = servers)
  • Removing a server: Its keys move to the next server clockwise. Other servers are completely unaffected
  • Why k/n is impressive: With 1M keys and 10 servers, removing one server only remaps ~100K keys instead of ~900K with naïve hashing
Hash Ring — Keys Map to Next Server Clockwise
Problem: Uneven Distribution — The "Hot Spot" Issue
Edge Case
With few servers, positions on the ring may be clustered — Server A gets a small slice, Server B gets a huge slice. Server B becomes overloaded while A sits idle. This is the "hot partition" problem.
  • Solution: Virtual Nodes — each physical server gets multiple positions on the ring (e.g. Server A gets positions at 12°, 84°, 201°, 330°...)
  • These fake positions are called "virtual nodes" or "vnodes"
  • With 100+ virtual nodes per server, the distribution evens out dramatically via the law of large numbers
  • Trade-off: More virtual nodes = better balance but more memory to store the ring (typically 100–200 vnodes per server is the sweet spot)
  • Heterogeneous servers: Powerful servers can get more virtual nodes (proportional to capacity) — elegant way to weight servers differently
Virtual Nodes — Each Server Gets Multiple Ring Positions

Interview Questions
Why do we need consistent hashing? What problem does it solve?
Click to reveal answer
Normal modulo hashing (hash(key) % N) requires remapping nearly all keys when N changes (a server is added/removed). In a cache cluster, this causes a thundering herd — all requests miss cache simultaneously and pound the database. Consistent hashing ensures only 1/N of keys need remapping when one server changes, making the transition smooth and database-safe.
What are virtual nodes and why are they needed?
Click to reveal answer
With few physical servers, their positions on the hash ring may cluster unevenly — one server could own 60% of the ring while another owns only 5%. Virtual nodes solve this by giving each server many positions on the ring (100–200 is typical). With many positions spread across the ring, each server ends up owning roughly equal shares. Bonus: servers with more RAM/CPU can get more virtual nodes to handle proportionally more traffic.
How would you handle a hot partition in consistent hashing?
Click to reveal answer
Hot partitions happen when many popular keys hash to the same server. Fixes: (1) Increase virtual nodes for the overloaded server — splits its ring segment into smaller pieces. (2) Add a new server that takes over a slice of the hot server's range. (3) Use key splitting — append a random suffix to hot keys and scatter them across multiple servers. (4) Application-level caching (local cache) to absorb repeated reads for the same keys.
How does consistent hashing differ from Redis Cluster's approach?
Click to reveal answer
Redis Cluster uses a fixed 16,384 hash slot approach — each key maps to one of 16,384 slots via CRC16, and slots are assigned to nodes. This is conceptually similar to consistent hashing but with a fixed ring size. Consistent hashing uses a continuous ring. Both minimize key movement on topology changes. Redis's approach is simpler to reason about and implement in client SDKs at the cost of less flexibility.

Design a Key-Value Store

Distributed NoSQL · CAP Theorem · Quorum · LSM Tree
CAP Theorem — The Fundamental Constraint
Analogy — The Bank vs The Social Feed
Imagine your bank balance. If you transfer $500 and immediately check your balance from a different ATM, you MUST see the updated balance. Stale data = real money problems. That's Consistency. Now imagine Instagram's feed. If a post takes 2 seconds to appear on all servers, that's fine — slightly stale is acceptable but you can't afford Instagram going down for everyone just because one data center lost power. That's Availability. The choice between these is CAP.
  • CAP: a distributed system can guarantee only 2 of 3: Consistency, Availability, Partition Tolerance
  • Partition Tolerance is non-negotiable — networks always partition eventually (cable cut, router crash). So the real choice is C vs A
  • CP (Consistency + Partition Tolerance): If a partition happens, block writes until consistency is restored. Accept downtime, never return stale data. Examples: HBase, Zookeeper, traditional RDBMS
  • AP (Availability + Partition Tolerance): During partition, keep serving (possibly stale) data. Sync up later. Examples: Cassandra, DynamoDB, CouchDB
  • When to use CP: financial transactions, inventory management, anything where stale reads cause real harm
  • When to use AP: social feeds, user profiles, product recommendations — stale by 1 second is fine
CAP Theorem — Pick Two (but P is mandatory)
Data Replication — Don't Lose Data
  • Why replicate? A single-node store loses all data if that machine dies. N replicas mean N-1 failures before data loss
  • How: Use consistent hashing ring. When writing key K, walk clockwise from K's position and write to the next N unique physical servers (skip virtual nodes of same physical machine)
  • Typical N=3: Each piece of data lives on 3 different machines in different racks or data centers
  • Cross-DC replication: Spread replicas across availability zones to survive data center outages
Quorum Consensus — Read/Write Trade-offs
Analogy — A Committee Vote
To pass a law, you need majority approval. Quorum works the same: to "confirm" a write, you need W out of N servers to acknowledge it. To "confirm" a read, you need R out of N servers to agree. The key insight: if W + R > N, at least one server that participated in the write must also participate in the read — guaranteeing you see the latest value.

Conflict Resolution — Vector Clocks
Analogy — Google Docs vs. Dropbox
Two people edit the same document offline. When they reconnect, who wins? Google Docs merges changes (conflict resolution). Dropbox creates two conflicting copies and asks you to choose. Distributed key-value stores face the same problem — two writes to the same key on different replicas, which one is "correct"?
  • Versioning: Each write creates a new version (never overwrite). Conflicts arise when two versions neither dominates the other
  • Vector clock: A list of [server, version] pairs. Every write increments the version for the server that handled it
  • If clock A dominates clock B (all A's values ≥ B's), A is newer — no conflict
  • If neither dominates (A has higher v on server 1, B has higher v on server 2) → conflict, needs resolution
  • Resolution pushed to client: Amazon's shopping cart example — if two devices add different items offline, the cart merges both (union). The client sees both versions and merges them
  • Downside: Vector clocks grow with number of servers that touched the key. Cap size by removing oldest entries (may lead to false conflicts)
Vector Clock — Step-by-Step Conflict Example
Failure Detection & Handling
  • Gossip protocol: Each node maintains a membership list (node ID + heartbeat counter). Every second, gossip to 2–3 random nodes. If a node's heartbeat hasn't increased after N rounds → suspect it's dead. Like office rumors — news spreads quickly without a central coordinator
  • Sloppy quorum: The "first W/R healthy servers" during a partition, not necessarily the intended replicas. Keeps availability high
  • Hinted handoff: If node A is down, node B handles A's writes and stores a "hint" (a note saying "deliver this to A when it comes back"). When A recovers, B ships the hint. Like leaving a note for a sick coworker
  • Anti-entropy (Merkle Trees): To sync two replicas, don't compare every key — instead compare a tree of hashes. If top hashes match, everything is in sync. If not, drill down to find exactly which keys differ. Minimizes data transfer for repair
Merkle Tree — Efficiently Finding Which Data Differs
Write & Read Path — LSM Tree + SSTable
Analogy — Sticky Notes → Folder → Filing Cabinet
You jot quick notes on sticky notes (Memtable in RAM — fast). When sticky notes pile up, you copy them to a folder (SSTable on disk). Over time, folders are merged into organized filing cabinet drawers (compaction). To find something, check your desk first, then recent folders, then older ones.

  • Commit log (WAL): Written to disk first, sequentially (fast). If crash before Memtable flush → replay log on restart
  • Memtable: In-memory sorted map (like a Red-Black tree). Blazingly fast writes and reads for hot data
  • SSTable: When Memtable exceeds size threshold, flush to disk as sorted, immutable file. Multiple SSTables are periodically merged (compacted) to reclaim space and speed up reads
  • Bloom filter: A probabilistic data structure — "definitely not in this SSTable" or "might be here." Skips reading SSTables that definitely don't contain the key. Makes reads much faster
Interview Questions
Explain CAP theorem. Which would you pick for a banking app vs. a social media app?
Click to reveal answer
CAP: you can only guarantee 2 of {Consistency, Availability, Partition Tolerance}. Since partitions are unavoidable, choose C or A. Banking → CP: A user sees an incorrect balance is a serious bug. Worth accepting brief unavailability to ensure reads are never stale. Social media → AP: A post appearing 500ms late on a different device is invisible to users, but crashing the feed for everyone during a network blip is very visible. Accept eventual consistency.
What is a quorum? How do W + R > N guarantee strong consistency?
Click to reveal answer
Quorum = minimum number of nodes that must agree for an operation to succeed. With N=3, W=2, R=2: any write is confirmed by 2 nodes. Any read consults 2 nodes. Since W+R=4 > N=3, at least 1 node that confirmed the write must be in the read set. That node returns the latest version. This overlap guarantees you never read data older than the last committed write.
What is gossip protocol and how does it detect failures?
Click to reveal answer
Gossip protocol is a decentralized failure detection mechanism. Each node keeps a membership list with heartbeat counters. Every few seconds, each node increments its own heartbeat and sends its list to a few random peers. Peers merge lists, taking the max heartbeat per node. If a node's heartbeat hasn't increased after a timeout threshold (e.g. 10 gossip rounds), it's marked suspicious → suspected dead → declared dead after further confirmation. No central coordinator needed — information spreads like a virus through the cluster.
Why use LSM Trees instead of B-Trees for a write-heavy key-value store?
Click to reveal answer
B-Trees do random I/O — updating a value means seeking to its position on disk and overwriting. This is expensive on spinning disks (HDDs) and causes write amplification on SSDs. LSM Trees (Log-Structured Merge Trees) convert random writes into sequential writes — append to commit log, buffer in memory, then flush as sequential SSTable files. Sequential I/O is 10–100× faster than random I/O. The trade-off: reads may need to check multiple SSTables (bloom filters mitigate this). Used by: RocksDB, Cassandra, LevelDB.
How do vector clocks detect and resolve write conflicts?
Click to reveal answer
A vector clock is a list of (server, version) pairs. Each server increments its own counter on every write. To check if version A supersedes B: if every counter in A ≥ corresponding counter in B (and at least one is strictly greater), A is newer — no conflict. If A has higher counter on server1 but B has higher counter on server2, neither dominates — there's a conflict. The application (or a merge function) must resolve it. Amazon DynamoDB uses this for shopping cart merges — union of items from both conflicting versions.

Design a Unique ID Generator in Distributed Systems

Global uniqueness · Time-sortable · 64-bit · Twitter Snowflake
Why Not Just Use a Database Auto-Increment?
Analogy — DMV Ticket Numbers
At a DMV, there's one machine that dispenses ticket numbers sequentially. Works great for one building. But imagine 100 DMV offices each needing to issue globally unique ticket numbers without talking to each other. You can't have one central machine — it becomes a bottleneck. This is exactly the problem with DB auto-increment at scale.
  • A single DB auto-increment is a bottleneck and single point of failure — all ID generation goes through one machine
  • Multi-master DB (each server increments by N): Server 1 generates 1, 3, 5... Server 2 generates 2, 4, 6... Works but IDs aren't time-sortable and adding servers is complex
  • UUID (128-bit): Globally unique, no coordination needed, but 128 bits is large, not sortable, not numeric — bad for DB primary keys (index fragmentation)
  • Ticket server (Flickr's approach): Dedicated DB server just for ID generation. Simple, but single point of failure
Requirements — What the Ideal ID Looks Like

Twitter Snowflake — The Solution
Analogy — A License Plate
A license plate encodes multiple pieces of info in a fixed format: state code + year + serial number. Each part has a fixed width. You can read the plate and instantly know which state issued it and roughly when. Snowflake IDs are the same — a fixed-width 64-bit number where different bit segments encode different info.

  • Bit 63 (Sign): Always 0 — ensures the 64-bit number is positive (Java's long is signed)
  • Bits 22–62 (41-bit timestamp): Milliseconds since a custom epoch (e.g. Twitter uses Nov 04, 2010). 2⁴¹ ms ≈ 69 years of IDs before overflow. Larger timestamps = larger IDs = time-sorted automatically!
  • Bits 17–21 (5-bit datacenter ID): 2⁵ = 32 possible data centers. Each DC is assigned a unique ID at startup
  • Bits 12–16 (5-bit machine ID): 32 machines per DC × 32 DCs = 1,024 total machines can generate IDs simultaneously with zero coordination
  • Bits 0–11 (12-bit sequence): Counter that resets to 0 every millisecond. 2¹² = 4,096 IDs per millisecond per machine = ~4 million IDs/sec per machine
  • Why IDs are sortable: Timestamp is the high-order bits, so sorting 64-bit IDs numerically gives you time order
The Clock Skew Problem
Critical Edge Case
NTP (Network Time Protocol) can cause system clock to go backward slightly. If clock goes back 5ms, the machine might generate IDs with a timestamp from "the past" — colliding with IDs already generated in that millisecond range!
  • Detection: Track the last-used timestamp. If current time < last timestamp, the clock went backward
  • Fix: Pause ID generation until current time catches up to last timestamp. For small skews (<10ms) this pause is imperceptible
  • Large skews: Log a critical alert — investigate the NTP configuration. Consider using a monotonic clock that never goes backward
Interview Questions
Why is UUID not a good choice for a distributed ID generator?
Click to reveal answer
UUIDs are 128-bit (vs. 64-bit for Snowflake), so they take twice the storage. They're not time-sortable (random UUID v4 or non-sequential UUID v1), which causes B-tree index fragmentation — as new IDs are inserted randomly throughout the index, not at the end, causing expensive page splits and cache misses. They're also non-numeric strings, which require more space in joins and comparisons. Snowflake IDs are 64-bit integers that fit in a database BIGINT column, are auto-sorted by time, and are far more index-friendly.
How many IDs per second can a single Snowflake machine generate?
Click to reveal answer
12-bit sequence = 4,096 IDs per millisecond = ~4,096,000 IDs per second per machine. With 1,024 machines (32 DCs × 32 machines), that's about 4 billion IDs/second globally. Twitter's actual peak is a few million tweets/day — Snowflake vastly overprovisioned, which is fine. The math: 4096 IDs/ms × 1000 ms/sec = 4,096,000 IDs/sec/machine.
How long will 41-bit timestamp Snowflake IDs last before they overflow?
Click to reveal answer
2⁴¹ milliseconds = 2,199,023,255,552 ms ÷ 1000 ÷ 60 ÷ 60 ÷ 24 ÷ 365 ≈ 69.7 years. Twitter chose a custom epoch of Nov 4, 2010, so IDs will be valid until around 2079. After that, the timestamp bits overflow. Solution: shift the custom epoch forward before overflow, or migrate to a larger ID scheme. (Fun fact: this is a "Y2K38" type problem for Snowflake systems.)
What happens if two machines have the same machine ID in Snowflake?
Click to reveal answer
They would generate identical IDs at the same millisecond for the same sequence number — a collision catastrophe. Prevention: machine IDs must be assigned and managed centrally at startup. Common approaches: (1) Use Zookeeper to atomically assign and lease machine IDs. (2) Store machine IDs in a config DB with uniqueness constraints. (3) Assign IDs based on host IP (risky — IPs can be reused). Zookeeper is the standard production approach — it provides distributed coordination with atomic operations.

Design a URL Shortener

Hashing · Base62 · HTTP Redirect · Read-heavy caching
What Are We Building?
Analogy — Coat Check at a Restaurant
You walk in with a big coat (long URL). The coat check gives you a small ticket (short code). The ticket is easy to carry around. When you want your coat back, you hand in the ticket and get the full coat. The system needs to: issue unique tickets, store the ticket-to-coat mapping, and look up coats quickly when tickets are returned.
  • Input: https://www.example.com/very/long/path/that/is/hard/to/share?utm_source=...
  • Output: https://tinyurl.com/abc123 → redirects to the original URL
  • Two core operations: (1) Shorten: long URL → short code. (2) Expand: short code → redirect to long URL
  • Traffic estimate: 100M URLs shortened per day = 1,160 writes/sec. Read:write = 100:1 = 116,000 reads/sec. Very read-heavy → optimize for reads
API Design
  • POST /api/v1/data/shorten — body: {"longUrl": "https://..."} → response: {"shortUrl": "https://tinyurl.com/abc123"}
  • GET /{shortCode} → HTTP 301 or 302 redirect to long URL
  • Idempotency: If the same long URL is shortened twice, should we return the same short URL? Yes for deduplication, but it requires checking existence before insert (a DB read per write). Trade-off: simpler implementation generates a new code each time
301 vs 302 Redirect — A Critical Detail
CodeMeaningBrowser Caches?Server Sees Subsequent Requests?Best For
301 Permanent This URL has moved permanently Yes — browser caches and redirects locally No — after first visit, browser goes directly to destination Reduce server load, save bandwidth. Sacrifice click analytics
302 Temporary This URL is temporarily elsewhere No — browser asks server every time Yes — every redirect goes through your server Track every click. Full analytics. Higher server load
Interview tip: If the interviewer asks "how do you track clicks?" — use 302. If they ask "how do you minimize latency/cost?" — use 301. If analytics are important (most commercial URL shorteners), 302 is the right answer.
Two Approaches to Generate Short Codes

Approach 1: Hash + Collision Resolution

  • Hash the long URL: MD5 or SHA-256 → 128-bit output
  • Take first 7 characters of the hash
  • Collision: if that short code already maps to a different long URL, append a suffix to the long URL and re-hash
  • Use bloom filter to quickly check if short code exists before DB query
  • ✗ Must query DB on every write to check collision
  • ✗ Hard to guarantee URL-safe characters

Approach 2: Base62 Encoding ✓ (Recommended)

  • Generate a unique 64-bit ID (using Snowflake or DB auto-increment)
  • Encode the ID in Base62 (digits 0-9, a-z, A-Z)
  • 62⁷ ≈ 3.5 trillion unique 7-char codes
  • ID 123456789 → Base62 → "8M0kX"
  • ✓ Zero collisions by design
  • ✓ No DB lookup needed during creation
  • ✗ IDs are predictable (sequentially enumerable)
Why Base62?
Think of it like a number system with 62 digits instead of 10. Just as decimal number 255 is "FF" in hex (base 16), we can express large numbers very compactly in base 62. The number 3,521,614,606,208 expressed in base 62 with 7 characters gives us ~3.5 trillion unique short codes.
Full System Architecture
URL Shortener — Write Path vs Read Path
  • Cache layer (Redis): Stores shortCode → longURL mappings. Cache hit = 0 DB queries = sub-millisecond redirect. Cache eviction: LRU (least recently used). Cache hit rate for popular URLs approaches 100%
  • Database: NoSQL (e.g. Cassandra or DynamoDB) — no complex joins needed. Schema: shortCode (PK), longUrl, userId, createdAt, expiresAt
  • Write path: User sends long URL → generate ID → encode to Base62 → save to DB → cache it → return short URL
  • Read path: Request for short code → check Redis → if miss, check DB → cache result → 301/302 redirect
  • Scale: With 100M URLs/day stored for 5 years = 182.5B records = ~180TB of data. Use sharding by shortCode prefix
Interview Questions
How would you handle custom short URLs (e.g. bit.ly/mycompany)?
Click to reveal answer
Store custom aliases in the same table. Add a isCustom flag and validate that the alias contains only URL-safe characters. Check uniqueness before saving. Custom aliases should never be overwritten — return an error if the alias exists. Reserve certain words as system aliases (e.g. "api", "admin"). Rate limit custom alias creation per user to prevent squatting. A separate index on the alias column ensures fast lookups.
How would you implement link expiration?
Click to reveal answer
Store an expiresAt timestamp in the DB. On each redirect request, check if expiresAt is in the past — if yes, return 410 Gone. For cleanup, run a background job (cron or Kafka consumer) that periodically scans for expired links and deletes them. Also add a Redis TTL to cached entries matching the expiration time — expired links auto-evict from cache. Don't rely solely on Redis TTL (cache might be cold after restart).
How would you scale the URL shortener to handle 100K redirects per second?
Click to reveal answer
Redis cache is the key — popular URLs get cached and serve redirects without touching the DB. Scale Redis horizontally with cluster mode. Add read replicas to the DB. Use CDN (CloudFront) to cache 301 redirects at edge nodes globally — the redirect itself never hits your servers for permanently cached URLs. Use connection pooling and async I/O on web servers. Scale web servers horizontally behind a load balancer. At 100K req/sec, the bottleneck is usually DB for cache misses — use read replicas and DB sharding.
Why use NoSQL instead of a relational database?
Click to reveal answer
The URL shortener access pattern is simple: put(key, value) and get(key). No joins, no complex transactions, no aggregations. Relational databases shine for structured queries but add overhead for simple key-value lookups at massive scale. NoSQL (Cassandra, DynamoDB) provides horizontal scalability, automatic sharding, and high availability out of the box. The trade-off: no ACID transactions, no foreign key constraints — but we don't need them here. The primary concern is throughput and partition tolerance.

Design a Web Crawler

BFS traversal · Politeness · URL Frontier · Deduplication
What is a Web Crawler?
Analogy — A Librarian Cataloging All Books
Imagine a librarian who wants to catalog every book in existence. They start with a list of known books. For each book, they read it, catalog it, and note all books it references. Then they get those books, catalog them, note their references, and so on. The Web is the library. Pages are books. Links are references. The crawler is the librarian, doing a breadth-first search of infinite hyperlinked pages.
  • Search indexing: Google/Bing use crawlers to discover new pages for their search index
  • Web archiving: Internet Archive's Wayback Machine crawls and stores historical snapshots
  • Web mining: Extract prices from e-commerce sites, sentiment from news articles
  • Link checking: Detect broken links on websites
  • Scale at Google: ~15 billion web pages, re-crawl every few weeks. Must handle 100s of millions of URLs per day
Key Properties a Good Crawler Must Have
  • Scalability: Web has 5+ billion pages. Must be distributed across many machines, resumable after crashes
  • Robustness: Servers go down, pages timeout, HTML is malformed, infinite redirect loops. Crawler must handle all of these gracefully
  • Politeness: Don't hammer a single website — wait between requests to the same domain. Respect robots.txt (a file websites use to tell crawlers what they can/can't access)
  • Extensibility: Today you crawl HTML. Tomorrow you need to crawl PDFs, images, videos. Design for plug-in parsers
Core Architecture — How it Works
Web Crawler — Full Architecture Loop
  • Seed URLs: Initial starting points — popular domains, sitemaps. Quality seeds = broader coverage faster
  • URL Frontier: A queue (actually two levels — front queues for priority, back queues for politeness). This is the heart of the crawler — it decides which URL to fetch next
  • HTML Downloader: Fetches pages. First checks robots.txt cache. Handles timeouts, 3xx redirects, gzip decompression
  • DNS Resolver with cache: DNS lookups are slow (10–200ms). Cache domain → IP mappings with short TTL (~1 min). Saves huge time at scale
  • Content Parser: Validates HTML structure. Avoids storing garbage (malformed pages, error pages, spam)
  • Content Seen? (Deduplication): Hash the page body (SHA-256) and check if seen before. 30% of web pages are near-duplicates (mirrors, print versions)
  • Link Extractor: Parses all <a href="..."> tags. Converts relative URLs (/about) to absolute (https://example.com/about)
  • URL Filter: Skip: already-crawled, blacklisted domains, non-HTML content, URLs that are too long (spider trap indicator)
  • URL Seen? (Bloom Filter): Probabilistic set membership check — "have we crawled this URL?" Bloom filter is memory-efficient: 1 billion URLs stored in ~1GB RAM vs. 50GB in a hash set
URL Frontier — The Scheduler of the Crawler
Analogy — Airport Priority Lane + Gate Assignment
At an airport, first-class passengers (high-priority URLs like CNN.com) are processed first. But each airline gate (domain) has its own queue to avoid chaos — only one plane (request) departs each gate at a time, with spacing between departures. The URL Frontier is this two-level system.
  • Front queues (Priority): Multiple queues with different priorities. A "prioritizer" assigns URLs to queues based on PageRank, update frequency, traffic. High-priority URLs are fetched first
  • Back queues (Politeness): One queue per domain. A back queue router ensures all URLs for domain X go into queue X. Crawler workers pull from queues with a minimum delay between pulls from the same queue (e.g. 1 second)
  • Why back queues? Without them, a crawler might hit example.com 1000 times/second — a DDoS attack against that website. One queue per domain limits it to 1 req/second
  • Queue selector: Picks which back queue to pull from next. Round-robin among non-empty queues, but respects per-domain rate limits
  • Storage: URL frontier can have hundreds of millions of URLs. Store most on disk, keep a small in-memory buffer of "ready to fetch" URLs for performance
URL Frontier — Two-Level Queue Design
Robustness — Handling the Wild Web
  • Spider traps: Some sites generate infinite URLs (e.g. a calendar with infinite "next day" links: /calendar/2024/01/01, /calendar/2024/01/02...). Fixes: cap URL depth (max 10 hops), cap URL length (max 200 chars), track URL patterns and skip repeating patterns
  • Data noise: Ads, spam, low-quality auto-generated content. Filter via heuristics: text/link ratio, domain reputation, content quality scores
  • Crash recovery: Persist URL frontier state to disk periodically. On restart, resume from last checkpoint instead of starting over
  • Timeout + retry: If a page doesn't respond in 30 seconds, mark as timeout. Retry with exponential backoff (1s, 2s, 4s, 8s...). After 5 failures, mark as unreachable
  • Consistent hashing for distribution: Assign URLs to crawler workers by domain hash. All URLs for same domain → same worker → easier politeness management
BFS vs DFS — Why Crawlers Use BFS
Analogy — Exploring a City vs. a Deep Cave
BFS (Breadth-First Search) is like exploring a city block-by-block — you cover the whole neighborhood before venturing far. DFS (Depth-First Search) is like following one street as far as it goes before backtracking. For the web, BFS is better — it discovers popular, high-quality pages first (since they're heavily linked and thus close to seeds), rather than diving deep into obscure corners.
  • BFS advantage: Discovers all pages at depth 1, then depth 2, etc. Links with many incoming links (popular pages) tend to have short paths from seeds → BFS finds important content first
  • DFS problem: Could get lost in an infinite deep path (spam site linking to itself recursively) before crawling any other sites
  • Priority BFS: Extend basic BFS with priority scores — high-PageRank URLs jump the queue. This is what real crawlers use

Interview Questions
How do you handle duplicate content in a web crawler?
Click to reveal answer
Two types of duplicates: (1) Duplicate URLs: Use a bloom filter (memory-efficient, fast) to check if a URL has been seen. Bloom filters can answer "definitely not seen" or "probably seen" with a very low false positive rate. Also maintain a persistent hash set for ground truth. (2) Duplicate content: Hash the page body (MD5/SHA-256). Store content hashes in a DB. If hash already exists, the page is a duplicate — don't store it again, just update the URL-to-content mapping. Near-duplicate detection uses simhash (locality-sensitive hashing) to detect pages that are 90%+ similar.
How does a web crawler respect robots.txt?
Click to reveal answer
robots.txt is a file at https://domain.com/robots.txt that tells crawlers which paths they're allowed to visit. Example: Disallow: /private/ means don't crawl anything under /private/. The crawler fetches and caches robots.txt for each domain (TTL ~1 day) before crawling any page on that domain. Before downloading any URL, check if it matches any Disallow rule. Also respect Crawl-delay directives (minimum seconds between requests). Ignoring robots.txt is technically legal in some jurisdictions but unethical and can get your IP banned.
How would you scale the crawler to crawl 1 billion pages per day?
Click to reveal answer
1B pages/day = ~11,600 pages/second. Each page takes ~100-500ms to fetch. So you need 1,160–5,800 concurrent download threads. Distribute across 100s of crawler servers. Use consistent hashing to assign domains to servers (one server handles all of google.com, another handles all of wikipedia.org — simplifies politeness). URL Frontier becomes a distributed queue (Kafka). Store content in distributed storage (HDFS or S3). Each crawler server runs a pool of async workers. Use distributed DNS caches. At this scale, network bandwidth (~1TB/day) and storage (100s of TB) become as important as computational resources.
What is a spider trap and how do you detect/handle it?
Click to reveal answer
A spider trap is a set of web pages that cause a crawler to loop infinitely or generate an exponentially growing URL set. Example: /calendar?date=2024-01-01 has "next day" links going forever. Detection: (1) Track URL depth from seed — reject URLs more than N hops deep. (2) Detect URL patterns — if a URL path keeps getting longer with repeating segments, skip it. (3) Track how many URLs a single domain has generated — cap per-domain URL count. (4) Length cap — URLs over 200 characters are suspicious. All these are heuristics; perfect detection is impossible, but a combination works well in practice.
How do you prioritize which URLs to crawl first?
Click to reveal answer
Priority is a multi-factor score: (1) PageRank — pages with many incoming links are likely important. (2) Update frequency — news sites update every minute; a personal blog might update monthly. Crawl more frequently updated sites more often. (3) Traffic/popularity — Alexa rank, common crawl data. (4) Freshness — time since last successful crawl. (5) Domain importance — .gov, .edu, major news domains get higher baseline priority. These factors feed into a score, and URLs with higher scores sit in higher-priority front queues in the URL Frontier.

Design a Notification System

Push · SMS · Email · Queues · Retries · Opt-outs
The Big Picture
Analogy — The Post Office
You drop off a letter; the post office decides whether to deliver it by email, SMS, or hand. It queues letters when carriers are busy, retries failed deliveries, and respects "do not disturb" flags. That's a notification system.
Three Notification Types

Push (Mobile)

  • iOS → APNs (Apple Push Notification Service)
  • Android → FCM (Firebase Cloud Messaging)
  • Requires device token stored in your DB
  • Token can expire or change (app reinstall)

SMS

  • Third-party: Twilio, Nexmo
  • High delivery rate but costs per message
  • Best for critical alerts and OTP codes

Email

  • Third-party: SendGrid, Mailchimp
  • Supports rich HTML content
  • Least time-sensitive of the three

  • Notification service: Receives event (e.g. "user X liked your post"), looks up user preferences, routes to the correct channel queues
  • Per-channel queues: Separate queues for push / SMS / email; decouple slow third-party providers from your internal services
  • Workers: Stateless consumers pull from queues → call third-party APIs → mark delivered in DB; scale horizontally by adding workers
  • Retry + idempotency: On provider failure, retry with exponential backoff; idempotency key prevents duplicate sends if a retry succeeds after a partial delivery
  • Opt-out store: User preferences (per-channel, per-notification type) stored in DB; always check before sending — legally required in many regions (GDPR, CAN-SPAM)
  • Monitoring: Track delivery rate, failure rate, p99 latency per channel; alert if delivery rate drops below threshold

Why use message queues between the notification service and workers?
Click to reveal answer
Decouples your service from slow, unreliable third-party providers. If APNs is slow, the queue absorbs the backlog — your internal services are unaffected. Queues also enable independent scaling of workers per channel and guaranteed retry on failure.
How do you prevent sending the same notification twice?

The Big Picture
Analogy — The Newspaper Editor
When a celebrity publishes an article, do you deliver a printed copy to every subscriber immediately (fanout on write)? Or do you print on-demand when a subscriber asks (fanout on read)? The answer depends on whether your celebrities have millions or just hundreds of followers.
Two Core Operations
  • Publish a post: POST /v1/me/feed — user creates content; system propagates to followers
  • Retrieve feed: GET /v1/me/feed — user opens app; system returns ranked list of posts
Fanout Strategies Compared

  • Feed cache: Redis sorted set per user — score = timestamp, value = post_id. O(log N) inserts; O(log N) range reads. Return top 20 post IDs, hydrate with full post data in a second DB query.
  • Post storage: NoSQL (wide-column, e.g. Cassandra) for high write throughput. Posts are immutable — append-only. Partition by user_id.
  • User graph: Who follows whom — adjacency list in relational DB or a dedicated graph store. Used during fanout to find all follower IDs.
  • Feed ranking: Chronological is simplest. ML ranking on engagement signals (likes, comments, watch time) is more complex but increases engagement. Cache the ranked feed with a short TTL.
Interview Questions
What is the "Lady Gaga problem" in feed systems?
Click to reveal answer
If Lady Gaga has 30M followers and posts a tweet, fanout on write means writing her post_id to 30M Redis sorted sets. This creates a massive write spike that can saturate the cache cluster and take minutes. The fix: skip fanout on write for users above a follower threshold (e.g. >5,000). When a normal user opens their feed, the system fetches regular posts from the pre-built cache, then makes one additional DB query for celebrities they follow, and merges the results.
What data structure stores a user's feed in cache and why?
Click to reveal answer
Redis sorted set. Score = Unix timestamp (or ranking score), value = post_id. This gives O(log N) inserts and O(log N) range queries to get the top N most-recent posts. Sorted sets also allow efficient removal of old posts (trim the set to keep only the last 1,000 entries).
How do you handle a user who follows 10,000 accounts (fanout on read is slow)?
Click to reveal answer
For power users with many follows, maintain a pre-built feed cache via fanout on write — the same approach used for normal users. The distinction is from the producer side (celebrities skip write fanout), not the consumer side. A power follower still gets a pre-built sorted set; they just may need it refreshed more frequently.

Design a Chat System

WebSocket · Message storage · Presence · Group chat
Why WebSocket?
Analogy — The Walkie-Talkie
A walkie-talkie stays open — both sides can talk any time. HTTP is like sending a letter and waiting for a reply. For real-time chat, you need the open channel. That's WebSocket.
  • Short polling: Client asks "any new messages?" every N seconds. Wasteful bandwidth; messages arrive with N-second latency.
  • Long polling: Server holds the connection open until a message arrives, then responds. Better latency, but server must hold thousands of open connections doing nothing. Hard to scale.
  • WebSocket ✓: Bidirectional persistent TCP connection. Established via HTTP upgrade handshake. Both client and server can push at any time. Minimal per-message overhead.
Architecture
  • Chat servers: Maintain one WebSocket connection per online user. Stateful — a user's connection is tied to one chat server. Multiple servers sit behind a load balancer (sticky routing by user_id).
  • Message storage: Key-value store (e.g. HBase, Cassandra). Partition by conversation_id. Messages are immutable (append-only). Requires ordered message IDs.
  • Message ID: Must be unique and ordered within a conversation. Can't use DB auto-increment across distributed nodes. Use Snowflake-style IDs (timestamp + sequence + server_id) scoped per conversation.
  • Presence service: Tracks online/offline status. Client sends a heartbeat every 5s. No heartbeat for 30s → mark offline. On connect → mark online. Status changes propagate to friends via pub/sub (e.g. Redis pub/sub).
  • Group chat: Sending to a group of N members = N WebSocket pushes. Fine for small groups. For very large groups (>1,000), switch to pull model: server stores the message, clients poll periodically.
  • Offline users: Store message with "undelivered" status. When user reconnects, client syncs all messages since last_seen_message_id. Trigger a push notification via APNs/FCM to wake the app.
Interview Questions
Why use WebSocket instead of HTTP for chat?
Click to reveal answer
HTTP is request-response — the server can only send data when the client asks. For real-time chat you'd need polling, which wastes bandwidth and adds latency. WebSocket is a persistent full-duplex channel — either side can push at any time with minimal overhead per message. It's the standard for chat, gaming, and live collaboration tools.
How do you ensure message ordering in a distributed chat system?
Click to reveal answer
Use a per-conversation sequence number. Store a Redis INCR counter per conversation_id — each new message atomically gets the next integer. This gives strictly ordered IDs within a conversation without a global sequence. Combine with a timestamp as a tiebreaker for display. Key insight: ordering only needs to be total within one conversation, not globally.
How do you handle a user who goes offline mid-conversation?
Click to reveal answer
When a message is sent to an offline user: (1) Persist it in the message store with status "undelivered". (2) Send a push notification (APNs/FCM) to the device to wake the app. (3) When the app wakes, client syncs by calling GET /messages?since={last_message_id} and fetches everything it missed. This "client-driven sync on reconnect" pattern is simpler and more reliable than server-driven replay.

Design a Search Autocomplete System

Trie · Top-K caching · Data pipeline · Sharding
The Big Picture
Analogy — The Experienced Librarian
A librarian who's heard thousands of book requests instantly knows "Harry P..." means Harry Potter because they've learned from frequency. That's a trie — a tree that stores completions ranked by how often they've been searched.
  • Requirements: Return top 5 completions as user types each character; sorted by frequency; response under 100ms
The Trie Data Structure
  • Structure: A tree where each node represents one character. A path from root spells a prefix. Each node stores the top-K (e.g. top 5) complete query strings reachable from it, plus their frequencies.
  • Query: Traverse character-by-character following the typed prefix → O(prefix length). Return the pre-stored top-K at the final node — no subtree traversal needed.
  • Pre-storing top-K: Without this, you'd traverse the entire subtree to find completions — O(subtree size). With it, every query is O(prefix length), making <100ms possible even at scale.
  • Build: Aggregate search logs weekly → compute frequency for every query → rebuild trie bottom-up storing top-K at each node → swap into memory. Read-heavy; rebuild offline, serve from cache.
  • Pruning: Keep only the top 10,000 most-searched queries. Discarding rare queries keeps the trie small enough to fit in RAM.
Scaling & Optimisations
  • Prefix caching: For 1–3 character prefixes (e.g. "a", "go", "hel") there are only ~18,000 combinations but they're queried millions of times/second. Cache results directly in Redis with TTL.
  • Sharding: Shard trie by first character (a–z + digits). Each shard owns its letter range. Horizontal scale with simple routing.
  • Trending queries: Weekly batch trie won't reflect a query that spiked in the last hour. Solution: a secondary real-time layer (streaming via Kafka) tracks last-hour trends; merge results from both at query time.
  • Never update the live trie: Trie updates under load cause lock contention. Instead, rebuild a shadow trie, then atomically swap the pointer. Zero-downtime update.
Interview Questions
Why store top-K at each trie node instead of computing them at query time?
Click to reveal answer
Computing at query time means traversing the full subtree under the matching prefix — O(subtree size), which could be millions of nodes. Pre-storing top-K at each node makes every query O(prefix length), which is at most ~50 operations. This is the key optimisation that makes sub-100ms responses possible.
How do you handle a trending query that spiked in the last hour?
Click to reveal answer
The weekly-rebuilt trie won't include it. Add a secondary real-time layer: stream search events into Kafka → a consumer counts queries per minute → top trending queries stored in Redis with a short TTL. At query time, merge the trie results with the real-time trending list, boosting trending queries to the top. The two layers serve different time horizons.
How do you scale autocomplete to handle billions of searches per day?
Click to reveal answer
Shard by first character (each of 26+ shards owns one letter). All "go…" queries route to the "g" shard. Cache 1–3 char prefix results in Redis (small number of keys, enormous hit rate). Deploy read replicas of each shard for redundancy. The trie itself fits in RAM per shard (~hundreds of MB with 10K queries pruned).

Design YouTube

Upload · Transcode · CDN · Adaptive bitrate streaming
The Big Picture
Analogy — The Movie Theater Chain
A director submits a film reel; it gets converted into dozens of formats (IMAX, 3D, standard) before any screening. Finished reels are shipped to theaters near you. You watch at your local theater, not from Hollywood. That's upload → transcode → CDN → stream.
  • Scale: 2B logged-in users/month; 500 hours of video uploaded every minute; traffic is bandwidth-heavy, not compute-heavy
Upload & Transcode
  • Upload flow: Client → API server issues pre-signed S3 URL → client uploads raw video directly to S3 (bypasses your servers) → S3 event triggers message queue → transcoding workers pick up the job
  • Why separate upload from transcoding: Transcoding is slow (minutes to hours). Keeping them separate means the upload API stays fast and users can check status asynchronously.
  • Transcoding: Convert to multiple formats (mp4, webm) and resolutions (360p, 720p, 1080p, 4K). Encode each resolution in parallel using a DAG of workers. Output chunks stored in blob storage; metadata in relational DB.
  • Encoding DAG: Split video into segments → encode segments in parallel → merge → upload. Parallel encoding dramatically reduces wall-clock time.
Streaming & CDN
  • Adaptive bitrate streaming (HLS/DASH): Player downloads video in small 2–10 second segments. After each segment it measures bandwidth. Fast connection → request higher resolution next. Slow → lower resolution. User never sees "loading" — quality adapts in real time.
  • CDN strategy: Popular videos (top 20% by views) pushed to all edge PoPs. Unpopular videos served from origin or a regional CDN. ~80% of views served from edge — dramatically reduces origin bandwidth.
  • View / like counts: Write-heavy. Don't write every view directly to MySQL. Buffer counts in Redis (INCR), batch-flush to DB every 60 seconds. Accept slightly stale counts — exact real-time numbers don't matter for a like counter.
Interview Questions
Why transcode to multiple resolutions?
Click to reveal answer
Different devices have different screen sizes; users have different bandwidth. Adaptive bitrate streaming (HLS/DASH) switches resolution every few seconds based on measured download speed. Without multiple resolutions, a user on a slow connection would buffer constantly instead of just watching at a lower quality.
What is adaptive bitrate streaming and how does it work?
Click to reveal answer
The video is split into small segments (2–10s each), each encoded at multiple quality levels. The player downloads one segment at a time, measures download speed, and requests the next segment at a quality level proportional to available bandwidth. If bandwidth drops, quality drops — but playback never stops. HLS (Apple) and DASH (standard) are the two dominant protocols.
How would you handle billions of view-count updates without crashing the DB?
Click to reveal answer
Don't write every view directly to MySQL — at millions of views per second that's impossible. Instead: (1) Increment a Redis counter per video_id using INCR (O(1), atomic). (2) A background job reads Redis counts every 60s and batch-upserts them to the DB. (3) Accept that the displayed count may be ~60s stale — nobody notices or cares. This pattern (write-to-cache, batch-flush-to-DB) is reused everywhere: likes, downloads, play counts.

Design Google Drive

Block storage · Delta sync · Conflict resolution · Cold storage
The Big Picture
Analogy — The Smart Photocopier
A smart photocopier only copies the pages that changed. If you update page 5 of a 100-page document, it records only the new page 5. That's block-level delta sync — only changed chunks travel over the network.
Core Concepts
  • Block storage: Split files into fixed-size blocks (~4MB). Each block is content-addressed by its SHA-256 hash. On upload, only blocks whose hash isn't already on the server are sent. Same block never stored twice (deduplication).
  • Sync client: Watches filesystem for changes → splits file into blocks → computes hashes → diffs against last-synced state → uploads only changed blocks → notifies server → server pushes delta to other devices.
  • Upload flow: Client uploads changed blocks to S3 → updates block metadata in DB → notifies other devices via WebSocket or long-poll → other devices fetch and reassemble changed blocks.
  • Conflict resolution: Last-write-wins for most files (simple, loses data). Conflict copy (create both versions, notify user) — Dropbox approach. Operational transform (merge at character level) — Google Docs approach for collaborative editing.
  • Cold storage: Files not accessed in 6+ months → move to S3 Glacier (10× cheaper). Triggered by a batch job scanning access timestamps. Transparent to user — restore takes minutes on next access.
  • Storage deduplication: Same block hash = same bytes = store once. Saves enormous space for backup tools where many files share common content.

Interview Questions
Why split files into blocks instead of uploading the whole file?
Click to reveal answer
Three reasons: (1) Delta sync — if only 5% of a file changed, only upload the changed blocks. Massive bandwidth saving for large files. (2) Deduplication — identical blocks (common in backups) are stored once across all users. (3) Parallel upload — multiple blocks can be uploaded simultaneously, speeding up large file transfers.
How do you handle two people editing the same file at the same time?
Click to reveal answer
Three approaches with increasing complexity: (1) Last write wins — whoever saves last overwrites the other. Simple, but can cause data loss. (2) Conflict copy (Dropbox) — save both versions, name one "file (conflicted copy)", notify both users. No data loss but user must manually resolve. (3) Operational transform (Google Docs) — track every character-level change and merge them automatically. Complex to implement but enables real-time collaboration. Choose based on your use case.
How do you notify all a user's devices when a file changes on one device?
Click to reveal answer
Options by complexity: (1) Long polling — each device asks "anything new since timestamp T?" every 30s. Simple, slight latency. (2) WebSocket — persistent connection, server pushes immediately. Real-time but more infrastructure. (3) Push notification — for mobile devices that aren't running the app. Each device keeps a cursor (last_sync_timestamp or last_version_id) and fetches only the diff since its last sync.
